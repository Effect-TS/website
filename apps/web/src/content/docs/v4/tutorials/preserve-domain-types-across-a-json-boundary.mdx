import { TutorialCheckpoint } from "@astrojs/starlight/components"

`JSON.parse` returns ordinary JavaScript values. A timestamp is still a string,
a URL is still a string, an array is still an array, and an application class
is not constructed for you. A TypeScript assertion can claim otherwise, but it
does not inspect or transform the value at runtime.

In this tutorial, we will start with a conventional `node:http` endpoint and
replace that assertion with one Schema-driven boundary. The finished
`POST /orders` endpoint will have these observable behaviors:

| Request                                     | Boundary behavior                              | HTTP result |
| ------------------------------------------- | ---------------------------------------------- | ----------- |
| Valid order JSON                            | Builds rich values, then encodes response JSON | `201`       |
| Wrong field type                            | Stops before order logic                       | `400`       |
| Order id without the required `ord_` prefix | Stops before constructing the domain `OrderId` | `400`       |

The HTTP server will remain ordinary TypeScript. Schema will own the two jobs
at the boundary: decoding unknown request data into domain values and encoding
domain values into JSON-safe response data.

Each step ends with a checkpoint: a short summary of the behavior reached so far.

## 1. Start with a familiar JSON endpoint

This tutorial requires Node.js 22.18.0 or newer because it runs `server.ts`
directly with Node's built-in TypeScript support.

To create the project manually, run:

```sh title="Create the project"
mkdir preserve-domain-types
cd preserve-domain-types
npm init -y
npm pkg set type=module
npm install --save-dev @types/node@22
```

Create `server.ts` with this conventional implementation:

```ts title="server.ts" collapse={19-34,46-50}
import { createServer } from "node:http"

class OrderId {
  readonly value: string

  constructor(value: string) {
    this.value = value
  }
}

interface OrderSubmission {
  readonly orderId: OrderId
  readonly quantity: number
  readonly requestedAt: Date
  readonly callbackUrl: URL
  readonly labels: ReadonlySet<string>
}

const server = createServer(async (request, response) => {
  const sendJson = (status: number, body: unknown): void => {
    response.writeHead(status, { "content-type": "application/json" })
    response.end(JSON.stringify(body))
  }

  if (request.method !== "POST" || request.url !== "/orders") {
    sendJson(404, { error: "NotFound" })
    return
  }

  try {
    let body = ""
    for await (const chunk of request) {
      body += chunk
    }

    const submission = JSON.parse(body) as OrderSubmission

    console.log({
      orderIdIsOrderId: submission.orderId instanceof OrderId,
      requestedAtIsDate: submission.requestedAt instanceof Date,
      callbackIsUrl: submission.callbackUrl instanceof URL,
      labelsAreSet: submission.labels instanceof Set,
    })

    sendJson(201, { ...submission, status: "accepted" })
  } catch (error) {
    console.error(error)
    sendJson(500, { error: "InternalServerError" })
  }
})

server.listen(3000, () => console.log("Listening on http://localhost:3000"))
```

Start the server with `--watch`. Node.js will reload the file after every edit,
so keep this terminal running throughout the tutorial:

```sh title="Keep running throughout the tutorial"
node --watch server.ts
```

Open a second terminal pane and send an order:

```sh title="Send a valid-looking order"
curl -i -sS http://localhost:3000/orders \
  -H 'content-type: application/json' \
  -d '{"orderId":"ord_2026_0001","quantity":2,"requestedAt":"2026-08-09T10:00:00.000Z","callbackUrl":"https://example.com/order-events","labels":["priority","b2b"]}'
```

The endpoint returns the expected-looking JSON:

```text title="Expected response"
HTTP/1.1 201 Created
...

{"orderId":"ord_2026_0001","quantity":2,"requestedAt":"2026-08-09T10:00:00.000Z","callbackUrl":"https://example.com/order-events","labels":["priority","b2b"],"status":"accepted"}
```

The server log tells a different story:

```text title="Expected server log"
{
  orderIdIsOrderId: false,
  requestedAtIsDate: false,
  callbackIsUrl: false,
  labelsAreSet: false
}
```

`as OrderSubmission` affects only TypeScript's view of the code. At runtime,
`orderId`, `requestedAt`, and `callbackUrl` are strings, while `labels` is an
array. Calling an `OrderId` method, a date method, or `Set.prototype.has` would
fail even though the editor says those operations are allowed.

## 2. Watch invalid data pass the assertion

The same assertion also accepts values that do not resemble the declared
types. Send this request without changing the server:

```sh title="Send wrong field types"
curl -i -sS http://localhost:3000/orders \
  -H 'content-type: application/json' \
  -d '{"orderId":42,"quantity":"two","requestedAt":"soon","callbackUrl":"not a url","labels":"priority"}'
```

It still returns `201`:

```text title="Expected response"
HTTP/1.1 201 Created
...

{"orderId":42,"quantity":"two","requestedAt":"soon","callbackUrl":"not a url","labels":"priority","status":"accepted"}
```

`JSON.parse` checks JSON syntax, not the application shape. The assertion does
neither runtime validation nor conversion. We need to treat parsed request data
as `unknown` until the boundary proves what it contains.

## 3. Validate the JSON shape

Keep the server running. In the second terminal pane, install Effect:

```sh title="Install Effect"
npm install effect@4.0.0-beta.104
```

Replace the assertion with a Schema decoder:

```ts title="server.ts" ins={2,4-12,31-36} collapse={14-29,38-45}
import { createServer } from "node:http"
import { Result, Schema } from "effect"

const OrderSubmissionJson = Schema.Struct({
  orderId: Schema.String,
  quantity: Schema.Finite,
  requestedAt: Schema.String,
  callbackUrl: Schema.String,
  labels: Schema.Array(Schema.String),
})

const decodeOrderSubmission = Schema.decodeUnknownResult(OrderSubmissionJson)

const server = createServer(async (request, response) => {
  const sendJson = (status: number, body: unknown): void => {
    response.writeHead(status, { "content-type": "application/json" })
    response.end(JSON.stringify(body))
  }

  if (request.method !== "POST" || request.url !== "/orders") {
    sendJson(404, { error: "NotFound" })
    return
  }

  try {
    let body = ""
    for await (const chunk of request) {
      body += chunk
    }

    const decoded = decodeOrderSubmission(JSON.parse(body))
    if (Result.isFailure(decoded)) {
      sendJson(400, { error: "InvalidOrder" })
      return
    }
    const submission = decoded.success

    sendJson(201, { ...submission, status: "accepted" })
  } catch (error) {
    console.error(error)
    sendJson(500, { error: "InternalServerError" })
  }
})

server.listen(3000, () => console.log("Listening on http://localhost:3000"))
```

A Schema is an immutable value that describes which inputs are accepted and
what value decoding produces. Defining or composing one does not inspect any
request. The decoder created from it performs that work when the handler calls
`decodeOrderSubmission`.

[`Schema.Struct`](/docs/v4/api/effect/Schema#Struct-function) combines property
schemas into an object schema. Here every request must have `orderId`,
`quantity`, `requestedAt`, `callbackUrl`, and `labels` with the shapes declared
inside the object.

[`Schema.String`](/docs/v4/api/effect/Schema#String-variable) describes a
JavaScript string. It validates the three string fields in this first boundary
schema and also supplies the element schema inside `labels`.
[`Schema.Finite`](/docs/v4/api/effect/Schema#Finite-variable) describes a finite
JavaScript number. The decoded `quantity` is a `number`, while `NaN`, positive
infinity, negative infinity, strings, and other values are rejected.
[`Schema.Array`](/docs/v4/api/effect/Schema#Array-variable) builds an array
schema from an element schema, so `Schema.Array(Schema.String)` requires an
array in which every label is a string.

[`Schema.decodeUnknownResult`](/docs/v4/api/effect/Schema#decodeUnknownResult)
creates a decoder for untrusted input. Calling it returns a `Result`: success
contains the decoded object, while failure contains a `SchemaError` that
describes why the value did not match. A shape error is returned as data rather
than thrown. [`Result.isFailure`](/docs/v4/api/effect/Result#isFailure) checks
whether that `Result` is its failure case. Inside the `if`, TypeScript knows
decoding failed; after the early return, it knows `decoded.success` is
available.

Decoding and encoding are directional terms. Decoding moves from data at the
boundary into data used by the application. Encoding, which we will add later,
moves an application value back toward its boundary representation.

Wait for the watched server to reload, then repeat the invalid request from the
previous step. It now returns:

```text title="Expected response"
HTTP/1.1 400 Bad Request
...

{"error":"InvalidOrder"}
```

The valid request still returns `201`. Its date, URL, labels, and order id are
still plain JSON values, though. This step validates only their outer shape.

## 4. Decode JSON into useful runtime values

The shape is safe, but order logic still receives strings and an array. Change
the field schemas to describe the values the application actually wants:

```ts title="server.ts" ins={2,4,7-9,12,39-43} collapse={15-36,45-52}
import { createServer } from "node:http"
import { DateTime, Result, Schema } from "effect"

const OrderSubmission = Schema.Struct({
  orderId: Schema.String,
  quantity: Schema.Finite,
  requestedAt: Schema.DateTimeUtc,
  callbackUrl: Schema.URL,
  labels: Schema.ReadonlySet(Schema.String),
})

const OrderSubmissionJson = Schema.toCodecJson(OrderSubmission)
const decodeOrderSubmission = Schema.decodeUnknownResult(OrderSubmissionJson)

const server = createServer(async (request, response) => {
  const sendJson = (status: number, body: unknown): void => {
    response.writeHead(status, { "content-type": "application/json" })
    response.end(JSON.stringify(body))
  }

  if (request.method !== "POST" || request.url !== "/orders") {
    sendJson(404, { error: "NotFound" })
    return
  }

  try {
    let body = ""
    for await (const chunk of request) {
      body += chunk
    }

    const decoded = decodeOrderSubmission(JSON.parse(body))
    if (Result.isFailure(decoded)) {
      sendJson(400, { error: "InvalidOrder" })
      return
    }
    const submission = decoded.success

    console.log({
      requestedAt: DateTime.formatIso(submission.requestedAt),
      callbackHost: submission.callbackUrl.host,
      labels: [...submission.labels],
    })

    sendJson(201, { ...submission, status: "accepted" })
  } catch (error) {
    console.error(error)
    sendJson(500, { error: "InternalServerError" })
  }
})

server.listen(3000, () => console.log("Listening on http://localhost:3000"))
```

The `OrderSubmission` schema describes domain values. The derived
`OrderSubmissionJson` codec describes how those values cross JSON. A codec is a
schema that keeps both directions. In this codec, its decoded `Type` contains a
`DateTime.Utc`, a `URL`, and a `ReadonlySet<string>`. Its `Encoded` side contains
the JSON-compatible ISO string, URL string, and string array.

[`Schema.DateTimeUtc`](/docs/v4/api/effect/Schema#DateTimeUtc-variable)
describes an immutable Effect `DateTime.Utc` value that represents an instant
in UTC. It is a different runtime type from JavaScript `Date`. Its canonical
JSON codec decodes a UTC ISO string such as `2026-08-09T10:00:00.000Z` into
that value and encodes the value back to a UTC ISO string.

[`Schema.URL`](/docs/v4/api/effect/Schema#URL-variable) describes a JavaScript
`URL` instance. Its canonical JSON codec accepts a valid URL string, constructs
the `URL`, and turns the instance back into a string during encoding.
[`Schema.ReadonlySet`](/docs/v4/api/effect/Schema#ReadonlySet-function) builds a
schema for a JavaScript `ReadonlySet`. The inner schema validates its elements.
Its canonical JSON codec decodes a JSON array into a `Set` and encodes the set
back into an array.

[`Schema.toCodecJson`](/docs/v4/api/effect/Schema#toCodecJson-function) derives
a JSON-compatible codec recursively. In this object it selects the ISO string
representation for `DateTime.Utc`, a string for `URL`, and an array for
`ReadonlySet`, while ordinary strings and numbers stay unchanged.

[`DateTime.formatIso`](/docs/v4/api/effect/DateTime#formatIso) formats a
`DateTime` value as an ISO string. Calling it here demonstrates that
`requestedAt` is no longer the request's original JavaScript string.

Wait for the watched server to reload, then send the valid request again. The
server log now contains useful domain data:

```text title="Expected server log"
{
  requestedAt: '2026-08-09T10:00:00.000Z',
  callbackHost: 'example.com',
  labels: [ 'priority', 'b2b' ]
}
```

The response reveals the next boundary problem:

```text title="Expected response"
HTTP/1.1 201 Created
...

{"orderId":"ord_2026_0001","quantity":2,"requestedAt":"2026-08-09T10:00:00.000Z","callbackUrl":"https://example.com/order-events","labels":{},"status":"accepted"}
```

`JSON.stringify` does not know how to serialize a `Set`, so `labels` becomes an
empty object. Decoding solved the incoming direction. We still need to use the
codec in the outgoing direction.

## 5. Encode the response through Schema

Define the accepted response as domain data, derive its JSON codec, and encode
before calling `JSON.stringify`:

```ts title="server.ts" ins={15-25,57-65} collapse={1-13,27-55,66-72}
import { createServer } from "node:http"
import { DateTime, Result, Schema } from "effect"

const OrderSubmission = Schema.Struct({
  orderId: Schema.String,
  quantity: Schema.Finite,
  requestedAt: Schema.DateTimeUtc,
  callbackUrl: Schema.URL,
  labels: Schema.ReadonlySet(Schema.String),
})

const OrderSubmissionJson = Schema.toCodecJson(OrderSubmission)
const decodeOrderSubmission = Schema.decodeUnknownResult(OrderSubmissionJson)

const AcceptedOrder = Schema.Struct({
  orderId: Schema.String,
  quantity: Schema.Finite,
  requestedAt: Schema.DateTimeUtc,
  callbackUrl: Schema.URL,
  labels: Schema.ReadonlySet(Schema.String),
  status: Schema.Literal("accepted"),
})

const AcceptedOrderJson = Schema.toCodecJson(AcceptedOrder)
const encodeAcceptedOrder = Schema.encodeResult(AcceptedOrderJson)

const server = createServer(async (request, response) => {
  const sendJson = (status: number, body: unknown): void => {
    response.writeHead(status, { "content-type": "application/json" })
    response.end(JSON.stringify(body))
  }

  if (request.method !== "POST" || request.url !== "/orders") {
    sendJson(404, { error: "NotFound" })
    return
  }

  try {
    let body = ""
    for await (const chunk of request) {
      body += chunk
    }

    const decoded = decodeOrderSubmission(JSON.parse(body))
    if (Result.isFailure(decoded)) {
      sendJson(400, { error: "InvalidOrder" })
      return
    }
    const submission = decoded.success

    console.log({
      requestedAt: DateTime.formatIso(submission.requestedAt),
      callbackHost: submission.callbackUrl.host,
      labels: [...submission.labels],
    })

    const encoded = encodeAcceptedOrder({
      ...submission,
      status: "accepted",
    })
    if (Result.isFailure(encoded)) {
      throw encoded.failure
    }

    sendJson(201, encoded.success)
  } catch (error) {
    console.error(error)
    sendJson(500, { error: "InternalServerError" })
  }
})

server.listen(3000, () => console.log("Listening on http://localhost:3000"))
```

[`Schema.Literal`](/docs/v4/api/effect/Schema#Literal-function) describes one
exact value rather than every string. The accepted response can therefore
contain only `status: "accepted"`.

[`Schema.encodeResult`](/docs/v4/api/effect/Schema#encodeResult) creates an
encoder for values already typed as the schema's decoded side. A successful
`Result` contains JSON-safe data. A failure means application code tried to
encode a value that did not satisfy the response schema.

Request decoding failures are client errors, so the handler returns `400`.
Response encoding failures indicate a server-side mistake, so this code throws
the `SchemaError` into the existing `catch` and returns `500`. The two boundary
directions now have different policies.

Wait for the watched server to reload, then send the valid request again. The
complete response shape is restored:

```text title="Expected response"
HTTP/1.1 201 Created
...

{"orderId":"ord_2026_0001","quantity":2,"requestedAt":"2026-08-09T10:00:00.000Z","callbackUrl":"https://example.com/order-events","labels":["priority","b2b"],"status":"accepted"}
```

The handler uses a `Set`; the wire uses an array. That difference is now an
explicit part of the codec instead of an accident of `JSON.stringify`.

## 6. Give the order id a domain class

The remaining `orderId` is still a string inside the handler. Make it a class
without changing the JSON contract:

```ts title="server.ts" ins={2,4-22,25,36,72-73} collapse={26-34,37-70,74-94}
import { createServer } from "node:http"
import { DateTime, Result, Schema, SchemaTransformation } from "effect"

const OrderIdText = Schema.TemplateLiteral(["ord_", Schema.String])

class OrderId extends Schema.Class<OrderId>("OrderId")({
  value: OrderIdText,
}) {
  toString(): string {
    return this.value
  }
}

const OrderIdFromString = OrderIdText.pipe(
  Schema.decodeTo(
    OrderId,
    SchemaTransformation.transform({
      decode: (value) => ({ value }),
      encode: ({ value }) => value,
    }),
  ),
)

const OrderSubmission = Schema.Struct({
  orderId: OrderIdFromString,
  quantity: Schema.Finite,
  requestedAt: Schema.DateTimeUtc,
  callbackUrl: Schema.URL,
  labels: Schema.ReadonlySet(Schema.String),
})

const OrderSubmissionJson = Schema.toCodecJson(OrderSubmission)
const decodeOrderSubmission = Schema.decodeUnknownResult(OrderSubmissionJson)

const AcceptedOrder = Schema.Struct({
  orderId: OrderIdFromString,
  quantity: Schema.Finite,
  requestedAt: Schema.DateTimeUtc,
  callbackUrl: Schema.URL,
  labels: Schema.ReadonlySet(Schema.String),
  status: Schema.Literal("accepted"),
})

const AcceptedOrderJson = Schema.toCodecJson(AcceptedOrder)
const encodeAcceptedOrder = Schema.encodeResult(AcceptedOrderJson)

const server = createServer(async (request, response) => {
  const sendJson = (status: number, body: unknown): void => {
    response.writeHead(status, { "content-type": "application/json" })
    response.end(JSON.stringify(body))
  }

  if (request.method !== "POST" || request.url !== "/orders") {
    sendJson(404, { error: "NotFound" })
    return
  }

  try {
    let body = ""
    for await (const chunk of request) {
      body += chunk
    }

    const decoded = decodeOrderSubmission(JSON.parse(body))
    if (Result.isFailure(decoded)) {
      sendJson(400, { error: "InvalidOrder" })
      return
    }
    const submission = decoded.success

    console.log({
      orderIdIsOrderId: submission.orderId instanceof OrderId,
      orderId: submission.orderId.toString(),
      requestedAt: DateTime.formatIso(submission.requestedAt),
      callbackHost: submission.callbackUrl.host,
      labels: [...submission.labels],
    })

    const encoded = encodeAcceptedOrder({
      ...submission,
      status: "accepted",
    })
    if (Result.isFailure(encoded)) {
      throw encoded.failure
    }

    sendJson(201, encoded.success)
  } catch (error) {
    console.error(error)
    sendJson(500, { error: "InternalServerError" })
  }
})

server.listen(3000, () => console.log("Listening on http://localhost:3000"))
```

[`Schema.TemplateLiteral`](/docs/v4/api/effect/Schema#TemplateLiteral-function)
builds a string schema from fixed and variable parts. `OrderIdText` accepts
strings that start with `ord_`, so an id such as `wrong` fails before any
`OrderId` is constructed.

[`Schema.Class`](/docs/v4/api/effect/Schema#Class-variable) creates a class that
is also a schema. Decoding its field object constructs an `OrderId` instance,
and encoding an instance produces that field object. The `<OrderId>` type
argument tells TypeScript which class is being defined, while `"OrderId"` is a
stable identifier used in Schema diagnostics. The class body can add ordinary
methods such as `toString`.

`OrderIdText.pipe(...)` passes `OrderIdText` into the function returned by
`Schema.decodeTo(...)`. Reading from top to bottom, the code starts with the
wire string schema and connects it to the `OrderId` class schema. Composing the
schemas does not decode a value; the request decoder does that later.

[`Schema.decodeTo`](/docs/v4/api/effect/Schema#decodeTo-function) connects a
source schema to a target schema. This codec starts from validated `OrderIdText`
and ends at an `OrderId` instance when decoding; encoding travels from the
instance back to its string representation.

[`SchemaTransformation.transform`](/docs/v4/api/effect/SchemaTransformation#transform)
supplies two conversions that cannot fail on their own. `decode` wraps the
validated string in the field object consumed by `OrderId`; `encode` extracts
the validated string from that object on the return trip.

Wait for the watched server to reload, then send the valid request once more.
The server log now begins with:

```text title="Expected server log"
orderIdIsOrderId: true
orderId: 'ord_2026_0001'
```

The response still contains `"orderId":"ord_2026_0001"`. The class is a domain
choice, not a wire-format change.

Now verify the class invariant:

```sh title="Send an invalid order id"
curl -i -sS http://localhost:3000/orders \
  -H 'content-type: application/json' \
  -d '{"orderId":"wrong","quantity":2,"requestedAt":"2026-08-09T10:00:00.000Z","callbackUrl":"https://example.com/order-events","labels":["priority"]}'
```

It returns:

```text title="Expected response"
HTTP/1.1 400 Bad Request
...

{"error":"InvalidOrder"}
```

The boundary now performs a round trip with one source of truth:

```text title="Boundary flow"
request JSON
  -> decode with OrderSubmissionJson
  -> OrderId, DateTime.Utc, URL, and Set in order logic
  -> encode with AcceptedOrderJson
  -> response JSON
```

## Read the final boundary

`OrderSubmission` and `AcceptedOrder` describe the runtime values used by the
application. `Schema.toCodecJson` derives the boundary representations of those
same definitions. `Schema.decodeUnknownResult` protects incoming data, while
`Schema.encodeResult` protects outgoing data.

There is no assertion, replacer, reviver, or field-by-field reconstruction in
the HTTP handler. When a domain field changes, its schema keeps validation,
decoding, and encoding together.
