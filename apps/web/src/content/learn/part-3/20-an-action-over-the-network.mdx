Every action so far appends a line to a file on your disk. The useful actions
leave the machine: a webhook, a chat message, a notification on your phone.
Since [Recording runs with Effect.onExit](/learn/part-2/12-an-engine-that-records),
an `httpPost` rule has been stored and then skipped with the reason
`httpPost actions run from lesson 20`. In this lesson the action is sent, and
you read three ways it can go wrong side by side: a 500, a timeout, and a bug
in your own code.

In this lesson you will:

- build and send an HTTP request as a value with `HttpClientRequest` and
  `HttpClient`
- see how `failed` and `crashed` differ in `runs list` and in the viewer
- read what a `Cause` holds: typed failures, defects and interruptions

## 1. Send the request

Add `postMessage` to `src/Action.ts`. It POSTs the action's message as plain
text. When the action sets `includePayload`, the payload follows as JSON on
the next line. When the action has `headers`, they are sent too:

<LessonCode file="checkpoints/20/src/Action.ts" />

It is `poll` from the previous lesson in the other direction:

- `HttpClientRequest.post(url)` builds the request.
  `HttpClientRequest.setHeaders` and `HttpClientRequest.bodyText` add to it,
  piped one after the other. A request is a value until `client.execute`
  sends it.
- No answer at all, such as a refused connection, is `ActionFailed` with
  reason `io`.
- An answer outside 2xx is `ActionFailed` with reason `status`, and the
  message names the URL and the status.

In `src/Engine.ts`, change the `httpPost` branch of `run` so that it calls
`postMessage` and returns `succeeded`, instead of returning a skip. Hand the
Engine's `HttpClient` to it with `Effect.provideService`, the same way the
`FileSystem` is handed to `appendLine`. From here on, `skipped` has only its
two reasons: the condition was false, or a field was missing.

The timeout needs no new code. `Effect.timeout` already wraps `run` inside
the span, so a receiver that takes too long is cut off after 10 seconds,
interrupted, and recorded as `failed (timeout)`.

## 2. Compare a 500 and a timeout

With `pnpm receiver` and `pnpm dev:server` running, add the two rules and run
each one on its own:

```sh
pnpm cli rules add fixtures/rules/post-fail.json
pnpm cli rules add fixtures/rules/post-slow.json
pnpm cli rules run <post-fail id> --event fixtures/events/laptop.json
pnpm cli rules run <post-slow id> --event fixtures/events/laptop.json
```

The first prints `failed (status)` with the 500. The second takes 10 seconds
and prints `failed (timeout)`. `runs list` shows:

| Rule file        | Receiver answer         | `runs list`                              |
| ---------------- | ----------------------- | ---------------------------------------- |
| `post-fail.json` | `/fail?status=500`: 500 | `failed (status): POST ... answered 500` |
| `post-slow.json` | `/slow?ms=15000`: late  | `failed (timeout): timed out after 10s`  |

Both are the world misbehaving. `failed` means the action was attempted and
did not succeed, and the reason says how: the receiver refused, or it did not
answer in time. Trying again later is reasonable.

In the viewer, both `Engine.execute` spans are red. The status message tells
them apart: the 500 and the `TimeoutError`. The timed-out span is exactly as
long as the timeout.

## 3. Read what a Cause holds

When an effect does not succeed, its `Exit` holds a `Cause`. A `Cause` can
hold three kinds of thing:

- A typed failure. This is the error type you have read in hovers since
  [Defining errors with Schema.TaggedError](/learn/part-1/04-failure-you-can-see).
  Here, that is `ActionFailed` and `TimeoutError`.
- A defect. Something that was never in the error type, such as a thrown
  exception, or an `Effect.orDie` like the database errors in
  [Storing data in SQLite with SqlClient](/learn/part-3/17-survive-a-restart).
- An interruption. From `FiberMap.remove`, a timeout, or Ctrl-C.

`terminal` in `src/Engine.ts` reads the `Exit` in that order. It checks
`Cause.hasInterruptsOnly` first, because a run that was only stopped did not
fail. Then it calls `Cause.squash`, which picks the main error of what is
left. A typed failure becomes `failed` with its reason. Anything else is a
defect and becomes `crashed`.

The type tells you which typed failures are possible. The `Cause` tells you
what happened, including what the type cannot show.

## Try it

Plant a bug for two minutes and read it as `crashed`, the third row next to
the two from step 2:

1. In `postMessage`, change the headers line so it trims the `Title` header,
   with a `!` that tells the compiler the headers are there. For
   `post-ok.json`, they are not. `pnpm check` still passes.
2. Add the rule with `pnpm cli rules add fixtures/rules/post-ok.json` and note
   the id it prints.
3. Run only that rule, with
   `pnpm cli rules run <post-ok id> --event fixtures/events/laptop.json`. Do
   not submit the event to every rule: `post-fail` and `post-slow` match
   expenses too, have no headers either, and would crash as well.
4. The CLI prints `crashed` with
   `Cannot read properties of undefined (reading 'Title')`, and the server
   logs `run crashed` at error level, with the stack. In `runs list`, the
   `crashed` row sits next to `failed (status)` and `failed (timeout)`. In the
   viewer, all three `Engine.execute` spans are red, and only the crashed one
   carries a stack.
5. Put the line back. Run the same `rules run` again. It prints `succeeded`,
   and `pnpm check` passes.

The exact line, and the file with the bug planted, are in `exercises/20/`. A
`crashed` row is your code misbehaving: the receiver is fine, and the bug
happens on every run until you fix it. For an interval rule it is also what
stops the loop.

## What you learned

- An `httpPost` action is a request value, sent through the `HttpClient`
  service. Its failures are `ActionFailed` with a reason.
- The boundary records it with no new outcome.
- `failed` means the action was attempted and the other side did not do its
  part. `crashed` means a bug in your code.
- A `Cause` holds typed failures, defects and interruptions, and `terminal`
  reads them in that order.
- The cost is an action you no longer control. It can be slow, and while it
  is slow, the next rule waits. The next lesson,
  [Running work concurrently with Effect.forEach](/learn/part-3/21-many-at-once),
  fixes that.
