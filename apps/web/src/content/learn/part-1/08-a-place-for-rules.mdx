The rules are constants in this file, and `program` hands them to `evaluate`
one call at a time. In Part 2 the rules come from a file and then from an
HTTP API. In Part 3 they come from SQLite. The code that evaluates rules
should not change every time the place they are stored does. It should ask
for the rules and leave it to something else to answer.

By the end of this lesson `evaluateAll` asks a `RuleStore` service for the
rules. The file ends with a type error at the run line. That is the intended
end state, and the next lesson fixes it.

In this lesson you will:

- define a service with `Context.Service`
- use a service inside an Effect with `yield*`
- read the requirements type of an Effect
- read the error TypeScript reports when a requirement is not provided

## 1. Define the service

`Context.Service` defines a **service**: a name and the shape of what it
offers, with no implementation yet. Add `Context` to the `effect` import,
then declare `RuleStore` below `decodeRule`:

Like `Schema.TaggedError`, `Context.Service` is called twice:

- The angle brackets take the class's own name and the shape. This shape has
  one member, `list`, an Effect that gives back the stored rules as JSON
  strings.
- The string in the second call, `"reflex/RuleStore"`, is the service's key.
  It must be unique in the program.

## 3. Read the requirements type

Hover `evaluateAll`. Its return type is
`Effect<void, SchemaError, RuleStore>`.

The requirements type is what an Effect needs before it can run. It has
been `never` since your first Effect. Now it names `RuleStore`, and `program`
carries it too. Hover `program` to see it.

## 4. Read the error at the run line

Look at the last line, `NodeRuntime.runMain(program)`. It is underlined in
red, the terminal shows the same type error, and the program does not run.
The playground only runs a file that typechecks.

The error is long. The part that matters is its last line:
`Type 'RuleStore' is not assignable to type 'never'.` `runMain` only runs an
Effect whose requirements type is `never`, and `program` still needs a
`RuleStore`.

This is where the lesson ends. The Solve button shows the same red line,
because it is the lesson's end state.

## What you learned

- `Context.Service` defines a service by its name and shape.
- `yield* RuleStore` inside an Effect gives you the implementation.
- The requirements type lists the services an Effect still needs. Every
  Effect that uses a service carries it in its type until something provides
  it.
- `runMain` refuses an Effect whose requirements type is not `never`, so a
  missing service is caught before anything runs.
- The next lesson,
  [Providing a service with a layer](/learn/part-1/09-provide-it), provides
  the service.
