`handleEvent` is still a `for...of` over the rules, one `yield*` after
another. That was fine while every action was a line in a file. Now an action
can take up to the 10 second timeout, and every rule after it waits. In this
lesson the rules an event matches run at the same time, up to a limit, and
the limits of the server move out of the code into `Config`.

In this lesson you will:

- see the rules of one event wait for each other in the viewer
- run them concurrently with `Effect.forEach` and a `concurrency` limit
- read the timeout, the concurrency and two more limits from the environment
  with `Config`
- send an alert to your phone through ntfy.sh

## 1. See the rules wait

Start clean, so the event matches only the rules this lesson adds. Every
server, yours and the checkpoints', keeps its rules in the same `reflex.db`,
and the rules from earlier lessons are still in it. Stop your server, delete
`reflex.db`, and start it again. Then start the receiver with the mixed
scenario:

```sh
pnpm receiver --scenario mixed
```

It prints four rules for one `expense` event:

- A and B post to `/ok`.
- C posts to `/slow?ms=15000`, which is past the timeout.
- D posts to `/fail?status=500`.

Add the four files from `fixtures/rules/mixed/` to your server and submit
`fixtures/events/laptop.json`:

```sh
pnpm cli rules add fixtures/rules/mixed/a-ok.json
pnpm cli rules add fixtures/rules/mixed/b-ok.json
pnpm cli rules add fixtures/rules/mixed/c-slow.json
pnpm cli rules add fixtures/rules/mixed/d-fail.json
pnpm cli events submit fixtures/events/laptop.json
```

Look in the viewer. D's `Engine.execute` span starts only after C's has run
its full 10 seconds, even though D had nothing to wait for. The time of the
event is the sum of the rules.

## 2. Run the rules concurrently

The rules an event matches do not depend on each other, so they can run at
the same time, up to a limit. In `src/Engine.ts`, change `handleEvent` to
filter the matching rules and run them with `Effect.forEach`:

<LessonCode file="checkpoints/21/src/Engine.ts" />

`Effect.forEach(rules, (rule) => execute(rule, event), { concurrency })` runs
`execute` for each rule, at most `concurrency` at a time. Each run gets a
fiber of its own. The outcomes come back in the order of the rules, not the
order in which they finished.

Submit the event again. `events submit` now takes about 10 seconds, the
timeout, and the four spans start together.

This is safe because of a decision made in
[Recording runs with Effect.onExit](/learn/part-2/12-an-engine-that-records):
`execute` cannot fail. The boundary writes each run's row and then turns
every failure and crash into an `Outcome` value. That matters because
`Effect.forEach` stops at the first failure and interrupts the rest, which is
right for work that only makes sense as a whole and wrong for independent
rules. Here there is no failure to stop at. D's 500 is a value. C's timeout
is a value. A and B finish whatever happens to the others.

The limit matters too. With 100 rules on one event, a limit of 4 means at
most four requests leave at once, instead of 100 hitting whoever the rules
point to.

## 3. Read the limits from Config

The timeout, the concurrency and two other limits are no longer constants.
Create `src/Limits.ts`, which reads each one from the environment with a
default:

<LessonCode file="checkpoints/21/src/Limits.ts" />

- `Config.Int("REFLEX_CONCURRENCY")` describes where a value comes from and
  how to parse it.
- `Config.withDefault(4)` makes it optional.
- `Config.all` combines several values into one.

Inside a layer, `yield* Limits` reads them all. If one is set to something it
cannot parse, the server fails to start with a message naming it.

The Engine reads `timeout` and `concurrency`. The API handlers read the other
two:

- More than `maxRules` rules (100) is `TooManyRules`, sent as a 409.
- An event whose JSON is more than `maxPayloadBytes` (64 KiB) is
  `PayloadTooLarge`, a 413. It is refused before any rule sees it, both from
  `events submit` and from `rules run`.

Both are typed errors on their endpoints, like `RuleNotFound`, so the CLI
prints each one as a single line.

To see a limit at work, start your server with
`REFLEX_CONCURRENCY=1 pnpm dev:server` and submit the mixed event again. D
waits for C, as it did before this lesson.

Send an alert to your phone. This is not part of the checkpoint.
[ntfy.sh](https://ntfy.sh) delivers a POST to `https://ntfy.sh/<topic>` to
every device subscribed to that topic, and uses the `Title` header as the
notification's title. That is an `httpPost` action:

A topic is not an account. Anyone who knows it can publish to it and read
what was sent, so the topic is the only secret, and a short one gets guessed.

1. Make a long random topic:

   ```sh
   node -e "console.log(crypto.randomUUID())"
   ```

2. Install the ntfy app on your phone and subscribe to that topic.
3. Copy `fixtures/rules/ntfy.json` to a file of your own, and put your topic
   in the URL.
4. Add it to the checkpoint's server and submit `fixtures/events/laptop.json`.
   Your phone shows "reflex", with "expense over 500" and the event under it.
5. Submit `fixtures/events/lunch.json`. Nothing arrives, because 40 is not
   over 500.

Send fixture data only. Whatever you post there, assume anyone could read it.

## What you learned

- Independent work runs with `Effect.forEach` and a `concurrency` limit.
- It is safe because each piece returns a value instead of failing.
- Limits are `Config` values with defaults, read once when the server starts.
- The cost is that runs of one event now overlap. Their log lines interleave,
  and their order in `runs list` is the order they started, not the order of
  the rules.
- The next lesson,
  [Diagnosing a request from its trace](/learn/part-3/22-diagnose-it),
  reads this exact trace to answer questions about it.

## Checkpoint

The checkpoint shows the four rules of the mixed scenario running together.
This lesson's checkpoint is number 21.

The four rules you added above are still in `reflex.db`, and adding them
again would add four more, because the store does not deduplicate. Stop your
server and delete `reflex.db` once more. Then, with the mixed receiver
running, start the checkpoint's server and add the four rules:

```sh
pnpm checkpoint 21 server
```

```sh
pnpm checkpoint 21 cli rules add fixtures/rules/mixed/a-ok.json
pnpm checkpoint 21 cli rules add fixtures/rules/mixed/b-ok.json
pnpm checkpoint 21 cli rules add fixtures/rules/mixed/c-slow.json
pnpm checkpoint 21 cli rules add fixtures/rules/mixed/d-fail.json
pnpm checkpoint 21 cli events submit fixtures/events/laptop.json
pnpm checkpoint 21 cli runs list
```

`events submit` takes about 10 seconds, the timeout, not the sum. It prints
two `succeeded`, one `failed (timeout)` and one `failed (status)`, and
`runs list` has the same four rows. In the viewer, the `Engine.handleEvent`
trace has four `Engine.execute` spans starting together under it. C's and D's
are red, and A's and B's are Ok.
