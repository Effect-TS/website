Suppose you submit an expense and no alert appears. Perhaps it was below
the threshold. Perhaps the event had no amount, or reflex couldn't write
the file. Our current program doesn't keep enough history to tell us
afterwards, and that will get harder to follow as we add more rules.

A run history will let us check what happened, including runs that didn't
produce an alert. We'll put the work of finding and running matching rules
in a service called `Engine`, and save their results in a `RunLog`. If one
action fails, the Engine should record that failure and still give the
remaining rules a chance to run.

with stored rules. If `get` or `remove` receives an unknown id, it fails
with `RuleNotFound`. The storage should feel familiar: `layerMemory` still

## Keep a run history

Now give those rules somewhere to leave a history. Create `src/RunLog.ts`.
Like `RuleStore`, it has a service definition and a memory layer. We'll
record when a run starts as well as how it ends:

- `start` opens a row with the outcome `started`.
- `finish` writes how the run ended.
- `list` reads rows back, newest first.

<LessonCode file="checkpoints/12/src/RunLog.ts" />

`RunResult` describes a completed run as `skipped`, `succeeded` or `failed`.
For a failure, it also requires a reason: `status`, `timeout` or `io`.
Only `io` can occur with the current file-writing action; the other two
are for the network action you will add later. At this checkpoint, skipped
runs do not yet have a reason.

## How the result reaches the history

The rows show what happened for each expense, even when no alert was
written. Now return to `execute` in the Engine to follow how a result
gets recorded. It starts with `runLog.start`, so a row exists before the
condition or action runs.

The inner `run` function evaluates the condition and performs the
action. Its `Effect.fn("Engine.execute")` creates a span, with the rule id
and trigger attached as attributes. If an action fails, that span ends
with an error. But a missing field is something we already know how to
handle: `run` catches `MissingField` and returns `skipped`. We successfully
decided not to run the action, so the span ends Ok and the row's `error`
column remains null.

After `run` ends, `Effect.onExit` receives its `Exit`, a value describing
how the effect ended. The callback writes a successful `RunResult` to the
row, or records `failed` for an `ActionFailed`. Other endings leave the row
as `started` for now.

This means each completed run costs two run-log writes, one for `started`
and one for the result. We keep both so that a run that began but didn't
finish looks different from a run that never started.

Only after recording the result does `Effect.catchTag` convert
`ActionFailed` into a `failed` value for the caller. This order matters:
the span and run log record the failure, while `handleEvent` receives an
outcome it can collect before continuing to the next rule. The effect
returned by `execute` has no typed failures; defects and interruption
are still possible.

For now, a defect or interruption can leave a row at `started`. We'll
handle those unfinished rows when we add scheduled work in
[Running rules on a schedule with FiberMap](/learn/part-3/19-rules-on-a-clock),
with `interrupted` and `crashed` outcomes and a timeout inside the span.

Although executing an action requires a file system, callers of `execute`
do not have to provide one. The layer retrieved it when it was built, and
`Effect.provideService` supplies that same instance to `appendLine`. The
annotation `Effect.fn.Return<RunResult, ActionFailed | MissingField>` checks
the generator's return values and typed failures, so an invalid result is
caught by TypeScript.

Finally, `handleEvent` loops through the stored rules, much like
`evaluateAll` in Part 1. For each event trigger matching the event's type,
it calls `execute` and collects the outcome.

## Try it

We can now see that `huge expense` was skipped, but the row doesn't say
why. A false condition, a missing field and an unsupported action would
each need a different response from us. Give each skip a reason and store
it as free text in the run history's `reason` column:

1. In `src/RunLog.ts`, give the `skipped` member of `RunResult` a
   `reason: Schema.String`. The compiler now lists every place that writes a
   skip without one.
2. Add reasons to the three skip results in `src/Engine.ts`:
   - When a condition is false, identify the condition in the reason.
   - In the `MissingField` catch, include the error's `field`, producing
     text such as `missing field amount`.
   - In the `httpPost` branch, explain that the action is introduced in the
     lesson on network actions.
3. Leave the `failed` result unchanged. Its reasons stay restricted to
   `status`, `timeout` and `io`, rather than the free text we're adding
   for skipped runs.

Check your work with `pnpm tsx src/main.ts`. It prints each skip with its
reason in brackets. The hint and the changed files are in `exercises/12/`.
From the next checkpoint on, the reference solution includes this change,
and the next lesson tests it.
