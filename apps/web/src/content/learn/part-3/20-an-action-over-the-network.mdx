An alert in `alerts.log` is useful while we're watching the terminal. To
reach us elsewhere, reflex needs to send that alert to another service,
perhaps a webhook or a notification service. Let's give our rules an HTTP
action. The server has accepted `httpPost` rules since
[Recording runs with Effect.onExit](/learn/part-2/12-an-engine-that-records),
but has skipped them with the reason
`httpPost actions run from lesson 20`.

We'll send to our local receiver first, where we can control the response.
That lets us try a rejected request and a slow one without depending on an
outside service. Later, we'll deliberately introduce a bug and compare it
with those failures. A red span alone won't tell us which problem needs
fixing; the details we record will.

## Build and send a POST request

Start in `src/Action.ts`, alongside the file action, and add `postMessage`.
It sends the action's message as a
plain-text POST body. If `includePayload` is true, it appends the payload as
JSON on the next line. It also includes any `headers` set on the action:

<LessonCode file="checkpoints/20/src/Action.ts" />

The request follows the describe-then-run pattern we started with.
`HttpClientRequest.post(url)` creates a request value. The pipeline adds
headers with `HttpClientRequest.setHeaders` and a body with
`HttpClientRequest.bodyText`; none of that sends anything yet. The network
operation happens when `client.execute(request)` runs.

We can reuse the error policy from `poll`. A request failure, such
as a refused connection, becomes `ActionFailed` with reason `io`. A
response outside 2xx becomes `ActionFailed` with reason `status`, with the
URL and status code in its message.

In `src/Engine.ts`, update the `httpPost` branch of `run` to call
`postMessage` and return `succeeded` once it completes. Use
`Effect.provideService` to provide the Engine's `HttpClient`, just as
`appendLine` receives `FileSystem`. The temporary skip for unimplemented
HTTP actions is no longer needed. The remaining skip reasons are a false
condition and a missing field.

There is no need to add another timer for the POST. The existing
`Effect.timeout` already covers `run` inside its execution
span. If the receiver takes longer than 10 seconds, it interrupts the
request and the run ends with `TimeoutError`. The boundary records
`failed (timeout)`, not `interrupted`, because the timeout is the reason
the run ended.

## Compare a rejected request with a timeout

Let's send two requests that won't succeed, for different reasons. With
`pnpm receiver` and `pnpm dev:server` running, add the two rules and run
each one on its own:

```sh
pnpm cli rules add fixtures/rules/post-fail.json
pnpm cli rules add fixtures/rules/post-slow.json
pnpm cli rules run <post-fail id> --event fixtures/events/laptop.json
pnpm cli rules run <post-slow id> --event fixtures/events/laptop.json
```

The first prints `failed (status)` with the 500. The second takes about 10 seconds
and prints `failed (timeout)`. `runs list` shows:

| Rule file        | Receiver answer         | `runs list`                              |
| ---------------- | ----------------------- | ---------------------------------------- |
| `post-fail.json` | `/fail?status=500`: 500 | `failed (status): POST ... answered 500` |
| `post-slow.json` | `/slow?ms=15000`: late  | `failed (timeout): timed out after 10s`  |

Notice that neither run says `crashed`. Both ended in a failure the program
explicitly handles. One received
a 500 response; the other did not receive a response before the deadline.
Neither result indicates a defect in the action implementation. Whether
retrying is appropriate depends on the receiver and whether repeating the
action could have unwanted effects.

Open their `Engine.execute` spans in the viewer. Both are red, but their
status messages distinguish the 500 response from `TimeoutError`. The
timed-out span lasts about as long as the configured timeout.

## Read the cause of an unsuccessful run

We've seen two failures that our code anticipates. An effect's error type
describes those expected failures. As you saw in
[Defining errors with Schema.TaggedError](/learn/part-1/04-failure-you-can-see),
that lets TypeScript check which errors your code handles. It does not
mean those are the only ways execution can stop.

For the fuller picture, we need the `Cause` inside an unsuccessful `Exit`.
It records typed failures, defects and interruptions, including the ways a
run can stop that aren't listed in its error type. In this Engine, `ActionFailed` and
`TimeoutError` are typed failures. A thrown exception is a defect, as is a
failure converted by `Effect.orDie`, such as the database errors in
[Storing data in SQLite with SqlClient](/learn/part-3/17-survive-a-restart).
Interruption occurs when work is cancelled, for example by
`FiberMap.remove` or Ctrl-C. A timeout also interrupts the work it cancels,
but the enclosing timed effect ends with the typed `TimeoutError`.

Go back to `terminal` in `src/Engine.ts` with those cases in mind. It first
handles a successful `Exit`. For an
unsuccessful one, it checks `Cause.hasInterruptsOnly` before inspecting any
error. A cause containing only interruption becomes `interrupted`. For
other causes, `Cause.squash` extracts a main error: `ActionFailed` and
`TimeoutError` become `failed` with the appropriate reason, while anything
else becomes `crashed`.

When we're diagnosing a run, that extra information matters. The error
type tells us what the implementation exposes for handling. The recorded
cause can also tell us that our own code threw, or that someone cancelled
the work.

## Try it

So far, the receiver or its timing explained the failure. Let's make the
problem our own this time. Introduce a bug in `postMessage`, then compare
its `crashed` row with the two `failed` rows. We'll undo the bug at the end:

1. In `postMessage`, change the headers line to trim the `Title` header.
   Use `!` to assert that the headers exist, even though `post-ok.json`
   does not define any. `pnpm check` still passes because the assertion
   suppresses that check in TypeScript; it does not add headers at runtime.
2. Add the rule with `pnpm cli rules add fixtures/rules/post-ok.json` and note
   the id it prints.
3. Run only that rule, with
   `pnpm cli rules run <post-ok id> --event fixtures/events/laptop.json`. Do
   not submit the event to every rule: `post-fail` and `post-slow` match
   expenses too, have no headers either, and would crash as well.
4. The CLI prints `crashed` with
   `Cannot read properties of undefined (reading 'Title')`, and the server
   logs `run crashed` at error level, with the stack. In `runs list`, the
   `crashed` row sits next to `failed (status)` and `failed (timeout)`. In the
   viewer, all three `Engine.execute` spans are red, and only the crashed one
   carries a stack.
5. Put the line back. Run the same `rules run` again. It prints `succeeded`,
   and `pnpm check` passes.

If you need the exact line, a copy of the file containing the bug is in
`exercises/20/`. Here the crash happens before the receiver can respond,
and retrying the rule cannot repair it. The code needs to be fixed. For an
interval rule, this outcome would also stop its loop.

With the line restored, reflex can send an alert over HTTP, and its
history can tell us why an attempt didn't work. The action fits the
existing execution boundary without adding a new outcome.

You probably noticed how long the slow request kept the CLI waiting.
`handleEvent` still executes rules sequentially, so that request would
also delay every rule after it. In
[Running work concurrently with Effect.forEach](/learn/part-3/21-many-at-once),
we'll let independent rules run without waiting for one another.

## Checkpoint

To compare your results with the reference version, use checkpoint 20 to
reproduce the two HTTP failures. Start the receiver
and checkpoint server in separate terminals:

```sh
pnpm receiver
pnpm checkpoint 20 server
```

In a third, add the two rules and run each one on its own:

```sh
pnpm checkpoint 20 cli rules add fixtures/rules/post-fail.json
pnpm checkpoint 20 cli rules add fixtures/rules/post-slow.json
pnpm checkpoint 20 cli rules run <post-fail id> --event fixtures/events/laptop.json
pnpm checkpoint 20 cli rules run <post-slow id> --event fixtures/events/laptop.json
```

The first prints `failed (status)` with the 500. The second takes about 10
seconds and prints `failed (timeout)`. The `crashed` result comes from the
Try it exercise on your own server, not from the unmodified checkpoint.
Because both servers use `reflex.db`, `runs list` can show all three rows
after you have completed that exercise. In the viewer, compare their three
red `Engine.execute` spans. You now have enough detail to tell a rejected
request, a timeout and a programming bug apart, even though they share a
color.
