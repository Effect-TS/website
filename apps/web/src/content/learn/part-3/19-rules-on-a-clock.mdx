Let's put that work to use. Suppose a service we rely on starts reporting
degraded performance. We'd like reflex to notice, rather than having to
check its status ourselves.

The server has accepted rules like this since

but hasn't executed them yet. We'll give each interval rule a loop like
the heartbeat, with a poll and an action in each iteration, or tick. This
rule starts polling as soon as it is added, then waits 5 seconds after each

Starting the checks is only part of the job. If we remove the rule, its
loop needs to stop too, even if it is waiting for a response. And a service
that is temporarily unavailable shouldn't stop us checking it later.
We'll build up that behavior using the run history and the scoped fibers
we already have. Start with the response we want the rule to inspect.

## Use the poll response as the payload

With expenses, someone handed us an event to evaluate. Here, we have to
fetch the data ourselves. The rule's payload is the GET response,
represented as `{ status, body }`. A valid JSON body
is parsed; any other body is kept as text. The condition can then read
`body.status` using a dotted field path, just as an expense condition reads
`amount`. Create `src/Poll.ts`:

The receiver won't always give us a usable response. A response outside
the 2xx range becomes `ActionFailed` with reason
`status`. A failure to make the request or read the response body becomes
`ActionFailed` with reason `io`.

In `src/Rule.ts`, change `lookup` and `evaluate` to accept a `Payload`
instead of an `Event`. `Payload` allows any object, so the same condition
evaluator can work with both a submitted event and a poll response.

## Record the poll as part of the run

It might seem natural to fetch the response first, then pass it to the
Engine. But if that request fails or hangs, we'd have no run record to
explain what happened. Our execution boundary, the code that records and
limits each run, needs to start recording before it fetches the payload.

Change it to accept a payload effect rather than a payload value. For an
event rule, use `Effect.succeed(event)`; for an interval rule, use
`poll(url)`. The boundary can then open the row before executing either
effect. An interval run follows this order:

1. `runLog.start` inserts a row with outcome `started`, before the GET.
2. Inside the `Engine.execute` span, `Effect.timeout` covers obtaining the
   payload, evaluating the condition and running the action. The poll and
   action share a 10 second timeout.
3. `Effect.onExit` uses the `Exit` to update the row with its terminal
   outcome.
4. Outside the span, a typed failure or defect becomes an `Outcome` value
   for the caller. Interruption remains an interruption; it is not converted
   into a return value.

Now even a poll that never returns will leave evidence. Whether it fails,
times out or is interrupted, we'll have one run row and one execution span,
just as we do for a completed action.

## Distinguish crashes from interruptions

Removing a rule during a poll isn't the same as the receiver rejecting
it. Nor is a bug in our own code. Let's give those results their own names
in the history: `interrupted` and `crashed`. Alongside the outcomes we
already record, `Effect.onExit` receives the `Exit` for all of these cases:

| How `run` ended                           | Row                         | Span  |
| ----------------------------------------- | --------------------------- | ----- |
| Success, condition false or field missing | `skipped` with its reason   | Ok    |
| Success                                   | `succeeded`                 | Ok    |
| `ActionFailed`                            | `failed` (`status` or `io`) | Error |
| `TimeoutError` from `Effect.timeout`      | `failed` (`timeout`)        | Error |
| A defect: a thrown exception, a bug       | `crashed` with the message  | Error |
| Interrupted                               | `interrupted`               | Unset |

To tell these cases apart, the new `terminal` function inspects the
unsuccessful `Exit`'s `Cause`, a record of why execution stopped.
`Cause.hasInterruptsOnly` checks for interruption without a
failure or defect, which becomes `interrupted`. Otherwise, `Cause.squash`
extracts a main error. The Engine recognizes `ActionFailed` and
`TimeoutError` as expected failures and records anything else as `crashed`.
A crash also produces an error-level log containing the cause.

There is a limit to what our history can promise. Recording the result
can itself fail, for example if the database cannot be
written. In that case, the Engine logs the write failure with the run id
and leaves the row as `started`. It preserves the original execution
result rather than replacing a success or an interruption with a logging
failure.

## Manage each rule's loop with FiberMap

Imagine adding a second status rule, then removing the first. We need to
stop just that first rule's work. The heartbeat's single fiber isn't
enough now; each rule needs its own. `FiberMap` keeps running fibers
indexed by a key, so we can find the one to stop using its rule id:

- `FiberMap.run(loops, id, effect)` starts the effect on a fiber and stores
  it under the rule id.
- `FiberMap.remove(loops, id)` interrupts that fiber and waits for it to end.
- A fiber that finishes on its own is removed from the map automatically.

The map belongs to the Engine layer's scope, so closing that scope also
interrupts every loop still in the map. This retains the heartbeat's
shutdown behavior while allowing individual rules to stop earlier.

Each loop repeats one `Engine.execute`, including its poll, with
`Effect.repeat(Schedule.spaced(...))`. The first tick starts immediately;
later ticks start `everySeconds` after the previous tick ends. Each tick
has its own trace rather than remaining a child of the request that
created the rule.

Next, look at what happens after a tick. A `failed` result allows another
tick, since a receiver that is unavailable now might recover. A
`crashed` result indicates a defect, so the tick converts it to a
`RuleStopped` failure to end `Effect.repeat`. The loop logs
`interval rule stopped` with the rule id and error, then its fiber finishes
and is removed from the map.

We can also use the map to answer whether a rule is running, without a
separate stored flag to keep in sync. The Engine implements
`isRunning(id)` with `FiberMap.has`, and `rules list` uses that answer to
show an interval rule as `running` or `stopped`. A stopped rule remains in
the store and will be started again on the next server startup.

## Start stored rules and wait for removed rules to stop

We made rules survive a restart in SQLite, but their fibers don't survive
with them. To resume checking our service after a restart, the Engine
layer prepares the stored state before serving requests:

1. `runLog.abandonStarted` changes any remaining `started` rows to
   `abandoned`. This process has not begun executing rules yet, so those
   rows are unfinished records from a previous process.
2. The Engine starts a loop for every stored interval rule.

Adding and removing rules through the CLI must keep the store and the
loops in agreement too. In
`src/server/Api.ts`, `create` stores the rule before starting it. `remove`
first stops the loop and waits for it to finish, then deletes the rule and
sends the response:

<LessonCode file="checkpoints/19/src/server/Api.ts" />

Now follow a removal through the code. If a run was active when removal
started, interruption reaches it inside its span and
`onExit` records `interrupted`. Because `FiberMap.remove` waits for the
fiber, that update completes before the response, provided the write
succeeds. If the loop was waiting between ticks, there is no active run to
record; it simply stops. If a crash had already ended the loop, there is no
fiber left to interrupt.

In each case, the rule's interval loop has finished by the time the CLI
prints `Removed`. Removal does not cancel an event execution already
started by a separate request. That execution can finish, but subsequent
events will no longer find the deleted rule.

The dependency order also matters during server shutdown. The Engine is
built after `RunLog` and the SQL layers, so it closes before them. On
Ctrl-C, its loops can record interruptions while SQLite is still open.

Cancellation has limits. It stops this program's work, but cannot undo a
request the receiver has already accepted. An `interrupted` row records
that this run was stopped; it does not prove that nothing happened at the
receiver.

Forced termination does not run cleanup at all. After `kill -9`, a power
cut or an out-of-memory kill, a row may remain `started` because `onExit`
could not run. On the next startup it becomes `abandoned`. That outcome
means the final result is unknown, not that the action necessarily failed.

## Test removal during an active poll

Let's check the case that is hardest to catch by hand: removing a rule
while its request is still waiting. A test shouldn't depend on us getting
the timing lucky. Instead, we'll use an `HttpClient` that deliberately
never responds.

Create `test/harness.ts`. It uses `HttpClient.make` to handle requests
without a network and provides a `Remote` service so the test can inspect
what happened:

The `Hang` reply gives us that waiting request. The client waits
indefinitely and sets `released`
when its `Effect.onInterrupt` handler runs. The `arrived` latch lets the
test wait until a request has actually reached the client:
`yield* remote.arrived.await` resumes when the client opens that latch.
Provide this fake client to the Engine in place of
`FetchHttpClient.layer`; the Engine itself needs no test-specific changes.

Use the test beginning `remove interrupts a poll in flight` in
`checkpoints/19/test/Interval.test.ts` as a reference. It calls the API
handlers through `HttpApiTest.groups`, which runs them in the test without
a socket. Those handlers still require services normally provided by the
server, including `HttpPlatform` and `Etag.Generator`. Merge
`HttpServer.layerServices` into the provided layer to satisfy those
requirements; without it, the test will not typecheck.

With that harness in place, write a test that follows a rule from its
first poll through removal:

1. Add an interval rule with the fake server set to `Hang`.
2. Await `arrived`. No clock adjustment is needed, because the first tick
   runs at once.
3. Assert that the rule's runs are exactly `["started"]`. That is the row
   opened before the GET.
4. Call `remove`. When it returns, assert that `released` is true and the
   runs are `["interrupted"]`.
5. `TestClock.adjust("6 seconds")`, past one interval, and assert there was
   still only one request.

Run `pnpm test`. With `it.effect`, the schedule uses `TestClock`, so the
test advances time with `TestClock.adjust` instead of waiting six real
seconds. The final assertion distinguishes a stopped loop from one that
is merely waiting for its next tick.

## Try it

Our status check works, but we shouldn't let a rule hammer the receiver
without a pause. The schema still accepts intervals that are too short.
Copy `status-degraded.json`, set `everySeconds` to 0
and add the copy. The server accepts it and polls as fast as the receiver
can respond. Remove this test rule before changing the schema. Otherwise,
it will remain in SQLite with an interval that the updated schema rejects.

Let's catch that mistake before a rule reaches the server. Require at
least 5 seconds in the `Rule` schema, starting with a test:

1. In `test/Rule.test.ts`, decode an interval rule at `everySeconds` 4 and at
   5, and expect one failure and one success. Run `pnpm test test/Rule.test.ts`.
   The first assertion fails.
2. In `src/Rule.ts`, add the lower bound to `everySeconds` with
   `Schema.isGreaterThanOrEqualTo(5)`.
3. Run the test again. It passes.
4. Run `pnpm cli rules add` with a rule whose `everySeconds` is 4. It prints
   the decoding error before anything is sent.

The hint and the changed files are in `exercises/19/`. Checkpoint 19 already
includes the check.

Reflex can now keep checking a service while we leave it alone, and we
can remove that check without restarting the server. Each interval rule
has a fiber and creates a run row on every tick, so adding more rules also
increases the amount of history we store. In
[Telling errors from defects with Cause](/learn/part-3/20-an-action-over-the-network),
we'll send alerts over HTTP and use these records to distinguish a failed
request from a bug in our code.

## Checkpoint

Let's watch the behavior we've been building. Checkpoint 19 covers a failed
poll that repeats, a crash that stops its loop, and removal during a poll.
Start the receiver
and the checkpoint server in separate terminals:

```sh
pnpm receiver
pnpm checkpoint 19 server
```

### 19a: failed polls keep running

In a third terminal:

```sh
pnpm checkpoint 19 cli rules add fixtures/rules/status-degraded.json
curl -X POST localhost:4600/status/mode -H 'content-type: application/json' -d '{"mode":"degraded"}'
```

You should see a new `succeeded` row in
`pnpm checkpoint 19 cli runs list` and a new line in `alerts.log` about
every 5 seconds.

Now switch `/status` to a 500 with `-d '{"mode":"error"}'`. New rows
show `failed (status)`, but `pnpm checkpoint 19 cli rules list` still shows
`running`. The failed request has not stopped the loop. Each row is opened
before its GET, which you will observe during the removal check below.

### 19b: a bug stops the loop

This path changes code, so it runs on your own server. Stop the checkpoint's
server and start `pnpm dev:server`, which restarts on every save.

Before introducing a bug, remember that the previous check left `/status`
returning 500. That response would fail
the poll before it reached the code you are about to change, so switch it
back to `degraded` first:

```sh
curl -X POST localhost:4600/status/mode -H 'content-type: application/json' -d '{"mode":"degraded"}'
```

Introduce a bug in the last line of `src/Poll.ts`. Instead of returning
`body` unchanged, cast it to an object with a `state` string and return
`state.trim()` as the body. `pnpm check` passes because TypeScript trusts
the cast. The actual response contains `status`, not `state`, so calling
`trim` will throw.

Save the file. The server restarts and starts the stored rule again. Check
these results:

- `runs list` gets one `crashed` row,
  `Cannot read properties of undefined (reading 'trim')`.
- The server logs `run crashed` and `interval rule stopped`.
- No further rows appear.
- `rules list` says `stopped`.

Undo the change so the line returns `body` again, then save. After the
restart, the rule produces a `succeeded` tick and `rules list` shows
`running` again.

### 19c: removal interrupts an active poll

Stop your own server, then restart the checkpoint server with
`pnpm checkpoint 19 server`. Add the slow poll, which waits 8 seconds for
every answer:

```sh
pnpm checkpoint 19 cli rules add fixtures/rules/slow-poll.json
pnpm checkpoint 19 cli runs list --rule <id>
```

The newest row is `started` because the GET has not completed. Remove the
rule while the request is still waiting, then immediately list its runs:

```sh
pnpm checkpoint 19 cli rules remove <id> && pnpm checkpoint 19 cli runs list --rule <id>
```

Look for `interrupted` in the newest row. The update completed before
the CLI printed `Removed`. If it shows `succeeded`, the 8 second request
finished before removal reached it. Add the rule again and remove it
sooner.

Keep the viewer running for this path. The CLI waits for its traces to be
delivered, and without a viewer each command takes seconds longer.

Wait 10 seconds and list again. Nothing came after the `interrupted` row. In
the viewer, that run is one Unset `Engine.execute` span.

Finally, remove the `status-degraded` rule while it is idle between ticks.
This time there is no active run to interrupt, so no new row is written,
and `rules list` no longer shows it.
`pnpm checkpoint 19 test` includes the harness test.
