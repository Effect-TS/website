**Effect is a TypeScript library for building applications that have to work in production.**

It gives you one set of tools for errors, retries, timeouts, concurrency, cancellation, dependency injection, resource cleanup, validation, and tracing without assembling and coordinating a different library for every problem.

Your service calls three APIs. One is slow, one returns invalid data, and the request is cancelled halfway through. You still need to stop the remaining work, retry only what makes sense, release every resource, preserve useful error information, and explain what happened in a trace.

That is what Effect is for.

## The difficult part is coordination

Calling one API from TypeScript is easy. Keeping the complete operation correct as requirements accumulate is where production code becomes difficult.

A conventional implementation may coordinate:

- rejected Promises and thrown exceptions;
- HTTP status handling and response validation;
- retry helpers and timers;
- `AbortController` instances;
- a concurrency limiter;
- `try`/`finally` cleanup;
- dependency wiring;
- manual trace start, propagation, and completion.

Each tool can be reasonable by itself. The risk lives in the connections: does a timeout abort the request, does a retry preserve cancellation, does cleanup run after interruption, and can the caller see which failures remain possible?

Effect keeps those concerns attached to the operation as it is built.

```ts
import { Effect } from "effect"

declare const placeOrder: Effect.Effect<
  AcceptedOrder,
  OutOfStock | PaymentDeclined,
  InventoryService | PaymentProvider
>

interface AcceptedOrder {
  readonly orderId: string
  readonly status: "accepted"
}

declare class OutOfStock {
  readonly _tag: "OutOfStock"
}

declare class PaymentDeclined {
  readonly _tag: "PaymentDeclined"
}

declare class InventoryService {
  readonly _tag: "InventoryService"
}

declare class PaymentProvider {
  readonly _tag: "PaymentProvider"
}
```

Read the type from left to right:

- the operation can produce an `AcceptedOrder`;
- it can fail with `OutOfStock` or `PaymentDeclined`;
- it still requires `InventoryService` and `PaymentProvider`.

As operations are combined, TypeScript keeps updating that information. At the application boundary, you supply the remaining services and choose how the program runs.

## What changes in day-to-day work

### Failures become explicit

Thrown values and Promise rejections normally reach `catch` as `unknown`. Effect
keeps expected failures visible in the operation's type, so each failure can
have an explicit retry, timeout, or HTTP response decision.

### Structured concurrency is built in

Concurrency limits, ordered results, timeouts, cancellation, and failure
propagation belong to the same runtime. If the complete operation stops, its
unfinished work stops too.

### Resources follow operation lifetimes

A `Scope` owns resources and their finalizers. When the operation's lifetime
ends, cleanup runs after success, failure, cancellation, or an unexpected bug.

### Rich domain models get JSON codecs

Schema describes both rich domain values and their representation over the
wire. Validation and JSON codecs can then be derived from the same description
instead of maintained as separate serialization code.

### Dependencies stay explicit without manual wiring

An operation's type records the services it requires. `Layer` selects and
builds their implementations at the application boundary, so dependencies stay
visible without passing them through every intermediate function.

### AI-generated code faces precise constraints

Effect's precise types make plausible but incorrect code harder to express.
Effect-aware developer tools identify suspicious code that still gets through.

### OpenTelemetry instrumentation follows the code

Named Effect functions create spans whose lifetimes and parent-child
relationships follow the operations they describe. Concurrency, failures, and
cancellation remain connected without manual tracing context propagation.
