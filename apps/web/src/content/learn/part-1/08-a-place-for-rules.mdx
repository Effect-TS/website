The rules are still constants in this file, and `program` hands them to
`evaluate` one call at a time. That won't last. In Part 2 the rules come from a
file and then from an HTTP API. In Part 3 they come from SQLite.

The code that evaluates rules shouldn't have to change every time the place
they're stored does. It should ask for "the rules" and leave it to something
else to answer.

You will learn:

- how to declare a service with `Context.Service`;
- how to use a service from inside an effect;
- what the third slot of an Effect's type means.

This lesson ends on purpose with a type error. Lesson 9 fixes it.

## Declaring a service

`Context.Service` declares a **service**: a name and the shape of what it
offers, with no implementation yet. Add `Context` to the `effect` import, then
declare `RuleStore`:

  declaration="RuleStore"

Like `Schema.TaggedError` in lesson 4, `Context.Service` is called twice:

- The angle brackets take the class's own name and the shape. This shape has
  one member, `list`, an effect that gives back the stored rules as JSON
  strings.
- The string in the second call, `"rulebook/RuleStore"`, is the service's key.
  It must be unique in the program.

## Using a service

Inside `Effect.gen` or `Effect.fn`, `const store = yield* RuleStore` hands you
the implementation, whatever it turns out to be. From then on you use it like
any other object, for example `yield* store.list`.

Now write `evaluateAll(event)` with `Effect.fn`. It should:

1. get the store;
2. list the rules;
3. evaluate each one against the event, with a `for...of` loop and
   `yield* evaluate(json, event)` inside it.

A plain loop is enough. Each `yield*` finishes before the next one starts, so
the rules run one at a time, in order. Lesson 21 comes back to that.

In `program`, replace the three `evaluate` calls with `evaluateAll(laptop)` and
`evaluateAll(taxi)`. Then delete the `largeExpense` and `malformed` constants.
The rules belong to the store now.

## The requirements type

Hover `evaluateAll`: `Effect<void, SchemaError, RuleStore>`.

The third slot is what an effect needs before it can run. It has said `never`,
meaning nothing, since lesson 2. Now it names `RuleStore`, and `program`
carries it too.

## Reading the missing-service error

Look at the run line at the bottom, `NodeRuntime.runMain(program)`. It's now
underlined in red. The terminal shows the same type error, and the program
doesn't start, because the playground only runs a file that typechecks.

The error is long. The part that matters is its last line:

> `Type 'RuleStore' is not assignable to type 'never'.`

This is where the lesson ends. The Solve button shows the same red line,
because it is the lesson's end state.

## Try it: explain the error

Before you open lesson 9, explain the error in your own words. Work through it
from the inside out:

- Hover `evaluateAll`, then `program`. Where does `RuleStore`
  enter the third slot, and why does it stay there all the way up?
- The error says `runMain` wants `never` in that slot. What would it mean to
  run a program that still needs something?
- You declared what a `RuleStore` looks like. Where in the file did you say
  which rules it holds?

## Recap

- `Context.Service` declares a service, and `yield*` hands you its
  implementation.
- The third slot of an Effect's type lists what the effect still needs.
- The cost of a service shows up right here. Every effect that touches it
  carries it in its type until someone supplies it. That's also what caught
  the mistake before anything ran.
- Lesson 9 supplies the service. Lesson 11 uses services that Effect itself
  ships, in the same way.
