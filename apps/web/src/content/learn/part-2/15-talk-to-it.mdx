The curl commands let you check the API, but adding rules and submitting
events would be easier through a CLI. The existing `Api` definition has
everything you need to derive a typed client for those commands. When you
change that definition, TypeScript will check the CLI against the updated
request and response types.

You will put the client in a service, use it in six command handlers, then
handle a `RuleNotFound` returned by the server.

## Create the client service

Create `src/ApiClient.ts`. The call
`HttpApiClient.make(Api, { baseUrl })` derives one client method per endpoint,
organized into the groups you defined in the API. For example:

- `client.rules.create({ payload })`
- `client.rules.run({ params: { id }, payload })`
- `client.runs.list({ query })`

Wrap the client in an `ApiClient` service so command handlers can access it
with `yield*`. The type `HttpApiClient.ForApi<typeof Api>` derives its
interface from the API too:

<LessonCode file="checkpoints/15/src/ApiClient.ts" />

The client checks and encodes request payloads using the endpoint schemas,
and decodes responses using the declared success and error schemas. It
sends requests through an `HttpClient` service; the CLI will provide
`FetchHttpClient.layer` for a client built on `fetch`.

The base URL comes from `Config.String("REFLEX_URL")`, which reads the
environment variable. `Config.withDefault("http://localhost:3000")` lets you
run against the local server without setting it. Because this configuration
is read inside the layer's effect, the URL is resolved when the layer is
built.

The CLI imports `Api` and its domain schemas, so it is checked against that
version of the API. A separately deployed server could use a different
version; keep the CLI and server versions compatible.

## Write the command handlers

Open the starter's `src/cli/main.ts`. The commands, arguments and flags are
already declared, but the six handler bodies are empty. Fill them in using
the client service. Each handler retrieves `ApiClient`, calls an endpoint
and prints the result:

<LessonCode file="checkpoints/15/src/cli/main.ts" />

- `rules add` reads the file with the same `readJson` as before, then calls
  `client.rules.create`.
- `rules run` and `events submit` print one outcome per line, with its
  reason or error.
- `runs list` has two optional flags, with types `string | undefined` and
  `number | undefined`. These match the optional query parameters. Pass
  `rule` as `ruleId` and `limit` as `limit` in `client.runs.list({ query })`.

Name the handlers with `Effect.fn("rules.add")` and the corresponding name
for each command. Those names will identify the command spans when you
export traces in the next lesson.

At the entrypoint, provide `ApiClient.layer` with `FetchHttpClient.layer`
for requests. Also provide `NodeServices.layer` so the handlers can read
rule and event files.

## Run the CLI against the server

Start the server with `pnpm dev:server` in one terminal. In a second:

```sh
pnpm cli rules add fixtures/rules/expense.json
pnpm cli rules list
pnpm cli events submit fixtures/events/laptop.json
pnpm cli runs list
```

`rules add` prints `Added <id>: large expense`. `events submit` prints one
line, `<id>: succeeded`, and `runs list` shows the row.

The Engine still skips actions it cannot execute yet. To check that the CLI
shows this outcome, add `fixtures/rules/ntfy.json`, whose action is
`httpPost`, then use its id to run it against an event:

```sh
pnpm cli rules run <id> --event fixtures/events/laptop.json
```

It prints one `skipped` outcome whose reason says that `httpPost` actions run
from a later lesson, and `runs list` shows the same row.
[Telling errors from defects with Cause](/learn/part-3/20-an-action-over-the-network)
adds the action.

## Inspect an error returned by the server

```sh
pnpm cli rules remove nope
```

The server returns a 404 response. Because the endpoint declares
`RuleNotFound`, the client decodes the response body into an instance of
that class. It becomes a typed failure of the client call, just as it was
a typed failure of the store. With no handler for it yet, the CLI prints
`RuleNotFound` with a stack trace.

Hover over the `rules remove` handler to inspect its error type. It includes
`RuleNotFound` alongside HTTP and schema errors. You can handle it with
`Effect.catchTag`, even though the failure originated in another process.

## Try it

An unknown id is an expected input mistake, so a stack trace is not a useful
CLI response. Print a short message instead, while keeping a non-zero exit
code so scripts can detect the failure.

1. Write one handler with `Effect.fn` that takes the `RuleNotFound`, prints
   `No rule with id <id>` with `Console.error`, and then fails with
   `new ExitCode({ code: 1 })` from `tools/entrypoint.ts`. `runMain` exits
   with that code and prints nothing more.
2. `Effect.fn` takes more arguments after the generator and applies each one
   to the effect it builds. Pass `Effect.catchTag("RuleNotFound", yourHandler)`
   there, in both the `rules remove` and `rules run` handlers.

Check your work with `pnpm cli rules remove nope` and
`pnpm cli rules run nope --event fixtures/events/laptop.json`. Each prints
one line and exits 1 (`echo $?`). The hint and the changed file are in
`exercises/15/`. From the next checkpoint on, the reference solution includes
this change.
