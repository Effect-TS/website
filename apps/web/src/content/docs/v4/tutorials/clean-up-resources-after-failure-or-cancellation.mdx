An order request can borrow a database connection, acquire an inventory lock,
and then fail before the request reaches its `finally` block. Even after that
gap is fixed, an HTTP client disconnect does not automatically cancel the
Promise that is still holding both resources.

In this tutorial, we will start with a familiar `node:http` order endpoint and
make its cleanup progressively more reliable. The finished `POST /orders`
endpoint will have these observable behaviors:

| Request outcome        | HTTP result | Resource behavior                                 |
| ---------------------- | ----------- | ------------------------------------------------- |
| Order is stored        | `201`       | Lock released, then connection released           |
| Lock acquisition fails | `500`       | The connection already acquired is released       |
| Client disconnects     | No response | Storage is interrupted, then both resources close |

The HTTP server will remain ordinary TypeScript. Effect will manage only the
part of the request that acquires, uses, and releases resources.

Each step ends with a checkpoint: a short verification to complete before continuing.

## 1. Find the gap around `finally`

This tutorial requires Node.js 22.18.0 or newer because it runs `server.ts`
directly with Node's built-in TypeScript support.

Create an empty project:

```sh title="Create the project"
mkdir clean-up-order-resources
cd clean-up-order-resources
npm init -y
npm pkg set type=module
npm install --save-dev @types/node@22
```

Create `server.ts`. The application is at the top. The collapsed section is a
deterministic tutorial fixture that stands in for a database pool and inventory

```ts title="server.ts" collapse={49-110}
import { createServer } from "node:http"
import { setTimeout as sleep } from "node:timers/promises"

interface PlaceOrderRequest {
  readonly orderId: string
}

interface StoredOrder {
  readonly orderId: string
  readonly status: "stored"
}

const server = createServer(async (request, response) => {
  const sendJson = (status: number, body: unknown): void => {
    response.writeHead(status, { "content-type": "application/json" })
    response.end(JSON.stringify(body))
  }

  if (request.method !== "POST" || request.url !== "/orders") {
    sendJson(404, { error: "NotFound" })
    return
  }

  try {
    let body = ""
    for await (const chunk of request) {
      body += chunk
    }
    const input = JSON.parse(body) as PlaceOrderRequest

    const connection = await checkoutDatabase(input.orderId)
    const lock = await acquireInventoryLock(connection, input.orderId)

    try {
      const order = await storeOrder(connection, lock, input.orderId)
      sendJson(201, order)
    } finally {
      releaseInventoryLock(connection, lock)
      releaseDatabase(connection)
    }
  } catch {
    console.error("request failed")
    sendJson(500, { error: "OrderFailed" })
  }
})

server.listen(3000, () => console.log("Listening on http://localhost:3000"))
```

release the connection acquired one line earlier.

## 2. Track partial acquisition manually

Move both acquisitions inside the protected region and keep optional references
for the resources that have actually been acquired:

```ts title="server.ts" collapse={1-28,58-116} ins={31-32,35-36,40-45}
import { createServer } from "node:http"
import { setTimeout as sleep } from "node:timers/promises"

interface PlaceOrderRequest {
  readonly orderId: string
}

interface StoredOrder {
  readonly orderId: string
  readonly status: "stored"
}

const server = createServer(async (request, response) => {
  const sendJson = (status: number, body: unknown): void => {
    response.writeHead(status, { "content-type": "application/json" })
    response.end(JSON.stringify(body))
  }

  if (request.method !== "POST" || request.url !== "/orders") {
    sendJson(404, { error: "NotFound" })
    return
  }

  try {
    let body = ""
    for await (const chunk of request) {
      body += chunk
    }
    const input = JSON.parse(body) as PlaceOrderRequest

    let connection: DatabaseConnection | undefined
    let lock: InventoryLock | undefined

    try {
      connection = await checkoutDatabase(input.orderId)
      lock = await acquireInventoryLock(connection, input.orderId)
      const order = await storeOrder(connection, lock, input.orderId)
      sendJson(201, order)
    } finally {
      if (connection !== undefined && lock !== undefined) {
        releaseInventoryLock(connection, lock)
      }
      if (connection !== undefined) {
        releaseDatabase(connection)
      }
    }
  } catch {
    console.error("request failed")
    sendJson(500, { error: "OrderFailed" })
  }
})

server.listen(3000, () => console.log("Listening on http://localhost:3000"))
```

## 3. Disconnect while both resources are in use

The `finally` block handles rejected Promises, but closing an HTTP connection
does not cancel an async request handler. Ask `curl` to disconnect while the
controlled storage operation is still running:

```sh title="Disconnect during slow storage"
curl --max-time 0.2 -sS http://localhost:3000/orders \
  -H 'content-type: application/json' \
  -d '{"orderId":"order-slow"}'
```

`curl` reports that its deadline was reached. At that moment, the server has
logged only the active work:

```text title="Log when the client disconnects"
checked out db-order-slow
acquired lock-order-slow using db-order-slow
store started for order-slow using db-order-slow and lock-order-slow
```

About 1.5 seconds after the request began, storage finishes and the `finally`
block eventually runs:

```text title="Later server log"
stored order-slow
released lock-order-slow using db-order-slow
released db-order-slow
```

No JavaScript control flow left the `try` block when the client disappeared.
The slow Promise kept running, so `finally` had no reason to run early. It
guarantees eventual cleanup, but it does not give the work the same lifetime as
the HTTP request.

<TutorialCheckpoint
  number={3}
  total={6}
  title="A disconnect does not cancel the Promise"
>
  The client receives no response, but storage continues for about 1.5 seconds.
  Both resources remain in use until that Promise finishes.
</TutorialCheckpoint>

## 4. Describe the existing workflow with Effect

Before changing cleanup again, move the same Promise workflow into Effect while
keeping its `finally` block. This introduces the Effect mental model without
changing the endpoint's behavior.

Keep the watched server running. In the second terminal pane, install Effect:

```sh title="Install Effect"
npm install effect@4.0.0-beta.104
```

Make the following changes:

```ts title="server.ts" collapse={64-122} ins={3,14-32,51-52}
import { createServer } from "node:http"
import { setTimeout as sleep } from "node:timers/promises"
import { Effect } from "effect"

interface PlaceOrderRequest {
  readonly orderId: string
}

interface StoredOrder {
  readonly orderId: string
  readonly status: "stored"
}

const placeOrder = (input: PlaceOrderRequest) =>
  Effect.tryPromise(async (signal) => {
    let connection: DatabaseConnection | undefined
    let lock: InventoryLock | undefined

    try {
      connection = await checkoutDatabase(input.orderId)
      lock = await acquireInventoryLock(connection, input.orderId)
      return await storeOrder(connection, lock, input.orderId, { signal })
    } finally {
      if (connection !== undefined && lock !== undefined) {
        releaseInventoryLock(connection, lock)
      }
      if (connection !== undefined) {
        releaseDatabase(connection)
      }
    }
  })

const server = createServer(async (request, response) => {
  const sendJson = (status: number, body: unknown): void => {
    response.writeHead(status, { "content-type": "application/json" })
    response.end(JSON.stringify(body))
  }

    sendJson(404, { error: "NotFound" })
    return
```

Calling `placeOrder` now creates an Effect: a value that describes a
computation. It does not check out a connection, acquire a lock, or store an
order yet. Transforming the Effect would still only produce another
description.

[`Effect.tryPromise`](/docs/v4/api/effect/Effect#tryPromise) adapts a function
that creates a Promise. Effect calls the function only when the computation
runs. A resolved Promise becomes a success, while a synchronous throw or
rejected Promise enters the error channel. Effect also supplies an
`AbortSignal`, which the workflow passes to `storeOrder`.

TypeScript infers this type for `placeOrder(input)`:

```ts
Effect.Effect<StoredOrder, Cause.UnknownError>
```

This display explains the inferred type. Do not paste it into `server.ts`.

[`Effect.Effect`](/docs/v4/api/effect/Effect#Effect) is the type of an Effect
value. Here, `StoredOrder` is the value produced when the complete Promise
workflow succeeds. `Cause.UnknownError` describes how that workflow can fail.

Effect calls the second type parameter its error channel. A rejected checkout,
lock acquisition, or storage operation enters this channel instead of
producing a `StoredOrder`.

[`Cause.UnknownError`](/docs/v4/api/effect/Cause#UnknownError-interface) is
Effect's built-in wrapper for an unclassified Promise rejection. Its `cause`
property preserves the original rejected value. We keep the tutorial's
existing HTTP decision, so the outer `catch` still returns `500`.

At the existing async HTTP boundary,
[`Effect.runPromise`](/docs/v4/api/effect/Effect#runPromise) runs the described
computation and returns a Promise. It resolves with the `StoredOrder` on
success. If the Effect does not succeed, the Promise rejects and the existing
`catch` handles it.

Wait for the server to reload, then send `order-ok` and
`order-lock-fails`. Their status codes, bodies, and cleanup logs remain the same
as the previous checkpoint. This step changed where the Promise workflow is
described, not its cleanup policy.

## 5. Give the resources one lifetime

The workflow is now an Effect, but its Promise callback still owns the mutable
resource variables and `finally` block. Replace that bookkeeping so each
successful acquisition registers its cleanup immediately:

```ts title="server.ts" collapse={71-128} ins={14-18,20-24,26-38,57}
import { createServer } from "node:http"
import { setTimeout as sleep } from "node:timers/promises"
import { Effect } from "effect"

interface PlaceOrderRequest {
  readonly orderId: string
}

interface StoredOrder {
  readonly orderId: string
  readonly status: "stored"
}

const databaseConnection = (orderId: string) =>
  Effect.acquireRelease(
    Effect.tryPromise(() => checkoutDatabase(orderId)),
    (connection) => Effect.sync(() => releaseDatabase(connection)),
  )

const inventoryLock = (connection: DatabaseConnection, orderId: string) =>
  Effect.acquireRelease(
    Effect.tryPromise(() => acquireInventoryLock(connection, orderId)),
    (lock) => Effect.sync(() => releaseInventoryLock(connection, lock)),
  )

const placeOrder = (input: PlaceOrderRequest) =>
  databaseConnection(input.orderId).pipe(
    Effect.flatMap((connection) =>
      inventoryLock(connection, input.orderId).pipe(
        Effect.flatMap((lock) =>
          Effect.tryPromise((signal) =>
            storeOrder(connection, lock, input.orderId, { signal }),
          ),
        ),
      ),
    ),
  )

const server = createServer(async (request, response) => {
  const sendJson = (status: number, body: unknown): void => {
    response.writeHead(status, { "content-type": "application/json" })
    response.end(JSON.stringify(body))
  }

  if (request.method !== "POST" || request.url !== "/orders") {
    sendJson(404, { error: "NotFound" })
    return
  }

  try {
    let body = ""
    for await (const chunk of request) {
      body += chunk
    }
    const input = JSON.parse(body) as PlaceOrderRequest

    const order = await Effect.runPromise(Effect.scoped(placeOrder(input)))
    sendJson(201, order)
  } catch {
    console.error("request failed")
    sendJson(500, { error: "OrderFailed" })
  }
})

server.listen(3000, () => console.log("Listening on http://localhost:3000"))
```

The success and error types remain `StoredOrder` and `Cause.UnknownError`.
Resource acquisition adds a third part to the inferred type of
`placeOrder(input)`:

```ts
Effect.Effect<StoredOrder, Cause.UnknownError, Scope.Scope>
```

This display explains the inferred type. Do not paste it into `server.ts`.

[`Scope.Scope`](/docs/v4/api/effect/Scope#Scope-interface) represents a lifetime
in which resources can register cleanup work. The `Scope.Scope` requirement in
the inferred type means `placeOrder` must run inside such a lifetime.

Each resource now describes its own acquisition and release with
[`Effect.acquireRelease`](/docs/v4/api/effect/Effect#acquireRelease). It runs
the acquisition inside the current Scope. If acquisition succeeds, it
immediately registers the release function as a finalizer. If acquisition
fails, no finalizer is registered for that resource. When the Scope closes,
finalizers run in reverse registration order after success, failure, or
interruption.

The distinction matters for `order-lock-fails`: checkout succeeds and registers
the connection finalizer. Lock acquisition fails before it can register a lock
finalizer. Scope closure therefore releases exactly the connection that exists.

[`Effect.sync`](/docs/v4/api/effect/Effect#sync) defers synchronous work until
the Effect runs. Here, it prevents the release functions from running while we
are only constructing the resource descriptions. Their `void` return becomes
each finalizer's successful value.

`pipe` passes an Effect description through transformations from top to bottom.
It does not run the described work.

[`Effect.flatMap`](/docs/v4/api/effect/Effect#flatMap) sequences a dependent
Effect. The first call receives the acquired database connection and describes
lock acquisition. The second receives that lock and describes storage. If an
earlier step fails, later steps are skipped and the Scope closes every resource
already acquired.

The HTTP handler supplies the required lifetime with
[`Effect.scoped`](/docs/v4/api/effect/Effect#scoped). It creates the Scope
required by `placeOrder`, runs the complete workflow in it, and closes the
Scope before returning. Closing it runs all registered finalizers and removes
`Scope.Scope` from the Effect's requirements.

Wait for the server to reload. Send `order-ok` and `order-lock-fails` again. The
first request returns `201` and closes the lock before the connection. The
second returns `500` and releases only its connection before `request failed`.
There are no mutable resource sentinels in `placeOrder`.

<TutorialCheckpoint

  total={6}

  closes only the connection that was acquired first.
</TutorialCheckpoint>

## 6. Interrupt the Scope when the client disconnects

The resource lifetime is now explicit, but the HTTP server still has to tell
Effect when that request lifetime ends. Connect the response's `close` event to
the running computation:

```ts title="server.ts" collapse={1-38,78-141} ins={50-57,65-67,70-72}
import { createServer } from "node:http"
import { setTimeout as sleep } from "node:timers/promises"
import { Effect } from "effect"

interface PlaceOrderRequest {
  readonly orderId: string
}

interface StoredOrder {
  readonly orderId: string
  readonly status: "stored"
}

const databaseConnection = (orderId: string) =>
  Effect.acquireRelease(
    Effect.tryPromise(() => checkoutDatabase(orderId)),
    (connection) => Effect.sync(() => releaseDatabase(connection)),
  )

const inventoryLock = (connection: DatabaseConnection, orderId: string) =>
  Effect.acquireRelease(
    Effect.tryPromise(() => acquireInventoryLock(connection, orderId)),
    (lock) => Effect.sync(() => releaseInventoryLock(connection, lock)),
  )

const placeOrder = (input: PlaceOrderRequest) =>
  databaseConnection(input.orderId).pipe(
    Effect.flatMap((connection) =>
      inventoryLock(connection, input.orderId).pipe(
        Effect.flatMap((lock) =>
          Effect.tryPromise((signal) =>
            storeOrder(connection, lock, input.orderId, { signal }),
          ),
        ),
      ),
    ),
  )

const server = createServer(async (request, response) => {
  const sendJson = (status: number, body: unknown): void => {
    response.writeHead(status, { "content-type": "application/json" })
    response.end(JSON.stringify(body))
  }

  if (request.method !== "POST" || request.url !== "/orders") {
    sendJson(404, { error: "NotFound" })
    return
  }

  const controller = new AbortController()

  response.once("close", () => {
    if (!response.writableEnded) {
      controller.abort()
    }
  })

  try {
    let body = ""
    for await (const chunk of request) {
      body += chunk
    }
    const input = JSON.parse(body) as PlaceOrderRequest

    const order = await Effect.runPromise(Effect.scoped(placeOrder(input)), {
      signal: controller.signal,
    })
    sendJson(201, order)
  } catch {
    if (controller.signal.aborted) {
      return
    }
    console.error("request failed")
    sendJson(500, { error: "OrderFailed" })
  }
})

  lock: InventoryLock,
  orderId: string,
  { signal }: { readonly signal?: AbortSignal } = {},
): Promise<StoredOrder> => {

    `store started for ${orderId} using ${connection.id} and ${lock.id}`,
  )

  signal?.addEventListener("abort", () => console.log("store aborted"), {

```

The response emits `close` both after a normal response and after a premature
disconnect. `response.writableEnded` distinguishes those cases. Only a
premature close aborts the controller.

The optional `signal` accepted by
[`Effect.runPromise`](/docs/v4/api/effect/Effect#runPromise) connects an
external `AbortSignal` to the running computation. When the client disconnects,
aborting the controller interrupts the complete scoped workflow. The returned
Promise rejects after the Scope's finalizers have finished, and the `catch`
writes nothing because the response is already gone.

Interruption is Effect's name for cancellation of a running computation. It is
not an expected failure in the error channel, so the disconnect does not become
a `Cause.UnknownError` or a `500` response.

The `AbortSignal` supplied to the callback by
[`Effect.tryPromise`](/docs/v4/api/effect/Effect#tryPromise) is also aborted
when the Effect is interrupted. The storage fixture passes it to the
Promise-based timer, so slow storage stops instead of continuing for 1.5
seconds.

Wait for the server to reload, then repeat the slow request:

```sh title="Disconnect from the scoped request"
curl --max-time 0.2 -sS http://localhost:3000/orders \
  -H 'content-type: application/json' \
  -d '{"orderId":"order-slow"}'
```

`curl` again reports that its deadline was reached and receives no response.
This time, cleanup follows immediately:

```text title="Expected server log"
checked out db-order-slow
acquired lock-order-slow using db-order-slow
store started for order-slow using db-order-slow and lock-order-slow
store aborted
released lock-order-slow using db-order-slow
released db-order-slow
```

There is no `stored order-slow` or `request failed` message. The external
signal interrupts the complete operation, `Effect.tryPromise` carries that
interruption into the Promise API, and Scope closure runs both finalizers before
`Effect.runPromise` rejects.

## Keep cleanup beside acquisition

`databaseConnection` and `inventoryLock` each own one acquisition and one
finalizer. `placeOrder` only describes how to use their successful values.
`Effect.scoped` owns their shared lifetime, while the HTTP boundary decides when
an abandoned request should interrupt that lifetime.

If another scoped resource is added later, it can register its finalizer at the
new acquisition site. The existing failure and cancellation paths do not need
another cleanup branch.
