You started with a single Effect in the browser. You finished with a server
that stores its rules, polls on a clock, runs actions over the network,
survives a restart, and stops cleanly. It was one program the whole way
through, and every checkpoint ran.

This page explains what you can build on top of reflex now, and what the
course left out on purpose.

## Follow-on projects

Each of these takes 15 to 30 minutes. They are listed roughly in the order
they build on what you have.

- **Notify only on a change.** The `degraded` rule alerts on every tick while
  the receiver is degraded. Make it alert only when the status goes from ok to
  degraded. This is where a `Ref`, and a stored last-match state per rule,
  finally have a job.
- **`{{field}}` substitution.** Let a message say `expense of {{amount}}` and
  fill it in from the payload. Handle a missing field the way conditions
  already handle one.
- **Retry with backoff.** Wrap the POST in `HttpClient.retryTransient`, so a
  500 or a dropped connection is tried a few more times before the run is
  `failed`. Once retries exist, decide what the timeout should cover.
- **`HttpApiTest` for the whole API.** The harness in
  [Running rules on a schedule with FiberMap](/learn/part-3/19-rules-on-a-clock)
  already uses it. Write the checks from
  [Serving an HTTP API with HttpApi](/learn/part-2/14-serve-it), the 404s and
  the 400s, as tests against the handlers instead of curl commands.
- **A metric per outcome.** A `Metric` counter tagged with the outcome, shown
  in the viewer next to the traces, answers "how many runs crashed today?"
  without reading `runs list`.
- **Queued execution.** Put events on a `Queue` and answer the request at
  once, with the runs happening behind it. Decide what `events submit` should
  print then.
- **`rules add` with several files.** Accept more than one file, add them in
  one request, and decide what happens when the third one is invalid.

## What the course left out, and why

Some things were kept out so that reflex could stay one growing program with
one main idea per lesson. None of them is a gap you were meant to notice
later. Each one is a course of its own.

- Authentication, deployment, and a browser UI.
- Distributed workers and exactly-once delivery. Reflex runs as one process,
  and a run can end `abandoned` or `interrupted` after its request was
  accepted.
  [Running rules on a schedule with FiberMap](/learn/part-3/19-rules-on-a-clock)
  explains why that is the accurate answer.
- A plugin system, user code in rules, an expression language, rule graphs,
  and scheduling beyond a fixed interval.
- `Deferred`, `Semaphore`, and `Stream`. `Effect.forEach` with a concurrency
  limit, plus `FiberMap`, covered every concurrency need the course had.
- `Ref` and `Option` in the core path. Every store method fails with
  `RuleNotFound` instead of returning an optional value, and no state is kept
  between runs. Deduplication, and the false-to-true transition state it
  needs, is the first follow-on above.
