An AI-generated endpoint can return the expected JSON and still be wrong in
ways that ordinary review misses. It can create work without running it, hide a
real failure from a type signature, or trust external JSON because a type cast
looks convincing.

In this tutorial, a coding agent will add `POST /orders/import` to a familiar
`node:http` server. The first implementation works for the supplied file, but
Effect-aware diagnostics expose three concrete mistakes. You will give that
evidence back to the agent, apply one bounded correction, and verify the same
endpoint again.

The finished backend has these observable results:

| Evidence                        | Generated change                  | Corrected change                          |
| ------------------------------- | --------------------------------- | ----------------------------------------- |
| `POST /orders/import`           | `200` with two imported order ids | The same `200` response                   |
| Import log                      | Missing                           | `Importing orders` appears                |
| Effect-aware static diagnostics | Three known findings              | No findings                               |
| File and decoding failure types | Public signature claims `never`   | Both failures remain in the error channel |

We will keep the HTTP server in ordinary TypeScript. Effect enters only in the
file-import change, which keeps the diagnostic and correction loop easy to
inspect.

The patch introduces the first Effect value in `readOrdersImplementation`,
then assigns that value to this narrower contract:

```ts title="Type written by the generated change"
Effect.Effect<ReadonlyArray<ImportedOrder>, never>
```

<EffectApi name="Effect.Effect" href="/docs/v4/api/effect/Effect#Effect">
  The type of a value that describes a computation. The first type argument is
  the success value, here a readonly array of imported orders. The second is the
  error channel, which lists expected failures. The generated annotation says
  `never`, so it claims the computation has no expected failure. A third,
  omitted type argument would list required services and defaults to `never`.
</EffectApi>

Creating an Effect does not read the file, parse JSON, or log anything. It
builds a description that can be transformed and later run.

<EffectApi
  name="Effect.tryPromise"
  href="/docs/v4/api/effect/Effect#tryPromise"
>
  Adapts the Promise returned by `readFile`. The function stays lazy and is
  called only when the Effect runs. A resolved Promise becomes a success, while
  a rejection enters the error channel. Effect also supplies an `AbortSignal`,
  which `readFile` observes if the running computation is interrupted.
</EffectApi>

Interruption is Effect's name for cancellation of a running computation.
Stopping a description before it runs is unnecessary because it has not done
anything yet.

TypeScript infers this actual type for `readOrdersImplementation`:

```ts title="Actual inferred type, not code to paste"
Effect.Effect<ReadonlyArray<ImportedOrder>, Cause.UnknownError>
```

<EffectApi
  name="Cause.UnknownError"
  href="/docs/v4/api/effect/Cause#UnknownError-interface"
>
  Effect's built-in wrapper for a rejection or thrown value that has not been
  classified. Its `cause` property preserves the original value. Here, both a
  rejected file read and a thrown `JSON.parse` call produce this expected error.
</EffectApi>

<EffectApi name="Effect.try" href="/docs/v4/api/effect/Effect#try">
  Defers synchronous code that may throw. Returning normally becomes success;
  throwing enters the error channel as `Cause.UnknownError` in this form. The
  generated code uses it to defer `JSON.parse`, but the cast still does not
  validate the parsed value.
</EffectApi>

<EffectApi name="Effect.flatMap" href="/docs/v4/api/effect/Effect#flatMap">
  Describes two dependent Effect operations in sequence. When the file read
  succeeds, its string is passed to the parsing function. A failure from either
  operation remains in the error channel. Combining them still does not run
  them.
</EffectApi>

<EffectApi name="Effect.log" href="/docs/v4/api/effect/Effect#log">
  Describes a log operation and succeeds with `void` when that operation runs.
  The generated handler creates this Effect and immediately ignores it, so no
  log is emitted.
</EffectApi>

<EffectApi
  name="Effect.runPromise"
  href="/docs/v4/api/effect/Effect#runPromise"
>
  Runs the computation at the HTTP handler boundary and returns a Promise.
  Success resolves with the imported orders. If the Effect does not succeed, the
  Promise rejects and the surrounding TypeScript `catch` returns `500`.
</EffectApi>

An expected failure belongs in the error channel. A defect is different: it is
an unexpected bug in the program. The generated code's false `never` annotation
does not turn a file failure into a defect. It attempts to hide that expected
failure from the public contract, which is why the diagnostic rejects the
assignment.

## 4. Correct only what the evidence exposed

The evidence gives the correction a precise boundary:

1. compose the log into the operation that is actually run;
2. preserve the file and decode failures in `readOrders`;
3. replace the cast with a Schema that checks the external value.

Apply the complete corrected `server.ts`:


The new Schema values describe the external data before the data receives an
application type.

<EffectApi
  name="Schema.Struct"
  href="/docs/v4/api/effect/Schema#Struct-function"
>
  Describes an object with named fields. Here, an imported order must contain an
  `externalOrderId` field accepted by the field's Schema.
</EffectApi>

<EffectApi
  name="Schema.String"
  href="/docs/v4/api/effect/Schema#String-variable"
>
  Describes a JavaScript string. It rejects a number, object, missing value, or
  any other non-string value at `externalOrderId`.
</EffectApi>

<EffectApi name="Schema.Array" href="/docs/v4/api/effect/Schema#Array-variable">
  Describes a readonly array whose every element must satisfy the supplied
  Schema. Here, every element must satisfy `ImportedOrderFromJson`.
</EffectApi>

<EffectApi
  name="Schema.fromJsonString"
  href="/docs/v4/api/effect/Schema#fromJsonString-function"
>
  Builds a Schema for JSON text whose parsed value must satisfy another Schema.
  `ImportedOrdersFromJson` therefore checks both JSON syntax and the array of
  imported-order objects.
</EffectApi>

<EffectApi
  name="Schema.decodeUnknownEffect"
  href="/docs/v4/api/effect/Schema#decodeUnknownEffect"
>
  Returns a function that decodes an unknown input with the supplied Schema.
  Applied after the file read, it describes an Effect that succeeds with the
  validated readonly array or fails with `Schema.SchemaError`. Decoding stays
  lazy until the complete operation runs.
</EffectApi>

<EffectApi
  name="Schema.SchemaError"
  href="/docs/v4/api/effect/Schema#SchemaError"
>
  The expected failure produced when external data does not satisfy a Schema. It
  carries a structured `issue` describing where and why decoding failed.
</EffectApi>

The corrected contract now says exactly what can happen:

```ts title="Corrected readOrders type"
Effect.Effect<
  ReadonlyArray<ImportedOrder>,
  Cause.UnknownError | Schema.SchemaError
>
```

The success channel contains validated orders. The error channel distinguishes
an unclassified file-read rejection from a Schema decoding failure. There is no
service requirement, so the omitted third type argument remains `never`.

The corrected handler also sequences `Effect.log` before `readOrders` with
`Effect.flatMap`. Both descriptions are now part of the one value passed to
`Effect.runPromise`, so the log runs instead of floating.

## Keep the correction loop narrow

The reliable workflow is small:

```text
bounded prompt → generated change → static evidence → bounded correction → real request
```

The diagnostics did not decide the endpoint's product behavior. They exposed
three decisions that the generated change had failed to state. You still chose
the public error contract, the external-data Schema, and which Effect operation
must run. The agent then made a correction that could be checked rather than
trusted.
