Before moving reflex to your own machine, take a few minutes to read
through the program you have built. The editor contains the completed
file from [Providing a service with a layer](/learn/part-1/09-provide-it).
Run it to confirm the three alert lines and three skips, then use the
types to check your understanding. There is no new code to write here
unless you choose one of the optional challenges below.

## The types in the file

Work through the names from top to bottom. For each function returning an
Effect, predict its success, error and requirements types before you
hover. In particular, check where `RuleStore` becomes a requirement and
where that requirement is satisfied.

| Name           | Type                                                                 | Notes                                                         |
| -------------- | -------------------------------------------------------------------- | ------------------------------------------------------------- |
| `Rule`         | A schema, with `type Rule` derived from it                           | The hover shows the rule's fields                             |
| `decodeRule`   | Accepts unknown input and returns `Effect<Rule, SchemaError, never>` | Parses JSON text and validates the parsed rule                |
| `RuleStore`    | A service with static `layer` and `layerFixtures` members            | The service key is `reflex/RuleStore`                         |
| `MissingField` | An error class with a string property named `field`                  | Identifies the field missing from an event                    |
| `matches`      | `(rule: Rule, amount: number) => boolean`                            | Calculates the result without an Effect                       |
| `evaluate`     | Returns `Effect<boolean, SchemaError, never>`                        | Handles a missing amount but leaves an invalid rule unhandled |
| `evaluateAll`  | Returns `Effect<void, SchemaError, RuleStore>`                       | Requires a provided `RuleStore`                               |
| `program`      | `Effect<void, SchemaError, never>`                                   | Provides the store, leaving no service requirements           |

If a type surprises you, use the reference below to return to the lesson
that introduced it, then trace how it is used in this file.

## Optional challenges

If you want more practice before Part 2, try one of these changes. They
are not included in the course time, and later lessons do not depend on
them.

1. Add `eq` and `neq` operators for "equal to" and "not equal to". Start
   with the schema, then update `matches` to handle the cases TypeScript
   reports as missing.
2. Make a skipped check distinguishable from a check that did not match.
   Instead of logging the skip and returning `false`, have `evaluate`
   return a `skipped` result containing a reason. Hover to confirm that
   the success type includes this new result alongside `boolean`, since
   a completed check still returns `flagged`.
   [Recording runs with Effect.onExit](/learn/part-2/12-an-engine-that-records)
   does a version of this.
3. Add another kind of event, such as a battery level, and a rule for it.
   The current alert message reads `event.amount`, which will not suit
   every event. Adapt the message for an event that has no amount.
