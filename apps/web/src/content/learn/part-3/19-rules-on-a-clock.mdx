## The problem

`fixtures/rules/status-degraded.json` is an `interval` rule. Every 5 seconds it
GETs the receiver's `/status` and appends an alert line when the answer says
`degraded`:

<LessonCode file="fixtures/rules/status-degraded.json" />

The server has stored rules like this since lesson 12 and never run one. To
run it, four things have to hold at once:

- adding the rule starts polling, and removing it stops polling, even in the
  middle of a request;
- a bad tick, such as a 500 from `/status`, is recorded and the loop goes on;
- a bug does not hide: it is recorded once, loudly, and the loop stops instead
  of failing the same way every 5 seconds;
- every tick leaves an honest row, including one that never got to finish.

## The poll is part of the run

An interval rule has no event. Its payload is the answer to the GET:
`{ status, body }`, with `body` parsed as JSON when it is JSON and kept as text
otherwise. Its condition reads that, so `body.status` is a dotted path like
`amount` was. `src/Poll.ts` makes the payload:

<LessonCode file="checkpoints/19/src/Poll.ts" />

An answer outside 2xx is `ActionFailed` with reason `status`. No answer at all
is reason `io`. `lookup` and `evaluate` in `Rule.ts` now take a `Payload`, any
object, instead of an `Event`.

The important decision is where the poll runs: inside the execution boundary,
not before it. Change the boundary from lesson 12 so it takes the payload as an
effect rather than a value. An event rule passes `Effect.succeed(event)`. An
interval rule passes `poll(url)`. Then every step of an interval run happens
after its row is opened and inside its `Engine.execute` span:

1. `runLog.start` writes `started`, before the GET.
2. Inside the span, under `Effect.timeout`: get the payload, evaluate the
   condition, run the action. The timeout covers the poll and the action
   together, 10 seconds for now.
3. `Effect.onExit` writes the one terminal row from the `Exit`.
4. Outside the span, a failure or a crash becomes an `Outcome` for the caller.
   An interruption is not caught; it goes on to whoever interrupted.

A poll that fails, a poll that hangs past the timeout and a poll that is
interrupted are now runs like any other, each with its row and its span.

## Every way a run can end

`Effect.onExit` sees the `Exit`, so the terminal row can name every ending:

| How `run` ended                           | Row                         | Span  |
| ----------------------------------------- | --------------------------- | ----- |
| Success, condition false or field missing | `skipped` with its reason   | Ok    |
| Success                                   | `succeeded`                 | Ok    |
| `ActionFailed`                            | `failed` (`status` or `io`) | Error |
| `TimeoutError` from `Effect.timeout`      | `failed` (`timeout`)        | Error |
| A defect: a thrown exception, a bug       | `crashed` with the message  | Error |
| Interrupted                               | `interrupted`               | Unset |

The last two are new. `terminal` reads them from the `Cause`, the full record
of why an effect failed: `Cause.hasInterruptsOnly` means it was stopped and
nothing went wrong, otherwise `Cause.squash` picks the main error. If that is
neither an `ActionFailed` nor a `TimeoutError`, it is a defect, and a `crashed`
row also gets an error-level log with the cause. Lesson 20 reads these side by
side.

The terminal write can itself fail; the disk can be full. Then the failure is
logged at error level with the run id, the row stays `started`, and the run
still ends the way it ended. A broken log does not turn a success into a
crash, or an interruption into a success.

## One loop per rule

`FiberMap` is a map from a key to a running fiber. `FiberMap.run(loops, id,
effect)` forks the effect and keeps its fiber under the rule's id.
`FiberMap.remove(loops, id)` interrupts that fiber and waits for it to end.
When a fiber ends on its own, it leaves the map. The map belongs to the
Engine layer's scope, like the heartbeat did in lesson 18, so stopping the
server interrupts every loop.

A loop is the lesson 18 shape with a run inside:

- One tick is one `Engine.execute`, poll included.
- `Effect.repeat(Schedule.spaced(...))` runs ticks `everySeconds` apart. The
  first tick is immediate.
- The stop decision. `failed` is an answer like any other: the receiver was
  down, try again next tick. `crashed` is a bug in your code, and it will
  happen again next tick. So the tick turns a `crashed` outcome into a
  `RuleStopped` failure, which ends `Effect.repeat`. The loop logs
  `interval rule stopped` with the rule id and the error, and its fiber leaves
  the map.
- Each tick is a trace of its own, not a child of the request that added the
  rule.

`rules list` asks the Engine `isRunning(id)`, which is `FiberMap.has`. An
interval rule shows `running` or `stopped`, and nothing new is stored to say
so. A restart of the server starts it again.

## Boot

When the Engine layer is built, it does two things before it answers anything:

1. `runLog.abandonStarted` marks every row still `started` as `abandoned`. No
   run of this process has started yet, so those rows belong to a process that
   ended without writing them.
2. Every stored interval rule is started.

## The removal contract

`DELETE /rules/:id` stops the loop and waits for it, then deletes the rule,
then answers:

<LessonCode file="checkpoints/19/src/server/Api.ts" />

There are three cases, and each one is honest:

- A run was active. The interruption reaches the run inside its span. Its
  `onExit` writes `interrupted`, and because `FiberMap.remove` waits for the
  fiber, that row exists before the response is sent, provided the write
  succeeds.
- The loop was idle between ticks. The loop stops and no row is written.
  Nothing ran, so nothing is invented.
- The loop had already stopped on a crash. There is no fiber; the rule row is
  deleted.

In every case, no interval work for the rule is running when the CLI prints
`Removed`. An event execution already in flight for the rule belongs to its
request and finishes. New events no longer match.

The same order holds for the whole server. The Engine is built after `RunLog`
and the SQL layers, so it is closed before them: on Ctrl-C every loop is
interrupted and writes its row while SQLite is still open.

## What this cannot do

Interruption stops your side of the work. It cannot undo the other side. If the
receiver already accepted a request when the run was interrupted, the request
happened, and the row says `interrupted` because your program stopped
waiting, not because nothing was sent. Forced termination is the other limit:
`kill -9`, a power cut or an out-of-memory kill run no finalizers, so no
`onExit` writes anything, and the row stays `started` until the next boot
marks it `abandoned`. That is what `abandoned` is for. It does not mean the run
failed; it means nobody knows how it ended.

## The harness test

Removing a rule mid-request is the case that is hard to see by hand and easy to
break later. Test it without a network and without waiting.

`test/harness.ts` is yours to write. It is a fake server: an `HttpClient` made
with `HttpClient.make`, which gets every request and decides how to answer,
next to a `Remote` service the test reads.

<LessonCode file="checkpoints/19/test/harness.ts" />

- `Hang` never answers. It records `released` in `Effect.onInterrupt`, so the
  test can see the request was let go.
- `arrived` is a `Latch`: closed until a request arrives, then open.
  `yield* remote.arrived.await` waits for that.
- The Engine layer is built over the fake client instead of
  `FetchHttpClient.layer`. Nothing else changes, as in lesson 13.

The core test, `remove interrupts a poll in flight` in
`checkpoints/19/test/Interval.test.ts`, calls the API handlers through
`HttpApiTest.groups`, a client that runs them in the test without a socket.
The handlers still need the services a real server gives them, such as
`HttpPlatform` and `Etag.Generator`, so merge `HttpServer.layerServices` into
the layer the test provides; without it the test does not typecheck. The test:

1. Add an interval rule with the fake server set to `Hang`.
2. Await `arrived`. No clock adjustment is needed, because the first tick is
   immediate.
3. Assert the rule's runs are exactly `["started"]`: the row opened before the
   GET.
4. Call `remove`. When it returns, assert `released` is true and the runs are
   `["interrupted"]`.
5. `TestClock.adjust("6 seconds")`, past one interval, and assert there was
   still only one request.

`it.effect` runs on the `TestClock`, so `Schedule.spaced` waits for
`TestClock.adjust` rather than for real time. Step 5 is what proves the loop
is gone and not just between ticks.

## Now and later

What you need now: the poll runs inside the boundary, so every interval run has
one row and one span whatever happens; `FiberMap` gives each rule one loop you
can stop and wait for; a crash stops its loop and a failure does not. The cost
is a fiber per interval rule and a run row every few seconds per rule. Unpacked
later: an action that leaves the machine, and its own way to time out (lesson
20).

## Checkpoint

Three paths. Start the receiver and the checkpoint's server in two terminals:

```sh
pnpm receiver
pnpm checkpoint 19 server
```

**19a: ticks that fail keep going.** In a third terminal:

```sh
pnpm checkpoint 19 cli rules add fixtures/rules/status-degraded.json
curl -X POST localhost:4600/status/mode -H 'content-type: application/json' -d '{"mode":"degraded"}'
```

Every 5 seconds a `succeeded` row appears in `pnpm checkpoint 19 cli runs list`
and a line is appended to `alerts.log`. Switch `/status` to a 500 with
`-d '{"mode":"error"}'`: `failed (status)` rows accumulate instead, and
`pnpm checkpoint 19 cli rules list` still says `running`. Each tick's row opens
before its GET; the third path shows one waiting.

**19b: a bug stops the loop.** This one changes code, so it runs on your own
server: stop the checkpoint's server and start `pnpm dev:server`, which
restarts on every save. Leave `/status` on `degraded`. In `src/Poll.ts`, plant
a bug in the last line. Instead of returning `body` as it is, cast it to an
object with a `state` string and return its `state.trim()` as the body.

`pnpm check` passes; the cast tells the compiler a `state` field is there. It
is not: the receiver answers with `status`. On save the server restarts and
starts the rule. `runs list` gets one `crashed` row,
`Cannot read properties of undefined (reading 'trim')`, the server logs
`run crashed` and `interval rule stopped`, no further rows appear, and
`rules list` says `stopped`. Undo the change, so the line returns `body`
again, and save. The restart starts the rule again: one `succeeded` tick, and
`rules list` says `running`.

**19c: removal.** Back on the checkpoint's server, add the slow poll, which
waits 8 seconds for every answer:

```sh
pnpm checkpoint 19 cli rules add fixtures/rules/slow-poll.json
pnpm checkpoint 19 cli runs list --rule <id>
```

Its newest row is `started`, waiting for its GET. Remove it while it waits,
then list its runs straight after:

```sh
pnpm checkpoint 19 cli rules remove <id> && pnpm checkpoint 19 cli runs list --rule <id>
```

The newest row is `interrupted`, not `started`: it existed before `Removed`
was printed. If it says `succeeded`, the 8 seconds ran out before the remove
arrived; add the rule again and be quicker. Keep the viewer running here: the
CLI waits for its traces to be delivered, and without a viewer each command
takes seconds longer. Wait 10 seconds and list again; nothing came after it. In the
viewer that run is one Unset `Engine.execute` span. Then remove the
`status-degraded` rule while it is idle between ticks: no new row is written,
and `rules list` no longer shows it. `pnpm checkpoint 19 test` includes the
harness test.
