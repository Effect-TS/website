Every action so far appends a line to a file on your disk. The useful actions
leave the machine: a webhook, a chat message, a notification on your phone.

Since lesson 12, an `httpPost` rule has been stored and then skipped with the
reason `httpPost actions run from lesson 20`. This is lesson 20. The action
goes over the network now, where the other side can say no, or say nothing at
all.

You will learn:

- how to build and send an HTTP request as a value;
- how `failed` and `crashed` differ, and why it matters;
- what a `Cause` holds, including the failures no type shows.

## Send the request with HttpClient

`postMessage` in `src/Action.ts` POSTs the action's message as plain text. When
the action sets `includePayload`, the payload follows as JSON on the next line.
If the action has `headers`, they're sent too.

<LessonCode file="checkpoints/20/src/Action.ts" />

It reads like `poll` from lesson 19, in the other direction:

- `HttpClientRequest.post(url)` builds the request. `HttpClientRequest.setHeaders`
  and `HttpClientRequest.bodyText` add to it, piped one after the other. A
  request is just a value until `client.execute` sends it.
- No answer at all, such as a refused connection, is `ActionFailed` with reason
  `io`.
- An answer outside 2xx is `ActionFailed` with reason `status`, and the message
  names the URL and the status.

In `src/Engine.ts`, the `httpPost` branch of `run` stops returning a skip and
calls `postMessage` instead. The Engine's `HttpClient` is handed over the same
way the `FileSystem` is. From here on, `skipped` has only its two reasons: the
condition was false, or a field was missing.

You don't need any new code for the timeout. `Effect.timeout` already wraps
`run` inside the span, so a receiver that takes too long to answer is cut off
after 10 seconds, interrupted, and recorded as `failed (timeout)`.

## Compare a 500, a timeout and a crash

Run three rules against the receiver, one at a time, and read what each one
leaves behind. With `pnpm receiver` and your server running:

| Rule file        | Receiver answer          | `runs list`                                                  |
| ---------------- | ------------------------ | ------------------------------------------------------------ |
| `post-fail.json` | `/fail?status=500`: 500  | `failed (status): POST ... answered 500`                     |
| `post-slow.json` | `/slow?ms=15000`: late   | `failed (timeout): timed out after 10s`                      |
| `post-ok.json`   | `/ok`, with a bug in you | `crashed: Cannot read properties of undefined (reading ...)` |

The first two are the world misbehaving. `failed` means the action was
attempted and didn't succeed, and the reason says how: the receiver refused, or
it didn't answer in time. Trying again later is reasonable.

The third is your code misbehaving. The receiver is fine, and the bug will
happen on every run until you fix it. That's `crashed`, with the message, plus
an error-level log with the stack on the server. For an interval rule it's
also what stops the loop, as you saw in lesson 19.

In the viewer, all three `Engine.execute` spans are red. The status message
tells you which is which: the 500, the `TimeoutError`, and the exception, which
is the only one with a stack. Notice that the timed-out span is exactly as long
as the timeout.

## Revisit: what a Cause holds

Back in lesson 5, you read that a thrown exception is a third kind of failure,
one that appears in no type. This is where it shows up.

When an effect doesn't succeed, its `Exit` holds a `Cause`. A `Cause` can hold
three kinds of thing:

- **A typed failure.** This is the `E` you've been reading in hovers since
  lesson 4. Here, that's `ActionFailed` and `TimeoutError`.
- **A defect.** Something that was never in `E`, such as a thrown exception, or
  an `Effect.orDie` like the database errors in lesson 17.
- **An interruption.** From `FiberMap.remove`, a timeout, or Ctrl-C.

`terminal` in `src/Engine.ts` reads the `Exit` in that order. It checks
`Cause.hasInterruptsOnly` first, because a run that was only stopped didn't
fail. Then it calls `Cause.squash`, which picks the main error of what's left.
A typed failure becomes `failed` with its reason. Anything else is a defect and
becomes `crashed`.

The type tells you which typed failures are possible. The `Cause` tells you
what actually happened, including what the type can't.

## Try it: plant a bug

Plant a bug for two minutes and watch it show up as `crashed`.

1. In `postMessage`, change the headers line so it trims the `Title` header,
   with a `!` that tells the compiler the headers are there. For
   `post-ok.json`, they aren't.
2. Add that rule to your server with `rules add fixtures/rules/post-ok.json`,
   and note the id it prints.
3. Run only that rule, with `rules run <post-ok id> --event fixtures/events/laptop.json`.
   Don't submit the event to every rule. `post-fail` and `post-slow` match
   expenses too, they have no headers either, and with the bug planted they
   would crash as well.
4. Read the `crashed` row next to the other two in `runs list`, and find its
   red span in the viewer.
5. Put the line back.

You're done when `pnpm check` passes and the same `rules run` against
`post-ok.json` prints `succeeded`. The exact line, and the file with the bug
planted, are in `exercises/20/`.

## Recap

- An `httpPost` action is a request value, sent through the `HttpClient`
  service. Its failures are `ActionFailed` with a reason.
- The boundary from lessons 12 and 19 records it with no new outcome.
- `failed` is the world. `crashed` is you.
- A `Cause` holds typed failures, defects and interruptions, and `terminal`
  reads them in that order.
- The price is an action you no longer control. It can be slow, and while it's
  slow, the next rule waits. Lesson 21 fixes that.
