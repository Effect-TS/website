Every function you named with `Effect.fn` runs inside a span,
`Engine.execute` included. You have seen those names in failures, but never
the spans themselves, because nothing sends them anywhere. Now one command
crosses two programs, a CLI and a server. In this lesson you export spans and
logs to the trace viewer and watch one command travel from one process into
the other.

In this lesson you will:

- export spans and logs with `OtlpTracer.layer` and `OtlpLogger.layer`
- provide one telemetry layer per program
- open a trace that crosses from the CLI into the server
- add your own attribute to a span

## 1. Write Telemetry.ts

The starter's `src/Telemetry.ts` exports a single `layer` with the service
name `reflex-lessons`. It is a placeholder, and nothing imports it. Replace
the whole file with two layers, one per program, `layerServer` and
`layerCli`:

<LessonCode file="checkpoints/16/src/Telemetry.ts" />

- `OtlpTracer.layer` exports spans to the viewer at
  `http://localhost:4318/v1/traces`.
- `OtlpLogger.layer` exports logs to `http://localhost:4318/v1/logs`.
- Both take a `resource` with a `serviceName`. The server is `reflex-server`
  and the CLI is `reflex-cli`, so the viewer can tell them apart.
- Both send JSON (`OtlpSerialization.layerJson`) over an `HttpClient`
  (`FetchHttpClient.layer`).

## 2. Provide it in both programs

Provide `Telemetry.layerServer` at the bottom of the server's layer stack in
`src/server/main.ts`, and `Telemetry.layerCli` in the CLI's run line in
`src/cli/main.ts`. Nothing in the Engine, the stores or the handlers
changes.

## 3. Open the trace

Start the viewer with `pnpm viewer` if it is not running, and the server with
`pnpm dev:server`. In a second terminal:

```sh
pnpm cli rules add fixtures/rules/expense.json
pnpm cli events submit fixtures/events/laptop.json
```

Open [http://localhost:8000](http://localhost:8000) and pick the
`events.submit` trace. It starts in `reflex-cli` and continues into
`reflex-server`, with `Engine.execute` under `Engine.handleEvent`:

![The events.submit trace: CLI spans, then the server's POST, Engine.handleEvent and Engine.execute nested under it](../_assets/viewer-trace.png "The checkpoint trace")

The CLI and the server are separate processes, and one trace crosses between
them. The CLI's `HttpClient` adds a `traceparent` header to every request,
carrying the current trace and span ids. The server starts its request span
as a child of that span. This is called **propagation**. You wrote none of
it. Both sides already speak the header.

Every row in the waterfall is a name you wrote:

- `Engine.handleEvent` and `Engine.execute` are the `Effect.fn` names from
  [Recording runs with Effect.onExit](/learn/part-2/12-an-engine-that-records).
- `evaluate` and `lookup` come from `Rule.ts`.
- `events.submit` and `rules.add` are the CLI handler names from the previous
  lesson.

[Reading a trace in the viewer](/learn/part-2/trace-viewer) describes each
part of this screen.

## Try it

The `Engine.execute` spans carry `rule.id` and `rule.trigger`, but nothing
says what the condition decided.

1. In `src/Engine.ts`, find where `Engine.execute` evaluates the condition.
   Give the result a name.
2. Add `Effect.annotateCurrentSpan("rule.condition", matched)`. It adds the
   attribute to the span the code is running in.
3. Leave the other paths alone. A rule without a condition has nothing to
   record, and a missing field fails before there is a result.

Check your work with the server and the viewer running. Submitting
`fixtures/events/lunch.json` gives an `Engine.execute` span with
`rule.condition` set to `false`, and `laptop.json` gives one with `true`. The
hint and the changed file are in `exercises/16/`. The checkpoints do not
include this change, because nothing later depends on it.

## What you learned

- Telemetry is one layer per program, provided at the edge.
- Traces cross processes on their own, carried by the `traceparent` header.
- `Effect.annotateCurrentSpan` adds your own facts to the span you are in.
- The cost is a little time per span, and a second program to keep running,
  the viewer.
- [Running rules on a schedule with FiberMap](/learn/part-3/19-rules-on-a-clock)
  and [Telling errors from defects with Cause](/learn/part-3/20-an-action-over-the-network)
  show what the viewer looks like when a run fails, times out, or is
  interrupted.
