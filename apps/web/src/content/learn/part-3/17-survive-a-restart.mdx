Stop the server, start it again, and run `rules list`. It prints nothing.
`runs list` prints nothing either. Both stores are Maps, and a Map lives
exactly as long as the process that created it. In this lesson you move both
stores into a SQLite file, `reflex.db`, so rules and run history survive a
restart. The Engine, the API handlers and the CLI do not change.

In this lesson you will:

- add a database to the program as a layer, with `SqliteClient` and a migrator
- write queries with the `sql` tag and decode their rows with a schema
- swap `RuleStore` and `RunLog` to SQLite in two lines of the entrypoint
- run the tests from the previous lessons against both kinds of store

## 1. Add the database layers

`SqliteClient.layer({ filename: "reflex.db" })` opens the file and provides
`SqlClient`, the service every query goes through. It is built on
`node:sqlite`, so there is no native module to compile. This is why the course
needs Node 22.16.

An empty file has no tables. The two SQL files in `migrations/` create them.
`SqliteMigrator.layer` runs the ones this database has not seen yet, in the
order of their number, and records each one it ran in a table of its own.
Starting the server a second time runs nothing.

## 2. Read the runs table

Open `migrations/0002_runs.sql`. The `runs` table has one column per field of
the run history, and a `CHECK` on `reason`:

```text
reason TEXT CHECK (outcome <> 'failed' OR reason IN ('status', 'timeout', 'io'))
```

When a `failed` row has a reason, it must be `status`, `timeout` or `io`. Any
other row may say anything or nothing.

The `CHECK` does half the job. SQLite lets a `NULL` through a `CHECK`, so on
its own it would accept a `failed` row with no reason. The `RunResult` schema
covers the other half: its `failed` variant requires one of the three reasons,
so the Engine never writes a `failed` result without one.

## 3. Store rules in SQL

Add `RuleStore.layerSql` next to `layerMemory` in `src/RuleStore.ts`. It
implements the same service, but it `yield*`s `SqlClient` instead of building
a Map:

<LessonCode file="checkpoints/17/src/RuleStore.ts" />

Three things do the work:

- The `sql` tag writes a query. Values inside `${}` become parameters, never
  part of the SQL text, so a rule name with a quote in it cannot break the
  query. `sql.insert(row)` turns an object into the column list and values of
  an `INSERT`.
- `SqlSchema.findAll` pairs a query with the schema of its rows and decodes
  every row it returns. `SqlSchema.void` does the same for a write with no
  result.
- `Schema.fromJsonString(Rule)` handles the `definition_json` column, which
  holds the rule as text. On the way in it encodes a `Rule` to JSON. On the
  way out it parses the text and decodes it with the same `Rule` schema the
  API uses. A row edited by hand into something that is not a rule fails
  there, with the same error a bad request gets.

Look at `get`. It runs `findById` and takes the first row. When there is no
row, it does `return yield* new RuleNotFound({ id })`, exactly what the memory
store does. Every caller keeps handling one typed error. `remove` uses
`RETURNING id` to find out whether it deleted anything.

Database errors go through `Effect.orDie`. A caller cannot do anything useful
about a broken disk, so `orDie` turns those errors into defects, which are
failures no caller is expected to handle and which do not appear in the error
type. The service type stays as it was: `create` cannot fail, and `get` and
`remove` fail only with `RuleNotFound`.
[Telling errors from defects with Cause](/learn/part-3/20-an-action-over-the-network)
looks at defects more closely.

## 6. Run the tests against both stores

Turn each store suite from
[Writing tests with @effect/vitest](/learn/part-2/13-first-tests) into a
function of a layer, with the tests inside unchanged:

```ts
(name, store) => layer(store, { buildPerTest: true })(name, (it) => ...)
```

Then call it once per layer. For SQLite, the layer is `Migrations.layer` over
`SqliteClient.layer({ filename: ":memory:" })`. That is a database that exists
only for one test, with the tables already created. `buildPerTest` gives every
test a fresh one.

## Try it

`pnpm cli runs list --rule <id>` gives the right rows against SQLite. But
`RunLog.layerSql` reads every row of `runs`, then filters and slices them in
TypeScript. With a few interval rules, the table grows by thousands of rows a
day, and every `runs list --rule` reads all of them to keep a handful. Make
SQLite do the filtering and the limit, in the query.

1. Give the `findAll` query a request schema with the two options, `ruleId`
   and `limit`, so `execute` receives them.
2. Add the `WHERE` clause with `sql.and`, and `LIMIT ${limit ?? -1}`. In
   SQLite, a negative limit means no limit.
3. Run `pnpm test`. It stays green.
4. With the server running, run `pnpm cli runs list --rule <id> --limit 2`. It
   prints at most two rows, all for that rule.

The hint and the changed file are in `exercises/17/`. From the next lesson on,
the checkpoints include this change.

## What you learned

- A database is a layer. `SqliteClient.layer` provides `SqlClient`, and
  `SqliteMigrator.layer` creates the tables from the SQL files.
- A query is the `sql` tag paired with a schema for its rows. Values in `${}`
  are always parameters.
- Swapping storage took two lines in the entrypoint, and the tests ran
  unchanged against both layers.
- The cost is a file on disk and a migration for every change to the tables.
  The checkpoint servers and yours all use `reflex.db` in the project root.
  Delete it whenever you want to start clean.
- A run whose process ended before it wrote its last row is handled in
  [Running rules on a schedule with FiberMap](/learn/part-3/19-rules-on-a-clock).

## Checkpoint

The checkpoint shows a rule and its run surviving a restart. This lesson's
checkpoint is number 17. Start the checkpoint's server, and in a second
terminal add a rule and submit an event:

```sh
pnpm checkpoint 17 server
```

```sh
pnpm checkpoint 17 cli rules add fixtures/rules/expense.json
pnpm checkpoint 17 cli events submit fixtures/events/laptop.json
```

Stop the server with Ctrl-C and start it again with the same command. Then:

```sh
pnpm checkpoint 17 cli rules list
pnpm checkpoint 17 cli runs list
```

The rule and its `succeeded` run are still there.
