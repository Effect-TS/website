Every expense so far has included an amount, but an incoming receipt might
be incomplete. Consider this taxi receipt: `{ type: "expense" }`. Without
an `amount`, `evaluate` cannot determine whether it exceeds 500. Returning
`false` would treat an unchecked expense as one that passed the check.

Instead, make `evaluate` fail with an error that identifies the missing
field. That possibility will appear in its Effect type, separate from its
successful boolean result. For now, an unhandled failure will stop the
program before the summary. The next lesson adds recovery.

## Defining the missing-field error

Add `Schema` to the `effect` import. Then declare `MissingField` between the
interface and the two expenses:

<LessonCode
  file="lessons/part1/04-failure-you-can-see/solution/main.ts"
  declaration="MissingField"
/>

The declaration uses two calls to `Schema.TaggedError`. The first,
`<MissingField>()`, supplies the class's own type. The second supplies the
**tag** `"MissingField"` and the fields stored on the error. The tag will
let you select this error in a handler; the `field` property will tell the
handler which value was missing.

Here, `Schema.String` describes the type of that property. You will use
schemas more extensively in
[Validating JSON with Schema](/learn/part-1/06-untrusted-json).

## Failing before the check

At the top of the `Effect.gen` block in `evaluate`, check for the amount. If
it is missing, fail:

<LessonCode
  file="lessons/part1/04-failure-you-can-see/solution/main.ts"
  declaration="evaluate"
/>

You can yield a `Schema.TaggedError` directly to fail the Effect. Here,
`return yield* new MissingField({ field: "amount" })` fails with the error
you just defined. The `return` also makes the end of this path explicit to
TypeScript. After the check, it can narrow `event.amount` to `number`, and
the red underline disappears.

Hover `evaluate`. Its type is
`(event: Event) => Effect<boolean, MissingField, never>`. The error type was
`never`; now it is `MissingField`. A caller can see both possible outcomes
in the type: success with a boolean or failure with a missing-field error.

## Following the failure through program

Run the file. The terminal prints `expense 1200 over 500` for the laptop.
Then it reports a `MissingField` failure for the taxi, and the program stops.
`1 of 2 expenses flagged` never appears. With no handler to recover from
the failure, `evaluate` cannot produce a boolean for the taxi. The failure
propagates through `yield* evaluate(taxi)` into `program`, which stops
without running the summary.

Hover `program`. The type is `Effect<void, MissingField, never>`. `program`
does not create the error, but it runs `evaluate`, so the failure is part of
its type too.

## Try it

The error type can include more than one possible failure. Add a check for
events that are not expenses:

1. Declare a second error, `NotAnExpense`, the same way as `MissingField`.
   Give it a `type` field.
2. At the top of the `Effect.gen` block in `evaluate`, fail with it when
   `event.type` is not `"expense"`.
3. Hover `evaluate`. The error type now lists both errors, as a union such
   as `NotAnExpense | MissingField`. Both typed failures are included, and
   `program` shows the same union.

This is practice only. The next lesson starts from the file without
`NotAnExpense`.

Using a schema for the error will also be useful beyond this file. In
[Serving an HTTP API with HttpApi](/learn/part-2/14-serve-it), these error
classes become part of the HTTP API.
