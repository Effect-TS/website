`run-once.ts` can check one rule against one event and write an alert, but
there is no record of the rules it skipped or the actions that failed.
Once you have several rules, you need to know which ones ran and how each
run ended. A failure in one rule should also leave the others able to run.

The `Engine` will coordinate this work. It will find the rules whose
triggers match an event, execute each one, and record the results in a
`RunLog`. You will build it as a service that depends on the rule store,
the run log and the file system.

## Give rules an id

Before you can associate a run with a rule, each stored rule needs an id.
Create `src/RuleStore.ts` with the store below. Its `create` method assigns
the id, and `list`, `get` and `remove` let you work with stored rules. If
`get` or `remove` receives an unknown id, it fails with `RuleNotFound`.

## Keep a run history

Create `src/RunLog.ts`. Like `RuleStore`, it has a service definition and a
memory layer. Its methods track the lifetime of a run:

- `start` opens a row with the outcome `started`.
- `finish` writes how the run ended.
- `list` reads rows back, newest first.

<LessonCode file="checkpoints/12/src/RunLog.ts" />

`RunResult` describes a completed run as `skipped`, `succeeded` or `failed`.
For a failure, it also requires a reason: `status`, `timeout` or `io`.
Only `io` can occur with the current file-writing action; the other two
are for the network action you will add later. At this checkpoint, skipped
runs do not yet have a reason.

## Build the Engine from its dependencies

The Engine needs access to all three services to execute a rule and record
its result. Create `src/Engine.ts` using `Layer.effect`, as you did for the
stores. Inside the layer, retrieve `RuleStore`, `RunLog` and `FileSystem`
with `yield*` before defining `execute` and `handleEvent`:

<LessonCode file="checkpoints/12/src/Engine.ts" />

Every execution begins in `execute`, which calls `runLog.start` before
evaluating the rule. That creates a row with the outcome `started`, even
if the action cannot complete.

The inner `run` function evaluates the condition and performs the action.
It uses `Effect.fn("Engine.execute")` to create a span, annotated with the
rule id and trigger. If an action fails, this span ends with an error.
If an event lacks a field the condition needs, `run` catches `MissingField`
and returns `skipped` instead. A skip is a successful result of evaluation,
so the span ends Ok and the run row's `error` column remains null.

After `run` ends, `Effect.onExit` receives its `Exit`, a value describing
how the effect ended. The callback writes a successful `RunResult` to the
row, or records `failed` for an `ActionFailed`. Other endings leave the row
as `started` for now.

Recording a completed run takes two run-log writes: one to create the
`started` row and another to record the result. This lets you distinguish
a run that began but did not finish from one that never started.

Only after recording the result does `Effect.catchTag` convert
`ActionFailed` into a `failed` value for the caller. This order matters:
the span and run log record the failure, while `handleEvent` receives an
outcome it can collect before continuing to the next rule. The effect
returned by `execute` has no typed failures; defects and interruption
are still possible.

[Running rules on a schedule with FiberMap](/learn/part-3/19-rules-on-a-clock)
will add the `interrupted` and `crashed` outcomes and a timeout inside the
span, so those endings can be recorded too.

Although executing an action requires a file system, callers of `execute`
do not have to provide one. The layer retrieved it when it was built, and
`Effect.provideService` supplies that same instance to `appendLine`. The
annotation `Effect.fn.Return<RunResult, ActionFailed | MissingField>` checks
the generator's return values and typed failures, so an invalid result is
caught by TypeScript.

Finally, `handleEvent` loops through the stored rules, much like
`evaluateAll` in Part 1. For each event trigger matching the event's type,
it calls `execute` and collects the outcome.

The program needs the stores to create rules and read the history, as well

## Try it

The output `huge expense: skipped` leaves you to work out whether the
condition was false, a field was missing, or the action was not supported
yet. Give each skip a reason and store it as free text in the run history's
`reason` column:

1. In `src/RunLog.ts`, give the `skipped` member of `RunResult` a
   `reason: Schema.String`. The compiler now lists every place that writes a
   skip without one.
2. Add reasons to the three skip results in `src/Engine.ts`:
   - When a condition is false, identify the condition in the reason.
   - In the `MissingField` catch, include the error's `field`, producing
     text such as `missing field amount`.
   - In the `httpPost` branch, explain that the action is introduced in the
     lesson on network actions.
3. Leave the `failed` result unchanged. Its reasons are restricted to
   `status`, `timeout` and `io`; the SQLite `runs` table introduced later
   will enforce that restriction for failed rows.

Check your work with `pnpm tsx src/main.ts`. It prints each skip with its
reason in brackets. The hint and the changed files are in `exercises/12/`.
From the next checkpoint on, the reference solution includes this change,
and the next lesson tests it.
