In the last lesson, you checked the Engine by running `main.ts`, reading
the printed run log and opening `alerts.log`. Repeating those checks after
every change would be tedious, and each run would append more data to a
real file. Tests can check the same behavior automatically without writing
alerts to disk.

You already separated the Engine from its dependencies by using services.
Now you can provide fresh memory stores and a recording file system for
tests, leaving the Engine itself unchanged. Start with the rule store, then
test the run history produced by the Engine.

## Write the first test

The starter uses `@effect/vitest` to run effects in Vitest tests. Test files
live in `test/`, next to `src/`, and you run them with `pnpm test`. The
package provides a test function, a way to supply services, and assertions:

- `it.effect("name", () => effect)` runs an Effect as a test. The test passes
  when the effect succeeds and fails when it fails.
- `layer(SomeLayer)("name", (it) => { ... })` builds the layer and provides it
  to every `it.effect` inside. With `{ buildPerTest: true }`, each test gets a
  fresh build, so one test's rules never leak into the next.
- `assert` has the usual checks: `strictEqual`, `deepStrictEqual`, `match`,
  `isNull`.

Create `test/RuleStore.test.ts`. Provide `RuleStore.layerMemory` and write a
test that stores two rules, then lists, gets and removes them:

<LessonCode file="checkpoints/13/test/RuleStore.test.ts" />

```sh
pnpm test test/RuleStore.test.ts
```

The test should pass. With `buildPerTest: true`, each test starts with an
empty memory store, so it can create and remove rules without affecting
another test.

## Test an expected failure

The store should fail with `RuleNotFound` when you request an unknown id.
To see how the test runner treats that failure, first try writing
`const error = yield* store.get("missing")`, followed by an assertion on
`error`.

Run `pnpm test test/RuleStore.test.ts`. The test fails, and Vitest prints a
`RuleNotFound` with `id: "missing"`.

The store behaved correctly, but the assertion was never reached. A failed
effect stops the generator, and `it.effect` reports that failure as a failed
test. You need to make the error available as a value you can inspect.

`Effect.flip` swaps success and failure. With
`yield* Effect.flip(store.get("missing"))`, a `RuleNotFound` becomes the
success value you can assert on. If the store unexpectedly returned a rule,
the flipped effect would fail instead. Wrap the call and run the test
again. It should now pass, as the second and third tests in the example do.

Keep checking that a test fails when the behavior is wrong. Passing
assertions are useful only if they can detect the mistake you care about.

## Record file writes without using the disk

To test an action, you need to check that the Engine attempted the right
write without creating `alerts.log`. Provide a file system that records
those attempts in an array instead.

`FileSystem.layerNoop` lets you replace selected file system methods without
performing real file operations. Keep a `writes` array in the test file and
override `writeFileString` with
`writeFileString: (path) => Effect.sync(() => writes.push(path))`. Override
`writeFile` in the same way. You can then assert on the recorded paths.
Only the methods you replace have the behavior your test needs; do not
assume that other file operations will succeed.

Build the test layer from `Engine.layer`, `RuleStore.layerMemory`,
`RunLog.layerMemory` and this recording file system. This is the same
composition as `main.ts`, with the real file system replaced. As in
[Providing a service with a layer](/learn/part-1/09-provide-it), the code
using the service does not need to change.

The reference solution uses `FileSystem.makeNoop` to construct the service
value inside a layer rather than using `FileSystem.layerNoop` directly.
For a simpler fake, you can wrap that value in `Layer.succeed`.

This separation also lets you reuse service tests with other implementations.
In [Storing data in SQLite with SqlClient](/learn/part-3/17-survive-a-restart),
you will run the store suites against SQLite.

## Try it

A missing field should produce a `skipped` run, with the field named in its
reason. Test the stored run rows as well as the result of `handleEvent`: the
rows will later be displayed by `runs list` and stored in SQLite. A correct
return value alone would not prove that the history is correct.

1. In `test/Engine.test.ts`, build the test layer described above. Store a rule
   with the `amount gt 500` condition, submit
   `{ type: "expense", description: "no amount" }`, and read the rows with
   `RunLog.list()`. Assert exactly one row, `skipped`, with a `reason` that
   matches `/amount/`, an `error` that is null, and no writes.
2. Run `pnpm test test/Engine.test.ts` and confirm that the test passes.
3. Introduce a deliberate mistake. Change the `MissingField` catch in `src/Engine.ts` to
   `reason: "no match"`. `pnpm check` still passes, because the row is
   well-typed. Run the test again and check that it fails with:
   `expected 'no match' to match /amount/`.
4. Restore `` `missing field ${error.field}` `` and confirm that the test
   passes again.

The test filter also matches `checkpoints/13/test/Engine.test.ts`, the
reference tests. They test the checkpoint, not your `src/`, so they stay
green throughout. The hint and the test are in `exercises/13/`.

## Checkpoint

After restoring the correct skip reason, run `pnpm test` to check that the
tests pass again. To run the reference suites for checkpoint 13, use:

```sh
pnpm checkpoint 13 test
```

The run log now carries reasons. The checkpoint program adds the
`no-amount.json` event to the previous lesson's two:

```sh
pnpm checkpoint 13
```

```text
large expense: succeeded
huge expense: skipped (condition amount gt 5000 is false)
every expense: succeeded
large expense: skipped (condition amount gt 500 is false)
huge expense: skipped (condition amount gt 5000 is false)
every expense: succeeded
large expense: skipped (missing field amount)
huge expense: skipped (missing field amount)
every expense: succeeded
```
