<EffectStrength title="Expected failures stay visible in the type">

A `Promise<Order>` describes only success. Its rejections reach `catch` as
`unknown`, so callers must recover the possible failures from documentation or
conventions.

An Effect keeps the success value and the expected failures in its type. The
caller can see the complete contract before running the operation.

</EffectStrength>

## What you will build

You will authorize a payment with a small simulated provider. The provider can
approve a payment, decline it, or be unavailable. The starting Promise handles
those cases correctly, but its type hides them. You will move the same failure
information into an Effect and then handle it explicitly.

A checkpoint marks each result in the progression.

## Project setup

The project uses one file:

| File      | Role                                                     |
| --------- | -------------------------------------------------------- |
| `main.ts` | Contains the payment simulation and the code you change. |

Run each version with:

```sh title="Run the example"
node main.ts
```

## Make the failure contract visible

### 1. Start with a competent Promise

The provider documents two error classes. The starting code checks both and
keeps a fallback for an undocumented rejection:

```ts title="main.ts"
// Simulated errors documented by the payment provider.
class PaymentDeclinedSdkError extends Error {}
class PaymentProviderUnavailableSdkError extends Error {}

interface PaymentAuthorization {
  readonly provider: string
}

// Special tokens make each provider outcome reproducible.
const authorizePayment = async (
  token: string,
): Promise<PaymentAuthorization> => {
  if (token === "declined") throw new PaymentDeclinedSdkError()
  if (token === "unavailable") throw new PaymentProviderUnavailableSdkError()
  return { provider: "primary-pay" }
}

const placeOrder = async (token: string) => {
  const payment = await authorizePayment(token)
  return { status: "accepted" as const, provider: payment.provider }
}

const handleOrder = async (token: string) => {
  try {
    return await placeOrder(token)
  } catch (cause) {
    // Promise rejections reach callers as unknown values.
    if (cause instanceof PaymentDeclinedSdkError) {
      return { status: "rejected" as const, reason: "PaymentDeclined" }
    }
    if (cause instanceof PaymentProviderUnavailableSdkError) {
      return {
        status: "rejected" as const,
        reason: "PaymentProviderUnavailable",
      }
    }
    return { status: "rejected" as const, reason: "UnexpectedFailure" }
  }
}

console.log(await handleOrder("declined"))
```

The result is correct:

```text title="Output"
{ status: 'rejected', reason: 'PaymentDeclined' }
```

The limitation is in the type of `placeOrder`:

```ts title="Inferred type, not code to copy"
declare function placeOrder(token: string): Promise<{
  status: "accepted"
  provider: string
}>
```

It says nothing about the two documented failures. A caller must know which
classes to check and remember to keep the fallback.

### 2. Describe the provider call with Effect

First, give each rejection an idiomatic Effect error. `Data.TaggedError`
creates a typed error class and adds a readonly `_tag` field with the supplied
name. Effect uses that standard field to distinguish failures without exposing
the provider classes to the caller:

```ts title="main.ts" ins={1,11-20,31-47}
import { Data, Effect } from "effect"

// Simulated errors documented by the payment provider.
class PaymentDeclinedSdkError extends Error {}
class PaymentProviderUnavailableSdkError extends Error {}

interface PaymentAuthorization {
  readonly provider: string
}

class PaymentDeclined extends Data.TaggedError("PaymentDeclined") {}
class PaymentProviderUnavailable extends Data.TaggedError(
  "PaymentProviderUnavailable",
) {}
class UnexpectedFailure extends Data.TaggedError("UnexpectedFailure")<{
  readonly cause: unknown
}> {}

type PaymentFailure =
  PaymentDeclined | PaymentProviderUnavailable | UnexpectedFailure

// Special tokens make each provider outcome reproducible.
const authorizePayment = async (
  token: string,
): Promise<PaymentAuthorization> => {
  if (token === "declined") throw new PaymentDeclinedSdkError()
  if (token === "unavailable") throw new PaymentProviderUnavailableSdkError()
  return { provider: "primary-pay" }
}

const placeOrder = (token: string) =>
  Effect.tryPromise({
    try: async () => {
      const payment = await authorizePayment(token)
      return { status: "accepted" as const, provider: payment.provider }
    },
    // Translate provider-specific errors into the application contract.
    catch: (cause): PaymentFailure => {
      if (cause instanceof PaymentDeclinedSdkError) {
        return new PaymentDeclined()
      }
      if (cause instanceof PaymentProviderUnavailableSdkError) {
        return new PaymentProviderUnavailable()
      }
      return new UnexpectedFailure({ cause })
    },
  })
```

Each `Data.TaggedError` instance is an `Error` with a typed `_tag`.
`UnexpectedFailure` also preserves the original rejection in its `cause`
field.

`Effect.tryPromise` adapts the Promise-producing function without calling it
yet. When the resulting Effect runs, a resolved Promise becomes a success and
the inline `catch` translates a rejection into one of the `PaymentFailure`
classes.

An Effect is a value that describes a computation. Creating or transforming it
does not run the provider call. The first type argument is the success value;
the second is the expected failure, called the error channel. The inferred type
is now:

```ts title="Inferred type, not code to copy"
declare function placeOrder(
  token: string,
): Effect.Effect<{ status: "accepted"; provider: string }, PaymentFailure>
```

The editor can now show every expected payment failure without inspecting the
implementation or provider documentation.

### 3. Handle both channels before running

Complete the program by handling every `_tag` before running the computation:

```ts title="main.ts" ins={49-65}
import { Data, Effect } from "effect"

// Simulated errors documented by the payment provider.
class PaymentDeclinedSdkError extends Error {}
class PaymentProviderUnavailableSdkError extends Error {}

interface PaymentAuthorization {
  readonly provider: string
}

class PaymentDeclined extends Data.TaggedError("PaymentDeclined") {}
class PaymentProviderUnavailable extends Data.TaggedError(
  "PaymentProviderUnavailable",
) {}
class UnexpectedFailure extends Data.TaggedError("UnexpectedFailure")<{
  readonly cause: unknown
}> {}

type PaymentFailure =
  PaymentDeclined | PaymentProviderUnavailable | UnexpectedFailure

// Special tokens make each provider outcome reproducible.
const authorizePayment = async (
  token: string,
): Promise<PaymentAuthorization> => {
  if (token === "declined") throw new PaymentDeclinedSdkError()
  if (token === "unavailable") throw new PaymentProviderUnavailableSdkError()
  return { provider: "primary-pay" }
}

const placeOrder = (token: string) =>
  Effect.tryPromise({
    try: async () => {
      const payment = await authorizePayment(token)
      return { status: "accepted" as const, provider: payment.provider }
    },
    // Translate provider-specific errors into the application contract.
    catch: (cause): PaymentFailure => {
      if (cause instanceof PaymentDeclinedSdkError) {
        return new PaymentDeclined()
      }
      if (cause instanceof PaymentProviderUnavailableSdkError) {
        return new PaymentProviderUnavailable()
      }
      return new UnexpectedFailure({ cause })
    },
  })

// Each key matches a PaymentFailure _tag.
const program = Effect.catchTags(placeOrder("declined"), {
  PaymentDeclined: () =>
    Effect.succeed({ status: "rejected" as const, reason: "PaymentDeclined" }),
  PaymentProviderUnavailable: () =>
    Effect.succeed({
      status: "rejected" as const,
      reason: "PaymentProviderUnavailable",
    }),
  UnexpectedFailure: () =>
    Effect.succeed({
      status: "rejected" as const,
      reason: "UnexpectedFailure",
    }),
})

console.log(await Effect.runPromise(program))
```

`Effect.catchTags` reads the `_tag` field and passes each error to its matching
handler. Every handler returns an Effect. Here `Effect.succeed` describes an
already available rejection response without performing a side effect. Because
the table handles every member of `PaymentFailure`, no expected failure remains
in the error channel; an accepted order passes through unchanged.

`Effect.runPromise` runs the completed computation at the edge of the program.
It returns a Promise that resolves with either the accepted order or one of the
handled rejection responses.

The output remains:

```text title="Output"
{ status: 'rejected', reason: 'PaymentDeclined' }
```

<TutorialCheckpoint
  number={3}

The strength is not that Effect can catch a rejected Promise. Ordinary
TypeScript already did that correctly. Effect keeps the failure contract
attached to the computation while the program is built and combined.
