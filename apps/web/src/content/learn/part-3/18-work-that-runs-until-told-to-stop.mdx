So far, the server does work only when it receives a request. Interval
rules will need to keep polling a URL without a new request for each poll.
They also need to stop when the server shuts down, before the database
they use closes.

Before adding those rules, try the same lifecycle with a smaller task. You
will create a heartbeat that periodically logs the number of stored rules,
then check that it stops and logs a final message on Ctrl-C. With no HTTP
request or action to debug, you can concentrate on how background work
starts and stops.

## Create a repeating effect

Create `src/Heartbeat.ts` to read and log the rule count at startup and then
every 30 seconds:

<LessonCode file="checkpoints/18/src/Heartbeat.ts" />

The inner `Effect.gen` block performs one iteration: it lists the rules and
logs the count. `Effect.repeat` repeats that effect according to a
`Schedule`, a value describing when subsequent iterations should run. With
`Schedule.spaced("30 seconds")`, the first iteration runs immediately, then
each subsequent iteration starts 30 seconds after the previous one ends.

Repeating the effect directly would keep layer construction waiting for a
loop that is intended to run indefinitely. `Effect.forkScoped` starts it on
a separate fiber instead. A fiber is an independently running computation;
the server can continue starting while this one logs and waits between
iterations.

The fiber belongs to the current scope, so it will be interrupted when that
scope closes. `Effect.onInterrupt` adds the log you will use to observe that
shutdown. It runs on interruption, not when an effect succeeds or fails for
another reason.

## Tie the heartbeat to the server lifecycle

`Layer.effectDiscard` is useful here because the heartbeat needs to start
with the server but does not provide a service for callers. Its effect runs
when the layer is built, and `forkScoped` uses the scope available during
that construction. When the server closes the scope, it interrupts the
heartbeat and waits for its interruption handler before shutdown completes.

The dependency on `RuleStore` determines the shutdown order. The store is
built before the heartbeat, and the heartbeat stops before the store
closes. This keeps the database available until the loop has finished using
it. You do not need to coordinate those two shutdown operations yourself.

Run `pnpm dev:server`. The heartbeat logs `rules stored:` followed by the
number of rules in `reflex.db`, then repeats every 30 seconds.

## Observe shutdown with Ctrl-C

Press Ctrl-C. The last log line before the process exits is:

```text
heartbeat stopped
```

That message comes from `onInterrupt`, without a signal handler in your
code. The runtime and the layer scope connect Ctrl-C to the loop:

1. `runMain` interrupts the main fiber when it receives Ctrl-C.
2. That interruption ends `Layer.launch`, which has been keeping the server
   running, and closes the layer scope.
3. The scope interrupts the heartbeat fiber and waits for it to stop.
4. The heartbeat runs its `onInterrupt` handler before it finishes.

The heartbeat keeps one fiber alive for the server's lifetime, although
it spends most of that time waiting between iterations. In
[Running rules on a schedule with FiberMap](/learn/part-3/19-rules-on-a-clock),
you will replace it with one loop per interval rule. Those loops need an
additional control: removing one rule must stop that rule's loop without
stopping the others.

## Checkpoint

Run checkpoint 18 to check the startup log and shutdown handler:

```sh
pnpm checkpoint 18 server
```

The heartbeat immediately logs `rules stored:` with the number of rules in
`reflex.db`, then logs it again every 30 seconds. If the previous
checkpoint's expense rule is the only stored rule, the count is 1. Press
Ctrl-C and look for the final line before the process exits:

```text
heartbeat stopped
```

With the viewer running, the same line is in the Logs tab, from
`reflex-server`.
