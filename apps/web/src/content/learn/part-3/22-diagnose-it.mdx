When a request fails while you are not watching, you need to reconstruct
what happened from the records it left. You have added run history and
traces throughout the course. Now check whether they contain enough detail
to explain the mixed scenario without reading the implementation.

There is no new code in this lesson. Run the previous lesson's scenario
again, then use only `runs list` and the viewer to answer four questions.
Leave the code and fixture files closed while you investigate. That makes
it easier to notice where the recorded evidence is useful and where
something is missing.

## Reproduce the mixed scenario

Use checkpoint 22, or your own server if it matched the previous
checkpoint. Start with an empty database so there is only one event's
results to inspect. Stop the server and delete `reflex.db`; this removes
the stored rules as well as the run history. Then start the mixed receiver
and server and run the commands below.

```sh
pnpm receiver --scenario mixed
```

```sh
pnpm checkpoint 22 server
```

```sh
pnpm checkpoint 22 cli rules add fixtures/rules/mixed/a-ok.json
pnpm checkpoint 22 cli rules add fixtures/rules/mixed/b-ok.json
pnpm checkpoint 22 cli rules add fixtures/rules/mixed/c-slow.json
pnpm checkpoint 22 cli rules add fixtures/rules/mixed/d-fail.json
pnpm checkpoint 22 cli events submit fixtures/events/laptop.json
pnpm checkpoint 22 cli runs list
```

After about 10 seconds, `events submit` prints four outcomes. `runs list`
should contain four rows. Open the newest `reflex-server` trace containing
an `Engine.handleEvent` span in the viewer.
[Reading a trace in the viewer](/learn/part-2/trace-viewer) describes each
part of the screen.

## Answer from the recorded evidence

Write down an answer to each question, including the evidence that supports
it. For example, identify the span you inspected, the fields in a run row,
or the duration you measured.

1. Which operation was slowest? How long did it take, and why that long?
2. Which operation failed, and with what?
3. Which work finished, and did it wait for the slow one? How long did the
   whole request take?
4. Did a timeout fire? Name two places that show it.

If the slow request succeeds rather than timing out, check whether
`REFLEX_TIMEOUT` is set in the server's shell. This exercise assumes the
default 10 second timeout, shorter than the receiver's 15 second response.

## Compare your answers

Once you have written all four answers, compare them with
[the expected answers](/learn/part-3/diagnose-it-answers). Your trace ids
and exact timings will differ, but the outcomes and their relationships
should match.

If a question required information you could not find in `runs list` or
the viewer, note what was missing. A trace can only explain what the
program recorded. That observation can become a follow-on improvement in
[Where to go next](/learn/part-4/what-comes-next).

## Checkpoint

You should be able to identify the slowest operation, distinguish its
timeout from the 500 response, and show that the two successful runs did
not wait for it. Support your explanation of the request duration with
the `Engine.handleEvent` span. Your evidence should include four run rows
and four execution spans: two red and two Ok.
