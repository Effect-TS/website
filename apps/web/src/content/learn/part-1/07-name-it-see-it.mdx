## Locating the failed call

Under the `SchemaError` in the terminal, look for a line beginning
`at evaluate (`. There's the name we supplied. The next line,
`at evaluate (definition)`, points to the function's declaration.
The error now connects the bad field to a particular call in our program.

Each call to the named function runs inside a **span** named `evaluate`.
A span records an operation's name, start time, duration and outcome. The
failure printed by `runMain` includes the name, which connects the schema
error to the call that failed.

For now, we're using the name in a text report. Later we'll connect a
[trace viewer](/learn/part-2/16-the-picture-you-already-know) to see those
spans on a timeline. The names we add here will help us recognize the same
operations there.

## Try it

We can make the location more specific. `evaluate` both decodes the rule
and checks an expense, and this failure happened during decoding. Try
giving that step its own name:

1. Turn `decodeRule` into a function made with `Effect.fn("decodeRule")`
   that takes the JSON string and decodes it.
2. Run the file and read the failure. It names both steps: `at decodeRule`
   first, then `at evaluate` under it. The decode failed, and it was running
   inside `evaluate`.

Two recognizable names now tell us where the failure happened and what
called that operation. Use names where that information will help you;
there's no need to wrap every helper. Our `matches` function can stay
plain TypeScript. Recording spans has a runtime cost, and exporting them
later adds network traffic.

Next we'll stop passing each rule to `evaluate` by hand. Reflex needs a
way to find all its rules, whether we keep them in memory for now or move
them to a database later.
