Changing the expense threshold currently means editing `isLarge`, and
changing the alert text means editing `evaluate`. Reflex should let you
change those choices without changing the evaluation code. Represent them
as a **rule** containing an operator, a threshold and a message.

Later, rules will arrive as JSON text from a file or an HTTP request. For
now, put the JSON in a string. This is the rule you have been using:

TypeScript cannot guarantee that text from outside the program contains a
valid rule. Before evaluating it, you need to parse the JSON and check its
fields. A **schema** defines both the runtime validation and the TypeScript
type of the validated value, so you do not have to maintain them separately.

## Describing a valid rule

Add the schema below the `Event` interface, and the type below it:

<LessonCode
  file="lessons/part1/06-untrusted-json/solution/main.ts"
  declaration="Rule"
/>

`Schema.Struct({ ... })` describes an object with the listed fields. Its
`name` and `message` must be strings, and its `value` must be a number.
`Schema.Literals(["gt", "lt"])` restricts `op` to those two strings, so a
rule with any other operator will fail validation.

Then add `type Rule = typeof Rule.Type`. The schema and the type share the
name `Rule`. TypeScript knows which one you mean from where you use it.

## Parsing and validating the JSON

Add one line below the type:

<LessonCode
  file="lessons/part1/06-untrusted-json/solution/main.ts"
  declaration="decodeRule"
/>

`Schema.fromJsonString(Rule)` describes parsing JSON text and checking the
parsed value against `Rule`. `Schema.decodeUnknownEffect` turns that
description into a decoding function. The resulting `decodeRule` accepts
unknown input and returns an Effect that succeeds with a `Rule` or fails
with a `SchemaError`.

Decoding adds runtime work, and the schema needs to be maintained as the
rule format changes. Once validation succeeds, the rest of the check can
use the resulting `Rule` without repeating those checks.

Run the file. The terminal shows three outcomes in order:

2. The taxi is skipped, as in the previous lesson: `skip: missing field amount`.
3. `malformed` fails with a `SchemaError`, and the program stops.

The existing `catchTag` handles only `MissingField`. An incomplete expense
still becomes a skip, while an invalid rule fails with `SchemaError` and
stops the program. This is why selecting a specific error mattered in the
previous lesson.

You have removed the summary because a run can now stop at an invalid
rule before reaching it. `evaluate` still returns whether the rule matched,
but `program` no longer counts those results. In
[Recording runs with Effect.onExit](/learn/part-2/12-an-engine-that-records),
you will record how each run ended, including failed runs.

## Finding the invalid field

Look at the malformed rule's error in the terminal. It reads
`SchemaError: Expected "gt" | "lt"` at `["op"]`. The path identifies the
invalid field, and the message lists its allowed values.

Decoding stops at the first problem it finds. `malformed` also has a string
where the value should be a number, and no message at all. Fix the operator
and the next problem is reported.

Hover `evaluate`. Its return type is
`Effect<boolean, SchemaError, never>`. Unlike `MissingField`, this error
comes from the decoder rather than a class you defined. It remains in the
type because you have not handled it.

## Try it

Extend the rule format with an equality operator. The schema change will
also change the TypeScript type used by `matches`:

1. Add `"eq"` to the literals. TypeScript underlines `matches`, because its
   `switch` no longer covers every case. Add the `eq` case,
   `amount === rule.value`.
2. Change the operator in `malformed` to `"between"` and run the file. The
   error now lists `"eq"` among the expected operators.

In this program, the JSON rule needs runtime validation because it arrives
as text. The `laptop` object is constructed in TypeScript and checked
against the `Event` interface, so it does not need a decoder here. Keep
that distinction in mind when you move to external input.

[Using FileSystem and NodeRuntime.runMain](/learn/part-2/11-your-program-your-entrypoint)
will expand `Rule` with triggers, actions and more operators. The same
approach will apply: validate incoming data, then use its inferred type
in the evaluation code.
