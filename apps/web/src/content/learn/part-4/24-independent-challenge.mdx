Imagine a rule that keeps sending alerts about a service you already know
is down. You want some quiet while you deal with it, but you'll want those
alerts back afterwards. So far, stopping an event rule means removing it
and losing its definition. Let's give reflex a way to pause a rule and
resume it later without recreating it.

This time, the implementation is yours. You've already worked with all the
APIs you need, including the tests that let us check a running loop without
waiting for real time to pass. The new work is deciding how those pieces
fit together. Allow about 40 minutes. Try an approach before opening
[the hints](/learn/part-4/challenge-hints), but use them if you get stuck;
you don't need to remember every earlier lesson to do this.

## Requirements

Someone using reflex should be able to pause a rule, see that it's paused,
and trust that it won't run in response to the next event or interval. Add
pause and resume support to the CLI and API with these requirements:

- The CLI gets `rules pause <id>` and `rules resume <id>`. Like every other
  command, they go through the server.
- A paused rule stays stored. `rules list` shows it as `paused`.
- Events do not execute a paused rule. It produces neither a row in
  `runs list` nor an `Engine.execute` span.
- Pausing an interval rule stops its loop. Resuming starts it again.
- Pausing or resuming an unknown id fails with a typed error. The CLI prints
  one line and exits with a non-zero code, just as it does when you remove
  an unknown rule.
- Decide what a server restart does to a pause, and say so in a comment.
  Either answer is fine, as long as you state it.

## Write the tests first

Start with the tests. A rule that doesn't run can look correct even when
its loop is simply broken, so we need to see it resume as well as pause.
Use the harness from
[Running rules on a schedule with FiberMap](/learn/part-3/19-rules-on-a-clock)
to check these cases before writing the implementation:

1. Use an interval rule whose poll never completes. Wait for its first
   request, pause the rule, then move the test clock past one interval.
   Assert that there is no new request and no new row.
2. Resume the rule and move the clock past one interval again, staying
   short of the timeout. Assert exactly one new request and one new row.
   This is the positive control: it shows that the loop can run when it is
   not paused. Without it, the first test could pass because the loop is
   broken, rather than because pausing works.
3. Pause an event rule and submit an event. Assert that there is no outcome
   for that rule and no row. Resume it, submit again, and assert one row.
4. Assert that pausing an unknown id fails with the typed error.

Run the tests and check that each fails for the behaviour you meant to
verify, just as we did in
[Writing tests with @effect/vitest](/learn/part-2/13-first-tests). Only then
start making them pass. You can work through one case at a time; there's
no need to finish the whole feature before getting feedback.

## Show it working

Once the tests pass, try the feature as someone using the CLI would. We'll
use the mixed scenario again so you can compare the result with the four
rules you already know.

Start with a fresh database so existing rules and runs don't affect the
result. Stop your server, delete `reflex.db`, and start it again. This
removes the rules and history in that database. Then:

1. Run `pnpm receiver --scenario mixed`.
2. Add the four mixed rules to your server.
3. Pause B and submit `fixtures/events/laptop.json`.

Look at `runs list`. It should show three new rows, not four. In the viewer,
the newest `Engine.handleEvent` trace has three `Engine.execute` spans, and
none of them is B's.

Resume B and submit again. This time you should get four new rows and four
spans. B is back at work, with the same definition it had before you paused
it. You've checked the feature through both the command someone types and
the work the server actually does.

## Checkpoint

When your four tests pass and the mixed scenario produces the expected rows
and spans, compare your implementation with checkpoint 24. It is one
possible solution, with tests in `checkpoints/24/test/`. Your code doesn't
need to look the same; compare how each version meets the requirements.
You can run the reference tests with:

```sh
pnpm checkpoint 24 test
```
