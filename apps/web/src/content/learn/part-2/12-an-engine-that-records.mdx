## The problem

`run-once.ts` runs one rule against one event and forgets it did. rulebook
needs more: every rule whose trigger matches the event runs, and every run
leaves a row saying what happened. Evaluating, acting and recording belong
together, in one place every caller goes through. That place is the `Engine`.

`RunResult` is the set of endings at this point: `skipped`, `succeeded`, or
`failed` with one of three reasons. `status`, `timeout` and `io` are reasons
on `failed` only. Nothing else uses them.

## The execution boundary

The `Engine` layer is a `Layer.effect` like the stores, except that it needs
other services to build: it yields `RuleStore`, `RunLog` and `FileSystem`
first, then builds `execute` and `handleEvent` on top of them.

`execute` is the boundary every run goes through, in this order:

1. Open the row: `runLog.start` writes `started` before anything else happens.
2. Run inside a span: `run` is `Effect.fn("Engine.execute")`, annotated with
   the rule id and trigger. It evaluates the condition, then runs the action.
   The span ends with `run`'s result, so a failed action ends it as an error.
3. Write the terminal row from the `Exit`: `Effect.onExit` sees how `run`
   ended, whatever that was. A success writes its `RunResult`; an
   `ActionFailed` writes `failed`. Any other ending leaves the row `started`
   for now. Later lessons give crashes and interruptions their own outcomes.
4. Turn the failure into a value: after the row is written, `Effect.catchTag`
   turns `ActionFailed` into a `failed` result, so `execute` cannot fail and
   one broken rule does not stop the others.

A missing field means the rule does not apply to this event. `run` catches
`MissingField` and returns `skipped`. A skip is not an error and is never shown
as one: the span ends Ok and the row's `error` column stays null.

<LessonCode file="checkpoints/12/src/Engine.ts" />

Two details in it:

- The service type says `execute` needs nothing. `run` uses the `FileSystem`
  the layer got at build time, handed over with `Effect.provideService`.
- `Effect.fn.Return<RunResult, ActionFailed | MissingField>` spells out what
  the generator returns and how it fails, so every `return` is checked against
  `RunResult`.

`handleEvent` is a `for...of` over the stored rules, like `evaluateAll` in
lesson 8, calling `execute` for each rule whose event trigger names the event.

## Now and later

What you need now: one boundary opens the row, runs inside a span, writes the
ending, and returns a value. The cost is that every run writes twice. Unpacked
later: the `interrupted` outcome and the timeout inside the span (lesson 19),
and `Cause`, which `onExit` reads to find the failure, with the `crashed`
outcome (lesson 20).
