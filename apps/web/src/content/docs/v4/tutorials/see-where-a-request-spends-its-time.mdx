A request can feel slow even when every provider succeeds. Ordinary logs show
which phase finished, but they rarely show which operations overlapped or which
child kept the whole request waiting.

In this tutorial, we will keep one `POST /orders` backend local and make its
timing visible. The finished server prints a graphical waterfall after every
order:

```text title="Finished trace shape"
Trace waterfall (one block is about 20 ms)
http.post.orders    |████████████|
  pricing.calculate |████        |
  inventory.reserve |███████     |
  shipping.quote    |█████       |
  payment.authorize |       ███  |
  orders.insert     |          ██|
attributes
  order.customer_id = "customer-123"
  order.quantity = 2
```

The exact number of blocks may vary slightly with machine load. Their positions
still reveal the important structure: pricing, inventory, and shipping overlap;
inventory is the slowest of those three; payment waits for them; and storage
waits for payment.

Everything runs in one Node.js process. The providers, tracer, and waterfall
renderer are deterministic local fixtures, so the tutorial needs no public
network, credentials, collector, or dashboard.

```ts title="server.ts" collapse={63-111} useDiffSyntax copyFinal
import { createServer } from "node:http"
import { setTimeout as sleep } from "node:timers/promises"

interface PlaceOrderRequest {
  readonly customerId: string
  readonly quantity: number
  readonly paymentToken: string
  readonly postalCode: string
}

const placeOrder = async (input: PlaceOrderRequest) => {
  const [subtotalCents, reservationId, shippingCents] = await Promise.all([
    calculatePrice(input.quantity),
    reserveInventory(input.quantity),
    quoteShipping(input.postalCode, input.quantity),
  ])
  console.log("planning finished")

  const paymentProvider = await authorizePayment(
    input.paymentToken,
    subtotalCents + shippingCents,
  )
  console.log("payment finished")

  const orderId = await insertOrder(input.customerId, reservationId)
  console.log("storage finished")

  return {
    orderId,
    status: "accepted",
    totalCents: subtotalCents + shippingCents,
    paymentProvider,
  }
}

const server = createServer(async (request, response) => {
  const sendJson = (status: number, body: unknown): void => {
    response.writeHead(status, { "content-type": "application/json" })
    response.end(JSON.stringify(body))
  }

  if (request.method !== "POST" || request.url !== "/orders") {
    sendJson(404, { error: "NotFound" })
    return
  }

  try {
    let body = ""
    for await (const chunk of request) {
      body += chunk
    }

    const order = await placeOrder(JSON.parse(body) as PlaceOrderRequest)
    sendJson(201, order)
  } catch (error) {
    console.error(error)
    sendJson(500, { error: "InternalServerError" })
  }
})

server.listen(3000, () => console.log("Listening on http://localhost:3000"))
```

The first `Effect.tryPromise` call creates an Effect value. An Effect is a value
that describes a computation. Creating it, combining it with other Effects, or
passing it through `pipe` does not call a provider. The providers run only when
the request handler reaches `Effect.runPromise`.

TypeScript infers this explanatory type for `placeOrder(input)`:

```ts title="Inferred type, not code to paste"
Effect.Effect<
  {
    orderId: string
    status: string
    totalCents: number
    paymentProvider: string
  },
  Cause.UnknownError
>
```

The first type argument is the successful order value. The second is the error
channel, which describes expected ways the computation can fail. Here, an
unclassified rejected Promise becomes `Cause.UnknownError`. Interruption is
cancellation of a running computation and is separate from that error channel.
An unexpected bug is called a defect and is also separate from an expected
failure.

<EffectApi name="Effect.all" href="/docs/v4/api/effect/Effect#all">
  Combines several Effects and returns their success values in the same order.
  With `concurrency: "unbounded"`, the three planning Effects can run at the
  same time instead of waiting for one another.
</EffectApi>

`pipe` passes the combined description through transformations from top to
bottom. It does not run the computation.

<EffectApi name="Effect.flatMap" href="/docs/v4/api/effect/Effect#flatMap">
  Uses a successful value to choose the next Effect. Payment is described only
  after all three planning values exist, and storage is described only after
  payment succeeds.
</EffectApi>

<EffectApi name="Effect.map" href="/docs/v4/api/effect/Effect#map">
  Transforms the success value while leaving the error channel unchanged. The
  final call turns the stored order id into the HTTP response object.
</EffectApi>

<EffectApi

## 3. Record the whole request as one span

A span is a timed record of one operation. It has a name, start and end times,
an optional parent, and attributes. A trace is the tree formed by a root span
and its children.

The next complete file supplies a small local tracer and waterfall renderer in
the collapsed fixture section. The tracer records spans in memory. The renderer
sorts them, rounds their positions to 20 millisecond blocks, and prints the
result after the Effect finishes. You do not need to design or edit either
fixture during this tutorial.

Add that fixture and wrap the order pipeline in a root span:

```ts title="server.ts" collapse={92-210} useDiffSyntax copyFinal
    const length = Math.min(
      available,
      Math.max(1, toColumn(status.endTime - status.startTime)),
    )
    const bar = `${" ".repeat(offset)}${"█".repeat(length)}`.padEnd(
      columns,
    )
    return `${labels[index]!.padEnd(labelWidth)} |${bar}|`
  })

  const attributes = [...root.attributes.entries()]
    .sort(([left], [right]) => left.localeCompare(right))
    .map(([key, value]) => `  ${key} = ${JSON.stringify(value)}`)

  return [
    "Trace waterfall (one block is about 20 ms)",
    ...lines,
    ...(attributes.length > 0 ? ["attributes", ...attributes] : []),
  ].join("\n")
}
```
