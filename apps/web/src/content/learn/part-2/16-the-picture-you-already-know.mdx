When you run `events submit`, the CLI reports an outcome in one line.
Quite a bit happens before that line appears: a request reaches the
server, the Engine finds a rule, and the action writes an alert. Let's
look at that work together in the viewer we started during setup.

The functions we've named along the way already record the information
we need. Each named `Effect.fn`, including `Engine.execute` and the CLI
handlers, creates a span for its operation. You've seen these names in
failure reports. Now we'll send the spans and logs from both programs
to the viewer so we can follow a whole request. The Engine and handlers
can stay as they are; we only need to connect the export layers at each
entrypoint.

## Configure telemetry for each program

Open the starter's `src/Telemetry.ts`. Telemetry is the information a
program reports about its work, here our spans and logs. The file currently
exports an unused placeholder `layer` with the service name
`reflex-lessons`. We want to tell CLI work apart from server work in the
viewer, so replace it with `layerServer` and `layerCli`, built by a shared
helper:

<LessonCode file="checkpoints/16/src/Telemetry.ts" />

`OtlpTracer.layer` exports spans to
`http://localhost:4318/v1/traces`, while `OtlpLogger.layer` exports logs to
`http://localhost:4318/v1/logs`. Both attach a `resource` with a
`serviceName`: `reflex-server` for the server and `reflex-cli` for the CLI.

Both use OTLP, the OpenTelemetry protocol for sending this data. The helper
provides their shared dependencies: `OtlpSerialization.layerJson` encodes
it as JSON, and `FetchHttpClient.layer` supplies the HTTP client that sends
it.

Exporting telemetry adds some work to each run, and you need to keep the
viewer running to receive it. The earlier lessons still work without a
viewer because they do not provide these export layers.

## Provide the telemetry layers

Let's connect each program to its export layer. In `src/server/main.ts`,
provide `Telemetry.layerServer` at the bottom of the server's layer stack.
In `src/cli/main.ts`, provide `Telemetry.layerCli` in the CLI's entrypoint
pipeline. These layers configure telemetry for the effects running in
each program. Leave the Engine, stores and handlers unchanged.

## Follow a command through both processes

We're ready to see a trace. Start the viewer with `pnpm viewer` if it
isn't running, and the server with `pnpm dev:server`. In another terminal,
add the expense rule and submit the laptop purchase:

```sh
pnpm cli rules add fixtures/rules/expense.json
pnpm cli events submit fixtures/events/laptop.json
```

Open [http://localhost:8000](http://localhost:8000) and pick the
`events.submit` trace. The list should no longer be empty. Follow the rows
from `reflex-cli` into `reflex-server`, then find `Engine.execute` under
`Engine.handleEvent`:

![The events.submit trace: CLI spans, then the server's POST, Engine.handleEvent and Engine.execute nested under it](../_assets/viewer-trace.png "The checkpoint trace")

These are two processes, but the viewer shows one connected trace. The
CLI's `HttpClient` includes a `traceparent` header in the request with
the current trace and span ids. The server reads that header and starts its
request span as a child of the client span. This propagation allows the
viewer to show work from two processes in one trace. The HTTP client and
server provide it without additional code in your handlers.

As you expand the nested rows in the waterfall, you should recognize the
functions we've been working on:

- `Engine.handleEvent` and `Engine.execute` are the `Effect.fn` names from
  [Recording runs with Effect.onExit](/learn/part-2/12-an-engine-that-records).
- `evaluate` and `lookup` come from `Rule.ts`.
- `events.submit` and `rules.add` are the CLI handler names from the previous
  lesson.

[Reading a trace in the viewer](/learn/part-2/trace-viewer) describes each
part of this screen.

## Try it

Select an `Engine.execute` span and look at its attributes. We already
attach `rule.id` and `rule.trigger`, but the condition's result is missing.
Let's add it so we can tell the lunch purchase from the laptop purchase
here, without opening the run history.

1. In `src/Engine.ts`, find where `Engine.execute` evaluates the condition.
   Store the result in a variable named `matched`.
2. Add `Effect.annotateCurrentSpan("rule.condition", matched)`. It adds the
   attribute to the span the code is running in.
3. Leave the other paths alone. A rule without a condition has nothing to
   record, and a missing field fails before there is a result.

With the server and viewer running, submit `fixtures/events/lunch.json`
and `laptop.json`, then compare their `Engine.execute` spans. Lunch should
have `rule.condition` set to `false`; the laptop should have `true`. Now
the trace tells you why one expense reached the action and the other
didn't. The hint and the changed file are in `exercises/16/`. The
checkpoints don't include this change, because nothing later depends on it.

## Checkpoint

With the viewer running, start the reference server for checkpoint 16:

```sh
pnpm checkpoint 16 server
```

In a second terminal:

```sh
pnpm checkpoint 16 cli rules add fixtures/rules/expense.json
pnpm checkpoint 16 cli events submit fixtures/events/laptop.json
```

The viewer shows one `events.submit` trace that starts in `reflex-cli` and
continues into `reflex-server`, with `Engine.execute` under
`Engine.handleEvent`, as in the screenshot above.

That's the application we set out to build in this part: you can give
reflex a rule, send it an expense and inspect what it did, through both
the run history and the trace. One limitation will become obvious as soon
as you restart the server: your rules and history disappear. We'll keep
them in SQLite next, so restarting doesn't mean starting over.
