`run-once.ts` runs one rule against one event and forgets that it did. Reflex
needs more. Every rule whose trigger matches an event should run, and every
run should leave a row saying how it ended. In this lesson you build the
`Engine`, the one place every run goes through, and a `RunLog` that keeps the
rows.

In this lesson you will:

- build a layer that depends on other services
- record how an effect ended, whatever happened, with `Effect.onExit`
- turn a failure into a value so one broken rule does not stop the rest

## 2. Keep a run history

Create `src/RunLog.ts`. `RunLog` is built the same way as `RuleStore`:

- `start` opens a row with the outcome `started`.
- `finish` writes how the run ended.
- `list` reads rows back, newest first.

<LessonCode file="checkpoints/12/src/RunLog.ts" />

`RunResult` lists the ways a run can end at this point: `skipped`,
`succeeded` or `failed`. A `failed` result also carries one of three reasons,
`status`, `timeout` or `io`. Only `failed` uses them.

## 3. Build the Engine

Create `src/Engine.ts`. The `Engine` layer is a `Layer.effect`, like the
stores. The difference is that it needs other services before it can build.
It `yield*`s `RuleStore`, `RunLog` and `FileSystem` first, then builds
`execute` and `handleEvent` on top of them:

<LessonCode file="checkpoints/12/src/Engine.ts" />

`execute` is the boundary every run goes through. It does four things, in
this order:

1. **Open the row.** `runLog.start` writes `started` before anything else
   happens.
2. **Run inside a span.** `run` is `Effect.fn("Engine.execute")`, annotated
   with the rule id and trigger. It evaluates the condition, then runs the
   action. The span ends with `run`'s result, so a failed action ends the
   span as an error.
3. **Write the final row from the `Exit`.** An `Exit` is the value that
   describes how an effect ended. `Effect.onExit` hands it to you however
   `run` ended. A success writes its `RunResult`, and an `ActionFailed`
   writes `failed`. Any other ending leaves the row `started` for now.
4. **Turn the failure into a value.** After the row is written,
   `Effect.catchTag` turns `ActionFailed` into a `failed` result. `execute`
   cannot fail, so one broken rule does not stop the others.

A missing field means the rule does not apply to this event. `run` catches
`MissingField` and returns `skipped`. A skip is not an error: the span ends
Ok and the row's `error` column stays null.

Two details to notice:

- The service type says `execute` needs nothing. `run` uses the `FileSystem`
  the layer got when it was built, handed over with `Effect.provideService`.
- `Effect.fn.Return<RunResult, ActionFailed | MissingField>` spells out what
  the generator returns and how it can fail, so every `return` is checked
  against `RunResult`.

`handleEvent` is a `for...of` over the stored rules, like `evaluateAll` in
Part 1. It calls `execute` for each rule whose event trigger names the event.

## Try it

`huge expense: skipped` does not say why. Give every skip a reason, kept as
free text in the run history's `reason` column:

1. In `src/RunLog.ts`, give the `skipped` member of `RunResult` a
   `reason: Schema.String`. The compiler now lists every place that writes a
   skip without one.
2. In `src/Engine.ts` there are three such places:
   - the condition was false, so say which condition;
   - the `MissingField` catch, so use the error's `field`, as
     `missing field amount`;
   - the `httpPost` branch, so say that the action runs from the lesson on
     network actions.
3. Leave `failed` alone. Its three reasons are fixed, because the `runs`
   table that a later lesson stores these rows in only accepts those three
   on a failed row.

Check your work with `pnpm tsx src/main.ts`. It prints each skip with its
reason in brackets. The hint and the changed files are in `exercises/12/`.
From the next checkpoint on, the reference solution includes this change,
and the next lesson tests it.

## What you learned

- One boundary, `execute`, opens the row, runs inside a span, writes how the
  run ended, and returns a value.
- `Effect.onExit` sees every ending. `Effect.catchTag` afterwards turns the
  expected failure into a result.
- A layer that `yield*`s other services depends on them, and
  `Layer.provideMerge` supplies them while keeping them available.
- The cost is that every run writes to the log twice.
- [Running rules on a schedule with FiberMap](/learn/part-3/19-rules-on-a-clock)
  adds the `interrupted` and `crashed` outcomes and a timeout inside the span.
