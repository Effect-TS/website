import { Aside } from "@astrojs/starlight/components"

Thrown errors work, but they leave a question unanswered: when you call a
function, **what can fail**?

This tutorial shows how `Effect` makes those failures part of a function's return type,
so each one is visible at runtime _and_ in the signature, where the type checker tracks it.

You're going to use one operation throughout the tutorial: process a payment
through a payment SDK (authorize it, validate the response, and return the
authorization). That operation can fail three ways:

- The provider is unreachable.
- The response fails to validate.
- The provider declines the payment.

Keep those three in mind, because making them visible is the whole point.

The SDK is simulated with sandbox payment tokens, so each token gives
a predictable result:

| Token            | Result                              |
| ---------------- | ----------------------------------- |
| `"tok_visa"`     | The provider authorizes the payment |
| `"tok_declined"` | The provider declines the payment   |
| `"tok_timeout"`  | The provider is unreachable         |

## Shape the failure surface

Nothing in the signature of a try/catch function tells you what can fail. Here is a common
version of the payment step without `Effect`: three named error classes, a
type guard (a function that narrows a type), and a try around the await.

```ts twoslash import.meta.vitest title="processPayment.ts"
interface Authorization {
  readonly authorizationId: string
  readonly status: "authorized" | "declined"
}

class NetworkError extends Error {
  constructor(cause?: unknown) {
    super("The provider is unreachable", { cause })
  }
}
class PaymentDeclinedError extends Error {
  constructor() {
    super("The provider declined the payment")
  }
}
class ParseError extends Error {
  constructor(args?: { cause?: unknown }) {
    super("The response is not an authorization", { cause: args?.cause })
  }
}

function isAuthorization(body: unknown): body is Authorization {
  const r = body as Authorization
  return (
    (r?.status === "authorized" || r?.status === "declined") &&
    typeof r?.authorizationId === "string"
  )
}

// Tutorial fixture: sandbox tokens make provider results reproducible.
type PaymentToken = "tok_visa" | "tok_declined" | "tok_timeout"

const authorizePayment = async (token: PaymentToken): Promise<unknown> => {
  if (token === "tok_timeout") {
    throw new Error("Provider unreachable")
  }
  if (token === "tok_declined") {
    return { authorizationId: "pauth_123", status: "declined" }
  }
  return { authorizationId: "pauth_123", status: "authorized" }
}

async function processPayment(token: PaymentToken): Promise<Authorization> {
  let response: unknown
  try {
    response = await authorizePayment(token)
  } catch (cause) {
    throw new NetworkError(cause)
  }

  if (!isAuthorization(response)) {
    throw new ParseError({})
  }
  if (response.status === "declined") {
    throw new PaymentDeclinedError()
  }
  return response
}

await processPayment("tok_visa") // => { authorizationId: "pauth_123", status: "authorized" }
```

The payment goes through. `Promise` says nothing about failure.

To find out, you have to read the implementation, or the docs if they exist and
haven't drifted from it. Either way, the signature never shows it.

`processPayment` is a common function signature that hides how it can fail:

{/* prettier-ignore */}
```ts showLineNumbers=false
//                      ┌─ Needs `token`
//                      │                             ┌─ Returns `Authorization`
//                      ▼                             ▼
function processPayment(token: PaymentToken): Promise<Authorization>
//                                            └─ How can it fail?
```

Worse, the compiler can't tell you any of this. Suppose a caller tries to handle
the failure:

```ts twoslash showLineNumbers=false
type PaymentToken = "tok_visa" | "tok_declined" | "tok_timeout"
interface Authorization {
  readonly authorizationId: string
  readonly status: "authorized" | "declined"
}
declare function processPayment(token: PaymentToken): Promise<Authorization>
class PaymentDeclinedError extends Error {}
// ---cut---
try {
  await processPayment("tok_declined")
} catch (error) {
  //       └─ `unknown`
  if (error instanceof PaymentDeclinedError) {
    // ...
  }
}
```

Every one of these still compiles:

1. `error` is `unknown`: the compiler cannot see which errors `processPayment`
   throws.
1. `error instanceof PaymentDeclinedError` compiles even if `processPayment`
   never throws it.
1. Forgetting an error that `processPayment` does throw still compiles.
1. When `processPayment` starts throwing a new error later, every caller still
   compiles, and the error reaches production.

A **good function signature** is a contract with three clauses:

1. what the function needs
1. what it returns on success
1. how it can fail

**Meet `Effect`**, which satisfies all three clauses and makes the contract explicit:

{/* prettier-ignore */}
```ts showLineNumbers=false
//                      ┌─ What the function needs
//                      │                            ┌─ What it returns on success
//                      │                            │              ┌─ How it can fail
//                      ▼                            ▼              ▼
function processPayment(token: PaymentToken): Effect<Authorization, PaymentDeclinedError | NetworkError | ParseError>
```

An `Effect<Success, Error>` is a description of a program with both a `Success` and an `Error` type parameter:

| Type parameter | Clause                     |
| -------------- | -------------------------- |
| `Success`      | what it returns on success |
| `Error`        | how it can fail            |

An `Effect`'s `Error` type parameter exposes all possible failures as a union type.

Now `processPayment`'s signature shows how it can fail: with a
`PaymentDeclinedError`, `NetworkError`, or `ParseError`.

<Aside type="note" title="Checkpoint">
  You can now read a signature and treat it as a contract. `Effect`'s `Success`
  and `Error` type parameters show what you need without reading the
  implementation.
</Aside>

## Model failures as values

So far the failures are only types in the `Error` type parameter. Next you build
the runtime values behind those.

You return each failure instead of throwing it:

- A thrown error becomes `unknown` in a `catch`, so the compiler loses it.
- A returned value keeps its type, so the compiler tracks it through every caller.

`Effect` uses two conventions for these values:

- an `Error` suffix on the class, to tell a failure from a success at a glance.
- a `_tag` property, unique to each failure, so the compiler can tell them apart.

`Data.TaggedError` builds both. Its argument becomes the `_tag`:

{/* prettier-ignore */}
```ts import.meta.vitest showLineNumbers=false mark=/class \w+(Error)|TaggedError[(](.ParseError.)[)]|[.](_tag)/
import { Data } from "effect"

//         ┌─ `Error` suffix
//         │                               ┌─ `_tag` property value
//         ▼                               ▼
class ParseError extends Data.TaggedError("ParseError") {}

const error = new ParseError()
error._tag // => "ParseError"
```

<Aside type="tip" title="Why use a class?">
  In TypeScript a class is both a type _and_ a value. One declaration gives you
  the failure type to name in a signature and the constructor to build it, with
  no extra imports.
</Aside>

Refactor the three error classes to `Data.TaggedError`:

```ts twoslash import.meta.vitest collapse={3-6,25-37} {8-10,12,14-16} {"Still throws the errors as before":39} title="processPayment.ts"
import { Data } from "effect"

interface Authorization {
  readonly authorizationId: string
  readonly status: "authorized" | "declined"
}

class NetworkError extends Data.TaggedError("NetworkError")<{
  readonly cause?: unknown
}> {}

class PaymentDeclinedError extends Data.TaggedError("PaymentDeclinedError") {}

class ParseError extends Data.TaggedError("ParseError")<{
  readonly cause?: unknown
}> {}

function isAuthorization(body: unknown): body is Authorization {
  const r = body as Authorization
  return (
    (r?.status === "authorized" || r?.status === "declined") &&
    typeof r?.authorizationId === "string"
  )
}

// Tutorial fixture: sandbox tokens make provider results reproducible.
type PaymentToken = "tok_visa" | "tok_declined" | "tok_timeout"

const authorizePayment = async (token: PaymentToken): Promise<unknown> => {
  if (token === "tok_timeout") {
    throw new Error("Provider unreachable")
  }
  if (token === "tok_declined") {
    return { authorizationId: "pauth_123", status: "declined" }
  }
  return { authorizationId: "pauth_123", status: "authorized" }
}

async function processPayment(token: PaymentToken): Promise<Authorization> {
  let response: unknown
  try {
    response = await authorizePayment(token)
  } catch (cause) {
    throw new NetworkError({ cause })
  }

  if (!isAuthorization(response)) {
    throw new ParseError({})
  }
  if (response.status === "declined") {
    throw new PaymentDeclinedError()
  }
  return response
}
```

The `{ ... }` after each `TaggedError` declares the shape of the fields the
failure carries.

<Aside type="note" title="Checkpoint">
  You now model each failure as a value: a class from `Data.TaggedError`, with
  an `Error` suffix and a `_tag` that tells it apart from the others. These
  values are the members of an `Effect`'s `Error` union.
</Aside>

## Rewrite `processPayment` with Effect

Now you build the program with `Effect`, and every failure you yield lands in its `Error` type parameter.

### Write the program like an `async` function

An `Effect` is lazily executed: creating one doesn't run it. It describes a program that can succeed or fail.

Here is the same two-step program, first with a `Promise`, then with an `Effect`:

<div class="not-prose my-6 grid grid-cols-1 gap-x-6 md:grid-cols-2">

<div>

**Promise**

```ts twoslash import.meta.vitest showLineNumbers=false
interface Authorization {
  readonly authorizationId: string
  readonly status: "authorized" | "declined"
}
type PaymentToken = "tok_visa" | "tok_declined" | "tok_timeout"
const authorizePayment = async (
  token: PaymentToken,
): Promise<Authorization> => {
  if (token === "tok_timeout") throw new Error("Provider unreachable")
  if (token === "tok_declined")
    return { authorizationId: "pauth_123", status: "declined" }
  return { authorizationId: "pauth_123", status: "authorized" }
}
// ---cut---
async function program() {
  const first = await authorizePayment("tok_visa")
  const second = await authorizePayment("tok_declined")
  return { first: first.status, second: second.status }
}

await program() // => { first: "authorized", second: "declined" }
```

</div>

<div>

**Effect**

```ts twoslash import.meta.vitest showLineNumbers=false
import { Effect } from "effect"

interface Authorization {
  readonly authorizationId: string
  readonly status: "authorized" | "declined"
}
type PaymentToken = "tok_visa" | "tok_declined" | "tok_timeout"
const authorizePayment = (token: PaymentToken): Effect.Effect<Authorization> =>
  Effect.succeed(
    token === "tok_declined"
      ? { authorizationId: "pauth_123", status: "declined" }
      : { authorizationId: "pauth_123", status: "authorized" },
  )
// ---cut---
const program = Effect.gen(function* () {
  const first = yield* authorizePayment("tok_visa")
  const second = yield* authorizePayment("tok_declined")
  return { first: first.status, second: second.status }
})

await Effect.runPromise(program) // => { first: "authorized", second: "declined" }
```

</div>

</div>

Same shape, three swaps:

- `async function` becomes `Effect.gen(function* ...)`
- `await` becomes `yield*`
- `await program()` becomes `await Effect.runPromise(program)`

If a step fails, the rest do not run, the same way a thrown error stops an `async`
function.

### Give the SDK call a failure type

A `Promise` hides its failures, so wrap the SDK call with `Effect.tryPromise` to
give them a type. `try` creates the `Promise`, and `catch` maps a rejection to
one of your failures:

```ts twoslash import.meta.vitest
interface Authorization {
  readonly authorizationId: string
  readonly status: "authorized" | "declined"
}
type PaymentToken = "tok_visa" | "tok_declined" | "tok_timeout"
const authorizePayment = async (
  token: PaymentToken,
): Promise<Authorization> => {
  if (token === "tok_timeout") {
    throw new Error("Provider unreachable")
  }
  if (token === "tok_declined") {
    return { authorizationId: "pauth_123", status: "declined" }
  }
  return { authorizationId: "pauth_123", status: "authorized" }
}
// ---cut---
import { Effect, Data } from "effect"

class NetworkError extends Data.TaggedError("NetworkError")<{
  readonly cause?: unknown
}> {}

//    ┌─ Effect<Authorization, NetworkError>
//    ▼
const request = Effect.tryPromise({
  try: () => authorizePayment("tok_visa"),
  catch: (cause) => new NetworkError({ cause }),
})

await Effect.runPromise(request) // => { authorizationId: "pauth_123", status: "authorized" }
```

A `Promise<Authorization>` that could reject is now an
`Effect<Authorization, NetworkError>`: an `Authorization` on success, a
`NetworkError` when it rejects.

### Fail a step with a tagged error

Inside `Effect.gen`, yield a failure value to fail the whole `Effect`, the way
`throw` stops a function. The yielded failure joins the `Error` type parameter,
next to the `NetworkError` from the wrapped call:

```ts twoslash
import { Effect, Data } from "effect"

interface Authorization {
  readonly authorizationId: string
  readonly status: "authorized" | "declined"
}
type PaymentToken = "tok_visa" | "tok_declined" | "tok_timeout"
const authorizePayment = async (
  token: PaymentToken,
): Promise<Authorization> => {
  if (token === "tok_timeout") {
    throw new Error("Provider unreachable")
  }
  if (token === "tok_declined") {
    return { authorizationId: "pauth_123", status: "declined" }
  }
  return { authorizationId: "pauth_123", status: "authorized" }
}
class NetworkError extends Data.TaggedError("NetworkError")<{
  readonly cause?: unknown
}> {}
// ---cut---
class PaymentDeclinedError extends Data.TaggedError("PaymentDeclinedError") {}

//    ┌─ Effect<Authorization, NetworkError | PaymentDeclinedError>
//    ▼
const program = Effect.gen(function* () {
  const authorization = yield* Effect.tryPromise({
    try: () => authorizePayment("tok_declined"),
    catch: (cause) => new NetworkError({ cause }),
  })

  if (authorization.status === "declined") {
    return yield* new PaymentDeclinedError()
  }

  return authorization
})
```

Success and failure leave the same way: `return authorization`, or
`return yield* new PaymentDeclinedError()`. The error exits like any other
result, which is exactly what lets the `Error` type parameter track it.

Now rewrite `processPayment` using `Effect`:

```ts import.meta.vitest title="processPaymentEffect.ts" twoslash collapse={3-37}
import { Effect, Data } from "effect"

interface Authorization {
  readonly authorizationId: string
  readonly status: "authorized" | "declined"
}

class NetworkError extends Data.TaggedError("NetworkError")<{
  readonly cause?: unknown
}> {}

class PaymentDeclinedError extends Data.TaggedError("PaymentDeclinedError") {}

class ParseError extends Data.TaggedError("ParseError")<{
  readonly cause?: unknown
}> {}

function isAuthorization(body: unknown): body is Authorization {
  const r = body as Authorization
  return (
    (r?.status === "authorized" || r?.status === "declined") &&
    typeof r?.authorizationId === "string"
  )
}

// Tutorial fixture: sandbox tokens make provider results reproducible.
type PaymentToken = "tok_visa" | "tok_declined" | "tok_timeout"

const authorizePayment = async (token: PaymentToken): Promise<unknown> => {
  if (token === "tok_timeout") {
    throw new Error("Provider unreachable")
  }
  if (token === "tok_declined") {
    return { authorizationId: "pauth_123", status: "declined" }
  }
  return { authorizationId: "pauth_123", status: "authorized" }
}

//    ┌─ (token: PaymentToken) => Effect.Effect<Authorization, PaymentDeclinedError | NetworkError | ParseError>
//    ▼
const processPayment = (token: PaymentToken) =>
  Effect.gen(function* () {
    const response = yield* Effect.tryPromise({
      try: () => authorizePayment(token),
      catch: (cause) => new NetworkError({ cause }),
    })

    if (!isAuthorization(response)) {
      return yield* new ParseError({})
    }

    if (response.status === "declined") {
      return yield* new PaymentDeclinedError()
    }

    return response
  })

await Effect.runPromise(processPayment("tok_visa")) // => { authorizationId: "pauth_123", status: "authorized" }
```

The compiler inferred its `Error` type parameter as the union of all three failures,
from the values you yield. You never wrote it by hand.

<Aside type="tip" title="More delegation to TypeScript's compiler">
  `Effect` infers both type parameters from the steps you build, so you rarely
  write an `Effect` signature by hand.
</Aside>
<Aside type="note" title="Checkpoint">
  You now build the work with `Effect.gen`, take each success with `yield*`,
  wrap a `Promise` with `Effect.tryPromise`, and fail by yielding a tagged
  error.
</Aside>

## Recover from failures

The signature lists what can fail. Now read it from the other side: a caller
that uses the list to recover.

### Handle one failure

`Effect.catchTag` takes the `_tag` of one failure and a handler. The handler is an `Effect` that receives the typed error as a parameter, not `unknown`. The example uses `pipe`, which applies a function to the `Effect`, like method chaining:

```ts twoslash import.meta.vitest
import { Effect, Data } from "effect"

interface Authorization {
  readonly authorizationId: string
  readonly status: "authorized" | "declined"
}

class NetworkError extends Data.TaggedError("NetworkError")<{
  readonly cause?: unknown
}> {}
class PaymentDeclinedError extends Data.TaggedError("PaymentDeclinedError") {}
class ParseError extends Data.TaggedError("ParseError")<{
  readonly cause?: unknown
}> {}

type PaymentToken = "tok_visa" | "tok_declined" | "tok_timeout"

const processPayment = (
  token: PaymentToken,
): Effect.Effect<
  Authorization,
  PaymentDeclinedError | NetworkError | ParseError
> =>
  token === "tok_declined"
    ? Effect.fail(new PaymentDeclinedError())
    : token === "tok_timeout"
      ? Effect.fail(new NetworkError({}))
      : Effect.succeed({ authorizationId: "pauth_123", status: "authorized" })
// ---cut---
const outcome = processPayment("tok_declined").pipe(
  Effect.catchTag("PaymentDeclinedError", (cause) =>
    //                                     └─ `PaymentDeclinedError`
    Effect.succeed("Payment declined"),
  ),
)

await Effect.runPromise(outcome) // => "Payment declined"
```

The handled error leaves the `Error` type parameter. The others stay:

{/* prettier-ignore */}
```ts showLineNumbers=false
//                                    ┌─ `PaymentDeclinedError` is removed
//                                    ▼
Effect.Effect<string | Authorization, NetworkError | ParseError>
```

<Aside type="note" title="Success type widens too">
  The handler returns `Effect.succeed("Payment declined")`, a `string`, while
  the original success was an `Authorization`.

So the `Success` type parameter now covers both: `string | Authorization`.

</Aside>

The compiler now has another job: it won't compile a handler for a `_tag` that isn't in the union.

### Handle all the failures

`Effect.catchTags` (notice the `s` at the end), handles all the tracked failures with one table: an object keyed by `_tag`.

For each `_tag`, its handler receives the typed error:

```ts twoslash import.meta.vitest
import { Effect, Data } from "effect"

interface Authorization {
  readonly authorizationId: string
  readonly status: "authorized" | "declined"
}

class NetworkError extends Data.TaggedError("NetworkError")<{
  readonly cause?: unknown
}> {}
class PaymentDeclinedError extends Data.TaggedError("PaymentDeclinedError") {}
class ParseError extends Data.TaggedError("ParseError")<{
  readonly cause?: unknown
}> {}

type PaymentToken = "tok_visa" | "tok_declined" | "tok_timeout"

const processPayment = (
  token: PaymentToken,
): Effect.Effect<
  Authorization,
  PaymentDeclinedError | NetworkError | ParseError
> =>
  token === "tok_declined"
    ? Effect.fail(new PaymentDeclinedError())
    : token === "tok_timeout"
      ? Effect.fail(new NetworkError({}))
      : Effect.succeed({ authorizationId: "pauth_123", status: "authorized" })
// ---cut---
const outcome = processPayment("tok_timeout").pipe(
  Effect.catchTags({
    //             ┌─ `NetworkError`
    //             ▼
    NetworkError: (cause) => Effect.succeed("Provider unreachable, try again"),

    //                     ┌─ `PaymentDeclinedError`
    //                     ▼
    PaymentDeclinedError: (cause) => Effect.succeed("Payment declined"),
  }),
)

await Effect.runPromise(outcome) // => "Provider unreachable, try again"
```

Two more rules the compiler enforces:

1. Every key must be a `_tag` from the union. A typo does not compile.
1. The result keeps what the table misses: `Effect.Effect<Authorization, ParseError>`.

When all the failures are handled, the `Error` type parameter becomes `never`:

```ts twoslash import.meta.vitest showLineNumbers=false
import { Effect, Data } from "effect"

interface Authorization {
  readonly authorizationId: string
  readonly status: "authorized" | "declined"
}

class NetworkError extends Data.TaggedError("NetworkError")<{
  readonly cause?: unknown
}> {}
class PaymentDeclinedError extends Data.TaggedError("PaymentDeclinedError") {}
class ParseError extends Data.TaggedError("ParseError")<{
  readonly cause?: unknown
}> {}

type PaymentToken = "tok_visa" | "tok_declined" | "tok_timeout"

declare const processPayment: (
  token: PaymentToken,
) => Effect.Effect<
  Authorization,
  PaymentDeclinedError | NetworkError | ParseError
>
// ---cut---
//    ┌─ (token: PaymentToken) => Effect.Effect<string | Authorization, never>
//    ▼
const recover = (token: PaymentToken) =>
  processPayment(token).pipe(
    Effect.catchTags({
      NetworkError: () => Effect.succeed("..."),
      ParseError: () => Effect.succeed("..."),
      PaymentDeclinedError: () => Effect.succeed("..."),
    }),
  )
```

<Aside type="note" title="Why `never`?">
  `never` is TypeScript's empty type: the union with no members left. Each
  handled tag drops out of the union, and once the last one is gone there is
  nothing to name, so the type is `never`. It is the type-level way of saying
  "this can no longer fail."
</Aside>

## Defects: the failures you didn't model

Every failure so far is one a caller can respond to. But `never` does not mean
the code cannot fail.

Some failures have no handler. In a payment program, they break a rule about
money:

- An authorization is captured once.
- The provider sends the status its contract promises.

Each rule above is an invariant: a condition that must hold for the money to be correct.

When one of those breaks, no handler applies. The safe action is to stop and
report. In `Effect` these are called **defects**.

A defect is a failure outside the intended control flow: an impossible state, a
broken invariant, a bug in third-party code. `Effect` records failures in two
places, and the compiler sees only one of them:

| Place                      | What it holds                                                                         | Who sees it  |
| -------------------------- | ------------------------------------------------------------------------------------- | ------------ |
| The `Error` type parameter | the failures you modeled                                                              | the compiler |
| The `Cause`                | everything else: defects, and interruptions <br /> (a run stopped before it finished) | the runtime  |

Here is the tutorial's signature, one more time. Every failure it names is one
a caller can respond to:

{/* prettier-ignore */}
```ts showLineNumbers=false
//                           ┌─ the failures you modeled
//                           ▼
Effect.Effect<Authorization, PaymentDeclinedError | NetworkError | ParseError>
```

A failure this type never names lands in the `Cause`. Key decisions below use
these `Effect` APIs:

| Decision                                        | `Effect` API         |
| ----------------------------------------------- | -------------------- |
| A failure no caller can respond to              | `Effect.die`         |
| Handle a defect where it is safe to             | `Effect.catchDefect` |
| Stop tracking failures no caller can respond to | `Effect.orDie`       |

### Raise a defect

The capture step guards the first invariant: an authorization is captured
once. The ledger fixture pretends the first attempt already succeeded, so this
run is the retry. Walk through what happens:

1. The capture finds the payment already in the ledger.
1. The invariant is broken.
1. No caller can respond to a broken invariant.

A typed error would promise a recovery that cannot exist. So the step dies
instead of failing: `Effect.die` sends the error to the `Cause` instead of the
`Error` type parameter, which stays empty.

```ts twoslash import.meta.vitest title="capturePayment.ts"
import { Data, Effect } from "effect"

interface Authorization {
  readonly authorizationId: string
  readonly status: "authorized" | "declined"
}

class DoubleCaptureError extends Data.TaggedError("DoubleCaptureError")<{
  readonly authorizationId: string
}> {}

// Tutorial fixture: an in-memory ledger, so captures are reproducible.
// The first attempt already captured the payment. This run is the retry.
const captured = new Set(["pauth_123"])

//    ┌─ Effect.Effect<Authorization>: no `Error` type parameter
//    ▼
const capturePayment = (
  authorization: Authorization,
): Effect.Effect<Authorization> =>
  Effect.gen(function* () {
    if (captured.has(authorization.authorizationId)) {
      // An authorization is captured once. No caller can respond to the
      // broken invariant, so the step dies instead of failing with a
      // modeled error.
      return yield* Effect.die(
        new DoubleCaptureError({
          authorizationId: authorization.authorizationId,
        }),
      )
    }
    captured.add(authorization.authorizationId)
    return authorization
  })

const outcome = capturePayment({
  authorizationId: "pauth_123",
  status: "authorized",
}).pipe(
  Effect.catchDefect((defect) =>
    defect instanceof DoubleCaptureError
      ? Effect.succeed(`terminated: ${defect.authorizationId} already captured`)
      : Effect.die(defect),
  ),
)

await Effect.runPromise(outcome) // => "terminated: pauth_123 already captured"
```

The signature says `Effect.Effect<Authorization>`: no `Error` type parameter.

So the capture cannot fail? The double capture says otherwise. The failure
never entered the `Error` type parameter: it became a defect.

`Effect.catchDefect` recovered from it. Without it, `Effect.runPromise` rejects
with the error. Unknown defects stay fatal, so the handler re-raises them with
`Effect.die`.

### Stop tracking failures no caller can respond to

`Effect.orDie` is a modeling decision: no caller can do anything with these
failures, so stop tracking them. Every typed error becomes a defect, and the
`Error` type parameter disappears.

Apply it at the boundary between your Effect code and its callers: inside, the
code still fails with typed errors, but the signature the caller sees has none
left.

```ts twoslash import.meta.vitest
import { Effect, Data } from "effect"

interface Authorization {
  readonly authorizationId: string
  readonly status: "authorized" | "declined"
}

class NetworkError extends Data.TaggedError("NetworkError")<{
  readonly cause?: unknown
}> {}
class PaymentDeclinedError extends Data.TaggedError("PaymentDeclinedError") {}
class ParseError extends Data.TaggedError("ParseError")<{
  readonly cause?: unknown
}> {}

// Tutorial fixture: sandbox tokens make provider results reproducible.
type PaymentToken = "tok_visa" | "tok_declined" | "tok_timeout"

// Fixture: `processPayment` reduced to the sandbox tokens, so the example runs.
const processPayment = (
  token: PaymentToken,
): Effect.Effect<
  Authorization,
  PaymentDeclinedError | NetworkError | ParseError
> =>
  token === "tok_declined"
    ? Effect.fail(new PaymentDeclinedError())
    : token === "tok_timeout"
      ? Effect.fail(new NetworkError({}))
      : Effect.succeed({ authorizationId: "pauth_123", status: "authorized" })
// ---cut---
//    ┌─ Effect.Effect<Authorization>: `Error` type parameter is gone
//    ▼
const reconcile = processPayment("tok_declined").pipe(Effect.orDie)

try {
  await Effect.runPromise(reconcile)
} catch (defect) {
  defect instanceof PaymentDeclinedError && defect._tag // => "PaymentDeclinedError"
}
```

A nightly reconciliation job: when the payment fails, the job crashes and
alerts whoever owns it. Nothing here is recoverable in place, so nothing is
left to track. The failure crossed the boundary as a defect:
`Effect.runPromise` rejected with the `PaymentDeclinedError` itself.

### Recover at the boundary

A defect is a bug. A handler cannot fix it. But the boundary decides what
happens next, once, in one place: the job runner, the HTTP handler, the batch
loop. For each defect, ask:

1. Could a caller respond to this? Then it is not a bug. Model it as a typed
   error: a class with a `_tag`, named in the `Error` type parameter.
1. Is it a bug? Report it, and let the program terminate.
1. Can the program continue without it? Catch it, report it, and go on.

Inside the program, defects stay fatal. Only the boundary decides.

`Effect.catchDefect` handles defects only. The next example is the other
direction from the previous section: typed errors pass through unchanged.

```ts twoslash import.meta.vitest
import { Effect, Data } from "effect"

interface Authorization {
  readonly authorizationId: string
  readonly status: "authorized" | "declined"
}

class NetworkError extends Data.TaggedError("NetworkError")<{
  readonly cause?: unknown
}> {}
class PaymentDeclinedError extends Data.TaggedError("PaymentDeclinedError") {}
class ParseError extends Data.TaggedError("ParseError")<{
  readonly cause?: unknown
}> {}

// Tutorial fixture: sandbox tokens make provider results reproducible.
type PaymentToken = "tok_visa" | "tok_declined" | "tok_timeout"

// Fixture: `processPayment` reduced to the sandbox tokens, so the example runs.
const processPayment = (
  token: PaymentToken,
): Effect.Effect<
  Authorization,
  PaymentDeclinedError | NetworkError | ParseError
> =>
  token === "tok_declined"
    ? Effect.fail(new PaymentDeclinedError())
    : token === "tok_timeout"
      ? Effect.fail(new NetworkError({}))
      : Effect.succeed({ authorizationId: "pauth_123", status: "authorized" })
// ---cut---
const outcome = processPayment("tok_declined").pipe(
  Effect.catchDefect((defect) =>
    defect instanceof Error
      ? Effect.succeed(`reported: ${defect.message}`)
      : Effect.die(defect),
  ),
)

try {
  await Effect.runPromise(outcome)
} catch (failure) {
  failure instanceof PaymentDeclinedError && failure._tag // => "PaymentDeclinedError"
}
```

The `catchDefect` handler never ran. `catch (failure)`, not `catch (defect)`:
the typed error was never a defect. It reached `runPromise` untouched,
exactly as its type said, with all three members still in the `Error` type
parameter.

A rule of thumb for the whole section:

- Prefer the typed operators for the failures you modeled: `Effect.catchTag`
  and `Effect.catchTags`.
- Use `Effect.catchDefect` only where recovering from the unexpected is
  intentional and safe.

<Aside type="note" title="Checkpoint">
  "Did I cover every case?" has two answers now. For the failures you modeled,
  the `Error` type parameter answers: it shrinks as you handle them. For the
  ones you didn't, the boundary answers: `catchDefect` sees them at the edge,
  where you report them and let the program terminate.
</Aside>

## Review what you built

You can now do five things. Each one maps to an operator you used.

- Read an `Effect` signature as a contract. The `Success` type parameter names the result, and the `Error` type parameter names every failure a caller can handle.
- Model each failure as a value with `Data.TaggedError`, so the compiler tracks the failure instead of losing it as `unknown` in a `catch`.
- Turn a rejecting `Promise` into typed failures with `Effect.tryPromise`, and fail inside `Effect.gen` with a yielded tagged error.
- Recover with `Effect.catchTag` for one `_tag` and `Effect.catchTags` for many. Each handled tag leaves the `Error` union. An empty union is `never`.
- Keep defects apart from typed failures. `Effect.die` records a defect in the `Cause`. `Effect.catchDefect` recovers at the boundary. `Effect.orDie` converts tracked failures you no longer handle.
