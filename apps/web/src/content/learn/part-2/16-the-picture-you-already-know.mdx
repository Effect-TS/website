Since lesson 7, every function you named with `Effect.fn` has run inside a
span, `Engine.execute` included. You've seen those names in failures, but
you've never seen the spans themselves, because nothing sends them anywhere.

Now you have two programs, a CLI and a server, and a single command crosses
both of them. That's exactly when a trace pays off. In this lesson you wire up
telemetry yourself, open your first trace, and watch one command travel from
one process into the other.

You will learn:

- how to export spans and logs with a telemetry layer;
- how a trace follows a request from one process into another;
- how to add your own attribute to a span.

## Writing Telemetry.ts

The starter's `src/Telemetry.ts` already exports a single `layer`, with the
service name `reflex-lessons`. It's a placeholder, and nothing in your program
imports it. Replace the whole file with two layers, one per program,
`layerServer` and `layerCli`:

- `OtlpTracer.layer` exports spans to the viewer at
  `http://localhost:4318/v1/traces`.
- `OtlpLogger.layer` exports logs to `http://localhost:4318/v1/logs`.
- Both take a `resource` with a `serviceName`. Use `reflex-server` for the
  server and `reflex-cli` for the CLI, so the viewer can tell them apart.
- They send JSON (`OtlpSerialization.layerJson`) over an `HttpClient`
  (`FetchHttpClient.layer`).

Provide `Telemetry.layerServer` at the bottom of the server's layer stack in
`src/server/main.ts`, and `Telemetry.layerCli` in the CLI's run line. That's
all. Nothing in the Engine, the stores or the handlers changes.

## One trace, two processes

The CLI and the server are separate processes, and yet one trace crosses
between them. Here's how.

The CLI's `HttpClient` adds a `traceparent` header to every request, carrying
the current trace and span ids. The server starts its request span as a child
of that span. This is called **propagation**. The trace id travels with the
request, and the viewer stitches both halves into one tree.

You didn't write any of that. Both sides already speak the header.

## Try it: record what the condition decided

The `Engine.execute` spans carry `rule.id` and `rule.trigger`, but nothing says
what the condition decided.

In `src/Engine.ts`, give the result of `evaluate` a name, and add it to the
span with `Effect.annotateCurrentSpan("rule.condition", matched)`. A rule
without a condition has nothing to record, and a missing field fails before
there's a result.

To check your work, run the server and the viewer. Submitting
`fixtures/events/lunch.json` should give an `Engine.execute` span with
`rule.condition` set to `false`, and `laptop.json` one with `true`. The hint
and the changed file are in `exercises/16/`. The checkpoints don't include this
change, because nothing later depends on it.

## Recap

- Telemetry is one layer per program, provided at the edge.
- Traces cross processes on their own, carried by the `traceparent` header.
- `Effect.annotateCurrentSpan` adds your own facts to the span you're in.
- The cost is a little time per span, and a second program to keep running,
  the viewer.
- Lessons 19 and 20 show what the viewer looks like when a run fails, times
  out, or is interrupted.
