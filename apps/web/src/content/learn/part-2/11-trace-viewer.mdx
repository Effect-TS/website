otel-desktop-viewer is the trace viewer the course uses. It runs on your
machine and shows what it receives at
[http://localhost:8000](http://localhost:8000). From
[Exporting traces with OtlpTracer](/learn/part-2/16-the-picture-you-already-know)
on, your programs send it spans and logs over OTLP on port 4318.

- `pnpm run doctor --viewer` downloads and starts it the first time.
- `pnpm viewer` starts it in later sessions.
- It keeps everything it receives until you stop it.

This page is a reference. Come back to it whenever a lesson asks you to look
at a span.

## Parts of a trace

A **trace** is one piece of work from start to finish: one CLI command, one
HTTP request, or one interval tick. A trace is a tree of spans.

A **span** is one named, timed step inside a trace. Every `Effect.fn("name")`
in your code produces a span with that name each time it runs.

The screenshot below is the checkpoint of
[Exporting traces with OtlpTracer](/learn/part-2/16-the-picture-you-already-know).
It shows `events.submit` from the CLI, with the expense rule stored,
submitting `laptop.json`.

![The events.submit trace in otel-desktop-viewer: CLI spans in green, server spans in purple, Engine.execute selected with status Ok](../_assets/viewer-trace.png "One trace from reflex-cli into reflex-server")

## Parts of the screen

- **Traces tab.** Lists traces by their root span, newest first. Pick one to
  open it. The sidebar toggle at the top left hides the list and gives the
  waterfall more room.
- **Waterfall.** One row per span. Indentation shows nesting. In the
  screenshot, `Engine.execute` ran inside `Engine.handleEvent`, which ran
  inside the server's `POST`. The number in brackets is how many children a
  span has.
- **Bar.** Shows when the span started and how long it took, against the time
  axis at the top. The colour is the service, not the result. Green is
  `reflex-cli` and purple is `reflex-server`.
- **Details panel.** Opens on the right when you select a row. It shows the
  span's duration, its `status.code`, and attributes such as `rule.id`. Logs
  written inside the span are listed under Events, and in the Logs tab.

## Span status

A span ends with the result of the effect it wraps. There are three results
you will see.

| Result | `status.code` | Colour | Meaning                                                     |
| ------ | ------------- | ------ | ----------------------------------------------------------- |
| Ok     | `1 (Ok)`      | none   | The effect succeeded.                                       |
| Error  | `2 (Error)`   | red    | The effect failed, or died with a defect.                   |
| Unset  | `0 (Unset)`   | none   | The effect was interrupted. It neither failed nor finished. |

### A failed span

![A rules.run trace with Engine.execute in red, status.code 2 (Error) and an exception event BadResource: FileSystem.writeFile (fixtures)](../_assets/viewer-error-span.png "An Engine.execute span that failed")

This trace comes from `rules run` against a rule whose `appendFile` path is
`fixtures`. That is a directory, so the write fails.

- The failed span, and the span it failed inside, are red. The trace header
  counts the errors (`1/2 err`), and the arrows next to the count step
  through them.
- `status.code` is `2 (Error)`. `status.message` and the `exception` event
  carry the error's message.
- The parent `POST` is not red. The engine turned the failure into a `failed`
  outcome, so the request itself succeeded. The run row says the same thing:
  `failed (io)`.

### An interrupted span

![A rules.run trace that took 1.24 s, Engine.execute selected with status.code 0 (Unset) and effect.fiber.interrupted true](../_assets/viewer-unset-span.png "An Engine.execute span that was interrupted")

This trace comes from pressing Ctrl-C on the CLI while `rules run` was
waiting on an append that could not finish. The server noticed the client had
gone and interrupted the handler, and with it `Engine.execute` and
`appendLine`.

- `status.code` is `0 (Unset)`. An ordinary span has the same code before
  anything sets it, so Unset does not mean success.
- `effect.fiber.interrupted` is `true`. This attribute is what tells an
  interruption apart from everything else.
- The bar ends at the moment of interruption. The duration is how long the
  work ran before it was stopped.

Until [Running rules on a schedule with FiberMap](/learn/part-3/19-rules-on-a-clock),
nothing writes a final row for an interrupted run, so its row stays
`started`. That lesson adds the `interrupted` outcome, and removing a rule in
the middle of a poll produces exactly this picture.
