curl works, but nobody wants to type
`-H 'content-type: application/json' -d @...` for every rule. Reflex needs a
command line. A CLI built on hand-written `fetch` calls would drift: rename a
field on the server and the CLI still compiles, then fails at run time. In
this lesson you build a CLI whose client is derived from the same `Api` value
the server implements, so it cannot drift.

In this lesson you will:

- derive a typed client from an `HttpApi` with `HttpApiClient.make`
- read configuration from the environment with `Config`
- write the six command handlers of the CLI
- handle a typed error that came back from the server

## 1. Create the client service

Create `src/ApiClient.ts`. `HttpApiClient.make(Api, { baseUrl })` derives a
client from the `Api` value. It has one method per endpoint, grouped like the
API:

- `client.rules.create({ payload })`
- `client.rules.run({ params: { id }, payload })`
- `client.runs.list({ query })`

Put the client in a service, `ApiClient`, like every other dependency. Its
type is `HttpApiClient.ForApi<typeof Api>`, so you never write the shape by
hand:

<LessonCode file="checkpoints/15/src/ApiClient.ts" />

- The payload is checked against the endpoint's schema before anything is
  sent, and the response is decoded with the success schema. If you change
  the API, the CLI stops compiling until it agrees.
- The client sends requests through an `HttpClient`, another service.
  `FetchHttpClient.layer` provides one built on `fetch`.
- The server's URL comes from `Config`. `Config.String("REFLEX_URL")` reads
  the environment variable, and `Config.withDefault("http://localhost:3000")`
  covers the usual case. A config you `yield*` inside a layer is read when
  the layer is built.

## 2. Write the command handlers

Open `src/cli/main.ts`. It came with the starter. Every command, argument and
flag is declared, and every handler body is empty. Write the six bodies. Each
one `yield*`s the `ApiClient`, makes one call, and prints the result:

<LessonCode file="checkpoints/15/src/cli/main.ts" />

- `rules add` reads the file with the same `readJson` as before, then calls
  `client.rules.create`.
- `rules run` and `events submit` print one outcome per line, with its
  reason or error.
- `runs list` has two optional flags. The declarations hand them to you as
  `string | undefined` and `number | undefined`. That is the shape the query
  takes, so they go straight into `client.runs.list({ query })`.

Name the handlers with `Effect.fn("rules.add")` and so on. The next lesson
shows why the names matter.

The run line at the bottom provides `ApiClient.layer`, its
`FetchHttpClient.layer`, and `NodeServices.layer` for reading files.

## 3. Run a command

Start the server with `pnpm dev:server` in one terminal. In a second:

```sh
pnpm cli rules add fixtures/rules/expense.json
pnpm cli rules list
pnpm cli events submit fixtures/events/laptop.json
pnpm cli runs list
```

`rules add` prints `Added <id>: large expense`. `events submit` prints one
line, `<id>: succeeded`, and `runs list` shows the row.

An action the engine does not have yet is skipped with a reason that says so.
Add `fixtures/rules/ntfy.json`, whose action is `httpPost`, and run it
against an event:

```sh
pnpm cli rules run <id> --event fixtures/events/laptop.json
```

It prints one `skipped` outcome whose reason says that `httpPost` actions run
from a later lesson, and `runs list` shows the same row.
[Telling errors from defects with Cause](/learn/part-3/20-an-action-over-the-network)
adds the action.

## 4. Read a typed error from the server

```sh
pnpm cli rules remove nope
```

The server answered 404. The client knows the endpoint declares
`RuleNotFound`, so it decodes the body into the same class the store fails
with. The CLI prints `RuleNotFound` with a stack trace.

Hover the `rules remove` handler. `RuleNotFound` is in its error type, next to
the HTTP and schema errors any request can have. You handle it like any other
failure.

## Try it

The stack trace from step 4 is no help to someone who typed an id wrong. Make
the CLI print one line and exit non-zero instead.

1. Write one handler with `Effect.fn` that takes the `RuleNotFound`, prints
   `No rule with id <id>` with `Console.error`, and then fails with
   `new ExitCode({ code: 1 })` from `tools/entrypoint.ts`. `runMain` exits
   with that code and prints nothing more.
2. `Effect.fn` takes more arguments after the generator and applies each one
   to the effect it builds. Pass `Effect.catchTag("RuleNotFound", yourHandler)`
   there, in both the `rules remove` and `rules run` handlers.

Check your work with `pnpm cli rules remove nope` and
`pnpm cli rules run nope --event fixtures/events/laptop.json`. Each prints
one line and exits 1 (`echo $?`). The hint and the changed file are in
`exercises/15/`. From the next checkpoint on, the reference solution includes
this change.

## What you learned

- A client derived from the API cannot drift from it, and it is a service
  like the rest.
- `Config` reads settings from the environment, with a default for the usual
  case.
- Errors the endpoint declares come back as the same typed classes, so you
  handle them like any other failure.
- The cost is that the CLI imports the server's domain types, so the two ship
  together.
- In [Exporting traces with OtlpTracer](/learn/part-2/16-the-picture-you-already-know)
  you follow one command from the CLI into the server as a single trace.
