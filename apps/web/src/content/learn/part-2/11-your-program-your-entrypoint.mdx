## A schema for triggers, conditions and actions

In Part 1, a rule only needed enough information to compare an amount
against a threshold. The file we just opened also says when to check that
condition and where to write the alert. Create `src/Rule.ts` with a schema
for those three parts:

- A trigger is an `event` or an `interval`.
- A condition is optional. It compares a `field` against a `value` using an
  `op`: `eq`, `neq`, `gt`, `lt` or `contains`. The field can be a dotted path
  such as `body.status`. Without a condition, evaluation returns `true`.
- An action is `appendFile` or `httpPost`.

On your first read, follow the rule we just opened: an `event` trigger,
the condition `amount gt 500`, and an `appendFile` action. The schema also
contains the interval and HTTP variants we'll use later. You don't need to
understand how those will run yet; keep your attention on getting this
expense alert into a file.

<LessonCode file="checkpoints/11/src/Rule.ts" />

If you've used discriminated unions in TypeScript, the `type` fields here
will be familiar. Each trigger or action variant is a `Schema.Struct`
with a distinct `type` literal. `Schema.Union` combines them and preserves
the information TypeScript needs to narrow the type. Inside
`case "appendFile":`, for example, you can access `rule.action.path` because
that property belongs to the `appendFile` variant.

`lookup` reads the dotted path from the event. When a key on the path is
absent it fails with `MissingField`, the error you defined in
[Defining errors with Schema.TaggedError](/learn/part-1/04-failure-you-can-see).

## Append a line to a file

Now we need the part that actually saves the alert. Create `src/Action.ts`
for the file-writing action. Effect provides the `FileSystem.FileSystem`
service, which you access in the same way as your own `RuleStore` from
[Defining a service with Context.Service](/learn/part-1/08-a-place-for-rules).
Use `yield*` to get the service, then call its methods.

<LessonCode file="checkpoints/11/src/Action.ts" />

We want to keep previous alerts, so `flag: "a"` makes `fs.writeFileString`
append rather than overwrite. If the file doesn't exist yet, the operation
creates it.

A write can fail, for example because the process lacks permission.
`FileSystem` represents that failure as a `PlatformError`, but callers of
`appendLine` need an error about the action they attempted. `Effect.mapError`
converts it to `ActionFailed`, preserving the original message and adding
the reason `io`.

For now, `io` is the only reason in `ActionFailed`. That's enough to
describe the file-writing failures we can encounter here.

We have a rule we can decode and an action we can run. Let's connect them.
Replace `src/run-once.ts` with the program below. Its `readJson` helper reads
a file and decodes its contents with a schema. We use it for both the rule
and the event, then check the condition and append an alert if it matches:

<LessonCode file="checkpoints/11/src/run-once.ts" />

Take a look at the bottom of the file. You'll recognize `NodeRuntime.runMain`
from Part 1. We left that run line alone in the browser; here we're adding
real Node services and choosing how errors and exit codes are reported.
The pipeline prepares the effect and runs it in this order:

1. `Effect.tapError` prints a typed error as one line, then passes the
   failure on unchanged.
2. `Effect.provide(NodeServices.layer)` provides Node's `FileSystem` and the
   other platform services, so the requirements type is `never`.
3. `NodeRuntime.runMain({ disableErrorReporting: true })` runs the program,
   sets the exit code, and turns Ctrl-C into an interruption. Error reporting
   is off because step 1 already printed the error.

The schema accepts an `httpPost` action, but the program does not execute
it yet. That branch logs a message explaining that the action is introduced
later.

## Check the file output

Try the laptop purchase first:

```sh
pnpm tsx src/run-once.ts fixtures/rules/expense.json fixtures/events/laptop.json
```

The terminal prints the following log line, prefixed by a timestamp and
`INFO`. The program also creates `alerts.log` and appends the alert text to it:

```text
large expense: appended "expense 1200 over 500" to alerts.log
```

Open `alerts.log` to check that the message is there. Then run the program
again with `fixtures/events/lunch.json`. Its amount, 40, is below
the threshold of 500, so the terminal prints `large expense: no match`
and the file is unchanged.

Run it with `fixtures/rules/malformed.json`. It prints a typed error with no
stack trace and exits with code 1:

```text
SchemaError: Expected "eq" | "neq" | "gt" | "lt" | "contains"
  at ["condition"]["op"]
```

## Try it

We can now change the expense without touching TypeScript. Let's make the
alert text just as easy to change. The `alertLine` function still builds
text such as `expense 1200 over 500` from the event and condition, even
though the rule file has its own `"message": "expense over 500"`. Make the
action write that message instead, so the person defining the rule can
choose what the alert says.

1. Add `message: Schema.String` to the `AppendFile` struct in `src/Rule.ts`.
2. In the `appendFile` case of `src/run-once.ts`, hover over
   `rule.action.message` to confirm that its type is `string`. Pass it to
   `appendLine` instead of the generated line.
3. Delete the unused `alertLine` function and its `words` lookup.
4. Copy the rule file, remove `message` from the copy, and run it. The error
   names the missing key and its path.

Check your work with
`pnpm tsx src/run-once.ts fixtures/rules/expense.json fixtures/events/laptop.json`.
It appends `expense over 500` to `alerts.log`. The hint and the changed files
are in `exercises/11/`. From the next checkpoint on, the reference solution
includes this change.
