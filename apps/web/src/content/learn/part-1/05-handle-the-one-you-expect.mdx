The taxi from lesson 4 stops the whole program. But an expense without an
amount isn't a disaster. It's normal. The alert simply doesn't apply to it, so
rulebook should note that it skipped the event and move on to the next one.

To see that working, you need more than one event. In this lesson you add the
laptop back, check both events with the same code, and turn the taxi's failure
into a skip.

You will learn:

- how to reuse steps by putting them in a function that returns an effect;
- how to handle one failure by its tag;
- how to add steps after an effect with `.pipe`.

## Handling one failure with catchTag

`Effect.catchTag` handles exactly one failure, picked out by its tag:

```ts
Effect.catchTag("MissingField", (error) => ...)
```

The handler receives the typed error and returns the effect to run in its
place. Here, that's a log line: `skip: missing field ${error.field}`. Every
other failure passes through untouched.

## Adding steps with .pipe

To attach `catchTag` to an effect, you need `.pipe`. It takes a minute to
learn. Every effect has a `.pipe` method:

- `effect.pipe(f)` is the same as `f(effect)`;
- `effect.pipe(f, g)` is the same as `g(f(effect))`.

It lets you add steps after an effect and read them left to right, in the
order they apply. Inside `evaluate`, add `.pipe(Effect.catchTag(...))` after
the `Effect.gen(...)`.

Now the terminal prints `expense 1200 over 500`, then
`skip: missing field amount`, and the program finishes normally.

## Try it: watch the type change

Hover `evaluate` before and after you add `catchTag`.

- Before: `Effect<string, MissingField, never>`.
- After: `Effect<string | void, never, never>`.

`MissingField` has left the error slot, because it's handled. Nothing else can
fail, so the slot says `never` again. The success slot picked up `void`,
because the skip branch logs a line and gives back nothing.

That type is honest, but not very useful yet. In Part 2, lesson 12 turns a skip
into a recorded outcome with a reason.

## Recap

- A function that returns an effect lets you run the same steps on different
  inputs.
- `catchTag` handles one failure by its tag and removes it from the second
  slot.
- `.pipe` adds steps after an effect, read left to right.
- Every failure is a decision: handle it here, or leave it in the type for the
  caller.
- Not every failure is one you expect. A rule that is itself broken is the
  next lesson. A thrown exception, which appears in no type at all, is a third
  kind of failure, and it waits until Part 3.
