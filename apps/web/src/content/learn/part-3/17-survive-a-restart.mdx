## The problem

Stop the server and start it again. `rules list` is empty and `runs list` has
forgotten everything. Both stores are Maps, and a Map lives exactly as long as
the process. Rules have to be added once and stay, and the run history is only
useful if it is still there tomorrow. This lesson keeps both in SQLite, in a
file called `rulebook.db`.

## A database is a layer

`SqliteClient.layer({ filename: "rulebook.db" })` opens the file and provides
`SqlClient`, the service every query goes through. It uses `node:sqlite`, which
is why the course needs Node 22.16: there is no native module to build.

An empty file has no tables. The two SQL files in `migrations/` create them,
and `SqliteMigrator.layer` runs the ones this database has not seen yet, in the
order of their number. It records each one it ran in a table of its own, so
starting the server a second time changes nothing.

<LessonCode file="checkpoints/17/src/Migrations.ts" />

This file is plumbing: the migrator's own loader imports `.js` and `.ts` files,
and the supplied migrations are plain SQL, so this loader reads each file and
runs its statements. Copy it to `src/Migrations.ts` and change the directory
line, because your `src/` sits one level below the project root, not three:

```ts
const directory = path.join(import.meta.dirname, "..", "migrations")
```

Open `migrations/0002_runs.sql`. The `runs` table is the run history from
lesson 12, one column per field. The `CHECK` on `reason` is the column
contract: a `failed` row names one of `status`, `timeout` or `io`, and any
other row may say anything or nothing.

## RuleStore over SQL

`RuleStore.layerSql` sits next to `layerMemory` in the same file and implements
the same service. It `yield*`s `SqlClient` instead of building a Map.

- The `sql` tag writes a query. Values inside `${}` become parameters, never
  part of the SQL text, so a rule name with a quote in it cannot break the
  query. `sql.insert(row)` turns an object into the column list and values of
  an `INSERT`.
- `SqlSchema.findAll` pairs a query with the schema of its rows, and decodes
  every row it returns. `SqlSchema.void` does the same for a write with no
  result.
- `definition_json` holds the rule as text. `Schema.fromJsonString(Rule)` is
  one schema for both directions: it encodes a `Rule` to JSON on the way in,
  and on the way out it parses the text and decodes it with the same `Rule`
  schema the API uses. A row that someone edited by hand into something that is
  not a rule fails right there, with the same error a bad request gets.

<LessonCode file="checkpoints/17/src/RuleStore.ts" />

`get` runs `findById` and takes the first row. No row means
`return yield* new RuleNotFound({ id })`, exactly what the memory store does,
so every caller keeps handling one typed error and nothing has to learn about
an optional result. `remove` uses `RETURNING id` to learn whether it deleted
anything.

A database error is not something a caller can act on. `Effect.orDie` turns it
into a defect, so the service type stays what it was: `create` cannot fail,
`get` and `remove` fail only with `RuleNotFound`.

## RunLog over SQL

`RunLog.layerSql` follows the same pattern. Times are stored as ISO 8601 text,
which sorts in time order, and `Schema.DateTimeUtcFromString` turns them back
into `DateTime` values on the way out. `finish` is one `UPDATE` of the row
`start` inserted.

`RuleStore` and `RunLog`. Lesson 9 promised this when the store was still a
Map in the playground.

The tests from lesson 13 make the same point without trusting you. Turn each
store suite into a function of a layer, `(name, store) => layer(store, {
buildPerTest: true })(name, (it) => ...)` with the lesson 13 tests inside
unchanged, and call it once per layer. For SQLite the layer is
`Migrations.layer` over `SqliteClient.layer({ filename: ":memory:" })`: a
database that exists only for one test, with the tables already created.
`buildPerTest` gives every test a fresh one.

## Exercise

`pnpm cli runs list --rule <id>` gives the right rows against SQLite, as it did
against the Map. But `RunLog.layerSql` reads every row of `runs` and then
filters and slices them in TypeScript. With a few interval rules (lesson 19)
that table grows by thousands of rows a day, and every `runs list --rule`
reads all of them to keep a handful. Make SQLite do the filtering and the
limit, in the query.

Check: `pnpm test` stays green, and with the server running,
`pnpm cli runs list --rule <id> --limit 2` prints at most two rows, all of that
rule. The hint and the changed file are in `exercises/17/`. From lesson 18 on,
the checkpoints include this change.

## Now and later

What you need now: a database is a layer, a query is the `sql` tag with a
schema for its rows, and swapping storage is two lines in the entrypoint. The
cost is a file on disk to manage and a migration for every change to the
tables. The checkpoint servers and yours all use `rulebook.db` in the project
root; delete it when you want to start clean. Unpacked later: a run whose
process ended before it could write its last row (lesson 19).

## Checkpoint

Start the checkpoint's server, and in a second terminal add a rule and submit
an event:

```sh
pnpm checkpoint 17 server
```

```sh
pnpm checkpoint 17 cli rules add fixtures/rules/expense.json
pnpm checkpoint 17 cli events submit fixtures/events/laptop.json
```

Stop the server with Ctrl-C and start it again with the same command. Then:

```sh
pnpm checkpoint 17 cli rules list
pnpm checkpoint 17 cli runs list
```

The rule and its `succeeded` run are still there.
