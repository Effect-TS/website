The course uses otel-desktop-viewer to inspect traces and logs locally.
Open its interface at [http://localhost:8000](http://localhost:8000). From
[Exporting traces with OtlpTracer](/learn/part-2/16-the-picture-you-already-know)
on, your programs send it spans and logs over OTLP on port 4318.

- `pnpm run doctor --viewer` downloads and starts it the first time.
- `pnpm viewer` starts it in later sessions.
- It keeps everything it receives until you stop it.

Use this page as a reference when a lesson asks you to inspect a span. The
screenshots show both a successful run and runs that failed or were
interrupted.

## Parts of a trace

A trace records a piece of work, such as a CLI command, an HTTP request or
an interval tick. It consists of spans arranged in a tree, so you can see
which operations ran inside others.

A span records the name and duration of an operation. Each call to a
function defined with `Effect.fn("name")` creates a span with that name.

The screenshot below shows the checkpoint from
[Exporting traces with OtlpTracer](/learn/part-2/16-the-picture-you-already-know).
The expense rule has been stored, and the CLI is submitting `laptop.json`
with `events.submit`.

![The events.submit trace in otel-desktop-viewer: CLI spans in pink, server spans in orange, Engine.execute selected with status Ok](../_assets/viewer-trace.png "One trace from reflex-cli into reflex-server")

## Parts of the screen

- The Traces tab lists traces by their root span, newest first. Select a
  trace to open it. You can hide this list with the sidebar toggle at the
  top left to make more room for the waterfall.
- The waterfall has one row per span, indented to show nesting. In the
  screenshot, `Engine.execute` ran inside `Engine.handleEvent`, which ran
  inside the server's `POST`. The number in brackets counts a span's children.
- Each bar shows when a span started and how long it took, using the time
  axis at the top. The colour identifies the service rather than the result:
  pink is `reflex-cli` and orange is `reflex-server`.
- Selecting a row opens the details panel on the right. It shows the span
  duration, `status.code` and attributes such as `rule.id`. Logs written
  inside the span appear under Events and in the Logs tab.

## Span status

A span created by Effect ends with the result of the effect it wraps. In
these course examples, you will see the following statuses:

| Result | `status.code` | Colour | Meaning                                                   |
| ------ | ------------- | ------ | --------------------------------------------------------- |
| Ok     | `1 (Ok)`      | none   | The effect succeeded.                                     |
| Error  | `2 (Error)`   | red    | The effect failed with a typed error or a defect.         |
| Unset  | `0 (Unset)`   | none   | The effect was interrupted before it succeeded or failed. |

### A failed span

![A rules.run trace with Engine.execute in red, status.code 2 (Error) and an exception event BadResource: FileSystem.writeFile (fixtures)](../_assets/viewer-error-span.png "An Engine.execute span that failed")

Here, `rules run` executes a rule whose `appendFile` path is `fixtures`.
Because that path is a directory rather than a file, the write fails.

- The failed action's span and its enclosing execution span are red. The
  trace header counts the errors (`1/2 err`); use the arrows next to the
  count to move between them.
- `status.code` is `2 (Error)`. `status.message` and the `exception` event
  carry the error's message.
- The parent `POST` is not red. The engine turned the failure into a `failed`
  outcome, so the request itself succeeded. The run row says the same thing:
  `failed (io)`.

### An interrupted span

![A rules.run trace that took 1.61 s, Engine.execute selected with status.code 0 (Unset) and effect.fiber.interrupted true](../_assets/viewer-unset-span.png "An Engine.execute span that was interrupted")

This trace was recorded after pressing Ctrl-C in the CLI while `rules run`
was waiting for an append that could not finish. When the client
disconnected, the server interrupted the request handler, including its
`Engine.execute` and `appendLine` effects.

- `status.code` is `0 (Unset)`. This is also the default code for a span
  whose status has not been set, so Unset alone does not identify an
  interruption or indicate success.
- `effect.fiber.interrupted` is `true`, identifying this as an interruption.
- The bar ends at the moment of interruption. The duration is how long the
  work ran before it was stopped.

Until [Running rules on a schedule with FiberMap](/learn/part-3/19-rules-on-a-clock),
the Engine does not finalize interrupted runs, so their rows remain
`started`. That lesson adds an `interrupted` outcome. Removing a rule during
a poll then produces an interrupted span like this one and a corresponding
`interrupted` row.
