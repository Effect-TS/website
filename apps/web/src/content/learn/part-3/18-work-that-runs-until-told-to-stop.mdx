So far, everything the server does is an answer to a request. Lesson 19 adds
work that nobody asks for in the moment: an interval rule polls a URL every few
seconds, for as long as the server runs.

Before that loop does anything real, it has to get one thing right that's easy
to get wrong. When the server stops, the loop must stop with it, cleanly, and
say so. This lesson builds a loop that does nothing useful, so that stopping is
the only thing you have to watch.

You will learn:

- how to repeat an effect on a schedule;
- how to run a loop in the background, tied to a layer's lifetime;
- where cleanup goes when a loop is stopped.

## Repeating on a schedule

The heartbeat logs how many rules are stored, once at startup and then every
30 seconds. Here's `src/Heartbeat.ts`:

<LessonCode file="checkpoints/18/src/Heartbeat.ts" />

Read it from the inside out:

- The inner `Effect.gen` block is one beat: list the rules, log the count.
- `Effect.repeat(Schedule.spaced("30 seconds"))` runs the beat, then runs it
  again 30 seconds after each run ends, forever. The first run happens at
  once. A `Schedule` is a value that describes when to go again, and `spaced`
  is the simplest one.
- `Effect.onInterrupt` runs its effect when the loop is interrupted, and only
  then. A loop that never ends on its own has exactly one way to stop, so
  that's where the log goes.
- `Effect.forkScoped` starts the loop on a fiber of its own and ties that fiber
  to the current scope. A **fiber** is a piece of work that runs alongside the
  rest of the program. Because the loop runs on its own fiber, building the
  layer finishes straight away and the loop carries on in the background.

## Stopping with the scope

`Layer.effectDiscard` builds a layer from an effect without providing any
service. Like every layer, it has a **scope**. The scope opens when the layer
is built and closes when the program that built it ends.

`forkScoped` puts the loop in that scope. So when the scope closes, the loop is
interrupted, `onInterrupt` logs, and only then does the layer finish closing.

That means you never stop the loop yourself. You stop the program, and the
program closes its layers. In `src/server/main.ts`, the heartbeat sits next to
the served API:

The heartbeat needs `RuleStore`, so it's built after the store and closed
before it. That order is what makes shutdown safe. The loop's last action can
never be a query against a database that has already closed.

## What Ctrl-C does

You didn't write a signal handler, and you don't need one. Here's the chain of
events when you press Ctrl-C:

1. `runMain`, from lesson 11, turns Ctrl-C into an interruption of the main
   fiber.
2. `Layer.launch` was holding the server open. Interrupted, it closes the
   layer.
3. Closing the layer closes its scope, which interrupts the heartbeat.
4. The heartbeat's `onInterrupt` logs.

## Recap

- A loop is an effect with `Effect.repeat` and a `Schedule`.
- `Effect.forkScoped` ties a loop to whoever started it, so it stops when they
  do.
- `Effect.onInterrupt` is where cleanup goes.
- The trade-off is a fiber that does nothing most of the time.
- Lesson 19 replaces the heartbeat with one loop per interval rule. Each of
  those has to stop on its own when its rule is removed, not only when the
  server stops.
