The file from Part 1 review is in your starter as `src/run-once.ts`. It
prints its alert lines and exits, and the alerts are gone with it. In this
lesson you turn it into a program that reads a rule and an event from JSON
files and appends an alert line to `alerts.log`.

In this lesson you will:

- read and write files with the `FileSystem` service
- describe the real `Rule` schema, with triggers, conditions and actions
- turn a file system error into an `ActionFailed`
- write the run line yourself with `NodeRuntime.runMain`

## 3. Describe the real rule

Create `src/Rule.ts`. The rule schema from Part 1 compared one amount. A real
rule has three parts, and two of them come in variants:

- A trigger is an `event` or an `interval`.
- A condition is optional. It names a `field`, which can be a dotted path such
  as `body.status`, an `op` out of `eq`, `neq`, `gt`, `lt` and `contains`, and
  a `value`. A rule without a condition matches every event.
- An action is `appendFile` or `httpPost`.

<LessonCode file="checkpoints/11/src/Rule.ts" />

Each variant is a `Schema.Struct` with a `type` literal, and `Schema.Union`
joins the variants. Because every variant has a different `type`, TypeScript
narrows on it. Inside `case "appendFile":` the compiler knows that
`rule.action.path` exists.

`lookup` reads the dotted path from the event. When a key on the path is
absent it fails with `MissingField`, the error you defined in
[Defining errors with Schema.TaggedError](/learn/part-1/04-failure-you-can-see).

## 4. Append a line to a file

Create `src/Action.ts`. Effect ships the file system as a service,
`FileSystem.FileSystem`. You use it like your own `RuleStore` from
[Defining a service with Context.Service](/learn/part-1/08-a-place-for-rules):
`yield*` it, then call its methods.

<LessonCode file="checkpoints/11/src/Action.ts" />

- `fs.writeFileString(path, text, { flag: "a" })` appends to the file and
  creates it when it is missing.
- It fails with a `PlatformError` when the disk says no. That error belongs to
  the file system. The caller only needs to know that the action did not
  happen, so `Effect.mapError` turns it into an `ActionFailed` with the reason
  `io` and the original message.

`io` is one of three reasons a failed action can have. The other two,
`status` and `timeout`, arrive with `httpPost` in
[Telling errors from defects with Cause](/learn/part-3/20-an-action-over-the-network).

matches:

<LessonCode file="checkpoints/11/src/run-once.ts" />

The run line at the bottom is yours now. It does three things, in order:

1. `Effect.tapError` prints a typed error as one line, then passes the
   failure on unchanged.
2. `Effect.provide(NodeServices.layer)` provides Node's `FileSystem` and the
   other platform services, so the requirements type is `never`.
3. `NodeRuntime.runMain({ disableErrorReporting: true })` runs the program,
   sets the exit code, and turns Ctrl-C into an interruption. Error reporting
   is off because step 1 already printed the error.

`httpPost` decodes, so rule files can use it. This program does not run it
yet. It only logs that the action arrives later.

## Try it

Every alert line reads like `expense 1200 over 500`, because `alertLine`
builds it from the event. The rule file already says what it wants written:
`"message": "expense over 500"`. Make the action write the rule's message
instead.

1. Add `message: Schema.String` to the `AppendFile` struct in `src/Rule.ts`.
2. In the `appendFile` case of `src/run-once.ts`, hover
   `rule.action.message`. It is a `string`. Write it instead of the built
   line.
3. Delete `alertLine`, which has no caller left, and `words` with it.
4. Copy the rule file, remove `message` from the copy, and run it. The error
   names the missing key and its path.

Check your work with
`pnpm tsx src/run-once.ts fixtures/rules/expense.json fixtures/events/laptop.json`.
It appends `expense over 500` to `alerts.log`. The hint and the changed files
are in `exercises/11/`. From the next checkpoint on, the reference solution
includes this change.

## What you learned

- `FileSystem.FileSystem` is a service Effect ships. You `yield*` it like a
  service you wrote, and `NodeServices.layer` provides the real one.
- `Schema.Union` of structs with a `type` literal describes variants that
  TypeScript narrows with a `switch`.
- `Effect.mapError` turns a low-level error into one that means something to
  the caller.
- `NodeRuntime.runMain` is your run line now. It sets the exit code and turns
  Ctrl-C into an interruption.
- The cost is one more `provide` at the edge of the program. In
  [Writing tests with @effect/vitest](/learn/part-2/13-first-tests) you swap
  in a fake `FileSystem` for tests without changing this code.
