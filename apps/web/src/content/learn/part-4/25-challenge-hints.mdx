If you're stuck on
[pausing and resuming rules](/learn/part-4/24-independent-challenge),
start with the first hint below. Each hint reveals a little more of one
possible solution, so stop as soon as you have enough to try something in
your own code. The rest will still be here if you need it.

## 1. Keep the pause in the Engine

A pause has to affect both interval loops and incoming events, and the
Engine is already where those two kinds of work meet, in its `FiberMap` and
`handleEvent`. So store a set of paused rule ids in the Engine layer, where
both can check it.

No new run outcome is needed. A paused rule is never executed by event
dispatch or by an interval loop, so it gets no run-log row at all. An
explicit `rules run` is a different case and is not affected by the pause.

## 2. Pause and resume in the right order

Read `stop` before writing the pause method. It already shows how to
interrupt a loop and wait for its final run-log update. To pause an
interval rule, add its id to the paused set first, then interrupt its loop
the same way, so the rule already reads as paused while the interruption
completes.

To resume it, remove its id from the paused set, then call `start`.

For event rules, filter out paused ids in `handleEvent` before it calls
`execute`. Because `execute` is never reached, no `Engine.execute` span is
created either.

## 3. Show the pause in rules list

Someone reading `rules list` needs to see that a rule was paused on
purpose, not that it stopped. The `list` handler already asks the Engine's
`isRunning` for an interval rule's status, so add a similar method that
says whether a rule is paused. Check it first, so that `paused` wins over
`running` and `stopped`, and add the new literal to `ListedRule` in
`src/api/Api.ts`.

## 4. Add the endpoints

For the HTTP and CLI pieces, follow the path that removing a rule already
takes. Add `pause` and `resume` to the `rules` group in `src/api/Api.ts`,
next to `remove`:

- `POST /rules/:id/pause`
- `POST /rules/:id/resume`

Declare `RuleNotFound` as the 404 error of each one. In each handler, look
the rule up with `store.get` first, so an unknown id fails with
`RuleNotFound` exactly as `remove` does.

`ApiClient` derives client methods for both endpoints automatically. Call
them from the two new CLI commands, and handle `RuleNotFound` the way
`rules remove` does.

## 5. Use the existing test harness

All four tests fit on the harness from
[Running rules on a schedule with FiberMap](/learn/part-3/19-rules-on-a-clock),
so there is no new harness to write.

For the interval test, adapt that lesson's core test, replacing remove with
pause. Await `remote.arrived`, pause the rule, then use `TestClock.adjust`
to advance past `everySeconds`. Assert that `remote.requests.length` has
not grown and the run rows have not changed.

The resume check has one detail that is easy to miss: keep the poll pending
for this positive control too. Resuming starts the loop, and its first tick
runs immediately, creating one request and one `started` row. Advance past
one interval but stay below the 10 second timeout. Because the request is
still pending, the loop cannot begin a second tick, so you can assert
exactly one additional request and one additional row. If the poll had
completed, the clock adjustment could allow a second tick and the count
would be two.

For the event test, use the `HttpApiTest` client from the same lesson and
assert on the outcomes returned by `events.submit`.

For the unknown-id test, use `Effect.flip` on `pause` to inspect the
`RuleNotFound` error, as in
[Writing tests with @effect/vitest](/learn/part-2/13-first-tests).

## 6. Decide what a restart does

Keeping pauses in memory is fine for this challenge. Starting the server
already restarts stopped loops, so with this choice a restart resumes
paused rules too. Leave a comment saying so, so that someone reading the
code knows the behaviour is deliberate.

Preserving pauses across restarts would need a database column and a
migration, which is more than the challenge's 40 minutes allow.
