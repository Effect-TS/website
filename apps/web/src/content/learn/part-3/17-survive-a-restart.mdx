Reflex can now accept an expense over HTTP, apply a rule and show you a
trace of what happened. That is useful progress, but try restarting the
server and running `rules list`. Your rules are gone, and `runs list` is
empty too. Setting up the same expense alert every time we restart would
get old quickly.

Both stores currently use Maps, which lose their data when the process
ends. Let's give reflex somewhere lasting to keep its rules and history:
a SQLite file named `reflex.db`. We'll add SQL implementations of
`RuleStore` and `RunLog` and keep the memory versions for tests. The Engine,
API handlers and CLI already use those services, so they won't need to
know where the data lives.

## Open the database and create its tables

We need to open the file before either store can use it.
`SqliteClient.layer({ filename: "reflex.db" })` does that and
provides `SqlClient`, the service we'll use to run queries. This client
uses `node:sqlite`, so there is no native module to compile. It is also why
the course requires Node 22.16.

An empty file doesn't yet have anywhere to put a rule. The two SQL files in
`migrations/` define the tables. These are migrations: changes to the
database structure that we apply in order. `SqliteMigrator.layer` runs
them in numeric order and records which migrations have completed in its own
table. On the next startup, it runs only migrations that have not completed
yet. If you have not added any, there is nothing to run.

The custom loader is needed because the migrator's file loader imports
`.js` and `.ts` files, while this project supplies plain SQL. Here, loading a
migration means reading its file and running the statements inside it.

## Check what the runs table accepts

Let's look at one of those tables before writing to it. Open
`migrations/0002_runs.sql`. You'll recognize the fields from the run history.
There is also a `CHECK` on `reason`:

```text
reason TEXT CHECK (outcome <> 'failed' OR reason IN ('status', 'timeout', 'io'))
```

For a `failed` row, a non-null reason must be `status`, `timeout` or `io`.
For other outcomes, this constraint places no restriction on the reason.

It is tempting to read this as the same guarantee our schema gives us, but
there is a small difference. SQLite
accepts `NULL` as the result of a `CHECK`, so this expression also permits a
`failed` row with no reason. The `RunResult` schema is stricter: its `failed`
variant requires one of the three reasons. The Engine supplies that reason
when it writes a failed result; the database constraint alone would not
guarantee it.

Start by looking at a query. The `sql` template tag may look like ordinary
string interpolation, but interpolated values become query
parameters rather than SQL text, so a quote in a value cannot change the
query. For inserts, `sql.insert(row)` generates the column list and
parameterized values from an object.

A row from SQLite isn't automatically a value we can trust as a `Rule`.
We still need to convert between database values and the types the service
uses. `SqlSchema.findAll` encodes the request with its request
schema, runs the query, and decodes each returned row with its result schema.
`SqlSchema.void` encodes a request for a write that has no result to decode.

The rules table keeps each definition in a `definition_json` text column.
`Schema.fromJsonString(Rule)` encodes a `Rule` as JSON for that column and
parses and validates the text when reading it back. This uses the same
`Rule` schema as the API. If someone edits the database into an invalid rule,
decoding fails rather than returning an unchecked value to the Engine.

Compare `get` with the memory implementation. It takes the first row from
`findById` and, if there is none, returns
`yield* new RuleNotFound({ id })`. Callers still handle the same typed error.
Likewise, `remove` uses `RETURNING id` to distinguish a deleted rule from a
missing one.

Notice that database and decoding errors go through `Effect.orDie`. We're
making a choice about the service interface here. Callers handle a missing
rule, but are not
expected to recover from storage failures here. `orDie` converts those
failures to defects, which do not appear in the typed error channel. Thus
`create` still has no typed error, and the only typed error of `get` and
`remove` is `RuleNotFound`. A disk failure can still stop the operation.
[Telling errors from defects with Cause](/learn/part-3/20-an-action-over-the-network)
looks at defects more closely.

The run log uses the same query-and-schema approach. It stores UTC times as
ISO 8601 text, so ordering by that text also orders the runs by time.
`Schema.DateTimeUtcFromString` decodes those strings into `DateTime` values
when reading them. As in the memory store, `start` creates a run and
`finish` updates it; in SQL, that is an `INSERT` followed by an `UPDATE` of
the same row.

## Run the same tests against both stores

Before we rely on the new stores, let's check that they behave like the old
ones. Turn each store suite from
[Writing tests with @effect/vitest](/learn/part-2/13-first-tests) into a
function of a layer, with the tests inside unchanged:

```ts
(name, store) => layer(store, { buildPerTest: true })(name, (it) => ...)
```

Then call the function once for each store implementation. For SQLite,
provide `Migrations.layer` with
`SqliteClient.layer({ filename: ":memory:" })` so the database has its tables
before the tests use it. `buildPerTest` builds a fresh in-memory database for
each test, preventing one test's writes from affecting another.

Run `pnpm test`. The same assertions should pass for both implementations.
We've changed where the data lives without changing what callers can expect.

## Try it

There's one query we can make less wasteful.
`pnpm cli runs list --rule <id>` returns the right rows, but look at how
`RunLog.layerSql` produces them. It reads the whole `runs` table, then
filters and slices the results in TypeScript. Once interval rules are
running, that table can grow by thousands of rows a day. A request for two
runs should not need to read all of them. Move the filter and limit into
the SQL query:

1. Give the `findAll` query a request schema with the two options, `ruleId`
   and `limit`, so `execute` receives them.
2. Add the `WHERE` clause with `sql.and`, and `LIMIT ${limit ?? -1}`. In
   SQLite, a negative limit means no limit.
3. Run `pnpm test`. It stays green.
4. With the server running, run `pnpm cli runs list --rule <id> --limit 2`. It
   prints at most two rows, all for that rule.

The hint and the changed file are in `exercises/17/`. From the next lesson on,
the checkpoints include this change.

You no longer need to re-create an expense rule after every restart. There
is a little more to look after now, though. Changes to the table
structure will need new migrations, and the database file needs to be kept
if you want to retain the rules and history. Your server and the checkpoint
servers all use `reflex.db` in the project root. Delete that file only when
you want to start clean.

Persistence also makes an unfinished run visible after a restart.
[Running rules on a schedule with FiberMap](/learn/part-3/19-rules-on-a-clock)
will handle rows left by a process that stopped before recording a result.

## Checkpoint

Let's finish by repeating the restart that lost our data at the beginning.
Use checkpoint 17 to verify persistence. Start its server, then add a rule
and submit an event in a second terminal:

```sh
pnpm checkpoint 17 server
```

```sh
pnpm checkpoint 17 cli rules add fixtures/rules/expense.json
pnpm checkpoint 17 cli events submit fixtures/events/laptop.json
```

Stop the server with Ctrl-C and start it again with the same command. Then:

```sh
pnpm checkpoint 17 cli rules list
pnpm checkpoint 17 cli runs list
```

The rule and its `succeeded` run are still there. You can stop the server
for the day without losing the setup or the record of what it did.
