Amounts don't appear out of nowhere. In rulebook they arrive inside an
**event**, a small object that says what happened, like
`{ type: "expense", amount: 1200 }`. And events from the outside world aren't
always complete. A taxi receipt might arrive with a type but no amount at all.

What should rulebook say about an expense with no amount? Not "no alert". The
honest answer is "I couldn't check this one", and that answer is a failure.

You will learn:

- how to give a failure a name;
- how to fail an effect with it;
- how failures show up in the second slot of an Effect's type.

`isLarge` wants a number. TypeScript is asking the same question you are: what
should happen when there's no amount?

## Defining an error

The second slot of an Effect type is for exactly this: the ways the effect can
fail. You name a failure by declaring a class for it.

There's a lot of punctuation here, so take it one piece at a time.
`Schema.TaggedError` is called twice:

- The first call, `<MissingField>()`, is empty. It takes the class's own name
  in angle brackets, so the class can refer to its own type.
- The second call takes a **tag** and the **fields**. The tag, `"MissingField"`,
  is how you'll pick this failure out later. The fields say what the error
  carries, here the name of the missing `field` as a `Schema.String`.

Schema gets a lesson of its own in lesson 6. For now it only lists what the
error carries.

## Failing with the error

At the top of `program`, check for the amount. If it's missing, fail with
`return yield* new MissingField({ field: "amount" })`.

`yield*` fails the effect with that error. `return` tells TypeScript that this
path ends here. After the check, TypeScript knows `taxi.amount` is a number, so
the red underline goes away. Build the message from `taxi.type` and
`taxi.amount`, as you did from `amount` before.

Now the terminal reports a `MissingField` failure, and the program stops.
Hover `program`. Its type is `Effect<string, MissingField, never>`. The failure
is part of the type, so any code that uses `program` can see that it can fail,
and how.

## Try it: a second failure

An event could also be something other than an expense. Add a second failure,
`NotAnExpense`, declared the same way as `MissingField`, and fail with it when
the event's `type` isn't `"expense"`.

Hover `program` again. The second slot now reads
`MissingField | NotAnExpense`. Every failure you can produce joins that union.

This one is only for practice. The next lesson starts from the file without
`NotAnExpense`, so don't worry about keeping it.

## Recap

- An event is a small object that says what happened. Its fields can be
  missing.
- Give the failures you expect a name with `Schema.TaggedError`, and fail with
  `return yield* new MissingField(...)`.
- Failures show up in the second slot of the type, so callers can see them.
- The cost is a class per failure. In lesson 14 these classes travel over
  HTTP, and that's where the Schema inside them earns its keep.
