We've spent a few lessons deciding what a rule means and what to do when
something goes wrong. Now imagine having a dozen rules. We wouldn't want
to add another `evaluate` call to the program every time someone creates
one. We'd want reflex to get the current list and check them all.

For now, that list can live in memory. Later we'll store rules in SQLite
so they're still there after a restart. The expense check shouldn't need
to know which of those we're using; it just needs to ask for the rules.

We'll build that separation in two steps. Here we'll describe what the
program needs from a rule store and write code that uses it. In the next
lesson we'll actually supply the store. That means this lesson ends with
a type error, even in the solution. It's intentional: we'll see how Effect
keeps track of a dependency we haven't provided yet.

## Say what we need from a store

Our first store needs just one operation, `list`, to return all the rule
strings. In Effect we can describe this as a **service**: an interface for
something our program needs, identified by a key. Declaring it won't
choose where the rules live or how we read them.

The two-call pattern should look familiar from `Schema.TaggedError`.
This time the type arguments describe the class and the service's
interface. `list` is an Effect that succeeds with a readonly array of
JSON strings. That's enough information to write code that uses the
store, even though we haven't built one.

The string `"reflex/RuleStore"` in the second call is the service's key.
Keep it unique within the program so that it identifies this service
unambiguously.

## Find the missing dependency

Look at the last line, `NodeRuntime.runMain(program)`. It should be
underlined in red. If you try to run the file, the terminal reports the
type error rather than running the program. This is the stopping point
we planned, not a mistake to work around.

To find out why, hover over `evaluateAll`. Its return type is
`Effect<void, SchemaError, RuleStore>`. The third type parameter, which
has been `never` until now, is the **requirements type**. It lists the
services we still need to provide. By retrieving `RuleStore`, this
function has added a requirement for it.

Hover over `program` and you'll find the same requirement. It calls
`evaluateAll`, so it needs a store too. Now read the last line of the
error at `runMain`:
`Type 'RuleStore' is not assignable to type 'never'.`
`runMain` needs an Effect with no outstanding requirements, while this
one still needs its `RuleStore`.

We've described the store's operations but never supplied their
implementation. Even the Solve button leaves this error in place. In the
next lesson we'll make it disappear by providing a store, rather than by
changing the checking code.

## Before moving on

Try explaining the error in your own words: what have we promised about
`RuleStore`, and what do we still need to build? If the difference isn't
clear yet, compare the declaration of `list` with the call that uses it.
There's a type for the operation, but no code choosing which rules to return.

We've written a check that can use a store without committing to how the
rules are kept. Continue to
[Providing a service with a layer](/learn/part-1/09-provide-it), where we'll
build the first implementation and get our alerts back.
