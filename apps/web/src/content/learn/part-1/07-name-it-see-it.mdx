checks and error handling in `evaluate`; only its definition changes.

## Locating the failed call

Look at the malformed rule's failure in the terminal. Under the
`SchemaError` there is now a line that starts with `at evaluate (`. That is
the name you passed to `Effect.fn`. The line after it,
`at evaluate (definition)`, points at where you declared the function.

Each call to the named function runs inside a **span** named `evaluate`.
A span records an operation's name, start time, duration and outcome. The
failure printed by `runMain` includes the name, which connects the schema
error to the call that failed.

You do not see spans drawn as a timeline yet. That needs a trace viewer,
which you connect in
[Exporting traces with OtlpTracer](/learn/part-2/16-the-picture-you-already-know).

## Try it

The failure now identifies `evaluate`, but that function both decodes and
checks an expense. Give decoding its own name to see how nested calls
appear in the report:

1. Turn `decodeRule` into a function made with `Effect.fn("decodeRule")`
   that takes the JSON string and decodes it.
2. Run the file and read the failure. It names both steps: `at decodeRule`
   first, then `at evaluate` under it. The decode failed, and it was running
   inside `evaluate`.

Use names for operations you want to identify when investigating a failure
or reading a trace. There is no need to wrap every helper: `matches` can
remain a plain function. Recording spans has a runtime cost, and exporting
them later adds network traffic.
