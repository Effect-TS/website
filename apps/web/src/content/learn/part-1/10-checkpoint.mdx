We started with a single message about a laptop. Reflex can now read a set
of rules, check an expense against each one, and explain why it skipped an
incomplete receipt. The rules are separate from the checking code, and we
can change where they come from without rewriting that code. That is enough
of an application to take out of the browser.

Before we do, let's pause and read what we have. The editor contains the
completed file from the previous lesson. Run it once more and look for the
three alert lines and the three skips, then read through it at your own
pace. There is no new code in this lesson, apart from the optional
challenges at the end.

## The types in the file

When you first hovered over `program`, most of its type was unfamiliar. You
have now seen each part of `Effect<Success, Error, Requirements>` in use.
Read the file from top to bottom and predict the three types of each
function before you hover over it. Follow `RuleStore` in particular: where
does the program start needing it, and where do we supply it?

| Name           | Type                                                                 | Notes                                                         |
| -------------- | -------------------------------------------------------------------- | ------------------------------------------------------------- |
| `Rule`         | A schema, with `type Rule` derived from it                           | The hover shows the rule's fields                             |
| `decodeRule`   | Accepts unknown input and returns `Effect<Rule, SchemaError, never>` | Parses JSON text and validates the parsed rule                |
| `RuleStore`    | A service with static `layer` and `layerFixtures` members            | The service key is `reflex/RuleStore`                         |
| `MissingField` | An error class with a string property named `field`                  | Identifies the field missing from an event                    |
| `matches`      | `(rule: Rule, amount: number) => boolean`                            | Calculates the result without an Effect                       |
| `evaluate`     | Returns `Effect<boolean, SchemaError, never>`                        | Handles a missing amount but leaves an invalid rule unhandled |
| `evaluateAll`  | Returns `Effect<void, SchemaError, RuleStore>`                       | Requires a provided `RuleStore`                               |
| `program`      | `Effect<void, SchemaError, never>`                                   | Provides the store, leaving no service requirements           |

If one of the types surprises you, the reference below links to the lesson
that introduced it. You don't need to remember every API name. What matters
for the next part is being able to say what the expense check returns, how
it can fail, and where its rules come from.

## Optional challenges

If you'd like more practice before Part 2, try one of these. They aren't
counted in the course time, and nothing later depends on them.

1. Add `eq` and `neq` operators for "equal to" and "not equal to". Start
   with the schema, then update `matches` to handle the cases TypeScript
   reports as missing.
2. Make a skipped check distinguishable from one that didn't match. Instead
   of logging the skip and returning `false`, have `evaluate` return a
   `skipped` result with a reason. Hover to confirm that the success type
   now includes this result alongside `boolean`, since a completed check
   still returns `flagged`.
   [Recording runs with Effect.onExit](/learn/part-2/12-an-engine-that-records)
   does a version of this for real.
3. Add another kind of event, such as a battery level, and a rule for it.
   The current alert message reads `event.amount`, which will not suit
   every event. Adapt the message for an event that has no amount.
