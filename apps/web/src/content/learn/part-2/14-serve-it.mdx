`main.ts` builds an Engine, runs it once and exits, and the memory stores go
with it. That isn't how reflex should behave. You want to add a rule once and
have it stay. Events should arrive whenever they happen, from a script, a cron
job or a phone.

So the engine has to outlive any one command. In this lesson it becomes a
server: one process holding one Engine and its stores, answering HTTP.

You will learn:

- how to describe an HTTP API as a value with `HttpApi`;
- how to implement that API with handlers;
- how to run a server until it's stopped, with `Layer.launch`;
- how typed errors travel over HTTP.

## Defining the API

`HttpApi` describes the server before any of it runs. An **endpoint** is a
method, a path, and the schemas for what goes in and comes out. For example,
`HttpApiEndpoint.post("create", "/", { payload: Rule, success: StoredRule })`
creates a rule.

Endpoints are grouped, and the groups make up the API:

- `rules`: create, list, get, remove, and `POST /rules/:id/run` to run one
  rule against an event;
- `events`: `POST /events` submits an event to every matching rule;
- `runs`: `GET /runs?ruleId=&limit=` lists the run history.

Every schema here already exists in the domain. The API doesn't add any types
of its own.

## Writing the handlers

`HttpApiBuilder.group(Api, "rules", ...)` implements one group. Inside an
`Effect.fn`, you `yield*` the services you need. Then `handlers.handleAll({...})`
takes one function per endpoint.

Each handler gets the decoded `params`, `query` and `payload`. The compiler
checks what it returns against the endpoint's success schema, and how it fails
against the endpoint's declared errors. The handlers stay thin, each one a
single call into the services from lessons 12 and 13.

## Launching the server

The server program is layers all the way down:

- `HttpApiBuilder.layer(Api)` turns the handlers into routes;
- `HttpApiScalar.layer` adds documentation at `/docs`;
- `HttpRouter.serve` serves both;
- `NodeHttpServer.layer` listens on port 3000.

The Engine, the memory stores and `NodeServices.layer` are provided underneath.

A layer normally builds, hands over its services, and is done. A server has
nothing to hand over. It should just keep running. `Layer.launch` builds the
layer and keeps it running until the program is interrupted, which `runMain`
does when you press Ctrl-C.

## Revisit: errors over HTTP

`get`, `remove` and `run` declare `RuleNotFound` as their error, with
`HttpApiSchema.status(404)`. The handler fails with the same `RuleNotFound`
that the store fails with, and the server sends it as a 404 with the error as
the body. Try `curl -i localhost:3000/rules/nope`. It answers `404 Not Found`
with:

```text
{"_tag":"RuleNotFound","id":"nope"}
```

A request that doesn't match a schema never reaches a handler at all. A rule
without an action, or `limit=abc`, gets a 400 from the decoder.

In lesson 15, the client decodes that 404 back into a `RuleNotFound`.

## Try it: validate the limit

`GET /runs?limit=-1` comes back with every run except the oldest, because
`RunLog.list` hands the number straight to `slice`. `limit=1.5` is accepted
too. The schema lets through numbers that aren't a count.

Make `limit` a whole number greater than 0 in the `runs` query, with
`Schema.Int.check(Schema.isGreaterThan(0))`. Notice that nothing in the
handlers or in `RunLog` has to change.

To check your work, start `pnpm dev:server`. Then
`curl -i 'localhost:3000/runs?limit=-1'` and `limit=1.5` should answer 400,
and `limit=2` should answer 200. The hint and the changed file are in
`exercises/14/`. From lesson 15 on, the checkpoints include this change.

## Recap

- The API is one value. Handlers implement it group by group.
- Typed errors declared on an endpoint travel over HTTP with a status code.
- Input that doesn't match a schema is rejected before any handler runs.
- `Layer.launch` runs a server until it's interrupted.
- The cost is a second process to keep running, and a memory store that resets
  with it. Lesson 15 derives a client from the same value, and lesson 17 adds
  stores that survive a restart.

## Checkpoint

Start the checkpoint's server. Then, in a second terminal, create a rule,
submit an event, and read the run:

```sh
pnpm checkpoint 14
```

```sh
curl -X POST localhost:3000/rules -H 'content-type: application/json' -d @fixtures/rules/expense.json
curl -X POST localhost:3000/events -H 'content-type: application/json' -d @fixtures/events/laptop.json
curl localhost:3000/runs
```

The event answers with one `succeeded` outcome, and `GET /runs` shows the row.
[http://localhost:3000/docs](http://localhost:3000/docs) renders the API
documentation.
