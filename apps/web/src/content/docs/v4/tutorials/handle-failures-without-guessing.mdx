<TutorialPainPoint title="Failures become unknown">

Backend operations can fail for different reasons, take too long, or continue
after the client disconnects. With ordinary Promise code, these behaviors
require separate conventions, while rejections reach `catch` as `unknown`.

With Effect, the **type system** tracks expected failures, while retry limits,
timeouts, and cancellation are defined directly on the operation.

</TutorialPainPoint>

## What you will build

The example is a `POST /orders` endpoint that calls a payment provider. It
starts by turning every rejected Promise into the same `500` response. Each
step makes one failure decision explicit until the finished backend behaves as
follows:

| Provider behavior                   | Decision                          | HTTP result |
| ----------------------------------- | --------------------------------- | ----------- |
| Payment succeeds                    | Accept the order                  | `201`       |
| Card is declined                    | Do not retry                      | `422`       |
| Provider is temporarily unavailable | Retry at most twice               | `201`/`503` |
| Provider fails unexpectedly         | Do not guess                      | `502`       |
| Provider takes too long             | Interrupt and retry at most twice | `504`       |
| Client disconnects                  | Interrupt the complete operation  | No response |

## Project setup

The project uses two files:

| File         | Role                                                                     |
| ------------ | ------------------------------------------------------------------------ |
| `fixture.ts` | Fixed fixture that provides the HTTP server and payment SDK simulation.  |
| `server.ts`  | Contains the order-processing code that the tutorial gradually improves. |

```ts title="fixture.ts"
// This fixed fixture does not change during the tutorial.
import { createServer } from "node:http"
import { setTimeout as sleep } from "node:timers/promises"

// Values exchanged between the HTTP fixture and server.ts.
export interface PlaceOrderInput {
  readonly customerId: string
  readonly paymentToken: string
}

export interface HttpResult {
  readonly status: number
  readonly body: unknown
}

export const json = (status: number, body: unknown): HttpResult => ({
  status,
  body,
})

// Expose the order handler as POST /orders.
export const startServer = (
  placeOrder: (
    input: PlaceOrderInput,
    signal: AbortSignal,
  ) => Promise<HttpResult>,
): void => {
  const server = createServer(async (request, response) => {
    const send = (result: HttpResult): void => {
      response.writeHead(result.status, { "content-type": "application/json" })
      response.end(JSON.stringify(result.body))
    }

    if (request.method !== "POST" || request.url !== "/orders") {
      send(json(404, { error: "NotFound" }))
      return
    }

    // Cancel the order when the client disconnects before receiving a response.
    const controller = new AbortController()
    response.once("close", () => {
      if (!response.writableEnded) controller.abort()
    })

    try {
      let body = ""
      for await (const chunk of request) body += chunk
      const result = await placeOrder(
        JSON.parse(body) as PlaceOrderInput,
        controller.signal,
      )
      send(result)
    } catch (cause) {
      if (controller.signal.aborted) return
      console.error(cause)
      send(json(500, { error: "InternalServerError" }))
    }
  })

  server.listen(3000, () => console.log("Listening on http://localhost:3000"))
}

export class PaymentDeclinedSdkError extends Error {}
export class ProviderUnavailableSdkError extends Error {}

let flakyAttempts = 0

// A deterministic simulation of a Promise-based payment SDK.
export const authorizePayment = async (
  token: string,
  { signal }: { readonly signal?: AbortSignal } = {},
) => {
  const attempt = token === "tok_flaky" ? ++flakyAttempts : 1
  console.log(`primary-pay authorization attempt ${attempt}`)

  if (token === "tok_declined") throw new PaymentDeclinedSdkError()
  if (token === "tok_unexpected")
    throw new Error("undocumented provider failure")
  // The flaky case recovers on its third call so retries are repeatable.
  if (token === "tok_flaky" && attempt < 3)
    throw new ProviderUnavailableSdkError()

  signal?.addEventListener(
    "abort",
    () => console.log("primary-pay authorization aborted"),
    {
      once: true,
    },
  )
  // Passing the signal makes the simulated provider latency cancellable.
  await sleep(token === "tok_slow" ? 2_000 : 80, undefined, { signal })

  if (token === "tok_flaky") flakyAttempts = 0
  return { provider: "primary-pay" }
}
```

Run the server with `--watch`. This option reloads `server.ts` after each saved
edit, so the same process can remain running throughout the tutorial:

```sh title="Watched server"
node --watch server.ts
```

In a second terminal pane, change `paymentToken` to select a provider behavior:

| Value            | Provider behavior                              |
| ---------------- | ---------------------------------------------- |
| `tok_approved`   | Approves the payment.                          |
| `tok_declined`   | Declines the payment.                          |
| `tok_flaky`      | Reports two temporary failures, then succeeds. |
| `tok_unexpected` | Reports an undocumented failure.               |
| `tok_slow`       | Takes two seconds to respond.                  |

```sh title="Successful order request"
  -H 'content-type: application/json' \
  -d '{"customerId":"customer-123","paymentToken":"tok_approved"}'
```

## The solution, step by step

### 1. A familiar Promise baseline

The initial `server.ts` uses conventional `async`/`await` to handle an order. It
calls the payment provider and decides which HTTP response to return:

```ts title="server.ts"
import {
  authorizePayment,
  json,
  startServer,
  type PlaceOrderInput,
} from "./fixture.ts"

const placeOrder = async (input: PlaceOrderInput) => {
  try {
    const payment = await authorizePayment(input.paymentToken)
    return json(201, {
      orderId: `order-${input.customerId}`,
      status: "accepted",
      paymentProvider: payment.provider,
    })
  } catch {
    // Every provider rejection produces the same response.
    return json(500, { error: "InternalServerError" })
  }
}

startServer(placeOrder)
```

This is a reasonable TypeScript starting point. An approved payment returns
`201`, but every rejection crosses the same `catch` boundary:

| Token            | Actual cause                  | HTTP result |
| ---------------- | ----------------------------- | ----------- |
| `tok_declined`   | Final business decision       | `500`       |
| `tok_flaky`      | Temporary provider outage     | `500`       |
| `tok_unexpected` | Undocumented provider failure | `500`       |

The problem is not that the endpoint fails. It is that the code has discarded
the information needed to decide whether a failure should be retried, exposed,
or treated as unexpected.

### 2. The provider call becomes an Effect description

[`Effect.tryPromise`](/docs/v4/api/effect/Effect#tryPromise) adapts the
Promise-producing provider without changing its observable behavior. The
complete current file is:

```ts title="server.ts" ins={1,9-11,15}
import { Effect } from "effect"
import {
  authorizePayment,
  json,
  startServer,
  type PlaceOrderInput,
} from "./fixture.ts"

// Describe the provider call without starting it.
const authorize = (token: string) =>
  Effect.tryPromise((signal) => authorizePayment(token, { signal }))

const placeOrder = async (input: PlaceOrderInput) => {
  try {
    const payment = await Effect.runPromise(authorize(input.paymentToken))
    return json(201, {
      orderId: `order-${input.customerId}`,
      status: "accepted",
      paymentProvider: payment.provider,
    })
  } catch {
    // Every provider rejection produces the same response.
    return json(500, { error: "InternalServerError" })
  }
}

startServer(placeOrder)
```

`authorize(input.paymentToken)` creates a value describing the provider call.
It does not call the provider yet. Its inferred type can be read as:

```ts title="Inferred type, not code to copy"
Effect.Effect<{ readonly provider: string }, Cause.UnknownError>
```

The first type argument is the success value. The second is the error channel,
which records expected ways the computation may fail. This description has no
service requirements, so its third type argument is omitted.

`Effect.tryPromise` adapts a function that returns a Promise. The function
remains lazy, resolved values become successes, and rejections enter the error
channel. Its `AbortSignal` is passed to the provider Promise.

The type [`Effect.Effect`](/docs/v4/api/effect/Effect#Effect) represents a value
that describes a computation. Here the success value is the provider result and
the error channel contains
[`Cause.UnknownError`](/docs/v4/api/effect/Cause#UnknownError-interface),
Effect's wrapper for an unclassified Promise rejection. Its `cause` field
preserves the original rejected value.

[`Effect.runPromise`](/docs/v4/api/effect/Effect#runPromise) runs the described
computation at the HTTP boundary and returns a Promise. That Promise resolves
with the success value and rejects if the Effect does not succeed.

The outer `try`/`catch` still turns every rejection into `500`. The benefit at
this stage is structural: the provider operation is now a lazy description,
and Effect has a channel in which more precise failures can be recorded.

### 3. Provider failures become explicit

The provider SDK exposes two error classes. `toPaymentError` translates those
classes at the boundary and gives every other rejection a safe, explicit name:

```ts title="server.ts" ins={1,5-6,11-15,17-23,27-30}
import { Data, Effect } from "effect"
import {
  authorizePayment,
  json,
  PaymentDeclinedSdkError,
  ProviderUnavailableSdkError,
  startServer,
  type PlaceOrderInput,
} from "./fixture.ts"

class PaymentDeclined extends Data.TaggedError("PaymentDeclined") {}
class ProviderUnavailable extends Data.TaggedError("ProviderUnavailable") {}
class UnexpectedPaymentProviderError extends Data.TaggedError(
  "UnexpectedPaymentProviderError",
)<{
  readonly cause: unknown
}> {}

// Convert SDK errors into the errors handled by server.ts.
const toPaymentError = (cause: unknown) => {
  if (cause instanceof PaymentDeclinedSdkError) return new PaymentDeclined()
  if (cause instanceof ProviderUnavailableSdkError)
    return new ProviderUnavailable()
  return new UnexpectedPaymentProviderError({ cause })
}

// Describe the provider call without starting it.
const authorize = (token: string) =>
  Effect.tryPromise({
    try: (signal) => authorizePayment(token, { signal }),
    catch: toPaymentError,
  })

const placeOrder = async (input: PlaceOrderInput) => {
  try {
    const payment = await Effect.runPromise(authorize(input.paymentToken))
    return json(201, {
      orderId: `order-${input.customerId}`,
      status: "accepted",
      paymentProvider: payment.provider,
    })
  } catch {
    // Every provider rejection produces the same response.
    return json(500, { error: "InternalServerError" })
  }
}

startServer(placeOrder)
```

The inferred error channel is now concrete:

```ts title="Inferred type, not code to copy"
Effect.Effect<
  { readonly provider: string },
  PaymentDeclined | ProviderUnavailable | UnexpectedPaymentProviderError
>
```

[`Data.TaggedError`](/docs/v4/api/effect/Data#TaggedError) creates a typed error
class. The string becomes the `_tag`; the optional type argument defines the
constructor fields.
`UnexpectedPaymentProviderError` therefore keeps the original rejection in
`cause`.

`_tag` is Effect's ubiquitous convention for distinguishing variants. It lets
TypeScript narrow the union without inspecting error messages or provider
implementation details.

The HTTP result is still `500` because the outer `catch` has not yet been
replaced. The important change is that the computation now preserves the
reason it failed.

<TutorialCheckpoint
  number={3}
  total={7}
  title="Every provider rejection has a name"
>
  The error channel distinguishes a decline, a temporary outage, and an
  unexpected provider failure before any HTTP decision is made.
</TutorialCheckpoint>

### 4. Every expected outcome becomes an HTTP result

The next version moves the successful result and all three expected failures
into the Effect description:

```ts title="server.ts" ins={32-50,52}
import { Data, Effect } from "effect"
import {
  authorizePayment,
  json,
  PaymentDeclinedSdkError,
  ProviderUnavailableSdkError,
  startServer,
  type PlaceOrderInput,
} from "./fixture.ts"

class PaymentDeclined extends Data.TaggedError("PaymentDeclined") {}
class ProviderUnavailable extends Data.TaggedError("ProviderUnavailable") {}
class UnexpectedPaymentProviderError extends Data.TaggedError(
  "UnexpectedPaymentProviderError",
)<{
  readonly cause: unknown
}> {}

// Convert SDK errors into the errors handled by server.ts.
const toPaymentError = (cause: unknown) => {
  if (cause instanceof PaymentDeclinedSdkError) return new PaymentDeclined()
  if (cause instanceof ProviderUnavailableSdkError)
    return new ProviderUnavailable()
  return new UnexpectedPaymentProviderError({ cause })
}

// Describe the provider call without starting it.
const authorize = (token: string) =>
  Effect.tryPromise({
    try: (signal) => authorizePayment(token, { signal }),
    catch: toPaymentError,
  })

// Convert every expected outcome into an HTTP response.
const placeOrder = (input: PlaceOrderInput) =>
  authorize(input.paymentToken).pipe(
    Effect.map((payment) =>
      json(201, {
        orderId: `order-${input.customerId}`,
        status: "accepted",
        paymentProvider: payment.provider,
      }),
    ),
    Effect.catchTags({
      PaymentDeclined: () =>
        Effect.succeed(json(422, { error: "PaymentDeclined" })),
      ProviderUnavailable: () =>
        Effect.succeed(json(503, { error: "ProviderUnavailable" })),
      UnexpectedPaymentProviderError: () =>
        Effect.succeed(json(502, { error: "UnexpectedPaymentProviderError" })),
    }),
  )

startServer((input) => Effect.runPromise(placeOrder(input)))
```

`pipe` passes the description through each transformation from top to bottom.
It builds a new description and does not run it.

[`Effect.map`](/docs/v4/api/effect/Effect#map) transforms the success channel
with a function and leaves the error channel unchanged. Here the provider
result becomes a `201` `HttpResult`.

[`Effect.catchTags`](/docs/v4/api/effect/Effect#catchTags) selects failures by
`_tag`. Each handler returns an Effect, and a handler that succeeds removes its
matching failure from the error channel. These handlers use
[`Effect.succeed`](/docs/v4/api/effect/Effect#succeed) to describe a computation
that succeeds with an already available HTTP result.

All expected outcomes now become successful `HttpResult` values before
`Effect.runPromise` reaches the HTTP server:

| Token            | HTTP result | Body                                         |
| ---------------- | ----------- | -------------------------------------------- |
| `tok_approved`   | `201`       | accepted order                               |
| `tok_declined`   | `422`       | `{"error":"PaymentDeclined"}`                |
| `tok_flaky`      | `503`       | `{"error":"ProviderUnavailable"}`            |
| `tok_unexpected` | `502`       | `{"error":"UnexpectedPaymentProviderError"}` |

An unexpected bug in the program is different from these expected failures.
Effect calls such a bug a defect. A defect still rejects `runPromise`, and the
stable HTTP support converts it to a real `500` rather than pretending it was a
provider decision.

<TutorialCheckpoint
  number={4}
  total={7}
  title="HTTP decisions follow typed failures"
>
  The endpoint returns `422`, `503`, or `502` from explicit error variants. The
  generic `500` remains reserved for unexpected bugs.
</TutorialCheckpoint>

### 5. Only recoverable failures are retried

A temporary outage may recover, while a declined payment or unexpected failure
must remain final. `Effect.retry` expresses that policy without a loop:

```ts title="server.ts" ins={35-39}
import { Data, Effect } from "effect"
import {
  authorizePayment,
  json,
  PaymentDeclinedSdkError,
  ProviderUnavailableSdkError,
  startServer,
  type PlaceOrderInput,
} from "./fixture.ts"

class PaymentDeclined extends Data.TaggedError("PaymentDeclined") {}
class ProviderUnavailable extends Data.TaggedError("ProviderUnavailable") {}
class UnexpectedPaymentProviderError extends Data.TaggedError(
  "UnexpectedPaymentProviderError",
)<{
  readonly cause: unknown
}> {}

// Convert SDK errors into the errors handled by server.ts.
const toPaymentError = (cause: unknown) => {
  if (cause instanceof PaymentDeclinedSdkError) return new PaymentDeclined()
  if (cause instanceof ProviderUnavailableSdkError)
    return new ProviderUnavailable()
  return new UnexpectedPaymentProviderError({ cause })
}

// Describe the provider call without starting it.
const authorize = (token: string) =>
  Effect.tryPromise({
    try: (signal) => authorizePayment(token, { signal }),
    catch: toPaymentError,
  })

// Convert every expected outcome into an HTTP response.
const placeOrder = (input: PlaceOrderInput) =>
  authorize(input.paymentToken).pipe(
    // Retry only failures that may recover on another attempt.
    Effect.retry({
      times: 2,
      while: (error) => error._tag === "ProviderUnavailable",
    }),
    Effect.map((payment) =>
      json(201, {
        orderId: `order-${input.customerId}`,
        status: "accepted",
        paymentProvider: payment.provider,
      }),
    ),
    Effect.catchTags({
      PaymentDeclined: () =>
        Effect.succeed(json(422, { error: "PaymentDeclined" })),
      ProviderUnavailable: () =>
        Effect.succeed(json(503, { error: "ProviderUnavailable" })),
      UnexpectedPaymentProviderError: () =>
        Effect.succeed(json(502, { error: "UnexpectedPaymentProviderError" })),
    }),
  )

startServer((input) => Effect.runPromise(placeOrder(input)))
```

[`Effect.retry`](/docs/v4/api/effect/Effect#retry) reruns the preceding
computation after selected failures. `times: 2` allows two retries after the
initial attempt, and `while` admits only `ProviderUnavailable`.

The fixture fails twice for `tok_flaky` and then succeeds. The endpoint returns
`201` after exactly three authorization attempts. `tok_declined` and
`tok_unexpected` still run only once because their tags do not satisfy the
predicate.

<TutorialCheckpoint
  number={5}
  total={7}
  title="Retries follow the recovery policy"
>
  A temporary outage gets at most three total attempts. A decline and an
  unexpected provider failure are never retried.
</TutorialCheckpoint>

### 6. Every attempt has a timeout

`tok_slow` takes two seconds. Without a timeout, one slow attempt can hold the
request open indefinitely. The timeout belongs before `Effect.retry`, so each
attempt receives the same 250 millisecond bound:

```ts title="server.ts" ins={13,36-40,44-46,60-61}
import { Data, Effect } from "effect"
import {
  authorizePayment,
  json,
  PaymentDeclinedSdkError,
  ProviderUnavailableSdkError,
  startServer,
  type PlaceOrderInput,
} from "./fixture.ts"

class PaymentDeclined extends Data.TaggedError("PaymentDeclined") {}
class ProviderUnavailable extends Data.TaggedError("ProviderUnavailable") {}
class PaymentTimedOut extends Data.TaggedError("PaymentTimedOut") {}
class UnexpectedPaymentProviderError extends Data.TaggedError(
  "UnexpectedPaymentProviderError",
)<{
  readonly cause: unknown
}> {}

// Convert SDK errors into the errors handled by server.ts.
const toPaymentError = (cause: unknown) => {
  if (cause instanceof PaymentDeclinedSdkError) return new PaymentDeclined()
  if (cause instanceof ProviderUnavailableSdkError)
    return new ProviderUnavailable()
  return new UnexpectedPaymentProviderError({ cause })
}

// Describe the provider call without starting it.
const authorize = (token: string) =>
  Effect.tryPromise({
    try: (signal) => authorizePayment(token, { signal }),
    catch: toPaymentError,
  })

// Convert every expected outcome into an HTTP response.
const placeOrder = (input: PlaceOrderInput) =>
  authorize(input.paymentToken).pipe(
    // Limit each authorization attempt, not the complete request.
    Effect.timeoutOrElse({
      duration: "250 millis",
      orElse: () => Effect.fail(new PaymentTimedOut()),
    }),
    // Retry only failures that may recover on another attempt.
    Effect.retry({
      times: 2,
      while: (error) =>
        error._tag === "ProviderUnavailable" ||
        error._tag === "PaymentTimedOut",
    }),
    Effect.map((payment) =>
      json(201, {
        orderId: `order-${input.customerId}`,
        status: "accepted",
        paymentProvider: payment.provider,
      }),
    ),
    Effect.catchTags({
      PaymentDeclined: () =>
        Effect.succeed(json(422, { error: "PaymentDeclined" })),
      ProviderUnavailable: () =>
        Effect.succeed(json(503, { error: "ProviderUnavailable" })),
      PaymentTimedOut: () =>
        Effect.succeed(json(504, { error: "PaymentTimedOut" })),
      UnexpectedPaymentProviderError: () =>
        Effect.succeed(json(502, { error: "UnexpectedPaymentProviderError" })),
    }),
  )

startServer((input) => Effect.runPromise(placeOrder(input)))
```

[`Effect.timeoutOrElse`](/docs/v4/api/effect/Effect#timeoutOrElse) gives the
preceding computation a time limit. When the limit wins, it interrupts that
attempt and runs the fallback Effect returned by `orElse`.

The fallback uses [`Effect.fail`](/docs/v4/api/effect/Effect#fail) to describe a
computation that fails when it runs. It does not throw while the description is
being built; it places `PaymentTimedOut` in the error channel.

For `tok_slow`, each timeout interrupts the active provider Promise through the
signal supplied by `Effect.tryPromise`. The retry predicate allows two more
attempts, then `Effect.catchTags` turns the final `PaymentTimedOut` into `504`.

```text title="Observable server log"
primary-pay authorization attempt 1
primary-pay authorization aborted
primary-pay authorization attempt 1
primary-pay authorization aborted
primary-pay authorization attempt 1
primary-pay authorization aborted
```

  number={6}
  total={7}
  title="Slow attempts share one fixed budget"
>
  Every provider attempt is limited to 250 milliseconds. Three timed-out
  attempts produce one `504` response.
</TutorialCheckpoint>

### 7. A disconnected client stops the work

`fixture.ts` already turns a closed HTTP response into an `AbortSignal`.
The final change supplies that signal to `Effect.runPromise`:

```ts title="server.ts" ins={67-68}
import { Data, Effect } from "effect"

  authorizePayment,
  json,

        orderId: `order-${input.customerId}`,
        status: "accepted",
        paymentProvider: payment.provider,
      }),
    ),
    Effect.catchTags({
      PaymentDeclined: () =>
        Effect.succeed(json(422, { error: "PaymentDeclined" })),
      ProviderUnavailable: () =>
        Effect.succeed(json(503, { error: "ProviderUnavailable" })),
      PaymentTimedOut: () =>
        Effect.succeed(json(504, { error: "PaymentTimedOut" })),
      UnexpectedPaymentProviderError: () =>
        Effect.succeed(json(502, { error: "UnexpectedPaymentProviderError" })),
    }),
  )

// Forward client disconnection to the running Effect.
startServer((input, signal) => Effect.runPromise(placeOrder(input), { signal }))
```

The optional `signal` accepted by `Effect.runPromise` observes cancellation
from outside Effect. When the client disconnects, the complete running
computation is interrupted, and the signal inside `Effect.tryPromise` aborts
the provider Promise.

Interruption is cancellation of a running computation. It is neither a success
nor a typed failure, so it does not become `PaymentTimedOut` and does not enter
the retry predicate.

For a local run, a client can disconnect before `tok_slow` completes:

```sh title="Cancellation request"
curl --max-time 0.1 -sS http://localhost:3000/orders \
  -H 'content-type: application/json' \
  -d '{"customerId":"customer-123","paymentToken":"tok_slow"}'
```

The provider logs one attempt followed by `primary-pay authorization aborted`.
No retry begins because the external signal stopped the complete operation,
rather than producing a retryable error.

## The final boundary

The finished `placeOrder` describes every expected provider outcome. It is
still a value until `Effect.runPromise` executes it once at the HTTP boundary.

That separation leaves three distinct concepts:

- the success channel contains the HTTP result;
- the error channel drives retry and response decisions before becoming empty;
- interruption stops the running computation without pretending to be either
  a business failure or a timeout.

The HTTP support retains one ordinary `try`/`catch` for malformed input and
unexpected bugs. It does not reinterpret either as a payment decision.
