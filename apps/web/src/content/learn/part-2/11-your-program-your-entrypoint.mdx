## The FileSystem service

Reading those files and appending to `alerts.log` needs the file system. Effect
ships it as a service, `FileSystem.FileSystem`, and you use it exactly like
`RuleStore` in lesson 8:

- `const fs = yield* FileSystem.FileSystem` puts it in the third slot of
  whatever uses it.
- `fs.readFileString(path)` reads a file.
- `fs.writeFileString(path, text, { flag: "a" })` appends, creating the file
  when it is missing.

Both fail with a `PlatformError` when the disk says no.

Something has to provide the service. `NodeServices.layer` from
`@effect/platform-node` is a layer with Node's implementation of `FileSystem`
and the other services the platform ships. Lesson 13 replaces it with a fake
file system for tests, without changing the code that uses it.

## Your own run line

In Part 1 the two run lines were supplied, with a note that `runMain` is
Part 2. This is Part 2. `NodeRuntime.runMain` runs the program, keeps the
process alive until it is done, and sets the exit code: 0 on success, 1 on
failure. It also turns Ctrl-C into an interruption, which lesson 18 relies on.

The run line has three steps:

1. Print a typed error as one line with `Effect.tapError`. It runs an effect on
   the failure and passes the failure on unchanged.
2. `Effect.provide(NodeServices.layer)`, so the program has its `FileSystem`.
3. `NodeRuntime.runMain({ disableErrorReporting: true })`, because the error
   was already printed.

The lesson 10 run line also provided `Telemetry.layer`. That is the part Part 1
hid from you: the wiring that sent spans and logs to the trace panel. Leave it
out of the new run line. Your spans still exist, but nothing exports them until
lesson 16, where you write `Telemetry.ts` yourself.

## Revisit: a schema with variants

The lesson 6 schema had one shape. A real rule has variants: a trigger is an
`event` or an `interval`, and an action is `appendFile` or `httpPost`. Each
variant is a `Schema.Struct` with a `type` literal, and `Schema.Union` joins
them. Because every variant has a different `type`, TypeScript narrows on it,
so in `case "appendFile":` the compiler knows `rule.action.path` exists.

The condition grows too. `field` is now a dotted path such as `body.status`,
the fifth operator `contains` is in, and `lookup` fails with `MissingField`
when a key on the path is absent.

<LessonCode file="checkpoints/11/src/Rule.ts" />

`httpPost` decodes now so rule files can use it, but `run-once.ts` only logs
that it arrives in lesson 20.

## Revisit: errors you can name

A `PlatformError` from `writeFileString` is the file system's error, with the
file system's vocabulary. The rule's caller wants to know that the action did
not happen. `Effect.mapError` turns one into the other: an `ActionFailed` with
the reason `io` and the original message. `io` is one of three reasons a failed
action can have; `status` and `timeout` arrive with `httpPost` in lesson 20.

## Exercise

Every alert line reads like `expense 1200 over 500`, because `alertLine`
builds it from the event. The rule files already say what they want written:
`"message": "expense over 500"`. Make the action write the rule's message:

1. Add `message: Schema.String` to the `AppendFile` struct.
2. In the `appendFile` case, hover `rule.action.message`: it is a `string`.
   Write it instead of the built line.
3. Delete `alertLine`, which has no caller left, and `words` with it.
4. Remove `message` from a copy of the rule file, run it, and read the error.
   It names the missing key and its path.

Check: `pnpm tsx src/run-once.ts fixtures/rules/expense.json fixtures/events/laptop.json`
appends `expense over 500` to `alerts.log`. The hint and the changed files are
in `exercises/11/`. From lesson 12 on, the checkpoints include this change.
