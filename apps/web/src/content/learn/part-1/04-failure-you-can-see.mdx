The laptop and lunch were straightforward to check because we knew what
each one cost. Let's try a less tidy receipt. This time it's a taxi ride,
and the amount is missing.

Reflex can't honestly say whether that ride was over our limit. Treating
it as `false` would make "we couldn't check" look the same as "we checked
and it was fine." We need to keep those two situations separate.

In this lesson we'll have the check fail with an error that tells us what
was missing. Seeing the program stop is part of the exercise, so don't
worry when we lose the summary. Once we can recognize this failure, we'll
be able to decide how to recover from it in the next lesson.

`Argument of type 'number | undefined' is not assignable to parameter of type 'number'`.

why it can't continue.

## Describe what went wrong

We'll use an error called `MissingField`, with a property recording the
field's name. Add `Schema` to the `effect` import, then place this
class between the interface and the two expenses:

<LessonCode
  file="lessons/part1/04-failure-you-can-see/solution/main.ts"
  declaration="MissingField"
/>

There's a little syntax to unpack here. `Schema.TaggedError` defines an
error class in two calls: `<MissingField>()` supplies the class's own
type, and the next call gives it the tag `"MissingField"` and its fields.
The tag identifies the kind of error; `field` tells us which value was
missing. `Schema.String` means that property is a string.

For now, that's all we need from Schema. We'll return to it when we start
reading rules from JSON.

## Stop when the amount is missing

At the top of the `Effect.gen` block in `evaluate`, check for the amount. If
it is missing, fail:

<LessonCode
  file="lessons/part1/04-failure-you-can-see/solution/main.ts"
  declaration="evaluate"
/>

You can yield a `Schema.TaggedError` directly to fail the Effect. Here,
`return yield* new MissingField({ field: "amount" })` fails with the error
you just defined. The `return` also makes the end of this path explicit to
TypeScript. After the check, it can narrow `event.amount` to `number`, and
the red underline disappears.

## See where the program stops

Run the file. The laptop still produces `expense 1200 over 500`. Then the
taxi produces a `MissingField` failure, and there's no
`1 of 2 expenses flagged` summary. We haven't told reflex how to recover,
so it stops at `yield* evaluate(taxi)` rather than inventing a result for
that receipt.

Now hover over `evaluate`. Its type is
`(event: Event) => Effect<boolean, MissingField, never>`. Remember the
error type we passed over in the first lesson? It's the second parameter.
It was `never`, meaning no typed failures; now it's `MissingField`, telling a caller that
the check can either succeed with a boolean or fail with this error.

Hover over `program` too. Its type is `Effect<void, MissingField, never>`.
It doesn't create the error itself, but because it runs `evaluate`, the
same failure can reach it. We can follow the failure through the types as
well as through the output.

## Try it

An amount isn't the only thing we might need to check. Try rejecting an
event whose type isn't `"expense"`, and watch what happens to the error
type:

1. Declare a second error, `NotAnExpense`, the same way as `MissingField`.
   Give it a `type` field.
2. At the top of the `Effect.gen` block in `evaluate`, fail with it when
   `event.type` is not `"expense"`.
3. Hover `evaluate`. The error type now lists both errors, as a union such
   as `NotAnExpense | MissingField`. Both typed failures are included, and
   `program` shows the same union.

This extra check is just for practice; the next lesson starts without
`NotAnExpense`.

The missing amount is no longer being mistaken for a small expense. We
know what went wrong, and reflex stops rather than quietly reporting the
wrong result. Next we'll make it more useful: keep that explanation,
skip the incomplete receipt, and let the rest of the program continue.
