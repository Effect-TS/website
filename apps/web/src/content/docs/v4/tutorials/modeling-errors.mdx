Thrown errors work, but they hide one thing: when you call a function,
**what can fail**?

This tutorial shows how Effect makes each error part of a function's return type,
so TypeScript tracks it through every caller.

You use two functions throughout the tutorial:

| Function           | Description                                      |
| ------------------ | ------------------------------------------------ |
| `authorizePayment` | Authorizes the payment.                          |
| `processPayment`   | Calls `authorizePayment` and handles the result. |

`authorizePayment` can fail three ways:

- The card is expired.
- The token is not valid.
- The provider is unreachable.

Keep those three in mind. Each one becomes visible to TypeScript later.

## Thrown errors are invisible

A function signature says what it needs and what it returns. It says nothing about what can fail.

The tutorial simulates a sandbox with payment tokens. Each token gives a
predictable result:

| Token               | Result                              |
| ------------------- | ----------------------------------- |
| `"tok_authorized"`  | The provider authorizes the payment |
| `"tok_declined"`    | The provider declines the payment   |
| `"tok_expiredcard"` | The card is expired                 |
| `"tok_invalid"`     | The token is not valid              |
| `"tok_timeout"`     | The provider is unreachable         |

Here is a common version of the payment step without Effect:

```ts twoslash import.meta.vitest
class NetworkError extends Error {}

class ExpiredCardError extends Error {}

class InvalidTokenError extends Error {}

interface Authorization {
  readonly id: string
  readonly status: "authorized" | "declined"
}

// Tutorial fixture: sandbox tokens make results reproducible
type PaymentToken =
  | "tok_authorized"
  | "tok_declined"
  | "tok_expiredcard"
  | "tok_invalid"
  | "tok_timeout"

const authorizePayment = async (
  token: PaymentToken,
): Promise<Authorization> => {
  if (token === "tok_timeout") {
    throw new NetworkError()
  }

  if (token === "tok_expiredcard") {
    throw new ExpiredCardError()
  }

  if (token === "tok_invalid") {
    throw new InvalidTokenError()
  }

  if (token === "tok_declined") {
    return { id: "pauth_456", status: "declined" }
  }

  if (token === "tok_authorized") {
    return { id: "pauth_123", status: "authorized" }
  }

  throw new InvalidTokenError()
}

const processPayment = async (token: PaymentToken) => {
  try {
    const payment = await authorizePayment("tok_declined")
  } catch (error) {
    //     └─ `unknown`
    if (error instanceof InvalidTokenError) {
      // ...
    }

    if (error instanceof ExpiredCardError) {
      // ...
    }

    if (error instanceof NetworkError) {
      // ...
    }
  }
}
```

Each `throw` matches one of the three errors listed above.

The payment goes through. `Promise` says nothing about failure.

To find out what can fail, you have to read the implementation, or the docs if
they exist and haven't drifted from it. Either way, the signature never shows it.

{/* prettier-ignore */}
```ts showLineNumbers=false
//                       ┌─ Needs `token`
//                       │                       ┌─ Returns `Authorization`
//                       ▼                       ▼
const authorizePayment: (token: PaymentToken) => Promise<Authorization>
//                                               └─ How can it fail?
```

Worse, TypeScript can't tell you any of this. Error handling here has four problems:

1. **Blindness**: `error` is `unknown`, so TypeScript cannot see which errors
   `authorizePayment` throws.
1. **Over-specification**: TypeScript compiles even if `authorizePayment` never throws it.
1. **Under-specification**: forgetting to handle an error in `processPayment` that `authorizePayment` does throw still compiles.
1. **Drift**: when `authorizePayment` starts throwing a new error later, `processPayment` still compiles, and the error can reach production.

## Make each error visible to TypeScript

A signature answers three questions for a caller:

1. What the function needs.
1. What it returns on success.
1. How it can fail.

`authorizePayment` answers only the first two.

Imagine a signature that named its errors:

{/* prettier-ignore */}
```ts showLineNumbers=false
// /!\ Not real TypeScript.
const authorizePayment: (token: PaymentToken) => Promise<Authorization> throws
  ExpiredCardError | NetworkError | InvalidTokenError
```

TypeScript has no `throws` clause. But a return type can take a second type parameter for the error.

Meet Effect. `Effect<Success, Error>` describes a program that either succeeds with a `Success` or fails with an `Error`, answering all three questions:

{/* prettier-ignore */}
```ts showLineNumbers=false
//                       ┌─ What the function needs
//                       │                              ┌─ What it returns on success
//                       │                              │              ┌─ How it can fail
//                       ▼                              ▼              ▼
const authorizePayment: (token: PaymentToken) => Effect<Authorization, ExpiredCardError | NetworkError | InvalidTokenError>
```

When the program fails, the error stays in the return type. TypeScript tracks it
through every caller.

These are the **expected errors**: failures a caller can handle, named in the `Error` type parameter.

Effect uses two conventions for typed errors:

- An `Error` suffix on the class, to tell an error from a success immediately.
- A `_tag` property, unique to each error, so TypeScript can tell them apart.

`Data.TaggedError` supplies the `_tag` from its argument. The class name carries
the suffix:

{/* prettier-ignore */}
```ts import.meta.vitest showLineNumbers=false mark=/class \w+(Error)|TaggedError[(](.InvalidTokenError.)[)]|[.](_tag)/
import { Data } from "effect"

//                ┌─ `Error` suffix
//                │                               ┌─ `_tag` property value
//                ▼                               ▼
class InvalidTokenError extends Data.TaggedError("InvalidTokenError") {}

const error = new InvalidTokenError()
error._tag // => "InvalidTokenError"
```

{/* prettier-ignore */}
{/*
Without a `_tag`, two classes that extend `Error` stay identical:

```ts twoslash
import { Effect } from "effect"

class NetworkError extends Error {}
class ExpiredCardError extends Error {}

// You put two errors in the `Error` type parameter...
declare const program: Effect.Effect<string, NetworkError | ExpiredCardError>

// ...but this compiles: to TypeScript the two are one type.
const oneError: Effect.Effect<string, NetworkError> = program
```

`_tag` is what keeps the errors distinct. Both classes have the same shape, so
TypeScript compares them structurally and drops `ExpiredCardError` out of the
union. The result is the "why did my other error disappear?" confusion that
trips up beginners. Add a `_tag` to each and the assignment stops compiling.
Every error becomes its own member of the union.
\*/}

<Aside type="tip" title="Why use a class?">
  In TypeScript a class is both a type _and_ a value. One declaration gives you
  the error type to name in a signature and the constructor to build it.
</Aside>

Refactor the three error classes to `Data.TaggedError`:

```ts twoslash import.meta.vitest {3,5,7}
  | "tok_declined"
  | "tok_expiredcard"
  | "tok_invalid"
  | "tok_timeout"

  token: PaymentToken,

  if (token === "tok_timeout") {
    throw new NetworkError()
  }

  if (token === "tok_expiredcard") {
    throw new ExpiredCardError()
  }

  if (token === "tok_invalid") {
    throw new InvalidTokenError()
  }

  if (token === "tok_declined") {
    return { id: "pauth_456", status: "declined" }
  }

  return { id: "pauth_123", status: "authorized" }
}

  } catch (error) {

  }

```

<Aside type="note" title="Checkpoint">
  Each error is now a class from `Data.TaggedError`. The classes are the members
  of an `Effect`'s `Error` type parameter union.
</Aside>

## Return errors instead of throwing them

Now you build the program with Effect. An `Effect` is lazily executed: creating one doesn't run it. It describes a program that can succeed or fail.

Here is the same two-step program, first with a `Promise`, then with an `Effect`:

**Promise**

Same shape, three swaps:

- `async function` becomes `Effect.gen(function* ...)`
- `await` becomes `yield*`
- `await program()` becomes `await Effect.runPromise(program)`

If a step returns an error, the rest do not run, the same way a thrown error stops an `async`
function.

Now refactor `authorizePayment` with Effect.

`return yield*` returns the same way as a success, and the rest of the `Effect` stops.
There is no `throw` and no outer `catch`. The error gets added the `Error` type parameter,
where TypeScript tracks it:

```ts twoslash
import { Effect, Data } from "effect"

interface Authorization {
  readonly id: string
  readonly status: "authorized" | "declined"
}

class NetworkError extends Data.TaggedError("NetworkError") {}

class ExpiredCardError extends Data.TaggedError("ExpiredCardError") {}

class InvalidTokenError extends Data.TaggedError("InvalidTokenError") {}

type PaymentToken =
  | "tok_authorized"
  | "tok_declined"
  | "tok_expiredcard"
  | "tok_invalid"
  | "tok_timeout"
// ---cut---
const authorizePayment = (
  token: PaymentToken,
): Effect.Effect<
  Authorization,
  NetworkError | ExpiredCardError | InvalidTokenError
> =>
  Effect.gen(function* () {
    if (token === "tok_timeout") {
      return yield* new NetworkError()
    }

    if (token === "tok_expiredcard") {
      return yield* new ExpiredCardError()
    }

    if (token === "tok_invalid") {
      return yield* new InvalidTokenError()
    }

    if (token === "tok_declined") {
      return { id: "pauth_456", status: "declined" }
    }

    return { id: "pauth_123", status: "authorized" }
  })
```

Refactor `processPayment` with Effect. Now calls `authorizePayment` and returns its result. It
inherits the three errors, so it sees them:

```ts import.meta.vitest twoslash
import { Effect, Data } from "effect"

interface Authorization {
  readonly id: string
  readonly status: "authorized" | "declined"
}

class NetworkError extends Data.TaggedError("NetworkError") {}

class ExpiredCardError extends Data.TaggedError("ExpiredCardError") {}

type PaymentToken =
  | "tok_authorized"
  | "tok_declined"
  | "tok_expiredcard"
  | "tok_invalid"
  | "tok_timeout"

const authorizePayment = (
  token: PaymentToken,
): Effect.Effect<
  Authorization,
  NetworkError | ExpiredCardError | InvalidTokenError
> =>
  Effect.gen(function* () {
    if (token === "tok_timeout") {
      return yield* new NetworkError()
    }

    if (token === "tok_expiredcard") {
      return yield* new ExpiredCardError()
    }

    if (token === "tok_invalid") {
      return yield* new InvalidTokenError()
    }

    if (token === "tok_declined") {
      return { id: "pauth_456", status: "declined" }
    }

    return { id: "pauth_123", status: "authorized" }
  })
// ---cut---
//    ┌─ (token: PaymentToken) => Effect.Effect<Authorization, NetworkError | ExpiredCardError | InvalidTokenError>
//    ▼
const processPayment = (token: PaymentToken) =>
  Effect.gen(function* () {
    const authorization = yield* authorizePayment(token)

    return authorization
  })

await Effect.runPromise(processPayment("tok_authorized")) // => { id: "pauth_123", status: "authorized" }
```

TypeScript inferred the `Error` type parameter as the union of the three errors
you return.

<Aside type="tip" title="More delegation to TypeScript">
  TypeScript infers both type parameters from the steps you build, so you rarely
  write an `Effect` signature by hand.
</Aside>

<Aside type="note" title="Checkpoint">
  You now build the work with `Effect.gen`, take each success with `yield*`, and
  fail by returning a tagged error with `return yield*`.
</Aside>

## Handle the expected errors you modeled

The signature of `authorizePayment` lists the expected errors. The caller uses the list to handle them.

`Effect.catchTag` takes the `_tag` of one error and a handler. The handler is an `Effect` that receives the typed error as a parameter, not `unknown`.

The example uses method `.pipe` (available to every `Effect`), to apply the handler to the `Effect`, like method chaining:

```ts twoslash import.meta.vitest
import { Effect, Data } from "effect"

interface Authorization {
  readonly id: string
  readonly status: "authorized" | "declined"
}

class NetworkError extends Data.TaggedError("NetworkError") {}
class ExpiredCardError extends Data.TaggedError("ExpiredCardError") {}
class InvalidTokenError extends Data.TaggedError("InvalidTokenError") {}

type PaymentToken =
  | "tok_authorized"
  | "tok_declined"
  | "tok_expiredcard"
  | "tok_invalid"
  | "tok_timeout"

const processPayment = (
  token: PaymentToken,
): Effect.Effect<
  Authorization,
  ExpiredCardError | InvalidTokenError | NetworkError
> =>
  Effect.gen(function* () {
    if (token === "tok_expiredcard") {
      return yield* new ExpiredCardError()
    }

    if (token === "tok_invalid") {
      return yield* new InvalidTokenError()
    }

    if (token === "tok_timeout") {
      return yield* new NetworkError()
    }

    return { id: "pauth_123", status: "authorized" }
  })
// ---cut---
const outcome = processPayment("tok_expiredcard").pipe(
  Effect.catchTag("ExpiredCardError", (error) =>
    //                                 └─ `ExpiredCardError`
    Effect.succeed("Card expired, ask for another"),
  ),
)

await Effect.runPromise(outcome) // => "Card expired, ask for another"
```

The handled error leaves the `Error` type parameter. The others stay:

{/* prettier-ignore */}
```ts showLineNumbers=false
//                                    ┌─ `ExpiredCardError` is removed
//                                    ▼
Effect.Effect<string | Authorization, InvalidTokenError | NetworkError>
```

<Aside type="note" title="Success type widens too">
  The handler returns `Effect.succeed("Card expired, ask for another")`, a
  `string`, while the original success was an `Authorization`.

So the `Success` type parameter now covers both: `string | Authorization`.

</Aside>

TypeScript now has another job: it won't compile a handler for a `_tag` that isn't in the union.

`Effect.catchTags` (notice the `s` at the end) handles several errors at once with one table: an object keyed by `_tag`.

For each `_tag`, its handler receives the typed error:

```ts twoslash import.meta.vitest
import { Effect, Data } from "effect"

interface Authorization {
  readonly id: string
  readonly status: "authorized" | "declined"
}

class NetworkError extends Data.TaggedError("NetworkError") {}
class ExpiredCardError extends Data.TaggedError("ExpiredCardError") {}
class InvalidTokenError extends Data.TaggedError("InvalidTokenError") {}

type PaymentToken =
  | "tok_authorized"
  | "tok_declined"
  | "tok_expiredcard"
  | "tok_invalid"
  | "tok_timeout"

const processPayment = (
  token: PaymentToken,
): Effect.Effect<
  Authorization,
  ExpiredCardError | InvalidTokenError | NetworkError
> =>
  Effect.gen(function* () {
    if (token === "tok_expiredcard") {
      return yield* new ExpiredCardError()
    }

    if (token === "tok_invalid") {
      return yield* new InvalidTokenError()
    }

    if (token === "tok_timeout") {
      return yield* new NetworkError()
    }

    return { id: "pauth_123", status: "authorized" }
  })
// ---cut---
const outcome = processPayment("tok_timeout").pipe(
  Effect.catchTags({
    //             ┌─ `NetworkError`
    //             ▼
    NetworkError: (error) => Effect.succeed("Provider unreachable, try again"),

    //                 ┌─ `ExpiredCardError`
    //                 ▼
    ExpiredCardError: (error) =>
      Effect.succeed("Card expired, ask for another"),
  }),
)

await Effect.runPromise(outcome) // => "Provider unreachable, try again"
```

Two more rules TypeScript enforces:

1. Every key must be a `_tag` from the union. A typo does not compile.
1. The result keeps what the table misses: `Effect.Effect<Authorization, InvalidTokenError>`.

When all the errors are handled, the `Error` type parameter becomes `never`:

```ts twoslash import.meta.vitest showLineNumbers=false
import { Effect, Data } from "effect"

interface Authorization {
  readonly id: string
  readonly status: "authorized" | "declined"
}

class NetworkError extends Data.TaggedError("NetworkError") {}
class ExpiredCardError extends Data.TaggedError("ExpiredCardError") {}
class InvalidTokenError extends Data.TaggedError("InvalidTokenError") {}

type PaymentToken =
  | "tok_authorized"
  | "tok_declined"
  | "tok_expiredcard"
  | "tok_invalid"
  | "tok_timeout"

declare const processPayment: (
  token: PaymentToken,
) => Effect.Effect<
  Authorization,
  ExpiredCardError | InvalidTokenError | NetworkError
>
// ---cut---
//    ┌─ (token: PaymentToken) => Effect.Effect<string | Authorization, never>
//    ▼
const handle = (token: PaymentToken) =>
  processPayment(token).pipe(
    Effect.catchTags({
      NetworkError: () => Effect.succeed("..."),
      ExpiredCardError: () => Effect.succeed("..."),
      InvalidTokenError: () => Effect.succeed("..."),
    }),
  )
```

<Aside type="note" title="Why `never`?">
  `never` is TypeScript's empty type: the union with no members left. Each
  handled tag drops out of the union, and once the last one is gone there is
  nothing to name, so the type is `never`. It is the type-level way of saying
  "this can no longer fail."
</Aside>

## Modeling unexpected errors: defects

Every error so far is one a caller can respond to. These are expected errors. But `never` does not mean the code cannot fail.

Some conditions must always hold, or the payment step charges a customer wrong. Each is an invariant:

- An authorization is captured once, never twice.
- The provider returns a status its contract promises.

When one breaks, no handler can respond, so the safe action is to stop and report.

Effect calls a failure like this an **unexpected error**, or a **defect**: an impossible state, a broken invariant, or a bug in third-party code.

Unlike an expected error, a defect is not tracked in the `Error` type parameter; the runtime records it in a `Cause`.

The capture step enforces the first invariant. The ledger fixture starts with
the payment already captured, so this run is the retry, and the invariant
breaks.

No caller can undo a double capture, so a typed error would promise a handler
that cannot exist. The step dies instead: `Effect.die` sends the error to the
`Cause`, and the `Error` type parameter stays empty.

```ts twoslash import.meta.vitest collapse={3-12,18-45} ins={14-16}
import { Data, Effect } from "effect"

interface Authorization {
  readonly id: string
  readonly status: "authorized" | "declined"
}

class NetworkError extends Data.TaggedError("NetworkError") {}

class ExpiredCardError extends Data.TaggedError("ExpiredCardError") {}

class InvalidTokenError extends Data.TaggedError("InvalidTokenError") {}

class DoubleCaptureError extends Data.TaggedError("DoubleCaptureError")<{
  readonly id: string
}> {}

type PaymentToken =
  | "tok_authorized"
  | "tok_declined"
  | "tok_expiredcard"
  | "tok_invalid"
  | "tok_timeout"

const processPayment = (
  token: PaymentToken,
): Effect.Effect<
  Authorization,
  ExpiredCardError | InvalidTokenError | NetworkError
> =>
  Effect.gen(function* () {
    if (token === "tok_expiredcard") {
      return yield* new ExpiredCardError()
    }

    if (token === "tok_invalid") {
      return yield* new InvalidTokenError()
    }

    if (token === "tok_timeout") {
      return yield* new NetworkError()
    }

    return { id: "pauth_123", status: "authorized" }
  })

// Tutorial fixture: an in-memory ledger, so captures are reproducible.
// The first attempt already captured the payment. This run is the retry.
const captured = new Set(["pauth_123"])

//    ┌─ Effect.Effect<Authorization>: no `Error` type parameter
//    ▼
const capturePayment = (
  authorization: Authorization,
): Effect.Effect<Authorization> =>
  Effect.gen(function* () {
    if (captured.has(authorization.id)) {
      // Invariant broken: the step dies instead of failing with a
      // typed error no caller could handle.
      return yield* Effect.die(
        new DoubleCaptureError({
          id: authorization.id,
        }),
      )
    }

    captured.add(authorization.id)

    return authorization
  })

const program = Effect.gen(function* () {
  const payment = yield* processPayment("tok_authorized")

  return yield* capturePayment(payment).pipe(
    Effect.catchDefect((defect) =>
      defect instanceof DoubleCaptureError
        ? Effect.succeed(`terminated: ${defect.id} already captured`)
        : Effect.die(defect),
    ),
  )
})

await Effect.runPromise(program) // => "terminated: pauth_123 already captured"
```

The signature promises `Effect.Effect<Authorization>` with no `Error` type
parameter, yet the double capture fails the run. The failure never entered the
type: it became a defect, and `Effect.catchDefect` caught it. Without that
handler, `Effect.runPromise` rejects. Unknown defects stay fatal, so the handler
re-raises them with `Effect.die`.

### Remove errors no caller can handle from the type

`Effect.orDie` is a modeling decision: no caller can do anything with these
errors, so stop tracking them. Every typed error becomes a defect, and the
`Error` type parameter disappears.

Apply it at the boundary between your Effect code and its callers: inside, the
code still fails with typed errors, but the signature the caller sees has none
left.

```ts twoslash import.meta.vitest
import { Effect, Data } from "effect"

interface Authorization {
  readonly id: string
  readonly status: "authorized" | "declined"
}

class NetworkError extends Data.TaggedError("NetworkError") {}
class ExpiredCardError extends Data.TaggedError("ExpiredCardError") {}
class InvalidTokenError extends Data.TaggedError("InvalidTokenError") {}

type PaymentToken =
  | "tok_authorized"
  | "tok_declined"
  | "tok_expiredcard"
  | "tok_invalid"
  | "tok_timeout"

const processPayment = (
  token: PaymentToken,
): Effect.Effect<
  Authorization,
  ExpiredCardError | InvalidTokenError | NetworkError
> =>
  Effect.gen(function* () {
    if (token === "tok_expiredcard") {
      return yield* new ExpiredCardError()
    }

    if (token === "tok_invalid") {
      return yield* new InvalidTokenError()
    }

    if (token === "tok_timeout") {
      return yield* new NetworkError()
    }

    return { id: "pauth_123", status: "authorized" }
  })
// ---cut---
//    ┌─ Effect.Effect<Authorization>: `Error` type parameter is gone
//    ▼
const reconcile = processPayment("tok_expiredcard").pipe(Effect.orDie)

try {
  await Effect.runPromise(reconcile)
} catch (defect) {
  defect instanceof ExpiredCardError && defect._tag // => "ExpiredCardError"
}
```

A nightly reconciliation job is one such boundary: when the card is expired, the
job crashes and alerts whoever owns it. The failure crossed the boundary as a
defect, so `Effect.runPromise` rejected with the `ExpiredCardError` itself.

### Handle defects at the application boundary

A defect is a bug. A handler cannot fix it. But the boundary decides what
happens next, once, in one place: the job runner, the HTTP handler, the batch
loop. For each defect, ask:

1. Could a caller respond to this? Then it is not a bug. Model it as a typed
   error: a class with a `_tag`, named in the `Error` type parameter.
1. Is it a bug? Report it, and let the program terminate.
1. Can the program continue without it? Catch it, report it, and go on.

Inside the program, defects stay fatal. Only the boundary decides.

`Effect.catchDefect` handles defects only. The next example shows that typed
errors pass through unchanged.

```ts twoslash import.meta.vitest
import { Effect, Data } from "effect"

interface Authorization {
  readonly id: string
  readonly status: "authorized" | "declined"
}

class NetworkError extends Data.TaggedError("NetworkError") {}
class ExpiredCardError extends Data.TaggedError("ExpiredCardError") {}
class InvalidTokenError extends Data.TaggedError("InvalidTokenError") {}
class DoubleCaptureError extends Data.TaggedError("DoubleCaptureError")<{
  readonly authorizationId: string
}> {}

type PaymentToken =
  | "tok_authorized"
  | "tok_declined"
  | "tok_expiredcard"
  | "tok_invalid"
  | "tok_timeout"

const processPayment = (
  token: PaymentToken,
): Effect.Effect<
  Authorization,
  ExpiredCardError | InvalidTokenError | NetworkError
> =>
  Effect.gen(function* () {
    if (token === "tok_expiredcard") {
      return yield* new ExpiredCardError()
    }

    if (token === "tok_invalid") {
      return yield* new InvalidTokenError()
    }

    if (token === "tok_timeout") {
      return yield* new NetworkError()
    }

    return { id: "pauth_123", status: "authorized" }
  })
// ---cut---
const outcome = processPayment("tok_expiredcard").pipe(
  Effect.catchDefect((defect) =>
    defect instanceof DoubleCaptureError
      ? Effect.succeed(`reported: ${defect.authorizationId} already captured`)
      : Effect.die(defect),
  ),
)

try {
  await Effect.runPromise(outcome)
} catch (failure) {
  failure instanceof ExpiredCardError && failure._tag // => "ExpiredCardError"
}
```

The `catchDefect` handler never ran. `catch (failure)`, not `catch (defect)`:
the typed error was never a defect. It reached `runPromise` untouched,
exactly as its type said, with all three members still in the `Error` type
parameter.

A rule of thumb for the whole section:

- Prefer the typed operators for the errors you modeled: `Effect.catchTag`
  and `Effect.catchTags`.
- Use `Effect.catchDefect` only where handling the unexpected is
  intentional and safe.

<Aside type="note" title="Checkpoint">
  "Did I cover every case?" has two answers now. For the errors you modeled, the
  `Error` type parameter answers: it shrinks as you handle them. For the ones
  you didn't, the boundary answers: `catchDefect` sees them at the edge, where
  you report them and let the program terminate.
</Aside>

## Let's review what we built

You can now do five things. Each one maps to an operator you used.

- Read an `Effect` signature as a contract. The `Success` type parameter names the result, and the `Error` type parameter names every error a caller can handle.
- Make each error visible to TypeScript with `Data.TaggedError`, so TypeScript tracks it instead of losing it as `unknown` in a `catch`.
- Return errors instead of throwing them. Inside `Effect.gen`, fail with `return yield* new XError()`, and the `Error` type parameter tracks each one.
- Handle one `_tag` with `Effect.catchTag`, and many with `Effect.catchTags`. Each handled tag leaves the `Error` union. An empty union is `never`.
- Keep defects apart from typed errors. `Effect.die` records a defect in the `Cause`. `Effect.catchDefect` handles defects at the boundary. `Effect.orDie` converts tracked errors you no longer handle.
