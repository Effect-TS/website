## The Collapsed Block

Remember the code we hid at the end of Part 4? Here's what was inside:

<ul class="[&>li]:my-0 [&>li>p]:my-0">
  <li>
    A `dad_inbox` table, so messages could be saved in the same transaction that
    marked them processed
  </li>
  <li>
    A `dad_jokes` table, so a joke could be written down before it was posted
  </li>
  <li>A `posted` flag, so Dad could tell which jokes made it to Slack</li>
  <li>
    A loop, every 500 milliseconds, to post anything left over from a crash
  </li>
  <li>`keepAlive` calls, so Dad wouldn't fall asleep with work still to do</li>
</ul>

Every one of those lines exists to answer the same question: _after a crash, what did I already do?_

Now imagine Dad gets a new feature. Say he should check whether anyone laughed. That's another step, so it needs another flag, another "did I already do this?" check, and another branch in the loop. Every step we add comes with its own bookkeeping, and the bookkeeping is the part that's easy to get wrong.

What we really want is for something else to remember what Dad has already done.

<DadSays>I don't need a to-do list. I need a done list.</DadSays>

## Recipes

Let's forget about computers for a minute and make pancakes.

You've got a recipe with five steps. Halfway through, the doorbell rings. You answer it, sign for a package, and come back to the kitchen. Where do you start?

If you've been ticking off each step as you finish it, it's easy. You start at the top of the recipe again, but before you do each step, you check whether it's ticked. If it is, you skip it. The first step without a tick is where you pick up.

Click **Step** to work through the recipe, and keep an ear out for the doorbell.

<RecipeVisual />

Without the ticks, you'd have no idea how far you got. You'd start again from the top, do every step again, and end up with six eggs in the bowl.

The recipe is the same either way. So is the doorbell. The only difference is that you wrote down what you'd finished.

That's a **workflow**: a list of steps, plus a journal of which steps are done.

## Dad's Recipe

Before we write any code, let's write Dad's recipe out in plain English. When a batch of messages comes in, he:

<ol class="[&>li]:my-0 [&>li>p]:my-0">
  <li>Writes a joke he hasn't told in this chat</li>
  <li>Posts it</li>
</ol>

That's the whole thing. Here it is as a workflow:

```ts showLineNumbers=false
import { Schema } from "effect"
import { Workflow } from "effect/workflow"

const Message = Schema.Struct({
  messageId: Schema.String,
  from: Schema.String,
  text: Schema.String,
})

export const TellJoke = Workflow.make("TellJoke", {
  payload: {
    // Which chat, and the batch of messages the joke is about
    chat: Schema.String,
    messages: Schema.Array(Message),
  },
  // Same batch, same execution
  idempotencyKey: ({ chat, messages }) => `${chat}/${messages[0]!.messageId}`,
})
```

`Workflow.make` looks a lot like `Entity.make`. There's a name, and a schema for the payload, which cluster uses to save the payload to the database.

The new part is `idempotencyKey`. Every time you run `TellJoke`, Workflow turns the key into an **execution ID**. Run it twice with the same key and you get the same execution, not a second one. It's the elevator button from [Part 4](/blog/module-of-the-week/cluster-idempotency#idempotency) again. Press it as many times as you like and you still get one elevator.

<ReaderAsks>Why only the first message's ID? Why not all of them?</ReaderAsks>

Because Slack's IDs never change, and neither does which message came first in a batch. We'll see why that matters when we hook Dad up to the workflow.

## Activities

Each step in the recipe becomes an **activity**: an effect with a name, whose result goes in the journal.

```ts showLineNumbers=false
import { Effect, Schema } from "effect"
import { ClusterSchema } from "effect/cluster"
import { SqlClient } from "effect/sql"
import { Activity } from "effect/workflow"

export const TellJokeLayer = TellJoke.toLayer(
  Effect.fn(function* ({ chat, messages }) {
    const punGenerator = yield* PunGenerator
    const slack = yield* Chat
    const sql = yield* SqlClient.SqlClient

    // Step 1: write a joke he hasn't told in this chat
    const joke = yield* Activity.make({
      name: "WriteJoke",
      // The journal saves the joke, so it needs a schema
      success: Schema.String,
      execute: Effect.gen(function* () {
        const notebook = yield* sql<{ joke: string }>`
          SELECT joke FROM dad_jokes WHERE chat = ${chat}
        `
        const joke = yield* punGenerator.generate(messages, {
          told: new Set(notebook.map((row) => row.joke)),
        })
        yield* sql`INSERT INTO dad_jokes ${sql.insert({ chat, joke })}`
        return joke
      }).pipe(Effect.orDie),
    }).annotate(ClusterSchema.WithTransaction, true)

    // Step 2: tell it
    yield* Activity.make({
      name: "PostJoke",
      execute: slack.reply(chat, joke),
    })
  }),
)
```

Two activities, run in order. Compare that to the collapsed block from last week.

`WriteJoke` is worth a closer look. The pun generator is random. Ask it about the same messages twice and you'll get two different jokes. Last week, that's exactly why Dad had to write each joke down in `dad_jokes` before posting it.

An activity's result goes in the journal, so `WriteJoke` only ever comes up with one joke per execution. After a crash, Dad doesn't ask for a new one. He reads the one he already wrote.

The `WithTransaction` annotation should look familiar from Part 4. It runs the activity inside the same transaction that writes its result to the journal. Either the joke goes in `dad_jokes` _and_ in the journal, or neither happens. The same rule from Part 4 applies, too: `dad_jokes` has to live in the same database as cluster's tables.

## Replaying

So how does Dad pick up where he left off after a crash? This is the part people usually get wrong, so let's go slowly.

<ReaderAsks>
  I'm guessing the workflow saves which line it was on, and jumps back there?
</ReaderAsks>

That would be nice, but JavaScript can't jump into the middle of a function. So a workflow does something simpler. It runs again, **from the top**.

Every activity checks the journal before it does anything. If the journal already has a result for it, the activity returns that result straight away, without running. If not, it runs for real, and its result goes in the journal.

Click **Step** to run the workflow, and keep stepping after the crash.

<ReplayVisual />

After a crash, the workflow ran from the top again. `WriteJoke` was in the journal, so it handed back the same joke without asking the pun generator. Only the steps that hadn't finished actually ran.

This has one consequence you need to remember.

<Aside type="caution" title="Everything outside an activity runs again">
  <p>
    Code outside an activity runs again on every replay. If you call
    `Math.random()` or read the clock outside an activity, the replay can take a
    different path from the first run. Anything random, and anything that
    touches the outside world, goes inside an activity.
  </p>
</Aside>

## Hooking Dad Up

Now let's give Dad's entity its job back. All he does now is collect a batch, start a workflow, and reply to the messages in the batch:

```ts showLineNumbers=false collapse={8-15}
export const DadLayer = Dad.toLayerQueue(
  Effect.gen(function* () {
    const address = yield* Entity.CurrentAddress

    return (mailbox, replier) => {
      // Wait for the chat to go quiet for 2.5 seconds, same as Part 3
      const nextBatch = Effect.gen(function* () {
        const batch = [yield* Queue.take(mailbox)]
        while (true) {
          const next = yield* Queue.take(mailbox).pipe(
            Effect.timeoutOption("2500 millis"),
          )
          if (Option.isNone(next)) return batch
          batch.push(next.value)
        }
      })

      return Effect.gen(function* () {
        const batch = yield* nextBatch

        // Hand the joke to a workflow. With `discard: true`, this returns as
        // soon as the workflow is saved, not when the joke is told.
        yield* TellJoke.execute(
          {
            chat: address.entityId,
            messages: batch.map((request) => request.payload),
          },
          { discard: true },
        )

        // The workflow's saved, so it's safe to mark the batch processed
        yield* Effect.forEach(batch, (request) =>
          replier.succeed(request, undefined),
        )
      }).pipe(Effect.forever)
    }
  }),
)
```

The inbox table is gone, and so are the outbox, the polling loop, and the `keepAlive` calls. Dad's messages are still persisted, and they still use Slack's `ts` as their primary key, so Slack's retries are still caught. The `WithTransaction` annotation moved off `NewMessage` and onto `WriteJoke`, the only step that writes to our database.

Workflow does need an engine to run on, and since we already have a cluster, we'll use that:

```ts showLineNumbers=false
const MainLayer = Layer.mergeAll(DadLayer, TellJokeLayer).pipe(
  Layer.provide(ServicesLayer),
  // Runs workflows on the cluster we already have
  Layer.provideMerge(ClusterWorkflowEngine.layer),
  Layer.provideMerge(ClusterLayer),
)
```

Let's do one last crash, between `execute` and the replies. The workflow is saved, but none of the messages are marked processed.

Cluster delivers the batch to Dad again, just like in Part 3. Dad calls `TellJoke.execute` again, and the first message in the batch is the same as before, so the idempotency key is the same, and so is the execution ID. Workflow sees it's already running that execution and doesn't start a second one. Dad replies, the batch is marked processed, and there's still only one joke in the chat.

That's why we keyed on the first message. Persisted messages from Part 3 make sure the batch comes back after a crash. Idempotency keys from Part 4 make sure it only starts one workflow.

<Aside title="Squeezing into a batch">
  <p>
    If a new message arrives while Dad is restarting, it can end up in the
    redelivered batch. That batch has the same key, so the message gets marked
    processed without being part of the joke. Dad can live with that. He's
    ignored worse. Ask Sebastian.
  </p>
</Aside>

## Sleeping

So far, Workflow has mostly replaced code we already had. Now let's use it for something that would have been a real pain last week.

Dad has a new rule: **if nobody laughs within an hour, he explains the joke.**

```ts showLineNumbers=false collapse={8-26}
import { Effect, Schema } from "effect"
import { ClusterSchema } from "effect/cluster"
import { SqlClient } from "effect/sql"
import { Activity, DurableClock } from "effect/workflow"

export const TellJokeLayer = TellJoke.toLayer(
  Effect.fn(function* ({ chat, messages }) {
    const punGenerator = yield* PunGenerator
    const slack = yield* Chat
    const sql = yield* SqlClient.SqlClient

    // Step 1: write a joke he hasn't told in this chat
    const joke = yield* Activity.make({
      name: "WriteJoke",
      success: Schema.String,
      execute: Effect.gen(function* () {
        const notebook = yield* sql<{ joke: string }>`
          SELECT joke FROM dad_jokes WHERE chat = ${chat}
        `
        const joke = yield* punGenerator.generate(messages, {
          told: new Set(notebook.map((row) => row.joke)),
        })
        yield* sql`INSERT INTO dad_jokes ${sql.insert({ chat, joke })}`
        return joke
      }).pipe(Effect.orDie),
    }).annotate(ClusterSchema.WithTransaction, true)

    // Step 2: tell it, and keep the Slack message's ts
    const ts = yield* Activity.make({
      name: "PostJoke",
      success: Schema.String,
      execute: slack.reply(chat, joke),
    })

    // Step 3: give the room an hour
    yield* DurableClock.sleep({ name: "WaitForLaughs", duration: "1 hour" })

    // Step 4: count the laughs
    const laughs = yield* Activity.make({
      name: "CountLaughs",
      success: Schema.Number,
      execute: slack.reactionCount(chat, ts),
    })

    // Step 5: if nobody laughed, they must not have got it
    if (laughs === 0) {
      yield* Activity.make({
        name: "ExplainJoke",
        execute: punGenerator
          .explain(joke)
          .pipe(
            Effect.flatMap((explanation) => slack.reply(chat, explanation)),
          ),
      })
    }
  }),
)
```

That's three more steps, and none of them need a table or a flag. `ExplainJoke` is random, just like `WriteJoke`, so it goes inside an activity too.

<ReaderAsks>
  Doesn't sleeping for an hour tie up a runner? What if it crashes in the
  meantime?
</ReaderAsks>

When a workflow starts a durable sleep, it **suspends**. It schedules a wake-up message in the database, timed to arrive in an hour, and then it stops running. No fiber is waiting, no memory is held, and no runner is responsible for it.

An hour later, the wake-up message is delivered to whichever runner owns the workflow's shard _at that time_. The workflow runs from the top, every step so far comes back from the journal, and it carries on from `CountLaughs`.

Click **Step** to run the workflow, and keep stepping.

<SleepingVisual />

While Dad was asleep, nothing was running. All that was left of him was a row in the journal with a time on it. When that time came, the workflow ran from the top, the same as after a crash, and the sleep came back from the journal as done.

<DadSays>If you have to explain it, it's still funny. To me.</DadSays>

<Aside title="Short naps stay in memory">
  <p>
    A durable sleep costs a database write and a scheduled message, so
    `DurableClock.sleep` only goes durable for sleeps over 60 seconds. Shorter
    ones run in memory as an ordinary activity. You can change the cutoff with
    `inMemoryThreshold`. It's also why Dad's 2.5 second wait for the chat to go
    quiet didn't need to be durable at all.
  </p>
</Aside>

## Wrapping up

That's it for this week! To recap what we've learned:

<ul class="[&>li]:my-0 [&>li>p]:my-0">
  <li>
    A workflow is a list of steps plus a journal. After a crash, it runs from
    the top and skips anything the journal already has a result for.
  </li>
  <li>
    Activities are the steps. Anything random, and anything that touches the
    outside world, belongs inside one.
  </li>
  <li>
    `DurableClock.sleep` lets a workflow wait for an hour, or a month, without
    anything running.
  </li>
</ul>
