Let's get our alerts back. The program knows how to ask for rules and
check them, but the red underline at `NodeRuntime.runMain(program)`
reminds us that we haven't given it a store to ask.

We'll start with something small: a Map containing the same rule strings
we've already used. Once the program runs again, we'll try a different
set of rules. The interesting part is how little of the program needs to
change when we swap the store.

## Build our first store

We need to create the Map and implement the `list` operation we promised
in `RuleStore`. We'll describe that construction with a **layer**.
`Layer.effect(RuleStore, effect)` associates the service with an Effect
that builds its implementation.

Add `Layer` to the `effect` import and put the `largeExpense` and
`malformed` constants back above the class. You can copy the original
JSON strings from [Validating JSON with Schema](/learn/part-1/06-untrusted-json).
Then add this static member to `RuleStore`, so the implementation lives
next to the interface:

```ts
static readonly layer = Layer.effect(
  RuleStore,
  Effect.sync(() => {
    const rules = new Map([["large expense", largeExpense], ["malformed", malformed]])
    return RuleStore.of({ list: Effect.sync(() => Array.from(rules.values())) })
  })
)
```

Inside the layer is a familiar Map and an object with a `list` member.
`RuleStore.of` lets TypeScript check that the object matches the
interface we declared. When `list` runs, it reads the Map's values into
an array.

The surrounding `Effect.sync` turns the synchronous callback into an
Effect. Like our logging Effect, it describes work to do later. This means
the Map is created when the layer is built, not as soon as the file loads.

## Connect the store to the program

Attach `Effect.provide(RuleStore.layer)` to `program` with `.pipe`.
The red underline at the run line should disappear. We now have both the
code that asks for a store and the layer that supplies one.

Run the file. The laptop gets its alert, followed by the malformed rule's
`SchemaError`. We've deliberately kept that rule in the store, so this
is the expected result. The program is running again and reading its
rules through `list`.

Hover over `program` to see what happened to the requirement. Its type
is now `Effect<void, SchemaError, never>`. Providing the layer satisfied
`RuleStore`, leaving no outstanding requirements. The possible schema
error remains, because supplying a store doesn't make all its rules valid.

Notice what you didn't have to edit: `evaluateAll`, `evaluate`, and the
rest of `program`. The same checking code read a different set of rules
because we changed the layer supplied to it. In Part 2, we'll use this
separation to supply test stores; later, we'll replace the memory store
with SQLite.

There is a little extra indirection to keep in mind. When you see
`yield* RuleStore`, you know which service is needed, but you'll have to
find the provided layer to see which implementation runs. Keeping the
layer next to the service declaration helps us follow that connection.

Reflex can now check every stored rule, and none of our valid rules stops
the run. That completes the browser part of the application. Before we
move to local files and a server, we'll take a short pause to review what
we've built.
