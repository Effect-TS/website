`handleEvent` still uses a `for...of` loop with one `yield*` after another.
Each rule waits for the previous rule to finish. That delay was barely
noticeable when actions only appended local files, but an HTTP action can
now take the full 10 second timeout before the next rule starts.

The rules matched by an event do not depend on one another, so they can run
concurrently. You will first observe the sequential behavior, then replace
the loop with `Effect.forEach` and a concurrency limit. The timeout and
other server limits will also become configuration values, so you can
adjust them without editing the implementation.

## Observe the sequential runs

Use a clean database so earlier rules do not obscure the result. Your
server and the checkpoint servers share `reflex.db`, so it still contains
rules from previous lessons. Stop the server, delete `reflex.db`, and start
it again. This discards the stored rules and history. In another terminal,
start the receiver with the mixed scenario:

```sh
pnpm receiver --scenario mixed
```

It prints four rules for one `expense` event:

- A and B post to `/ok`.
- C posts to `/slow?ms=15000`, which is past the timeout.
- D posts to `/fail?status=500`.

Add the four files from `fixtures/rules/mixed/` to your server and submit
`fixtures/events/laptop.json`:

```sh
pnpm cli rules add fixtures/rules/mixed/a-ok.json
pnpm cli rules add fixtures/rules/mixed/b-ok.json
pnpm cli rules add fixtures/rules/mixed/c-slow.json
pnpm cli rules add fixtures/rules/mixed/d-fail.json
pnpm cli events submit fixtures/events/laptop.json
```

Open the event's trace in the viewer. D's `Engine.execute` span starts
only after C has used its full 10 seconds. D does not need C's result, but
the sequential loop makes it wait anyway. The event request takes roughly
the sum of the individual run durations.

## Run independent rules concurrently

In `src/Engine.ts`, change `handleEvent` to select the matching rules and
execute them with `Effect.forEach`. It can run several effects at once
while limiting how many are active:

<LessonCode file="checkpoints/21/src/Engine.ts" />

`Effect.forEach(rules, (rule) => execute(rule, event), { concurrency })`
starts each execution on a fiber, with at most `concurrency` executions
active for this event. Its returned outcomes remain in the input rule
order, regardless of completion order.

There is an important dependency on the execution boundary introduced in
[Recording runs with Effect.onExit](/learn/part-2/12-an-engine-that-records).
`Effect.forEach` normally fails when one of its effects fails and interrupts
the remaining work. That is useful when all results are required for one
operation, but these rules should not cancel one another.

The boundary records each run, then converts its typed failure or defect
into an `Outcome` value. D's 500 and C's timeout are therefore successful
returns from `execute`, each containing a failed outcome. They do not cause
`Effect.forEach` to fail, so A and B can complete independently.
Interruption still cancels work; this conversion does not make the event
immune to server shutdown or request cancellation.

The concurrency limit prevents one event from starting every matching rule
at once. For 100 rules and a limit of 4, at most four of that event's runs
are active at a time. This is a per-event limit, not a server-wide cap:
other events and interval loops can also be running.

## Configure the server limits

The concurrency level that suits a local receiver might not suit a remote
service. Rather than changing code to try another value, describe the
limits with `Config`. Create `src/Limits.ts` to read the timeout,
concurrency and two API limits from environment variables, using defaults
when they are absent:

<LessonCode file="checkpoints/21/src/Limits.ts" />

`Config.Int("REFLEX_CONCURRENCY")` describes an integer configuration
value. `Config.withDefault(4)` supplies 4 when the variable is unset, and
`Config.all` combines the individual descriptions into one config object.
Inside a layer, `yield* Limits` reads and parses those values during server
startup. A value that cannot be parsed stops startup with an error naming
the variable, rather than failing later during a request.

The Engine uses `timeout` and `concurrency`. The API handlers use
`maxRules`, which defaults to 100, and `maxPayloadBytes`, which defaults
to 64 KiB. Adding a rule when the store already has `maxRules` rules fails
with `TooManyRules`, sent as HTTP 409. If an event's JSON exceeds
`maxPayloadBytes` in UTF-8 bytes, the API rejects it with
`PayloadTooLarge`, sent as HTTP 413, before executing any rule. That check
applies to both `events submit` and `rules run`.

Add the errors to the endpoint declarations in `src/api/Api.ts`, then read
`Limits` in `src/server/Api.ts` and check the rule count and payload size
before calling the services. Handle the new typed errors in
`src/cli/main.ts` as you did `RuleNotFound`, so each prints as a single line.
The corresponding files in `checkpoints/21/src/` show these changes.

With `Limits` in place and the server running again, submit the event.
With the default concurrency of 4, all four spans start together and
`events submit` takes about 10 seconds, determined by the slowest run.
A and B finish promptly, and D can report its 500 while C is still waiting.

To check the configuration, restart the server with
`REFLEX_CONCURRENCY=1 pnpm dev:server` and submit the mixed event again.
D waits for C, reproducing the sequential behavior without a code change.

## Try it

You can use the same HTTP action to send a notification to your phone.
This optional exercise is not part of the checkpoint.
[ntfy.sh](https://ntfy.sh) delivers messages posted to
`https://ntfy.sh/<topic>` to devices subscribed to that topic, using the
`Title` header as the notification title. The fixture already describes
that request as an `httpPost` action:

<LessonCode file="fixtures/rules/ntfy.json" />

This example uses a public topic without authentication. Anyone who knows
the topic can publish to it or read its messages, so choose a long random
name to make it harder to guess. That does not make it suitable for
sensitive data.

1. Make a long random topic:

   ```sh
   node -e "console.log(crypto.randomUUID())"
   ```

2. Install the ntfy app on your phone and subscribe to that topic.
3. Copy `fixtures/rules/ntfy.json` to a file of your own, and put your topic
   in the URL.
4. Add it to your running server and submit `fixtures/events/laptop.json`.
   Your phone shows "reflex", with "expense over 500" and the event under it.
5. Submit `fixtures/events/lunch.json`. Nothing arrives, because 40 is not
   over 500.

Use fixture data only, and assume anything you post could be read by
someone else.

Concurrent execution changes how you read the output. Log lines from
different runs can interleave, and `runs list` orders rows by start time
(newest first), not by the input rule order. Use rule ids and spans to
identify individual runs rather than assuming adjacent lines belong
together. In
[Diagnosing a request from its trace](/learn/part-3/22-diagnose-it),
you will use this mixed scenario to work out what happened from the
recorded data alone.

## Checkpoint

To compare your result with checkpoint 21, first stop your server and
delete `reflex.db` again. Otherwise, adding the four rules below would
duplicate the ones already stored; the store does not deduplicate rules.
With the mixed receiver still running, start the checkpoint server and add
the rules:

```sh
pnpm checkpoint 21 server
```

```sh
pnpm checkpoint 21 cli rules add fixtures/rules/mixed/a-ok.json
pnpm checkpoint 21 cli rules add fixtures/rules/mixed/b-ok.json
pnpm checkpoint 21 cli rules add fixtures/rules/mixed/c-slow.json
pnpm checkpoint 21 cli rules add fixtures/rules/mixed/d-fail.json
pnpm checkpoint 21 cli events submit fixtures/events/laptop.json
pnpm checkpoint 21 cli runs list
```

`events submit` takes about 10 seconds rather than the sum of the four
run durations. It prints two `succeeded`, one `failed (timeout)` and one
`failed (status)`, and `runs list` contains the same four outcomes. In the
viewer, look under `Engine.handleEvent` for four `Engine.execute` spans
starting together. C and D are red; A and B have status Ok.
