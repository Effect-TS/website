Each time you run `main.ts`, it builds an Engine, processes the example
events and exits. Its memory stores disappear when the process stops.
To submit events from another program, Reflex needs to keep running and
accept requests.

You will run one Engine and its stores in an HTTP server on port 3000.
The rules, events and run history already have schemas, so those same
schemas can define the API's requests and responses. The handlers will
call the services you have already written.

## Define the API

Create `src/api/Api.ts` to describe the API with `HttpApi`. An endpoint
definition specifies an HTTP method, a path, and schemas for its input and
output. For example,
`HttpApiEndpoint.post("create", "/", { payload: Rule, success: StoredRule })`
declares a POST endpoint that accepts a `Rule` and returns a `StoredRule`.
The definition does not create a rule by itself; you will implement that
behavior in a handler.

Endpoints are grouped, and the groups make up the API:

- `rules`: create, list, get, remove, and `POST /rules/:id/run` to run one
  rule against an event
- `events`: `POST /events` submits an event to every matching rule
- `runs`: `GET /runs?ruleId=&limit=` lists the run history

<LessonCode file="checkpoints/14/src/api/Api.ts" />

The API reuses the domain schemas for its payloads, results and errors.
The `get`, `remove` and `run` endpoints can fail with `RuleNotFound`, just
like the store. `HttpApiSchema.status(404)` associates that error with an
HTTP status, so the server can return a 404 when a rule does not exist.

## Implement the endpoints

Create `src/server/Api.ts` for the handlers.
`HttpApiBuilder.group(Api, "rules", ...)` implements the `rules` group.
Inside its `Effect.fn` callback, retrieve the services with `yield*`, then
pass a function for each endpoint to `handlers.handleAll({...})`:

<LessonCode file="checkpoints/14/src/server/Api.ts" />

Each handler receives the input its endpoint declares: decoded `params`,
`query` or `payload`. TypeScript checks its success and error types against
the API definition. Since the services already implement the behavior,
each handler needs only one service call. There is no JSON parsing or
manual response construction in these handlers.

## Launch the server

Create `src/server/main.ts` to assemble the server from layers:

- `HttpApiBuilder.layer(Api)` turns the handlers into routes.
- `HttpApiScalar.layer` adds documentation at `/docs`.
- `HttpRouter.serve` serves both.
- `NodeHttpServer.layer` listens on port 3000.

Provide the Engine, the memory stores and `NodeServices.layer` to satisfy
the handlers' dependencies.

<LessonCode file="checkpoints/14/src/server/main.ts" />

The server layer acquires resources, including a listening socket, that
must remain available while the program runs. `Layer.launch` builds the
layer and keeps its resources alive until interruption. `NodeRuntime.runMain`
runs that effect and interrupts it when you press Ctrl-C, allowing the
server to shut down and release its resources.

```sh
pnpm dev:server
```

This command watches for file changes and restarts the server. The stores
remain in memory, so each restart loses the rules and run history. You will
make them persistent in
[Storing data in SQLite with SqlClient](/learn/part-3/17-survive-a-restart).

## Call the API

In a second terminal, create a rule, submit an event, and read the run:

```sh
curl -X POST localhost:3000/rules -H 'content-type: application/json' -d @fixtures/rules/expense.json
curl -X POST localhost:3000/events -H 'content-type: application/json' -d @fixtures/events/laptop.json
curl localhost:3000/runs
```

The first response contains the stored rule and its assigned `id`. The
second contains one `succeeded` outcome, and the third lists the recorded
run. Keep the server running between requests so they use the same stores.

Now ask for a rule that does not exist:

```sh
curl -i localhost:3000/rules/nope
```

It answers `404 Not Found` with the error as the body:

```text
{"_tag":"RuleNotFound","id":"nope"}
```

The store's `RuleNotFound` passes through the handler to the HTTP response.
The endpoint's error declaration determines its status and encoded body.

Invalid input is handled earlier. A request whose input does not match the
endpoint schema is rejected before the handler runs. Try a rule without an
action, or a query with `limit=abc`: the decoder returns a 400 response.

Open [http://localhost:3000/docs](http://localhost:3000/docs) to see the API
documentation generated from the same definition. The next lesson will
also use that definition to build a client.

## Try it

The `limit` query parameter currently accepts any number. For example,
`GET /runs?limit=-1` returns every run except the oldest because
`RunLog.list` passes the number to `slice`. A fractional value such as
`limit=1.5` is accepted too. Neither value makes sense as a requested count.
Reject them in the API schema, before they reach the service.

1. In the `runs` query, make `limit` a whole number greater than 0 with
   `Schema.Int.check(Schema.isGreaterThan(0))`.
2. Keep the handlers and `RunLog` unchanged. The query schema should reject
   these values before they reach either one.

Check your work with `pnpm dev:server` running:

```sh
curl -i 'localhost:3000/runs?limit=-1'
curl -i 'localhost:3000/runs?limit=1.5'
curl -i 'localhost:3000/runs?limit=2'
```

The first two answer 400 and the last answers 200. The hint and the changed
file are in `exercises/14/`. From the next checkpoint on, the reference
solution includes this change.
