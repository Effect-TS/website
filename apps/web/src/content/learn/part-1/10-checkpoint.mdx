## Hover tour

Read each name from top to bottom. Before you hover, say what you expect in
each slot of an Effect: what it gives back, how it fails, what it needs.

- `Rule`: the schema. `type Rule` is the type derived from it.
- `decodeRule`: takes unknown input and returns
  `Effect<Rule, SchemaError, never>` (the hover spells out the rule's fields).
- `RuleStore`: the service, with `layer` and `layerFixtures` beside it.
- `MissingField`: the one failure you declared and still use.
- `matches`: `(rule, event) => boolean`. Plain, no Effect in sight.
- `evaluate`: `Effect<string | void, SchemaError, never>`. A missing field is
  handled inside; a malformed rule is not.
- `evaluateAll`: `Effect<void, SchemaError, RuleStore>`. It needs the store.
- `program`: `Effect<void, SchemaError, never>`. The store is provided.

If one of them surprised you, the lesson that introduced it is listed below.

## Challenges

These are optional and not counted in the course time. Part 2 does not depend
on them.

1. `contains`. Add a fifth operator: the field's text contains the
   condition's value. The value is a number today. Decide what the schema
   should say about it, and see what TypeScript asks of `matches`.
2. A `skipped` outcome with a reason. Instead of logging a skip and giving
   back nothing, make `evaluate` give back a value that says the rule was
   skipped and why. Watch `string | void` disappear from the hover. Lesson 12
   does a version of this for real.
3. A second event type. Add an event that is not an expense, such as a
   battery level, and a rule for it. The alert message reads `event.amount`;
   make it right for an event that has no amount.
