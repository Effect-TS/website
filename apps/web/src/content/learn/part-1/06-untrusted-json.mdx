Suppose 500 is no longer the amount you care about. You want an alert for
anything over 1000 instead, with a different message. At the moment, you'd
have to edit both `isLarge` and `evaluate`. That's inconvenient for us,
and it wouldn't work well for someone using reflex without touching its
source code.

Let's make those choices into data. A **rule** will contain the comparison,
the threshold and the message. Eventually we'll read rules from files and
accept them through an API. For now, a string of JSON gives us something
to work with right here in the browser. Here's our familiar expense rule
in that form:

<LessonCode

  declaration="largeExpense"
/>

You can probably read what it means without running it: "greater than
500," with the message "over 500." We'll move that existing rule into data
first; after that, changing 500 to 1000 won't require editing the evaluator.
But someone could misspell the operator
or put text where the amount belongs. TypeScript can't check arbitrary JSON
before our program receives it, so we need to check it while the program
runs. We'll use Schema to describe what a valid rule looks like.

## Decide what a rule can contain

We used `Schema.String` to describe the missing-field error. Now we'll
combine a few schemas to describe the whole rule. Add this one below the
`Event` interface:

<LessonCode
  file="lessons/part1/06-untrusted-json/solution/main.ts"
  declaration="Rule"
/>

`Schema.Struct({ ... })` describes an object with the listed fields. Its
`name` and `message` must be strings, and its `value` must be a number.
`Schema.Literals(["gt", "lt"])` restricts `op` to those two strings, so a
rule with any other operator will fail validation.

Below it, add `type Rule = typeof Rule.Type`. This gives us a TypeScript
type derived from the same description we'll use to validate the JSON.
We don't have to maintain a separate interface with the same fields.
The schema and type can both be named `Rule`; TypeScript distinguishes
them by how we use the name.

## Turn the text into a checked rule

Next we need a function to accept the JSON text and either return a rule
or explain what's wrong with it. Add this line below the type:

<LessonCode
  file="lessons/part1/06-untrusted-json/solution/main.ts"
  declaration="decodeRule"
/>

`Schema.fromJsonString(Rule)` describes parsing JSON text and checking the
parsed value against `Rule`. `Schema.decodeUnknownEffect` turns that
description into a decoding function. The resulting `decodeRule` accepts
unknown input and returns an Effect that succeeds with a `Rule` or fails
with a `SchemaError`.

We'll see the error in a moment. Once decoding succeeds, though, the rest
of the program can use the rule without checking those fields again.
Validation does take runtime work, and we'll need to update the schema
whenever we change the rule format.

not, because our `catchTag` handles only `MissingField`. We haven't
accidentally hidden a rule error by allowing incomplete receipts.

We've also set the summary aside for now. `evaluate` still returns a
boolean when it succeeds, but a broken rule can stop the program before
we've checked everything. Later we'll keep a run history that includes
failed checks as well as successful ones.

## Finding the invalid field

Take a closer look at the failure in the terminal. It reads
`SchemaError: Expected "gt" | "lt"` at `["op"]`. That's enough to find
the mistake without stepping through the decoder: `op` is the offending
field, and the message tells us which values it accepts.

Decoding stops at the first problem it finds. `malformed` also has a string
where the value should be a number, and no message at all. Fix the operator
and the next problem is reported.

Hover `evaluate`. Its return type is
`Effect<boolean, SchemaError, never>`. Unlike `MissingField`, this error
comes from the decoder rather than a class you defined. It remains in the
type because you have not handled it.

## Try it

Try adding a rule that matches an exact amount rather than a range.
Start with the schema and let TypeScript show you what else needs to change:

1. Add `"eq"` to the literals. TypeScript underlines `matches`, because its
   `switch` no longer covers every case. Add the `eq` case,
   `amount === rule.value`.
2. Change the operator in `malformed` to `"between"` and run the file. The
   error now lists `"eq"` among the expected operators.

In this program, the JSON rule needs runtime validation because it arrives
as text. The `laptop` object is constructed in TypeScript and checked
against the `Event` interface, so it does not need a decoder here. Keep
that distinction in mind when you move to external input.

Reflex now has a rule someone could edit without changing the checking
code, and a useful response when that rule is wrong. Before we add more
rules, let's make failures easier to locate. The error tells us which
field was invalid; next we'll add the name of the operation that found it.
