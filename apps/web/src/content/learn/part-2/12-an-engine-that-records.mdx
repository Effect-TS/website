`run-once.ts` runs one rule against one event, and then forgets it ever did.
Rulebook needs more than that. Every rule whose trigger matches the event
should run, and every run should leave a row saying what happened.

Evaluating, acting and recording belong together, in one place that every
caller goes through. In this lesson you build that place, the `Engine`.

You will learn:

- how a layer can depend on other services;
- how to record how an effect ended, whatever happened, with `Effect.onExit`;
- how to turn a failure into a value so one broken rule doesn't stop the rest.

and `remove` fail with `RuleNotFound` for an id the store doesn't know.

`RunLog` is the run history, built the same way:

- `start` opens a row with the outcome `started`;
- `finish` writes how the run ended;
- `list` reads rows back, newest first.

`RunResult` lists the ways a run can end, at this point in the course:
`skipped`, `succeeded`, or `failed`. A `failed` result also carries one of
three reasons, `status`, `timeout` or `io`. Only `failed` uses them.

## The execution boundary

The `Engine` layer is a `Layer.effect`, like the stores. The difference is
that it needs other services before it can build. It `yield*`s `RuleStore`,
`RunLog` and `FileSystem` first, then builds `execute` and `handleEvent` on
top of them.

`execute` is the boundary every run goes through. It does four things, in this
order:

1. **Open the row.** `runLog.start` writes `started` before anything else
   happens.
2. **Run inside a span.** `run` is `Effect.fn("Engine.execute")`, annotated
   with the rule id and trigger. It evaluates the condition, then runs the
   action. The span ends with `run`'s result, so a failed action ends the span
   as an error.
3. **Write the final row from the `Exit`.** An `Exit` is the value that
   describes how an effect ended. `Effect.onExit` hands it to you however `run`
   ended. A success writes its `RunResult`, and an `ActionFailed` writes
   `failed`. Any other ending leaves the row `started` for now. Later lessons
   give crashes and interruptions outcomes of their own.
4. **Turn the failure into a value.** After the row is written,
   `Effect.catchTag` turns `ActionFailed` into a `failed` result. So `execute`
   can't fail, and one broken rule doesn't stop the others.

A missing field means the rule doesn't apply to this event. `run` catches
`MissingField` and returns `skipped`. A skip is not an error, and it's never
shown as one: the span ends Ok, and the row's `error` column stays null.

<LessonCode file="checkpoints/12/src/Engine.ts" />

Two details are worth pointing out:

- The service type says `execute` needs nothing. That's because `run` uses the
  `FileSystem` the layer got when it was built, handed over with
  `Effect.provideService`.
- `Effect.fn.Return<RunResult, ActionFailed | MissingField>` spells out what
  the generator returns and how it can fail, so every `return` is checked
  against `RunResult`.

`handleEvent` is a `for...of` over the stored rules, like `evaluateAll` in
lesson 8. It calls `execute` for each rule whose event trigger names the
event.

## Try it: a reason for every skip

`huge expense: skipped` doesn't say why. Give `skipped` a reason, kept as free
text in the run history's `reason` column:

1. In `RunLog.ts`, give the `skipped` member of `RunResult` a
   `reason: Schema.String`. The compiler now lists every place that writes a
   skip without one.
2. In `Engine.ts`, there are three such places:
   - the condition was false, so say which condition;
   - the `MissingField` catch, so use the error's `field`, as
     `missing field amount`;
   - the `httpPost` branch, so say that the action runs from lesson 20.
3. Leave `failed` alone. Its three reasons are fixed, because the `runs` table
   that lesson 17 stores these rows in only accepts those three on a failed
   row.

To check your work, run `pnpm tsx src/main.ts`. It prints each skip with its
reason in brackets. The hint and the changed files are in `exercises/12/`.
From lesson 13 on, the checkpoints include this change, and lesson 13 tests it.

## Recap

- One boundary, `execute`, opens the row, runs inside a span, writes how the
  run ended, and returns a value.
- `Effect.onExit` sees every ending, and `Effect.catchTag` afterwards turns the
  expected failure into a result.
- The cost is that every run writes to the log twice.
- Lesson 19 adds the `interrupted` and `crashed` outcomes and a timeout inside
  the span. Lessons 19 and 20 introduce `Cause`, which `onExit` reads to tell
  those endings apart.
