## The problem

`handleEvent` is still the loop from lesson 8: a `for...of` over the rules, one
`yield*` after another. That was fine while every action was a line in a file.
Now an action can take up to the 10 second timeout, and every rule after it
waits. Start the receiver with the mixed scenario:

```sh
pnpm receiver --scenario mixed
```

It prints four rules on one `expense` event. A and B post to `/ok`, C posts to
`/slow?ms=15000`, past the timeout, and D posts to `/fail?status=500`. Add the
four files from `fixtures/rules/mixed/` to your lesson 20 server and submit
`fixtures/events/laptop.json`. In the viewer, D's `Engine.execute` span starts
only after C's has run its full 10 seconds. D had nothing to wait for. Add a
second slow rule and the event takes 20 seconds; the time is the sum of the
rules.

## Run them together

The rules an event matches are independent, so run them at the same time, up
to a limit:

<LessonCode file="checkpoints/21/src/Engine.ts" />

`handleEvent` filters the matching rules, then
`Effect.forEach(rules, (rule) => execute(rule, event), { concurrency })` runs
`execute` for each, at most `concurrency` at a time. Each run gets a fiber of
its own, and the outcomes come back in the order of the rules, not the order
they finished.

This is safe because of a decision made in lesson 12. `execute` cannot fail:
the boundary turns every failure and crash into an `Outcome` value after
writing its row. `Effect.forEach` stops at the first failure and interrupts
the rest, which is right for work that only makes sense as a whole and wrong
for independent rules. Here there is no failure to stop at. D's 500 is a
value, C's timeout is a value, and A and B finish no matter what happens to
the others. The boundary is what makes the concurrency one line.

The limit matters too. With 100 rules on one event, a limit of 4 means at most
four requests leave at once, instead of 100 at whoever the rules point to.

## Limits as Config

The timeout, the concurrency and two more limits are not constants any more.
`src/Limits.ts` reads each from the environment, with a default:

<LessonCode file="checkpoints/21/src/Limits.ts" />

`Config.Int("RULEBOOK_CONCURRENCY")` describes where a value comes from and how
to parse it. `Config.withDefault(4)` makes it optional. `Config.all` combines
them, and `yield* Limits` inside a layer reads them all, failing the server's
start with a clear message if one is set to something it cannot parse. The
Engine reads `timeout` and `concurrency`. The API handlers read the other two:

- More than `maxRules` rules (100) is `TooManyRules`, sent as a 409.
- An event whose JSON is more than `maxPayloadBytes` (64 KiB) is
  `PayloadTooLarge`, a 413, refused before any rule sees it, from
  `events submit` and from `rules run`.

Both are typed errors on their endpoints, like `RuleNotFound` in lesson 14, so
the CLI prints each one as one line. Try `RULEBOOK_CONCURRENCY=1 pnpm dev:server`
and submit the mixed event again: D waits for C, exactly as before this lesson.

## Checkpoint

With the mixed receiver running, start the checkpoint's server and add the four
rules:

```sh
pnpm checkpoint 21 server
```

```sh
pnpm checkpoint 21 cli rules add fixtures/rules/mixed/a-ok.json
pnpm checkpoint 21 cli rules add fixtures/rules/mixed/b-ok.json
pnpm checkpoint 21 cli rules add fixtures/rules/mixed/c-slow.json
pnpm checkpoint 21 cli rules add fixtures/rules/mixed/d-fail.json
pnpm checkpoint 21 cli events submit fixtures/events/laptop.json
pnpm checkpoint 21 cli runs list
```

`events submit` takes about 10 seconds, the timeout, not the sum. It prints
two `succeeded`, one `failed (timeout)` and one `failed (status)`, and
`runs list` has the same four rows. In the viewer the `Engine.handleEvent`
trace has four `Engine.execute` spans starting together under it: C's and D's
are red, A's and B's are Ok.

This is the checkpoint. If it matches, the lesson is done, and lesson 22 uses
exactly this scenario.

## Now and later

What you need now: independent work runs with `Effect.forEach` and a
`concurrency` limit, and it is safe because each piece returns a value instead
of failing. Limits are `Config` with defaults, read once when the server
starts. The cost is that runs of one event now overlap, so their log lines
interleave and their order in `runs list` is the order they started, not the
order of the rules. Unpacked later: reading this exact trace to answer
questions about it (lesson 22).

## The payoff: your phone

The last five minutes are for fun, and they are not the gate. The receiver
checkpoint above is.

[ntfy.sh](https://ntfy.sh) delivers a POST to `https://ntfy.sh/<topic>` to
every device subscribed to that topic, and uses the `Title` header as the
notification's title. That is an `httpPost` action and nothing else:

<LessonCode file="fixtures/rules/ntfy.json" />

A topic is not an account. Anyone who knows it can publish to it and read what
was sent, so the topic is the only secret, and a short one gets guessed. Make a
long random one:

```sh
node -e "console.log(crypto.randomUUID())"
```

Install the ntfy app on your phone and subscribe to that topic. Copy
`fixtures/rules/ntfy.json` to a file of your own, put your topic in the URL,
and add it to the checkpoint's server. Submit `fixtures/events/laptop.json`:
your phone shows "rulebook", with "expense over 500" and the event under it.
`lunch.json` sends nothing, because 40 is not over 500. Send fixture data only;
whatever you post there, assume anyone could read it.
