Suppose you submit an expense and no alert appears. Perhaps it was below
the threshold, perhaps the event had no amount, or perhaps Reflex could not
write the file. Our program keeps no history, so there is no way to tell
afterwards, and the question only gets harder as we add more rules.

Reflex needs a run history: a record of every run, including the ones that
produced no alert. In this lesson we put the work of finding and running
matching rules in a service called `Engine`, and save each result in a
`RunLog`. If one action fails, the Engine records the failure and still
gives the remaining rules their turn.

## Keep a run history

Now the rules need somewhere to leave their history. Create `src/RunLog.ts`.
Like `RuleStore`, it has a service definition and a memory layer, and it
records when a run starts as well as how it ends:

- `start` opens a row with the outcome `started`.
- `finish` writes how the run ended.
- `list` reads rows back, newest first.

<LessonCode file="checkpoints/12/src/RunLog.ts" />

`RunResult` describes a completed run as `skipped`, `succeeded` or `failed`.
A failure also carries a reason: `status`, `timeout` or `io`. Only `io` can
happen with our file-writing action; the other two are for the network
action we add later. At this checkpoint, skipped runs have no reason yet.

## How the result reaches the history

The rows show what happened for each expense, even when no alert was
written. Now return to `execute` in the Engine to follow how a result gets
recorded. It starts with `runLog.start`, so a row exists before the
condition or the action runs.

The inner `run` function evaluates the condition and performs the action.
Its `Effect.fn("Engine.execute")` creates a span, with the rule id and
trigger attached as attributes. If the action fails, that span ends with an
error. A missing field is different, because we already know how to handle
it: `run` catches `MissingField` and returns `skipped`. Deciding not to run
the action is a success, so the span ends Ok and the row's `error` column
stays null.

After `run` ends, `Effect.onExit` receives its `Exit`, a value describing
how the effect ended. The callback writes a successful `RunResult` to the
row, or records `failed` for an `ActionFailed`. Any other ending leaves the
row as `started` for now.

Each completed run therefore costs two run-log writes, one for `started`
and one for the result. We keep both so that a run which began but never
finished looks different from a run that never started.

Only after the result is recorded does `Effect.catchTag` convert
`ActionFailed` into a `failed` value for the caller. The order matters: the
span and the run log record the failure, and `handleEvent` receives an
outcome it can collect before moving on to the next rule. The effect
returned by `execute` has no typed failures, although defects and
interruption are still possible.

A defect or an interruption can still leave a row at `started`. We deal
with those unfinished rows when we add scheduled work in
[Running rules on a schedule with FiberMap](/learn/part-3/19-rules-on-a-clock),
with `interrupted` and `crashed` outcomes and a timeout inside the span.

Executing an action needs a file system, but callers of `execute` do not
have to provide one. The layer retrieved it when it was built, and
`Effect.provideService` hands that same instance to `appendLine`. The
annotation `Effect.fn.Return<RunResult, ActionFailed | MissingField>` checks
the generator's return values and typed failures, so TypeScript catches an
invalid result.

Finally, `handleEvent` loops through the stored rules, much like
`evaluateAll` in Part 1. For each event trigger that matches the event's
type, it calls `execute` and collects the outcome.

## Try it

The history shows that `huge expense` was skipped, but the row does not say
why. A false condition, a missing field and an unsupported action each call
for a different response from us, so give each skip a reason, stored as
free text in the run history's `reason` column:

1. In `src/RunLog.ts`, give the `skipped` member of `RunResult` a
   `reason: Schema.String`. The compiler now lists every place that writes a
   skip without one.
2. Add reasons to the three skip results in `src/Engine.ts`:
   - When a condition is false, identify the condition in the reason.
   - In the `MissingField` catch, include the error's `field`, producing
     text such as `missing field amount`.
   - In the `httpPost` branch, explain that the action is introduced in the
     lesson on network actions.
3. Leave the `failed` result unchanged. Its reasons stay restricted to
   `status`, `timeout` and `io`, rather than the free text we are adding
   for skipped runs.

Check your work with `pnpm tsx src/main.ts`. It prints each skip with its
reason in brackets. The hint and the changed files are in `exercises/12/`.
From the next checkpoint on, the reference solution includes this change,
and the next lesson tests it.
