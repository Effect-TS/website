## A schema for triggers, conditions and actions

The Part 1 schema was enough to compare an amount against a threshold. The
fixture needs a fuller description of when a rule runs and what it does.
Create `src/Rule.ts` with a schema for these three parts:

- A trigger is an `event` or an `interval`.
- A condition is optional. It compares a `field` against a `value` using an
  `op`: `eq`, `neq`, `gt`, `lt` or `contains`. The field can be a dotted path
  such as `body.status`. Without a condition, evaluation returns `true`.
- An action is `appendFile` or `httpPost`.

<LessonCode file="checkpoints/11/src/Rule.ts" />

Each trigger or action variant is a `Schema.Struct` with a distinct `type`
literal. `Schema.Union` combines them while preserving the information
TypeScript needs to narrow the type. Inside `case "appendFile":`, for
example, you can access `rule.action.path` because that property belongs to
the `appendFile` variant.

`lookup` reads the dotted path from the event. When a key on the path is
absent it fails with `MissingField`, the error you defined in
[Defining errors with Schema.TaggedError](/learn/part-1/04-failure-you-can-see).

## Append a line to a file

Create `src/Action.ts` for the file-writing action. Effect provides the
`FileSystem.FileSystem` service, which you access in the same way as your
own `RuleStore` from
[Defining a service with Context.Service](/learn/part-1/08-a-place-for-rules).
Use `yield*` to get the service, then call its methods.

<LessonCode file="checkpoints/11/src/Action.ts" />

The `flag: "a"` option makes `fs.writeFileString` append rather than
overwrite. If the file does not exist, the operation creates it.

A write can fail, for example because the process lacks permission.
`FileSystem` represents that failure as a `PlatformError`, but callers of
`appendLine` need an error about the action they attempted. `Effect.mapError`
converts it to `ActionFailed`, preserving the original message and adding
the reason `io`.

For now, `io` is the only reason in `ActionFailed`. The reasons `status`
and `timeout` arrive with `httpPost` in
[Telling errors from defects with Cause](/learn/part-3/20-an-action-over-the-network).

<LessonCode file="checkpoints/11/src/run-once.ts" />

In Part 1, the lesson runner executed your effects. This local program
needs its own entrypoint. The pipeline at the bottom prepares the effect
and runs it in this order:

1. `Effect.tapError` prints a typed error as one line, then passes the
   failure on unchanged.
2. `Effect.provide(NodeServices.layer)` provides Node's `FileSystem` and the
   other platform services, so the requirements type is `never`.
3. `NodeRuntime.runMain({ disableErrorReporting: true })` runs the program,
   sets the exit code, and turns Ctrl-C into an interruption. Error reporting
   is off because step 1 already printed the error.

The schema accepts an `httpPost` action, but the program does not execute
it yet. That branch logs a message explaining that the action is introduced
later.

## Try it

The `alertLine` function still builds text such as `expense 1200 over 500`
from the event and condition. The rule file contains a message of its own,
`"message": "expense over 500"`. Make the action write that message instead,
so the person defining the rule can choose the alert text.

1. Add `message: Schema.String` to the `AppendFile` struct in `src/Rule.ts`.
2. In the `appendFile` case of `src/run-once.ts`, hover over
   `rule.action.message` to confirm that its type is `string`. Pass it to
   `appendLine` instead of the generated line.
3. Delete the unused `alertLine` function and its `words` lookup.
4. Copy the rule file, remove `message` from the copy, and run it. The error
   names the missing key and its path.

Check your work with
`pnpm tsx src/run-once.ts fixtures/rules/expense.json fixtures/events/laptop.json`.
It appends `expense over 500` to `alerts.log`. The hint and the changed files
are in `exercises/11/`. From the next checkpoint on, the reference solution
includes this change.
