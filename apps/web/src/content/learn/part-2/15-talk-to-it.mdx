We can now send an expense to Reflex from another terminal, but the curl
commands make us remember paths, headers and request bodies every time. For
everyday use, a command such as `events submit laptop.json` would be far
more comfortable, so in this lesson we build that CLI.

We do not have to describe every request again. The `Api` definition from
the last lesson can give us a typed client, which the CLI's command handlers
use. If we change an endpoint later, TypeScript checks those calls against
the new request and response types.

## Create the client service

First, the commands need a way to reach the server. Create
`src/ApiClient.ts`. The call `HttpApiClient.make(Api, { baseUrl })` derives
one client method per endpoint, organized into the groups you defined in the
API, for example:

- `client.rules.create({ payload })`
- `client.rules.run({ params: { id }, payload })`
- `client.runs.list({ query })`

Wrap the client in an `ApiClient` service, so command handlers can access it
with the familiar `yield*`. The type `HttpApiClient.ForApi<typeof Api>`
derives its interface from the API too:

<LessonCode file="checkpoints/15/src/ApiClient.ts" />

The client checks and encodes request payloads with the endpoint schemas,
and decodes responses with the declared success and error schemas. It sends
requests through an `HttpClient` service, and the CLI provides
`FetchHttpClient.layer`, a client built on `fetch`.

The CLI should talk to our local server unless told otherwise.
`Config.String("REFLEX_URL")` reads an address from the environment, and
`Config.withDefault("http://localhost:3000")` supplies the local one when
`REFLEX_URL` is not set. The configuration is read inside the layer's
effect, so the URL is resolved when the layer is built.

The CLI imports `Api` and its domain schemas, so it is checked against that
version of the API. A separately deployed server could run a different
version, so keep the CLI and the server compatible.

## Write the command handlers

Open the starter's `src/cli/main.ts`. The command names, arguments and
flags are already declared, so what remains is what happens when someone
runs them. Fill in the six empty handler bodies using the client service.
Each one retrieves `ApiClient`, calls an endpoint and prints the result:

<LessonCode file="checkpoints/15/src/cli/main.ts" />

- `rules add` reads the file with the same `readJson` as before, then calls
  `client.rules.create`.
- `rules run` and `events submit` print one outcome per line, with its
  reason or error.
- `runs list` has two optional flags, with types `string | undefined` and
  `number | undefined`, matching the optional query parameters. Pass `rule`
  as `ruleId` and `limit` as `limit` in `client.runs.list({ query })`.

Keep naming the work as you did in the Engine, with `Effect.fn("rules.add")`
and the matching name for each command. Those names identify the command
spans when we look at traces in the next lesson.

At the entrypoint, provide `ApiClient.layer` with `FetchHttpClient.layer`
for requests, and `NodeServices.layer` so the handlers can read rule and
event files.

## Run the CLI against the server

Now we can repeat the expense check without curl. Start the server with
`pnpm dev:server` in one terminal. In a second, run:

```sh
pnpm cli rules add fixtures/rules/expense.json
pnpm cli rules list
pnpm cli events submit fixtures/events/laptop.json
pnpm cli runs list
```

`rules add` prints `Added <id>: large expense`. Then `events submit` prints
`<id>: succeeded`, and `runs list` shows the row. It is the same stored rule
and the same Engine behavior we checked through HTTP, reached with commands
that do not require remembering the request format.

A useful CLI has to show more than successful alerts. The Engine still
skips actions it cannot execute yet, so check that this outcome is visible
too. Add `fixtures/rules/ntfy.json`, whose action is `httpPost`, then use
its id to run it against an event:

```sh
pnpm cli rules run <id> --event fixtures/events/laptop.json
```

It prints one `skipped` outcome whose reason says that `httpPost` actions run
from a later lesson, and `runs list` shows the same row.
[Telling errors from defects with Cause](/learn/part-3/20-an-action-over-the-network)
adds the action.

## Inspect an error returned by the server

Now try removing a rule that does not exist:

```sh
pnpm cli rules remove nope
```

This time you see `RuleNotFound` with a stack trace. The server returns a
404 response, and because the endpoint declares `RuleNotFound`, the client
decodes the response body into an instance of that class. It is a typed
failure of the client call, just as it was a typed failure of the store, and
the CLI has no handler for it yet.

Hover over the `rules remove` handler to inspect its error type. It includes
`RuleNotFound` alongside HTTP and schema errors, so you can handle it with
`Effect.catchTag`, even though the failure originated in another process.

## Try it

We know what went wrong in that last command, but someone using the CLI
should not have to read a stack trace to find out. An unknown id is an
ordinary input mistake, so print a short message instead, while keeping a
non-zero exit code so scripts can still detect the failure.

1. Write one handler with `Effect.fn` that takes the `RuleNotFound`, prints
   `No rule with id <id>` with `Console.error`, and then fails with
   `new ExitCode({ code: 1 })` from `tools/entrypoint.ts`. `runMain` exits
   with that code and prints nothing more.
2. `Effect.fn` takes more arguments after the generator and applies each one
   to the effect it builds. Pass `Effect.catchTag("RuleNotFound", yourHandler)`
   there, in both the `rules remove` and `rules run` handlers.

Try the missing id again with `pnpm cli rules remove nope` and
`pnpm cli rules run nope --event fixtures/events/laptop.json`. Each now
prints one line and exits 1 (check with `echo $?`). The failure is not
hidden, only easier to understand. The hint and the changed file are in
`exercises/15/`. From the next checkpoint on, the reference solution
includes this change.

## Checkpoint

Checkpoint 15 repeats the API checks from the previous lesson through the
CLI. Start the server in one terminal:

```sh
pnpm checkpoint 15 server
```

In a second:

```sh
pnpm checkpoint 15 cli rules add fixtures/rules/expense.json
pnpm checkpoint 15 cli events submit fixtures/events/laptop.json
pnpm checkpoint 15 cli runs list
pnpm checkpoint 15 cli rules run <id> --event fixtures/events/laptop.json
```

Use the id that `rules add` printed. `rules run` produces one more row. Add
`fixtures/rules/ntfy.json` and run it the same way. You get one `skipped` row
whose reason says `httpPost` actions run from a later lesson:

```text
fd657e81-8ced-4afd-9c5e-8213677a25e9: skipped (httpPost actions run from lesson 20)
```

You can now add a rule, submit an expense and read the history entirely
through the CLI. Those commands involve two running programs, and next we
follow one expense through both of them in the trace viewer.
