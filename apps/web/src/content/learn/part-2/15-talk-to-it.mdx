We can now send an expense to reflex from another terminal. But the curl
commands make us remember paths, headers and request bodies every time.
For regular use, a command such as `events submit laptop.json` would be
much more comfortable. Let's build that CLI.

We don't have to describe every request again. The `Api` definition from
the last lesson can give us a typed client, which we'll use in the CLI's
command handlers. If we change an endpoint later, TypeScript will check
those calls against the new request and response types.

## Create the client service

First, give the commands a way to reach the server. Create
`src/ApiClient.ts`. The call
`HttpApiClient.make(Api, { baseUrl })` derives one client method per endpoint,
organized into the groups you defined in the API. For example:

- `client.rules.create({ payload })`
- `client.rules.run({ params: { id }, payload })`
- `client.runs.list({ query })`

These methods belong to the same groups we defined on the server. Wrap
the client in an `ApiClient` service so command handlers can access it
with the familiar `yield*`. The type `HttpApiClient.ForApi<typeof Api>`
derives its interface from the API too:

<LessonCode file="checkpoints/15/src/ApiClient.ts" />

The client checks and encodes request payloads using the endpoint schemas,
and decodes responses using the declared success and error schemas. It
sends requests through an `HttpClient` service; the CLI will provide
`FetchHttpClient.layer` for a client built on `fetch`.

For now, we want the CLI to talk to our local server.
`Config.withDefault("http://localhost:3000")` supplies that address unless
you set `REFLEX_URL`, which `Config.String("REFLEX_URL")` reads from the
environment. The configuration is read inside the layer's effect, so the
URL is resolved when the layer is built.

The CLI imports `Api` and its domain schemas, so it is checked against that
version of the API. A separately deployed server could use a different
version; keep the CLI and server versions compatible.

## Write the command handlers

Open the starter's `src/cli/main.ts`. The command names, arguments and
flags are already declared; we'll focus on what happens when someone runs
them. Fill in the six empty handler bodies using the client service. Each
retrieves `ApiClient`, calls an endpoint and prints the result:

<LessonCode file="checkpoints/15/src/cli/main.ts" />

- `rules add` reads the file with the same `readJson` as before, then calls
  `client.rules.create`.
- `rules run` and `events submit` print one outcome per line, with its
  reason or error.
- `runs list` has two optional flags, with types `string | undefined` and
  `number | undefined`. These match the optional query parameters. Pass
  `rule` as `ruleId` and `limit` as `limit` in `client.runs.list({ query })`.

Keep naming the work as you did in the Engine. Use `Effect.fn("rules.add")`
and the corresponding name for each command. Those names will identify
the command spans when we look at traces next.

At the entrypoint, provide `ApiClient.layer` with `FetchHttpClient.layer`
for requests. Also provide `NodeServices.layer` so the handlers can read
rule and event files.

## Run the CLI against the server

Let's repeat the expense check without curl. Start the server with
`pnpm dev:server` in one terminal. In a second, run:

```sh
pnpm cli rules add fixtures/rules/expense.json
pnpm cli rules list
pnpm cli events submit fixtures/events/laptop.json
pnpm cli runs list
```

`rules add` should print `Added <id>: large expense`. Then `events submit`
prints `<id>: succeeded`, and `runs list` shows the row. It's the same
stored rule and Engine behavior we checked through HTTP, with commands
we can use without remembering the request format.

A useful CLI needs to show more than successful alerts. The Engine still
skips actions it cannot execute yet, so let's check that we can see that
outcome too. Add `fixtures/rules/ntfy.json`, whose action is `httpPost`,
then use its id to run it against an event:

```sh
pnpm cli rules run <id> --event fixtures/events/laptop.json
```

It prints one `skipped` outcome whose reason says that `httpPost` actions run
from a later lesson, and `runs list` shows the same row.
[Telling errors from defects with Cause](/learn/part-3/20-an-action-over-the-network)
adds the action.

## Inspect an error returned by the server

Now try removing a rule that doesn't exist:

```sh
pnpm cli rules remove nope
```

You'll see `RuleNotFound` with a stack trace this time. The server returns
a 404 response, and because the endpoint declares `RuleNotFound`, the
client decodes the response body into an instance of that class. It
becomes a typed failure of the client call, just as it was a typed failure
of the store. We haven't given the CLI a handler for it yet.

Hover over the `rules remove` handler to inspect its error type. It includes
`RuleNotFound` alongside HTTP and schema errors. You can handle it with
`Effect.catchTag`, even though the failure originated in another process.

## Try it

We know what went wrong in that last command, but someone using the CLI
shouldn't need to read a stack trace to find out. An unknown id is an
ordinary input mistake. Print a short message instead, while keeping a
non-zero exit code so scripts can still detect the failure.

1. Write one handler with `Effect.fn` that takes the `RuleNotFound`, prints
   `No rule with id <id>` with `Console.error`, and then fails with
   `new ExitCode({ code: 1 })` from `tools/entrypoint.ts`. `runMain` exits
   with that code and prints nothing more.
2. `Effect.fn` takes more arguments after the generator and applies each one
   to the effect it builds. Pass `Effect.catchTag("RuleNotFound", yourHandler)`
   there, in both the `rules remove` and `rules run` handlers.

Try the missing id again with `pnpm cli rules remove nope` and
`pnpm cli rules run nope --event fixtures/events/laptop.json`. Each should
now print one line and exit 1 (check with `echo $?`). The failure hasn't
been hidden; it's just easier to understand. The hint and the changed file
are in `exercises/15/`. From the next checkpoint on, the reference solution
includes this change.
