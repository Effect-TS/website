import { TutorialCheckpoint } from "@astrojs/starlight/components"

Passing adapters as function arguments is familiar and explicit. As a backend
grows, however, request handlers and intermediate functions can become
responsible for choosing and forwarding infrastructure they do not use.

In this tutorial, we will start with a compact `node:http` order endpoint. Its
HTTP handler passes a payment provider and an order repository into the order
logic. We will move those requirements into the computation, compose their
implementations at the application boundary, and then replace the payment
provider without editing the HTTP handler or the order logic.

The same request will make the change visible:

| Application wiring | HTTP status | `paymentProvider` |
| ------------------ | ----------- | ----------------- |
| Primary payment    | `201`       | `primary-pay`     |
| Backup payment     | `201`       | `backup-pay`      |

The provider and repository are deterministic local fixtures. They imitate
Promise-based SDKs without credentials, network access, or another process.

Each step ends with a checkpoint: a short verification to complete before continuing.

## 1. Start with direct adapters

This tutorial requires Node.js 22.18.0 or newer because it runs `server.ts`
directly with Node's built-in TypeScript support.

Create an empty project:

```sh title="Create the project"
mkdir replace-infrastructure-without-changing-business-logic
cd replace-infrastructure-without-changing-business-logic
npm init -y
npm pkg set type=module
npm install --save-dev @types/node@22
```

Create `server.ts` with the complete file below. The application comes first.
The collapsed section contains tutorial fixtures that we will not modify.

```ts title="server.ts" collapse={88-112}
import { createServer } from "node:http"
import { setTimeout as sleep } from "node:timers/promises"

interface PlaceOrderRequest {
  readonly customerId: string
  readonly quantity: number
  readonly paymentToken: string
}

interface AcceptedOrder {
  readonly orderId: string
  readonly status: "accepted"
  readonly totalCents: number
  readonly paymentProvider: string
}

interface PaymentProvider {
  readonly authorize: (input: {
    readonly operationId: string
    readonly amountCents: number
    readonly paymentToken: string
    readonly signal?: AbortSignal
  }) => Promise<{ readonly provider: string }>
}

interface OrderRepository {
  readonly save: (
    order: AcceptedOrder,
    options?: { readonly signal?: AbortSignal },
  ) => Promise<void>
}

const placeOrder = async (
  input: PlaceOrderRequest,
  dependencies: {
    readonly payment: PaymentProvider
    readonly orders: OrderRepository
  },
): Promise<AcceptedOrder> => {
  const totalCents = 1_250 * input.quantity
  const authorization = await dependencies.payment.authorize({
    operationId: input.customerId,
    amountCents: totalCents,
    paymentToken: input.paymentToken,
  })

  const order: AcceptedOrder = {
    orderId: `order-${input.customerId}`,
    status: "accepted",
    totalCents,
    paymentProvider: authorization.provider,
  }

  await dependencies.orders.save(order)
  return order
}

const server = createServer(async (request, response) => {
  const sendJson = (status: number, body: unknown): void => {
    response.writeHead(status, { "content-type": "application/json" })
    response.end(JSON.stringify(body))
  }

  if (request.method !== "POST" || request.url !== "/orders") {
    sendJson(404, { error: "NotFound" })
    return
  }

  try {
    let body = ""
    for await (const chunk of request) {
      body += chunk
    }
    const input = JSON.parse(body) as PlaceOrderRequest

    const order = await placeOrder(input, {
      payment: primaryPaymentProvider,
      orders: consoleOrderRepository,
    })

    sendJson(201, order)
  } catch (error) {
    console.error(error)
    sendJson(500, { error: "InternalServerError" })
  }
})

// Tutorial fixtures
// You will not modify the code below.

const primaryPaymentProvider: PaymentProvider = {
  authorize: async ({ operationId, signal }) => {
    console.log(`primary-pay authorization for ${operationId}`)
    await sleep(40, undefined, { signal })
    return { provider: "primary-pay" }
  },
}

const backupPaymentProvider: PaymentProvider = {
  authorize: async ({ operationId, signal }) => {
    console.log(`backup-pay authorization for ${operationId}`)
    await sleep(40, undefined, { signal })
    return { provider: "backup-pay" }
  },
}

const consoleOrderRepository: OrderRepository = {
  save: async (order, { signal } = {}) => {
    await sleep(20, undefined, { signal })
    console.log(`saved ${order.orderId}`)
  },
}

server.listen(3000, () => console.log("Listening on http://localhost:3000"))
```

The starter is small, and direct injection is a reasonable design at this
size. The cost is already visible, though. The HTTP handler chooses
`primaryPaymentProvider` and `consoleOrderRepository`, builds a dependency
object, and forwards it to `placeOrder`. Transport code must know application
infrastructure even though it only needs the resulting order.

As more operations and adapters appear, that dependency object must travel
through every caller. We want `placeOrder` to retain explicit requirements
without making the handler carry those requirements as ordinary arguments.

## 2. Describe the order operation with Effect

The dependency object is still our target, but moving it and learning Effect at
the same time would hide what each change accomplishes. First, keep both direct
adapters exactly where they are and change only how `placeOrder` describes its
asynchronous work.

Keep the watched server running. In the second terminal pane, install Effect:

```sh title="Install Effect"
npm install effect@4.0.0-beta.104
```

Make the following changes to `server.ts`:

```ts title="server.ts" collapse={93-118} ins={3,34,40-48,50-55,57-59,79-84}
import { createServer } from "node:http"
import { setTimeout as sleep } from "node:timers/promises"
import { Effect } from "effect"

interface PlaceOrderRequest {
  readonly customerId: string
  readonly quantity: number
  readonly paymentToken: string
}

interface AcceptedOrder {
  readonly orderId: string
  readonly status: "accepted"
  readonly totalCents: number
  readonly paymentProvider: string
}

interface PaymentProvider {
  readonly authorize: (input: {
    readonly operationId: string
    readonly amountCents: number
    readonly paymentToken: string
    readonly signal?: AbortSignal
  }) => Promise<{ readonly provider: string }>
}

interface OrderRepository {
  readonly save: (
    order: AcceptedOrder,
    options?: { readonly signal?: AbortSignal },
  ) => Promise<void>
}

const placeOrder = (
  input: PlaceOrderRequest,
  dependencies: {
    readonly payment: PaymentProvider
    readonly orders: OrderRepository
  },
) =>
  Effect.tryPromise(async (signal) => {
    const totalCents = 1_250 * input.quantity
    const authorization = await dependencies.payment.authorize({
      operationId: input.customerId,
      amountCents: totalCents,
      paymentToken: input.paymentToken,
      signal,

    const order: AcceptedOrder = {
      orderId: `order-${input.customerId}`,
      status: "accepted",
      totalCents,
      paymentProvider: authorization.provider,

    await dependencies.orders.save(order, { signal })

        payment: primaryPaymentProvider,
        orders: consoleOrderRepository,
      }),
    )

  } catch (error) {
    console.error(error)
    sendJson(500, { error: "InternalServerError" })
  }
})

// Tutorial fixtures
```

`placeOrder` now returns this inferred type:

```ts title="Inferred type, not code to paste"
Effect.Effect<AcceptedOrder, Cause.UnknownError>
```

An Effect is a value that describes a computation. Calling `placeOrder` now
creates that description. It does not authorize a payment, save an order, or
perform any other side effect. [`Effect.Effect`](/docs/v4/api/effect/Effect#Effect)
is the type of that description. The first type argument, `AcceptedOrder`, is
the success value. The second is the error channel, which lists expected ways
the computation can fail. In this checkpoint it is `Cause.UnknownError`.

There is no third type argument yet. Both adapters are still supplied as
ordinary arguments before the Effect is created, so the computation has no
service requirement.

Interruption is cancellation of a running computation. A defect is an
unexpected bug, distinct from an expected failure in the error channel.

[`Effect.tryPromise`](/docs/v4/api/effect/Effect#tryPromise) adapts the
Promise-producing provider and repository calls. The async function remains
lazy until the Effect runs. Its resolved value becomes the Effect success, and
a rejection enters the error channel. Effect supplies an `AbortSignal`, which
the code passes to both Promise APIs so interruption can cancel their waits.

[`Cause.UnknownError`](/docs/v4/api/effect/Cause#UnknownError-interface) is
Effect's built-in wrapper for an unclassified Promise rejection. It preserves
the original rejected value in its `cause` property. Classifying provider
failures is a separate error-handling lesson, so this endpoint continues to
send `500` if either fixture rejects.

[`Effect.runPromise`](/docs/v4/api/effect/Effect#runPromise) runs the Effect at
the async HTTP boundary and returns a Promise. That Promise resolves with the
success value or rejects when the Effect does not succeed, so the existing
`try`/`catch` still controls the HTTP response. The runner can also accept an
external `AbortSignal` when a caller needs to interrupt the computation.

## 3. Make payment a Context requirement

The dependency object still crosses the HTTP boundary. Replace only its payment
entry with a `Context` service. The repository remains an ordinary argument for
one more checkpoint so we can see one requirement move at a time.

```ts title="server.ts" collapse={94-119} ins={3,27-30,38-59,80-84}
import { createServer } from "node:http"
import { setTimeout as sleep } from "node:timers/promises"
import { Context, Effect } from "effect"

interface PlaceOrderRequest {
  readonly customerId: string
  readonly quantity: number
  readonly paymentToken: string
}

interface AcceptedOrder {
  readonly orderId: string
  readonly status: "accepted"
  readonly totalCents: number
  readonly paymentProvider: string
}

interface PaymentProvider {
  readonly authorize: (input: {
    readonly operationId: string
    readonly amountCents: number
    readonly paymentToken: string
    readonly signal?: AbortSignal
  }) => Promise<{ readonly provider: string }>
}

const PaymentProvider = Context.Service<PaymentProvider>(
  "tutorial/PaymentProvider",
)

interface OrderRepository {
  readonly save: (
    order: AcceptedOrder,
    options?: { readonly signal?: AbortSignal },
  ) => Promise<void>
}

const placeOrder = (input: PlaceOrderRequest, orders: OrderRepository) =>
  PaymentProvider.use((payment) =>
    Effect.tryPromise(async (signal) => {
      const totalCents = 1_250 * input.quantity
      const authorization = await payment.authorize({
        operationId: input.customerId,
        amountCents: totalCents,
        paymentToken: input.paymentToken,
        signal,
      })

      const order: AcceptedOrder = {
        orderId: `order-${input.customerId}`,
        status: "accepted",
        totalCents,
        paymentProvider: authorization.provider,
      }

      await orders.save(order, { signal })
      return order
    }),
  )

const server = createServer(async (request, response) => {
  const sendJson = (status: number, body: unknown): void => {
    response.writeHead(status, { "content-type": "application/json" })
    response.end(JSON.stringify(body))
  }

    sendJson(404, { error: "NotFound" })
    return

    let body = ""
    for await (const chunk of request) {
      body += chunk
    }
    const input = JSON.parse(body) as PlaceOrderRequest

    const order = await Effect.runPromise(
      Effect.provideService(
        placeOrder(input, consoleOrderRepository),
        PaymentProvider,
        primaryPaymentProvider,
      ),
    )

    sendJson(201, order)
  } catch (error) {
    console.error(error)
    sendJson(500, { error: "InternalServerError" })
  }
})

// Tutorial fixtures
// You will not modify the code below.

  authorize: async ({ operationId, signal }) => {

```

There are now two declarations named `PaymentProvider`. TypeScript keeps types
and runtime values in separate namespaces. The interface remains the adapter
contract. The `const` is a stable runtime identity for finding an
implementation of that contract.

[`Context.Service`](/docs/v4/api/effect/Context#Service-variable) creates that
typed key for one service. The string is its runtime identity and must be
unique. `PaymentProvider.use` describes reading the implementation stored under
the key, then passing it to the callback. It does not read a global or run the
callback immediately. Until an implementation is supplied, the returned Effect
records `PaymentProvider` as a requirement.

`placeOrder(input, consoleOrderRepository)` now returns this inferred type:

```ts title="Inferred type, not code to paste"
Effect.Effect<AcceptedOrder, Cause.UnknownError, PaymentProvider>
```

The success and error types are unchanged from the previous checkpoint. The
new third type argument is the service requirement that must be supplied before
the computation can run. Unlike the dependency object's runtime value, this
requirement remains visible while Effects are composed.

[`Effect.provideService`](/docs/v4/api/effect/Effect#provideService) supplies
one already-created implementation for a matching `Context` key. Here it gives
`placeOrder` the primary provider and removes `PaymentProvider` from the
Effect's remaining requirements.

the same `curl` command. The response and fixture messages remain unchanged.
The handler supplies the payment implementation, but it no longer passes that
implementation as a business-function argument.

## 4. Move the repository requirement too

The remaining `orders` parameter still makes the HTTP handler select and
forward repository infrastructure. Give the repository its own service key and
read it inside the same computation.

`Context` is the typed collection from which an Effect reads services. A
service key identifies one entry in that collection. The service value stored
under `OrderRepository` must satisfy the `OrderRepository` interface, so the
key connects runtime lookup to compile-time checking.

The inferred type of `placeOrder(input)` now makes both infrastructure
requirements visible:

```ts title="Inferred type, not code to paste"
Effect.Effect<
  AcceptedOrder,
  Cause.UnknownError,
  PaymentProvider | OrderRepository

```

The union in the third type argument means the computation needs both
services. It does not mean either service is optional. `PaymentProvider.use`
and `OrderRepository.use` each add their key to that union.

The handler no longer passes infrastructure to `placeOrder`, but the two
nested `Effect.provideService` calls are becoming a new form of wiring. The
next checkpoint will replace those individual calls with one reusable service
graph.

## 5. Compose implementations with Layer

A `Context` key describes what a computation needs. We still need one place to
describe how the complete set of implementations is assembled. Replace the
nested provisioning calls with two Layers and merge them into the application
Layer.

```ts title="server.ts" collapse={96-120} ins={3,86,122-125}

import { setTimeout as sleep } from "node:timers/promises"
import { Context, Effect, Layer } from "effect"

interface PlaceOrderRequest {
  readonly customerId: string
  readonly quantity: number
  readonly paymentToken: string
}

interface AcceptedOrder {

  readonly status: "accepted"
  readonly totalCents: number
  readonly paymentProvider: string

interface PaymentProvider {
  readonly authorize: (input: {
    readonly operationId: string
    readonly amountCents: number
    readonly paymentToken: string

const PaymentProvider = Context.Service<PaymentProvider>(
  "tutorial/PaymentProvider",

    order: AcceptedOrder,

    const order = await Effect.runPromise(
      Effect.provide(placeOrder(input), AppLive),
    )

    sendJson(201, order)
  } catch (error) {
    console.error(error)
    sendJson(500, { error: "InternalServerError" })
  }
})

// Tutorial fixtures
// You will not modify the code below.

const primaryPaymentProvider: PaymentProvider = {
  authorize: async ({ operationId, signal }) => {

const PaymentLive = Layer.succeed(PaymentProvider, primaryPaymentProvider)
const OrdersLive = Layer.succeed(OrderRepository, consoleOrderRepository)
const AppLive = Layer.merge(PaymentLive, OrdersLive)

```

A Layer is a value that describes how to construct one or more services. Like
an Effect, creating a Layer does not run side effects. These implementations
already exist as fixture values, so their Layers cannot fail and do not need
other services to be built.

[`Layer.succeed`](/docs/v4/api/effect/Layer#succeed) creates a Layer for one
already-available service value. `PaymentLive` associates
`primaryPaymentProvider` with the `PaymentProvider` key, while `OrdersLive`
associates the console repository with its key.

[`Layer.merge`](/docs/v4/api/effect/Layer#merge) combines two independent
Layers into one Layer that provides both sets of services. `AppLive` therefore
describes a graph containing `PaymentProvider` and `OrderRepository`. Building
either Layer does not require the other one.

The inferred type of the composed Layer can be read as the services it makes
available:

```ts title="Inferred type, not code to paste"
Layer.Layer<PaymentProvider | OrderRepository>
```

[`Layer.Layer`](/docs/v4/api/effect/Layer#Layer) is the type of a Layer
description. Its first type argument lists the services the Layer provides.
Additional type arguments can describe construction failures and services
required to build it. Both default to `never` here because `Layer.succeed`
uses values that are already available, so `AppLive` has neither.

[`Effect.provide`](/docs/v4/api/effect/Effect#provide) builds the supplied
Layer and makes its services available to the Effect. Here it satisfies both
requirements of `placeOrder`. The resulting Effect has no remaining service
requirement, so `Effect.runPromise` can run it at the HTTP boundary.

This is the application boundary: `AppLive` chooses concrete infrastructure,
while `placeOrder` names only service contracts. If `OrdersLive` were omitted,
`OrderRepository` would remain in the Effect's requirement type and the call
to `Effect.runPromise` would not type-check. The incomplete graph is detected
before the server starts.

Wait for the watched server to reload and send the request again. It still
returns `primary-pay`; this checkpoint changes the wiring, not the observable
behavior.

<TutorialCheckpoint
  number={5}
  total={6}
  title="One Layer provides the application graph"
>
  `AppLive` composes the primary payment provider and console repository. The
  same request returns `201`, and no individual service is provisioned in the
  HTTP handler.
</TutorialCheckpoint>

## 6. Replace the payment Layer

The backup fixture already satisfies the same `PaymentProvider` contract. To
select it, change only the implementation associated with that service key:

```ts title="server.ts" collapse={1-121} ins={122}
import { createServer } from "node:http"
import { setTimeout as sleep } from "node:timers/promises"
import { Context, Effect, Layer } from "effect"

interface PlaceOrderRequest {
  readonly customerId: string
  readonly quantity: number
  readonly paymentToken: string
}

interface AcceptedOrder {
  readonly orderId: string
  readonly status: "accepted"
  readonly totalCents: number
  readonly paymentProvider: string
}

interface PaymentProvider {
  readonly authorize: (input: {
    readonly operationId: string
    readonly amountCents: number
    readonly paymentToken: string
    readonly signal?: AbortSignal
  }) => Promise<{ readonly provider: string }>
}

const PaymentProvider = Context.Service<PaymentProvider>(
  "tutorial/PaymentProvider",
)

interface OrderRepository {
  readonly save: (
    order: AcceptedOrder,
    options?: { readonly signal?: AbortSignal },
  ) => Promise<void>
}

const OrderRepository = Context.Service<OrderRepository>(
  "tutorial/OrderRepository",
)

const placeOrder = (input: PlaceOrderRequest) =>
  PaymentProvider.use((payment) =>
    OrderRepository.use((orders) =>
      Effect.tryPromise(async (signal) => {
        const totalCents = 1_250 * input.quantity
        const authorization = await payment.authorize({
          operationId: input.customerId,
          amountCents: totalCents,
          paymentToken: input.paymentToken,
          signal,
        })

        const order: AcceptedOrder = {
          orderId: `order-${input.customerId}`,
          status: "accepted",
          totalCents,
          paymentProvider: authorization.provider,
        }

        await orders.save(order, { signal })
        return order
      }),
    ),
  )

const server = createServer(async (request, response) => {
  const sendJson = (status: number, body: unknown): void => {
    response.writeHead(status, { "content-type": "application/json" })
    response.end(JSON.stringify(body))
  }

  if (request.method !== "POST" || request.url !== "/orders") {
    sendJson(404, { error: "NotFound" })
    return
  }

  try {
    let body = ""
    for await (const chunk of request) {
      body += chunk
    }
    const input = JSON.parse(body) as PlaceOrderRequest

    const order = await Effect.runPromise(
      Effect.provide(placeOrder(input), AppLive),
    )

    sendJson(201, order)
  } catch (error) {
    console.error(error)
    sendJson(500, { error: "InternalServerError" })
  }
})

// Tutorial fixtures
// You will not modify the code below.

const primaryPaymentProvider: PaymentProvider = {
  authorize: async ({ operationId, signal }) => {
    console.log(`primary-pay authorization for ${operationId}`)
    await sleep(40, undefined, { signal })
    return { provider: "primary-pay" }
  },
}

const backupPaymentProvider: PaymentProvider = {
  authorize: async ({ operationId, signal }) => {
    console.log(`backup-pay authorization for ${operationId}`)
    await sleep(40, undefined, { signal })
    return { provider: "backup-pay" }
  },
}

const consoleOrderRepository: OrderRepository = {
  save: async (order, { signal } = {}) => {
    await sleep(20, undefined, { signal })
    console.log(`saved ${order.orderId}`)
  },
}

const PaymentLive = Layer.succeed(PaymentProvider, backupPaymentProvider)
const OrdersLive = Layer.succeed(OrderRepository, consoleOrderRepository)
const AppLive = Layer.merge(PaymentLive, OrdersLive)

server.listen(3000, () => console.log("Listening on http://localhost:3000"))
```

The HTTP result now identifies the backup provider:

```text title="Expected response"
...

{"orderId":"order-customer-123","status":"accepted","totalCents":2500,"paymentProvider":"backup-pay"}
```

The server output confirms which fixture handled the authorization:

```text title="Expected server output"

saved order-customer-123
```

`placeOrder`, the HTTP handler, and `OrdersLive` are unchanged. The replacement
is confined to the Layer that associates an implementation with the

## Keep the infrastructure seam at the boundary

The two service interfaces describe what the order computation can use.
`Context.Service` gives each interface a stable identity, so the requirements
remain visible in the Effect type without appearing in the business argument
list. `Layer.succeed` associates those identities with concrete values, and
`Layer.merge` creates one application graph.

That separation gives the final one-line replacement its meaning. The Layer
changed how `PaymentProvider` is implemented; no code that calculates,
authorizes, saves, or serves an order had to change.
