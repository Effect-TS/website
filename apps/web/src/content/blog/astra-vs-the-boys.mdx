On September 3, the Effect repository hit GitHub's runner quota. Pull requests were piling up. Kit would shortly appear in the replies asking whether this was his fault.

The previous day, Tim had asked Kit not to send us 100 pull requests a day.

Kit gave his agent a goal of 99.

We ended up with **207 PRs, 195 merges, a maxed-out GitHub runner quota, and a Slack channel full of people actively making the situation worse.** I was one of those people. Keep that in mind when assessing my testimony.

The person sending the PRs was [Kit Langton](https://github.com/kitlangton) from [Anomaly](https://anomaly.co/). His agent was OpenAI's Astra. Receiving them was the [Effectful](https://effectful.co/) team, where [Tim Smart](https://x.com/tim_smart) had his own AI infrastructure, built with [Multica](https://multica.ai/). We call it **The Boys**.

Kit orchestrated the bug hunt. The Boys helped us work through the incoming PRs. The humans gave the final feedback and decided what to merge. [Namespace](https://namespace.so/) eventually had to come and rescue our CI.

To understand how we got there, we need to go back to the first report. It began with an apology.

_Dun dun._

## September 2. The first report.

On September 2, Kit dropped into our shared Effectful and Anomaly channel:

<Quote text="Sorry for PR spamming!" />

He'd found [a Queue bug](https://github.com/Effect-TS/effect/pull/7576) while working on [OpenCode](https://opencode.ai/). A producer that had been waiting for space could resume and deliver a message more than once. That's the sort of thing you would quite reasonably prefer your queue not to do.

After finding it, he'd sent some agents looking for similar bugs in Effect. They'd come back with more. What had looked like one Queue bug was turning into a much larger inquiry. The findings seemed plausible, he said, but we should feel free to ignore or close the PRs.

Tim's response was immediate in spirit, if not in wall-clock time:

<Quote text="I shall take your tokens." />

Kit described them as "some spare free tokens." Free from his point of view, anyway. Was there any part of the codebase we'd like him to go through with "an unreasonable number of agents"?

This is a dangerous question to ask people who maintain a TypeScript library for a living. We have a very long list of things we would like somebody else to investigate.

Tim told him to go for it. Use the `audit` PR label so he could work through the submissions in bulk. One small request, though. Sebastian Lorenz had previously sent him something like 100 audit PRs a day.

<Quote text="Maybe don't do that" />

A sensible boundary. Unfortunately, there were people in this channel willing to examine the wording.

## The Boys take the case

While I was pursuing the deeply important question of whether my first guess was right, Tim was reviewing actual code. A couple of hundred PRs needed more than a maintainer opening tabs and hoping for the best. Kit had agents producing work. **We also had agents working through it.**

The Boys are Tim's setup built with Multica, which lets him assign work to agents and track it as tasks. A PR can become a job to investigate, with progress and a result to review. Several of those jobs can be in flight while Tim looks at the work that has come back.

The `audit` label let him pull up the incoming batch and work through it. Even an army of agents needs the cases filed somewhere it can find them. Hence the administrative tragedy of Tim having to shift-click.

Here's the board Tim shared while Kit was still arguing that thirty was less than a hundred:

<StoryFigure
  src={reviewBoard}
  alt="Tim's work board showing audit PR tasks in In Progress and In Review, including fixes for SQL, Headers, Struct, Chunk, and SchemaGetter."

Each PR on that board was a separate investigation. Some fixes were in progress; others were waiting for review. Kit didn't have to wait for Tim to finish one investigation before another could start, and Tim didn't have to personally do every mechanical step of each fix. This was how we kept moving while the submissions kept coming.

The Boys could try to reproduce the reported behavior and check whether the patch actually fixed it. They could revise the implementation and bring back code and test results. Tim then had something concrete to question. If the implementation was wrong, the test was in the wrong place, or the proposed API wasn't one we wanted to maintain, his feedback sent the work around again.

**The final human feedback was the important bit.** An agent saying "done" was about to hear some follow-up questions. Did this belong in the existing test suite? Why did the overload differ from the one immediately above it? Why were we changing an API people already used?

Sometimes Tim wanted one or two tests that demonstrated the regression. Sometimes he wanted the old API preserved and a separate one introduced. Occasionally, the function itself failed to survive questioning.

The Boys could do the follow-through. The humans decided what the follow-through should be.

### The function does not survive questioning

In [#7657](https://github.com/Effect-TS/effect/pull/7657), the allegation was that `Channel.runDone` returned the wrong completion value. The agent had a proposed fix. You might expect the review to establish what the function should return and then correct it.

Tim looked at the proposed fix and [asked a different question](https://github.com/Effect-TS/effect/pull/7657#discussion_r3919950524).

<Backchannel
  source="Human feedback · GitHub"
  date="PR #7657"
  messages={[
    {
      author: "Tim Smart",
      text: "Lets just remove it as it does the same thing as runDrain?",
      href: "https://x.com/tim_smart",
    },
  ]}
/>

The resulting PR removed `runDone` and updated the tests, docs, migration guidance, and changeset to use `runDrain`.

The finding held up. The function didn't. Astra had identified a broken implementation; Tim had identified an API we could stop maintaining. In the final tally, that still counts as one merged PR.

The same thing happened with [#7987](https://github.com/Effect-TS/effect/pull/7987). The original proposal narrowed `Multipart.isPart` to streamed parts. Tim wanted to preserve the existing broad guard and add `isStreamPart` for the narrower check. His [review comment](https://github.com/Effect-TS/effect/pull/7987#discussion_r3930780970) became the final design. The follow-up changed the implementation, tests, documentation, and even the PR wording to match.

The reproduction could establish that something was wrong. It couldn't decide which API we wanted people to use next year. That decision came from Tim, and The Boys had to carry it through the patch before it could land.

### The court does not need ninety witnesses

The other recurring conversation was about tests. Agents are very willing to write tests. Getting them to stop writing tests can be its own project.

In [#8045](https://github.com/Effect-TS/effect/pull/8045), a line-ending fix for migration-document tooling arrived with a standalone 90-case matrix. Tim reduced it to three cases in the existing suite.

Ninety. For line endings. Somewhere a carriage return was receiving more individual attention than most of our public APIs.

The review comments elsewhere in the batch tell the same story. On [#7945](https://github.com/Effect-TS/effect/pull/7945), Tim asked for one or two tests that prevent the regression. On [#7829](https://github.com/Effect-TS/effect/pull/7829), he pointed out that the test was in the wrong file. It moved into the real libSQL integration suite, and the standalone file disappeared.

The Boys went back through the tests as well as the implementation. They could do the edits; Tim decided which tests earned a place in the suite. Otherwise, every small fix threatened to arrive with its own private testing framework and a moving van.

When we checked the GitHub histories, **185 of the 195 merged PRs retained maintainer-authored commits**. Tim appears in 184 of them; Giulio in one. There were recorded force pushes on 102 merged branches. A lot happened between "here is a bug" and "this belongs on main."

Those author names don't tell you which lines somebody typed by hand. The Boys' work also runs through Tim's account, and branches were rewritten during review. They do show why the merge rate is a measure of the whole process, including our revisions, rather than a grade for Astra's first attempt.

## The findings hold up

The patches gave Tim plenty to question. But the bugs kept checking out, which made it rather difficult to tell Kit to go away. His audit of Effect v4 was turning up findings across the runtime, data structures, platform integrations, SQL, type declarations, and tooling.

Open the PRs and you can see why we kept taking his calls:

- **Old cleanup touching new state.** Several cache and resource fixes dealt with an interrupted or stale operation removing a newer entry. [#7585](https://github.com/Effect-TS/effect/pull/7585) protects newer cache entries when a refresh is interrupted. [#7586](https://github.com/Effect-TS/effect/pull/7586) handles ownership when an old `RcRef` borrower releases a resource. These are the bugs where each operation looks reasonable on its own and the ordering ruins your afternoon.
- **Data disappearing from collections.** [#7617](https://github.com/Effect-TS/effect/pull/7617) fixes concatenation of sliced chunks. [#7774](https://github.com/Effect-TS/effect/pull/7774) stops removing a Trie child from also pruning a prefix that still has a value. Deleting `"abc"` should not make `"ab"` disappear as a bonus.
- **HTTP cleanup and wire formats.** [#7679](https://github.com/Effect-TS/effect/pull/7679) closes request scopes for streaming HEAD responses, where there is no response body to finish the cleanup. [#7683](https://github.com/Effect-TS/effect/pull/7683) preserves valid JSON-RPC control IDs of `0` and `""`. Falsy is not the same thing as missing, however enthusiastically JavaScript encourages the confusion.
- **SQL behaving differently on reuse.** [#7635](https://github.com/Effect-TS/effect/pull/7635) fixes placeholder numbering in cached returning fragments. [#7829](https://github.com/Effect-TS/effect/pull/7829) isolates transaction contexts between libSQL clients. Both are considerably more interesting than a spelling correction.
- **AI integrations mangling payloads.** [#7756](https://github.com/Effect-TS/effect/pull/7756) and [#7758](https://github.com/Effect-TS/effect/pull/7758) address base64 image handling in the OpenAI and Anthropic integrations. Double-encoding an image is a creative way to ensure nobody sees it.
- **Types and tools disagreeing with the code.** The run also found missing service requirements, recovery signatures accepting the wrong types, generated clients encoding forms as JSON, and Markdown/MDX examples that weren't getting executed properly. The audit eventually reached the tools we use to maintain the library itself.

Some changes needed more work after they landed. Tim's [PubSub follow-up](https://github.com/Effect-TS/effect/pull/7607) arrived less than twelve minutes after [the original merge](https://github.com/Effect-TS/effect/pull/7603), fixing a new polling check that confused a sentinel published as real data with an empty subscription. Giulio consolidated JSON Pointer and array-index handling into shared helpers in [#7823](https://github.com/Effect-TS/effect/pull/7823) and [#7855](https://github.com/Effect-TS/effect/pull/7855).

Even a merged PR could produce a new lead. We were following those up while Kit continued to supply us with more originals. Somewhere in all this, the machines running our tests were entitled to ask whether anybody had considered their workload.

## The alibi checks out. On the wrong commit.

The runner migration came up again in a case The Boys thought they could close. They had a clean test run and a confident report. Sebastian had an objection.

Sebastian had reported that [#7768](https://github.com/Effect-TS/effect/pull/7768), a generated form-urlencoded request fix, broke on Bun. Tim sent an investigation through The Boys and shared the "Team Lead" report.

All 13 targeted tests passed, including all six request-encoding variants. No code change or PR was needed, the report concluded. On paper, a perfectly good alibi.

Sebastian replied:

<Quote text="It does break ... Or rather, it did before I merged this:" />

He linked the runner PR. The one he'd already merged.

The detail that gave it away was the commit. The agent had tested `main` at `4372c79a32`. Sebastian's repair was already in that revision. He'd replaced the new test helper's Node/Babel compilation with Rolldown while expanding Bun test coverage.

So the tests passed. The agent was correct about that. It had successfully verified the fix Sebastian had already made, then delivered the excellent news that nobody needed to fix it.

The code change was in the test helper and CI execution. The report had the right test results and the wrong conclusion about whether work had been needed. Sebastian supplied the missing timeline.

Case closed, eventually. Credit to the person who had closed it before the report arrived.

<Quote text="I had to fix up every PR because the quality was average, so not sure how I feel about gpt 6 now lol. But the findings were good." />

Kit's self-certifying expert witness would have had a much shorter review procedure.

We'll leave the exact orchestration recipe to Kit. We can confirm that they flew.
