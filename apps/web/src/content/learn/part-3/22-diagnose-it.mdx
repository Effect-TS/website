Something went wrong on one event while you were not watching. All you have
is what the program recorded: the run history and the traces. In this lesson
you find out whether that is enough. You write no code. You run the mixed
scenario from the previous lesson once more and answer four questions about
it, using only `runs list` and the viewer.

Do not read the code or the fixture files while you answer. The point is to
learn whether what you built tells you enough on its own.

In this lesson you will:

- reproduce the mixed scenario on an empty run history
- answer four questions from `runs list` and the trace, and write the answers
  down
- check them against the expected answers

## 1. Reproduce the run

Use the checkpoint's server, or your own if your previous checkpoint matched.
This lesson's checkpoint is number 22. Start from an empty run history so the
rows are easy to find: stop the server, delete `reflex.db`, and start it
again.

```sh
pnpm receiver --scenario mixed
```

```sh
pnpm checkpoint 22 server
```

```sh
pnpm checkpoint 22 cli rules add fixtures/rules/mixed/a-ok.json
pnpm checkpoint 22 cli rules add fixtures/rules/mixed/b-ok.json
pnpm checkpoint 22 cli rules add fixtures/rules/mixed/c-slow.json
pnpm checkpoint 22 cli rules add fixtures/rules/mixed/d-fail.json
pnpm checkpoint 22 cli events submit fixtures/events/laptop.json
pnpm checkpoint 22 cli runs list
```

`events submit` takes about 10 seconds and prints four outcomes. `runs list`
shows four rows.

In the viewer, open the newest `reflex-server` trace that has an
`Engine.handleEvent` span.
[Reading a trace in the viewer](/learn/part-2/trace-viewer) describes each
part of the screen.

## 2. Answer four questions

Write your answers down. For each one, name what you looked at: a span, a
row, or a duration.

1. Which operation was slowest? How long did it take, and why that long?
2. Which operation failed, and with what?
3. Which work finished, and did it wait for the slow one? How long did the
   whole request take?
4. Did a timeout fire? Name two places that show it.

If you see four `succeeded` rows, the receiver answered `/slow` before the
timeout. Check that `REFLEX_TIMEOUT` is not set in the server's shell.

## 3. Check your answers

Once all four are written down, compare them with
[the expected answers](/learn/part-3/diagnose-it-answers). Your trace ids and
times differ, but the shape does not.

If one of your answers needed something you could not find in `runs list` or
the viewer, note what was missing. That note is a starting point for one of
the follow-ons in [Where to go next](/learn/part-4/what-comes-next).

## What you learned

- One row per run and one span per run are enough to tell a timeout from a
  refused request, and to see which runs waited for which.
- Span start times show what ran together. The parent span shows how long the
  whole request took.
- The reasons in `runs list` and the status messages in the viewer say the
  same thing in two places.

## Checkpoint

Your written answers match the expected ones: the slowest operation and the
timeout, the failure and its status, the two that completed without waiting,
and the request taking about as long as the timeout. Two red spans, two Ok,
four rows.
