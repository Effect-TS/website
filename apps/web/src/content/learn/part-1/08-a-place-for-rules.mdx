The rules are still constants passed directly to `evaluate`. In Part 2,
you will load them from a file and manage them through an HTTP API; in
Part 3, you will store them in SQLite. The evaluation code should not need
to change along with the storage code.

Separate those concerns with a `RuleStore` service. Its interface will let
evaluation code list the rules without choosing how they are stored.
This lesson deliberately ends before that choice is made,
with a type error at the run line. The next lesson supplies an
implementation and makes the program runnable again.

## Declaring the RuleStore service

`Context.Service` defines a **service** with a key and an interface. It
does not implement the operations in that interface. Add `Context` to the
`effect` import, then declare `RuleStore` below `decodeRule`:

The declaration follows a pattern similar to `Schema.TaggedError`. The
type arguments include the class's own type and the interface of the
service. Here that interface has one member, `list`, an Effect whose
successful result is a readonly array of JSON strings.

The string `"reflex/RuleStore"` in the second call is the service's key.
Keep it unique within the program so that it identifies this service
unambiguously.

## Reading rules through the service

retrieves the implementation provided for `RuleStore`. Its interface lets
you use `yield* store.list` to obtain the rules without knowing how they
were stored.

## The new requirement

Hover `evaluateAll`. Its return type is
`Effect<void, SchemaError, RuleStore>`.

The third type parameter lists the services that still need to be
provided. Until now it has been `never`. Retrieving `RuleStore` inside
`evaluateAll` adds that requirement. Calling `evaluateAll` from `program`
means `program` also requires the store. Hover `program` to confirm it.

## Why the program cannot run yet

Look at the last line, `NodeRuntime.runMain(program)`. It is underlined in
red, the terminal shows the same type error, and the program does not run.
The playground only runs a file that typechecks.

The error is long. The part that matters is its last line:
`Type 'RuleStore' is not assignable to type 'never'.` `runMain` only runs an
Effect whose requirements type is `never`, and `program` still needs a
`RuleStore`.

The declaration tells TypeScript what operations a `RuleStore` must
provide, but no implementation exists in this file yet. The error is
therefore expected, including when you use the Solve button.

## Try it

Before moving on, trace the missing requirement through the file:

1. Hover `evaluateAll`, then `program`. Find where `RuleStore` enters the
   requirements type and why it stays there up to `program`.
2. Look for code that implements `list` and chooses which rules it returns.
   There is none yet; the service declaration only specifies its type.

Continue to [Providing a service with a layer](/learn/part-1/09-provide-it)
to implement the store and satisfy the requirement.
