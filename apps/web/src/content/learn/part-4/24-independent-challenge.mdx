A rule may send too many alerts, or you may need to disable it while an
outside service is down. So far, the only way to stop a rule is to remove
it, which also deletes its definition. Add a way to pause a rule and resume
it later without recreating it.

This time, you have the requirements but no implementation to follow. You
have used all the APIs you need in earlier lessons; the challenge is to
choose how they fit together. Allow about 40 minutes, and try it before
opening [the hints](/learn/part-4/challenge-hints).

## Requirements

Add `rules pause <id>` and `rules resume <id>` to the CLI and API, with the
following behaviour:

- The CLI gets `rules pause <id>` and `rules resume <id>`. Like every other
  command, they go through the server.
- A paused rule stays stored. `rules list` shows it as `paused`.
- Events do not execute a paused rule. It produces neither a row in
  `runs list` nor an `Engine.execute` span.
- Pausing an interval rule stops its loop. Resuming starts it again.
- Pausing or resuming an unknown id fails with a typed error. The CLI prints
  one line and exits with a non-zero code, just as it does when you remove
  an unknown rule.
- Decide what a server restart does to a pause, and say so in a comment.
  Either answer is fine, as long as you state it.

## Write the tests first

Write the tests before the code, on the harness from
[Running rules on a schedule with FiberMap](/learn/part-3/19-rules-on-a-clock):

1. Use an interval rule whose poll never completes. Wait for its first
   request, pause the rule, then move the test clock past one interval.
   Assert that there is no new request and no new row.
2. Resume the rule and move the clock past one interval again, staying
   short of the timeout. Assert exactly one new request and one new row.
   This is the positive control: it shows that the loop can run when it is
   not paused. Without it, the first test could pass because the loop is
   broken, rather than because pausing works.
3. Pause an event rule and submit an event. Assert that there is no outcome
   for that rule and no row. Resume it, submit again, and assert one row.
4. Assert that pausing an unknown id fails with the typed error.

Run the tests and check that each fails for the behaviour it is meant to
verify, as in
[Writing tests with @effect/vitest](/learn/part-2/13-first-tests). Only then
write the code that makes them pass.

## Show it working

Use a fresh database so that existing rules and runs do not affect the
result. Stop your server, delete `reflex.db`, and start it again. Then:

1. Run `pnpm receiver --scenario mixed`.
2. Add the four mixed rules to your server.
3. Pause B and submit `fixtures/events/laptop.json`.

`runs list` shows three new rows, not four. In the viewer, the newest
`Engine.handleEvent` trace has three `Engine.execute` spans, and none of them
is B's.

Resume B and submit again. This time you get four new rows and four spans.

## Checkpoint

When your four tests pass and the mixed scenario produces the expected rows
and spans, compare your implementation with checkpoint 24. It is one
possible solution, with tests in `checkpoints/24/test/`:

```sh
pnpm checkpoint 24 test
```
