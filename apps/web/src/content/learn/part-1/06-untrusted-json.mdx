Nobody is going to write rulebook's rules in TypeScript. They'll arrive as JSON
text, first from a file and later from an HTTP request. The start file reflects
that. The rules `largeExpense` and `malformed` are now JSON strings, and
`evaluate` takes a string and reads it with
`const rule: Rule = JSON.parse(json)`.

That `: Rule` annotation is a promise TypeScript can't check. `JSON.parse`
returns `any`, so `rule` is whatever the text happened to contain.

Look at `malformed`. Its operator is `greater`, its value is the string
`"500"`, and it has no message at all. Your `UnknownOperator` check catches the
operator. Nothing catches the other two problems.

You will learn:

- how to describe the shape of your data with a schema;
- how to decode untrusted input into a type you can trust;
- how to read the errors a schema reports.

## Describing a shape with a schema

A schema describes a shape once. From that one description, Effect derives both
the TypeScript type and a check that runs on real data. For a rule you need:

- `Schema.Struct({ ... })` for the object, with `Schema.String` and
  `Schema.Number` for its fields;
- `Schema.Literals(["eq", "neq", "gt", "lt"])` for the operator, meaning one of
  those four strings and nothing else;
- `Schema.optional(...)` around the condition, because a rule without a
  condition always runs.

Then `type Rule = typeof Rule.Type` gives you the type. The schema and the type
share the name `Rule`, and TypeScript knows which one you mean from where you
use it.

## Try it: delete what the schema replaced

This is the course's first simplification. The schema makes three pieces of
hand-written code redundant, so delete them:

1. The `interface Rule`. The schema gives you the type now.
2. `UnknownOperator`, the list of operators, and the check in `evaluate`.
   Decoding already rejects `greater`.
3. The `default` branch in `matches`. TypeScript now knows the operator is one
   of four strings, so the `switch` covers every case without it.

Now read the error for the malformed rule in the terminal:

> `SchemaError: Expected "eq" | "neq" | "gt" | "lt"` at `["condition"]["op"]`

It tells you what it expected and where it looked. Decoding stops at the first
problem it finds. To see the next one, change the operator in `malformed` to
`gt`. The next run reports `Expected number` at `["condition"]["value"]`.

Put `greater` back when you're done. Lesson 7 needs the rule broken.

Finally, hover `evaluate`: `Effect<string | void, SchemaError, never>`. Two of
your own failures became one that the library defines and reports for you.

## Recap

- Data from outside goes through a schema once, at the edge. The rest of the
  program works with a type it can trust.
- `Schema.decodeUnknownEffect(Schema.fromJsonString(...))` parses and checks
  JSON, and fails with a `SchemaError` that says what was wrong and where.
- The cost is a decode on every input and a schema to keep. That's worth it
  where data is untrusted. Values you build yourself in TypeScript, like
  `laptop`, don't need one.
- Lesson 11 extends `Rule` with actions, and lesson 17 decodes the same JSON
  from a database column.
